# HubEx.Wiki — вики HubEx для ИИ-агентов

> **Что здесь:** автономная копия вики HubEx (wiki.hubex.ru): вербатим-страницы, дистиллированные индексы и пайплайн обновления.
> **Когда сюда идти:** нужен факт о поведении или настройке продукта HubEx — начни с [index.md](index.md).

**HubEx** — облачная мультитенантная FSM-платформа (Field Service Management) для выездного обслуживания: заявки с жизненным циклом, объекты/оборудование, исполнители, SLA, чек-листы, акты, склад, аналитика.

Ключевая механика: **Заявка** проходит стадии настраиваемого жизненного цикла, привязана к **Объекту/Оборудованию** и **Компании**-заказчику; исполнители назначаются вручную или правилами автоназначения (вид работ, навыки, участок, график, геопозиция); сроки контролирует SLA.

Основные роли:
- **Диспетчер** — создаёт заявки в web-приложении, назначает исполнителей, контролирует выполнение.
- **Исполнитель (сервисный специалист)** — работает в мобильном приложении: принимает заявки, выезжает на объекты, фиксирует работы и чек-листы, получает подпись заказчика.
- **Заказчик** — подаёт заявки через своё мобильное приложение или клиентский портал, следит за статусом.
- **Администратор** — настраивает бизнес-процессы, роли, жизненные циклы и правила автоназначения в консоли администратора.

Приложения: web-приложение (диспетчеры, руководители), моб. «HubEx Исполнитель» (Android/iOS), моб. «HubEx Заказчик» (Android/iOS), клиентский портал, консоль администратора.

## Правила

- Страницы `pages/**` руками не правятся — их перезаписывает пайплайн. Правятся только индексы (точечно), README, `tools` и оверрайды дат `context/release-dates.tsv`. Сжатый контекст (`hubex-context.md`, `.context-dist/body.md`) в рабочем дереве отсутствует и руками не правится — он живёт на ветке `dist/context`, подробности ниже.
- Не выдумывай факты о продукте: нет в страницах — так и скажи.
- URL страницы на вики: поле `url` во frontmatter; общее правило `pages/<section>/<slug>.md` ↔ `https://wiki.hubex.ru/docs/FAQ/RU/<section>/<slug>.html`. Slug в имени файла URL-декодирован: страницы с кириллицей в адресе лежат как `pages/ReleaseNotes/cкладской-документ-….md`, а в `url` тот же slug percent-encoded.
- Кросс-ссылки между курируемыми страницами — локальные относительные; картинки и прочие ссылки — абсолютные URL вики.
- Страница пропала с вики → пайплайн помечает `removed` в отчёте; копию и строку индекса удаляет человек.

## Получить и подтянуть (потребителю)

Вика — обычный git-репозиторий, для чтения пайплайн не нужен:

```
git clone <url>      # первый раз
git pull             # подтянуть свежую версию
```

Дальше читай слоями: [index.md](index.md) / [releasenotes-index.md](releasenotes-index.md) → страница в [pages/](pages/). Пайплайн (`tools/`) — git-сабмодуль; обычный `clone`/`pull` его **не тянет**, и это норма: для ответов по продукту он не нужен.

## Обновить из источника (мейнтейнеру)

Свежую версию вики с `wiki.hubex.ru` гонит пайплайн — он в отдельном репозитории `HubEx.Wiki.Pipeline`, подключён сабмодулем в `tools/`. Выкачай его один раз:

```
git submodule update --init          # или клонируй репозиторий с --recursive
```

Затем запускай обновление:

```
python3 tools/wiki_cli.py update [--page <section>/<slug>] [--recompress] [--report-file PATH] [--jobs N]
```

Без флагов — отчёт new/changed/removed (ничего не пишет). `--recompress` перезаписывает затронутые страницы и обновляет строки-аннотации индексов моделью; всё остаётся unstaged — ревью и коммит за человеком. Детали — [tools/README.md](tools/README.md) (доступен после `submodule update --init`).

## Ночной автоперезабор

На машине мейнтейнера крон каждую ночь в 00:00 МСК (21:00 UTC) гонит:

```
python3 tools/wiki_cli.py sync [--dry-run]
```

Это `update --recompress`, обвязанный гейтами: дерево не чисто или история разошлась с origin → прогон пропускается; не подключён worktree артефактов (или на его месте обычный каталог) → отказ до `update`, за секунду и ничего не тронув; worktree артефактов не чист или его ветка разошлась с origin → прогон пропускается так же, как при грязном основном дереве; не больше 5 ошибок забора страниц (разовый сетевой сбой) — прогон продолжается, такие страницы остаются вчерашними и перезабираются следующей ночью; больше — как и ошибка модели/guard или недоступный sitemap — коммита нет, изменения остаются человеку. После успешного `update` тем же прогоном правится `hubex-context.md` по фактически изменившимся страницам — guard-проблема здесь тоже блокирует коммит. Дальше два раздельных коммита: сперва артефакты (`.context-dist/hubex-context.md`, `.context-dist/body.md`) коммитятся и пушатся в их собственном worktree на ветку `dist/context` — провал здесь останавливает весь прогон, `main` не трогается. Следом, если артефакты ушли успешно, коммит `chore: ночной перезабор вики <дата>` (`pages/`, `index.md`, `releasenotes-index.md`) и пуш в `main`. Логи — `~/.local/state/hubex-wiki/`.

Следствия для человека: незакоммиченные правки в дереве отменяют ночной прогон (в том числе разъехавшийся указатель сабмодуля `tools/`, а также незакоммиченные артефакты в `.context-dist/`); `removed`-страницы робот не удаляет; `export-llms` и выкладка на хостинг остаются ручным шагом. Детали и коды возврата — [tools/README.md](tools/README.md).

## Экспорт для сайта (llms.txt)

Готовый к выкладке на `wiki.hubex.ru` набор в формате [llms.txt](https://llmstxt.org/):

```
python3 tools/wiki_cli.py export-llms [--out dist]
```

Собирает в `dist/` (в `.gitignore`, не коммитится): `llms.txt` (каталог со ссылками на `.html.md`; релиз-ноуты в нём — одним указателем), `llms-releasenotes.txt` (отдельный каталог по релизам), `llms-full.txt` (вся вика одним файлом) и постраничные `docs/FAQ/RU/<section>/<slug>.html.md`. Раскладка `dist/` = зеркало корня сайта: выкладка сводится к копированию содержимого `dist/` в корень хостинга. Сеть и модель не нужны — чистое преобразование текущего контента; запускать после `update` перед выкладкой. Доставка на хостинг — вне пайплайна.

## Сжатый контекст (hubex-context.md)

`hubex-context.md` — весь продукт одним markdown-файлом, цель ~150 тыс. символов, для чатов облачных ИИ-агентов (Perplexity, ChatGPT, DeepSeek и т.п.), которым этот репозиторий недоступен. Основной потребитель — отдел продаж: файл прикладывается в чат вместо ссылок на вики.

### Где лежит артефакт

В рабочем дереве `main` файла нет — намеренно: агент, которому дали папку, обязан идти `index.md` → `pages/` и читать первоисточник, а сжатый пересказ рядом с оглавлением выглядит готовым ответом и путает индексаторы, которые заберут и страницу, и её лоссовый пересказ. `hubex-context.md` и его тело `.context-dist/body.md` живут на ветке-сироте `dist/context`, подключённой отдельным worktree в каталоге `.context-dist/` (в `.gitignore` основного дерева).

Подключить worktree на новой машине (тот же репозиторий, ветка уже существует в origin):

```
git worktree add .context-dist dist/context
```

Если ветки `dist/context` в origin ещё нет (первичная настройка), создать её плюмбингом — `git worktree add --orphan` не поддерживается в git < 2.42:

```
EMPTY=$(git hash-object -t tree /dev/null)
COMMIT=$(git commit-tree "$EMPTY" -m "chore: ветка артефактов сжатого контекста")
git branch dist/context "$COMMIT"
git push -u origin dist/context
git worktree add .context-dist dist/context
```

Без подключённого worktree пайплайн (`compact`) откажет понятной ошибкой с этими же командами, а не трейсбеком; ночной `sync` — тем же отказом, но до `update`. Проверяется не наличие каталога, а что это именно worktree ветки `dist/context`: из обычного каталога на этом месте git-команды уходят в основной репозиторий, и коммит артефактов попадает в `main`. Каталог удаляли через `rm -rf` — запись о worktree осталась, перед повторным `worktree add` нужен `git worktree prune`.

Файл собирается пайплайном `python3 tools/wiki_cli.py compact` в двух режимах:

- Ночная точечная правка — часть `sync`, отдельной команды не имеет. Изменившиеся страницы дают дифф по содержательной части (без frontmatter и навигационного хвоста), модель точечно правит тело `.context-dist/body.md`, файл пересобирается и проверяется. Не прошла проверка — тело возвращается к прежнему состоянию, файл не перезаписывается, изменения остаются в дереве человеку.
- Полная пересборка — `compact --rebuild`. Агентный прогон модели заново читает все страницы вики и пишет тело `.context-dist/body.md` с нуля; занимает около часа. Нужна раз в квартал либо после крупных изменений вики. Пайплайн результат **не коммитит** — закончив и сверив, закоммитить и запушить руками: `git -C .context-dist add -A && git -C .context-dist commit -m "chore: полная пересборка сжатого контекста" && git -C .context-dist push origin dist/context`. Пока пересборка не закоммичена, ночной прогон пропускается гейтом грязного worktree, и вика не обновляется. `compact --rebuild --from-body` — восстановление: собрать файл из уже готового `.context-dist/body.md`, не вызывая модель заново (нужно, если генерация отработала, а обёртка не дождалась ответа). Без `--rebuild` команда ничего не делает — печатает подсказку и возвращает код 2.

Детали, пороги проверок и коды возврата — [tools/README.md](tools/README.md). После квартальной пересборки полноту файла проверяет набор из 40 вопросов в [docs/context-recall/](docs/context-recall/README.md).

Даты релизов для блока «Последние релизы» ведёт человек оверрайдами в необязательном `context/release-dates.tsv` (`ReleaseNotes/<slug>` \t `ГГГГ-ММ-ДД`, формат — в [tools/README.md](tools/README.md)). `.context-dist/body.md` и `hubex-context.md` руками не правятся, это вывод пайплайна.
