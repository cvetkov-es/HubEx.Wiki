# HubEx.Wiki — вики HubEx для ИИ-агентов

> **Что здесь:** автономная копия вики HubEx (wiki.hubex.ru): вербатим-страницы, дистиллированные индексы и пайплайн обновления.
> **Когда сюда идти:** нужен факт о поведении или настройке продукта HubEx — начни с [index.md](index.md).

**HubEx** — облачная мультитенантная FSM-платформа (Field Service Management) для выездного обслуживания: заявки с жизненным циклом, объекты/оборудование, исполнители, SLA, чек-листы, акты, склад, аналитика.

Ключевая механика: **Заявка** проходит стадии настраиваемого жизненного цикла, привязана к **Объекту/Оборудованию** и **Компании**-заказчику; исполнители назначаются вручную или правилами автоназначения (вид работ, навыки, участок, график, геопозиция); сроки контролирует SLA.

Основные роли:
- **Диспетчер** — создаёт заявки в web-приложении, назначает исполнителей, контролирует выполнение.
- **Исполнитель (сервисный специалист)** — работает в мобильном приложении: принимает заявки, выезжает на объекты, фиксирует работы и чек-листы, получает подпись заказчика.
- **Заказчик** — подаёт заявки через своё мобильное приложение или клиентский портал, следит за статусом.
- **Администратор** — настраивает бизнес-процессы, роли, жизненные циклы и правила автоназначения в консоли администратора.

Приложения: web-приложение (диспетчеры, руководители), моб. «HubEx Исполнитель» (Android/iOS), моб. «HubEx Заказчик» (Android/iOS), клиентский портал, консоль администратора.

## Правила

- Страницы `pages/**` руками не правятся — их перезаписывает пайплайн. Правятся только индексы (точечно), README и tools.
- Не выдумывай факты о продукте: нет в страницах — так и скажи.
- URL страницы на вики: поле `url` во frontmatter; общее правило `pages/<section>/<slug>.md` ↔ `https://wiki.hubex.ru/docs/FAQ/RU/<section>/<slug>.html`. Slug в имени файла URL-декодирован: страницы с кириллицей в адресе лежат как `pages/ReleaseNotes/cкладской-документ-….md`, а в `url` тот же slug percent-encoded.
- Кросс-ссылки между курируемыми страницами — локальные относительные; картинки и прочие ссылки — абсолютные URL вики.
- Страница пропала с вики → пайплайн помечает `removed` в отчёте; копию и строку индекса удаляет человек.

## Получить и подтянуть (потребителю)

Вика — обычный git-репозиторий, для чтения пайплайн не нужен:

```
git clone <url>      # первый раз
git pull             # подтянуть свежую версию
```

Дальше читай слоями: [index.md](index.md) / [releasenotes-index.md](releasenotes-index.md) → страница в [pages/](pages/). Пайплайн (`tools/`) — git-сабмодуль; обычный `clone`/`pull` его **не тянет**, и это норма: для ответов по продукту он не нужен.

## Обновить из источника (мейнтейнеру)

Свежую версию вики с `wiki.hubex.ru` гонит пайплайн — он в отдельном репозитории `HubEx.Wiki.Pipeline`, подключён сабмодулем в `tools/`. Выкачай его один раз:

```
git submodule update --init          # или клонируй репозиторий с --recursive
```

Затем запускай обновление:

```
python3 tools/wiki_cli.py update [--page <section>/<slug>] [--recompress] [--report-file PATH] [--jobs N]
```

Без флагов — отчёт new/changed/removed (ничего не пишет). `--recompress` перезаписывает затронутые страницы и обновляет строки-аннотации индексов моделью; всё остаётся unstaged — ревью и коммит за человеком. Детали — [tools/README.md](tools/README.md) (доступен после `submodule update --init`).

## Ночной автоперезабор

На машине мейнтейнера крон каждую ночь в 00:00 МСК (21:00 UTC) гонит:

```
python3 tools/wiki_cli.py sync [--dry-run]
```

Это `update --recompress`, обвязанный гейтами: дерево не чисто или история разошлась с origin → прогон пропускается; ошибки страниц/модели/guard или недоступный sitemap → коммита нет, изменения остаются человеку. После успешного `update` тем же прогоном пересобирается `hubex-context.md` по фактически изменившимся страницам — guard-проблема здесь тоже блокирует коммит. Если всё чисто и что-то поменялось — коммит `chore: ночной перезабор вики <дата>` (`pages/`, `index.md`, `releasenotes-index.md`, `context/`, `hubex-context.md`) и пуш в `main`. Логи — `~/.local/state/hubex-wiki/`.

Следствия для человека: незакоммиченные правки в дереве отменяют ночной прогон (в том числе разъехавшийся указатель сабмодуля `tools/`); `removed`-страницы робот не удаляет; `export-llms` и выкладка на хостинг остаются ручным шагом. Детали и коды возврата — [tools/README.md](tools/README.md).

## Экспорт для сайта (llms.txt)

Готовый к выкладке на `wiki.hubex.ru` набор в формате [llms.txt](https://llmstxt.org/):

```
python3 tools/wiki_cli.py export-llms [--out dist]
```

Собирает в `dist/` (в `.gitignore`, не коммитится): `llms.txt` (каталог со ссылками на `.html.md`; релиз-ноуты в нём — одним указателем), `llms-releasenotes.txt` (отдельный каталог по релизам), `llms-full.txt` (вся вика одним файлом) и постраничные `docs/FAQ/RU/<section>/<slug>.html.md`. Раскладка `dist/` = зеркало корня сайта: выкладка сводится к копированию содержимого `dist/` в корень хостинга. Сеть и модель не нужны — чистое преобразование текущего контента; запускать после `update` перед выкладкой. Доставка на хостинг — вне пайплайна.

## Сжатый контекст (hubex-context.md)

[hubex-context.md](hubex-context.md) — весь продукт одним markdown-файлом ~110 тыс. символов, для чатов облачных ИИ-агентов (Perplexity, ChatGPT, DeepSeek и т.п.), которым этот репозиторий недоступен. Основной потребитель — отдел продаж: файл прикладывается в чат вместо ссылок на вики.

Файл собирается пайплайном из разделов `context/sections/**` по карте `context/map.tsv` (тема раздела, бюджет символов, страницы-источники):

```
python3 tools/wiki_cli.py compact [--all] [--page <section>/<slug>] [--report-file PATH]
```

Ночной `sync` пересобирает файл сам по изменившимся страницам — руками запускать `compact` нужно только точечно (например, после правки карты). Детали и коды возврата — [tools/README.md](tools/README.md).

Карту `context/map.tsv` — какие страницы в какой раздел и с каким бюджетом попадают — ведёт человек. `context/sections/**` и `hubex-context.md` руками не правятся, это вывод пайплайна.
