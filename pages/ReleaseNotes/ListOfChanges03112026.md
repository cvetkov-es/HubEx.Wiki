### 📧 Email-интеграция: управление уведомлениями через триггеры

Мы обновили работу email-интеграции, чтобы она была единообразной с другими каналами коммуникации в HubEx.

Раньше часть писем отправлялась автоматически настройками почтового ящика. Теперь почтовый ящик отвечает только за приём и отправку писем, а правила уведомлений настраиваются через триггеры.

Это позволяет централизованно управлять:

* событием, при котором отправляется письмо;
* получателями;
* темой и содержанием письма;
* включением и отключением конкретных уведомлений.

Дополнительно, раньше невозможно было вести переписку с заказчиком по почте, если заявка была создана из HubEx, а не с почты. Теперь клиент может ответить на email-уведомление прямо из почтового ящика. Ответ будет добавлен в соответствующий чат заявки.

### Что изменилось в настройках email-интеграции

Из формы настройки адреса отправителя удалён параметр **«Возможность ответа заказчику через чат»**.

Теперь этот параметр больше не используется в интерфейсе настройки почтовой интеграции.

Настройка почтового ящика теперь определяет только сам адрес почты: откуда HubEx принимает и отправляет письма. Правила отправки уведомлений задаются в разделе триггеров.

### Как теперь работает переписка по заявке через email

Если заказчик отвечает на письмо по почте:

1. HubEx находит заявку по идентификатору заявки.
2. Проверяет отправителя и его доступ к заявке.
3. Добавляет текст ответа и вложения в соответствующий чат заявки.

Ответ заказчика попадает в чат с заказчиком. Ответ сотрудника компании — в чат команды.

Для отправки ответа используется почтовый ящик компании или выданный почтовый ящик формата \*\*\*@client.hubex.ru, настроенный для приёма входящих писем.

### Когда ответ не будет добавлен в чат

Ответ не попадёт в чат, если:

* в компании нет включённого почтового ящика для приёма ответов;
* письмо невозможно связать с заявкой;
* отправитель неизвестен HubEx;
* у отправителя нет доступа к заявке.

Вложения из ответа добавляются к сообщению в чате, если размер каждого файла не превышает 50 МБ.

### Какие дополнительные триггеры уведомлений добавлены

Для email-интеграции автоматически добавлены четыре новых триггера уведомления:

| Триггер | Назначение |
| --- | --- |
| **Email: триггер создания заявки** | Срабатывает при создании новой заявки, отправляет инициатору сообщение по почте |
| **Email: триггер закрытия заявки** | Срабатывает при переходе заявки на стадию с включенным действием «Закрыть заявку», отправляет инициатору сообщение по почте |
| **Email: триггер сообщения по заявке (чат с заказчиком)** | Срабатывает при добавлении нового сообщения в чат с заказчиком, отправляет сообщение заказчику по почте |
| **Email: триггер сообщения по заявке (чат с командой)** | Срабатывает при добавлении нового сообщения в чат с командой, отправляет сообщение по почте всему списку наблюдателей по заявки. |

### Какие автоматические отправки изменились

Письмо о создании заявки больше не отправляется отдельной фоновой логикой почтовой интеграции. Теперь за него отвечает триггер события **«Заявка создана»** и для заявок созданных по интеграции по почте и для заявок созданных сразу в HubEx.

Аналогично, уведомления при изменении статусов в сценарии пересылки управляются через триггеры, а не отправляются автоматически настройками интеграции.

### Кому стандартные триггеры включены автоматически

В рамках реализации доработки весь стандартный набор из четырёх триггеров создан для всех компаний автоматически.

Для компаний без активной email-интеграции триггеры созданы, но остаются выключенными. Это позволяет не удалять настройки и автоматически использовать их после подключения почты.

Триггеры включаются по умолчанию для следующих компаний:

* компаний с действующей подпиской, начавшейся 1 апреля 2026 года или позже;
* компаний, в которых за последние шесть месяцев создавалась хотя бы одна заявка со способом подачи **«Электронная почта»**.

Для остальных компаний стандартные триггеры создаются выключенными. Их можно включить вручную в настройках уведомлений.

**Важно:** наличие почтового ящика само по себе не является достаточным условием для автоматического включения триггеров. Если почтовую интеграцию подключить позднее, потребуется вручную включить нужные триггеры уведомлений в настройках вашей Компании.

### Что нужно проверить после обновления

Если компания использует email-интеграцию, рекомендуем проверить:

1. Включён ли почтовый ящик для приёма ответов.
2. Созданы ли стандартные email-триггеры.
3. Включены ли нужные триггеры.
4. Настроены ли получатели сообщений.
5. Используется ли корректный адрес для ответа на письма.

После обновления email-интеграция работает по единой логике: почта обеспечивает обмен сообщениями, а триггеры определяют, когда, кому и какие уведомления отправлять.

### 🔢 Маска номера заявки - расчет ограничения

Мы обновили работу с маской номера заявки в типах заявок. Теперь ограничение считается не по количеству введённых символов в поле, а по длине итогового номера, который получится из маски. Максимальная длина — **32 символа**.

### Где работает

Ограничение действует в формах создания и редактирования типа заявки — в поле **«Маска номера заявки»**.

### Как считается длина

Считается не количество символов в поле маски, а длина номера заявки, который из неё получится:

| Блок маски | Длина |
| --- | --- |
| «Год ГГГГ», «Код компании» | 4 символа |
| «Год ГГ», «Месяц ММ», «День ДД» | 2 символа |
| «Диапазон чисел (0-9)», «Диапазон букв (А-Я)», «Символ /», «Символ \_», «Символ .» | 1 символ |
| Свой символ в квадратных скобках, например `[-]` или `[А]` | 1 символ |

**Пример:** `[{День ДД}][{Месяц ММ}][0-9][0-9][0-9]` — 7 символов.

### Что видит пользователь

* **Счётчик у поля маски** в формате «N/32»: текущая длина номера и лимит. Обновляется при каждом изменении маски.
* **Кнопки блоков** («Год ГГГГ», «Диапазон чисел (0-9)» и др.) становятся неактивными и серыми, если блок не помещается в оставшийся лимит. Например, при длине 30 недоступны «Год ГГГГ» и «Код компании», а «Месяц ММ» доступен.
* **Ручной ввод**: когда длина достигла 32, ввести новые символы в поле нельзя — удалять можно.
* **Сохранение**: если длина больше 32 (например, длинную маску вставили из буфера), тип заявки не сохраняется, под полем появляется ошибка «Максимальная длина маски номера заявки — 32 символа». Маска ровно на 32 символа сохраняется.

Прежнее ограничение поля в 256 введённых символов убрано: теперь лимит задаёт длина номера, а не текст маски.

### Что не изменилось

* Пустая маска по-прежнему не сохраняется: «Маска обязательное поле».
* Некорректная маска (например, текст вне квадратных скобок) по-прежнему даёт ошибку «Данные введены некорректно. Воспользуйтесь преднастроенными блоками для настройки маски».
* Маски уже созданных типов заявок автоматически не меняются. Если такая маска длиннее 32, её придётся сократить при следующем сохранении типа заявки.

### ✅ «Выбрать все» в Административной панели в списках учитывает строку поиска

Мы обновили поведение кнопки **«Выбрать все»** в полях множественного выбора в административной панели: теперь она добавляет только те варианты, которые видны в отфильтрованном по поиску списке, а не весь справочник целиком.

### Где работает

* **Жизненный цикл заявки** — переход между стадиями → «Предоставить доступ отдельным ролям» → поле «Роли»;
* **Сервисные учётные записи** — пользователь API и анонимный пользователь, поля «Роли» и «Участки»;
* **Триггеры** — «Получатели уведомления», «Критичности заявки, при которых будет отправлено уведомление», «Стадии заявки, на которых будет отправлено уведомление»;
* **Правила выбора получателей** — «Получатели уведомления»;
* **Вебхуки** — «Привязать к событию», «Привязать к стадии».

### Как теперь работает «Выбрать все»

* **Поиск введён** — добавляются только варианты, которые видны в отфильтрованном списке. Раньше добавлялись все варианты справочника независимо от поиска.
* **Уже выбранные значения остаются**, даже если не подходят под поиск. Повторно они не добавляются — дублей нет.
* **Поиск пустой** — добавляется весь список, как и раньше.
* **Нет совпадений** (в списке «Совпадений нет») — ничего не добавляется, выбранные ранее значения не снимаются.
