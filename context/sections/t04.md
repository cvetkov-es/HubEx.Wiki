## Позиционирование против смежных классов

Чем отвечать на «у нас уже есть HelpDesk / ТОиР / 1С» и как HubEx встаёт в существующий ландшафт заказчика. Опора — заявленный класс продукта и способы встраивания.

**Модель.** Заявленный класс: отечественная ERP-система класса FSM (Field Service Management) для сервисных подразделений с мобильным персоналом; профиль работ — ремонты, техобслуживание, обходы, клининг. Три сценария посадки:
1. Платформа целиком — WEB для офисного персонала (руководители, диспетчеры, логисты, менеджеры) + мобильные приложения исполнителей + отдельное приложение заказчика работ.
2. Только мобильное приложение — прямо заявлено: может использоваться отдельно от платформы, подключается по API к HelpDesk/ServiceDesk/ТОиР системе компании. Ход для лида, который учётную систему менять не собирается: HubEx закрывает полевой слой.
3. Сосуществование с 1С-контуром — 1С-конфигурация в составе платформы (опционально), для упрощения интеграции с 1С-совместимыми системами.

Смежные функции, закрываемые самим HubEx: электронный паспорт объекта как репозиторий данных об оборудовании — параметры, история обслуживания, документация, гарантия, контакты ([s07]). BI-слой не собственный: конструктор отчётов — Power BI или Apache SuperSet ([s18], [s19]).

Импортозамещение: реестр российского ПО с 15.07.2020, рег. №6816.

**Настройка.** Глубина встраивания задаётся не настройкой, а вариантом развёртывания и уровнем расширения (конфигуратор → HubEx Automate → плагины → проектные → продуктовые доработки) — [s21]. Интеграционный контур: открытый API + Swagger, REST API/SOAP в HubEx Automate; см. [s24].

**Ограничения.** Плотный обмен с внешней учётной системой упирается в вариант развёртывания: в public cloud интеграции свыше 10 запросов/сек не поддерживаются, при превышении доступ может быть принудительно ограничен, интеграция отключена; выделенные серверы такую нагрузку держат без рисков отключения. Проектные доработки и самостоятельное использование Power BI / Apache SuperSet требуют локального развёртывания или выделенных серверов — в публичном облаке не делаются. На лето 2024 HubEx Automate не позволяет изменять уже существующие в системе интерфейсы, только создавать новые: «повторить привычный экран их системы» — это уже проектная ветка. Плагин не умеет взаимодействовать с данными системы, ещё не сохранёнными пользователем на сервер. Детали вариантов и трудоёмкости — [s21].

**⚠ Грабли.** Сценарий «мобильное приложение отдельно» описан именно как подключение мобильного клиента HubEx к HelpDesk/ServiceDesk/ТОиР заказчика; обратной конфигурации (HubEx как бэкенд для чужого мобильного клиента) в источниках нет — не обещать. Отдельная ветка разработки под клиента расходится по коду с продуктом: замедляется обновление, растёт стоимость поддержки, при отказе от обновлений возможность обновляться может быть утрачена вовсе — цена «подгонки под их процесс» кодом, а не конфигуратором.
