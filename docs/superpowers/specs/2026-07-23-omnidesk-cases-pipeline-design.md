# Пайплайн кейсов поддержки из Omnidesk — дизайн (Фаза 2)

> Статус: черновик на ревью. Дата: 2026-07-23.
> Предшествует: Фаза 1 (спайк, `omnidesk/spike/`, gitignored) — польза подтверждена.

## 1. Цель и не-цели

**Цель.** Автоматически превращать накопленные переписки поддержки в Omnidesk в
переиспользуемые **обобщённые кейсы** и публиковать их как третий слой знаний
`HubEx.Wiki/cases/`. Главный потребитель — бот **Сова 2.0** (нужны обобщённые случаи,
а не сырые тикеты), плюс агенты-потребители самой вики.

**Не-цели.**
- Не документировать разовые инциденты (сбои серверов, «есть ли сейчас проблемы?»).
- Не дублировать продуктовый канон `pages/{admin,user}` — только то, чего в вике нет.
- Не тащить стек предшественников (n8n / Supabase / пер-тикетные саммари из старого CSV).
- Не строить stateful-машинерию (центроиды-как-первичный-ключ, пул, жизненный цикл) —
  преждевременно. См. §11.

## 2. Контекст и принятые решения

Проработано в брейншторме (2026-07-23):

- **Размещение — третий слой знаний по образцу релиз-ноутов.** Отдельный `cases-index.md`
  + каталог `cases/`, НЕ вмешивать в `pages/{admin,user}`. Репо уже суперсет (`index.md`
  + `releasenotes-index.md` — параллельные слои). Память: `omnidesk-support-cases`.
- **Уровень сложности — батч-ребилд с инкрементальным кэшем** (не stateful, не плоский RAG).
  Обоснование: плоский RAG отдаёт *сырые тикеты* (нарушает «обобщённые случаи») и инороден
  Сове (у неё BM25 по markdown, не вектор-стор). Stateful — избыточен, пока поток не огромен.
- **Публикация — авто, без human-in-the-loop.** Значит фильтры = единственный контроль
  качества; подстраховка — git-история (аудит + откат) и обязательный PII-скраб.
- **Доступ к Omnidesk — есть API** (`getCases`/`getMessage`).

## 3. Архитектура

Стадии, в стиле `HubEx.Wiki.Pipeline`. Дорогое (Omnidesk + LLM-саммари) — строго
инкрементально и кэшируется; полный пересчёт только на дешёвой локальной кластеризации.

```
Omnidesk API ──(дельта по watermark)──►  raw/      сырые переписки (кэш, копится)
raw/ ──(только новые)──► summarize+embed ─► corpus/  саммари+эмбеддинги (кэш, ключ id+updated)
corpus/ (ВЕСЬ, локально) ─► cluster ─► generalize ─► filters ─► render ─► cases/  (коммит в вику)
```

1. **Ingest.** Omnidesk API инкрементально по watermark (дата/id последней обработанной
   переписки). Чистка HTML, отсев бан-слов/служебных сообщений (логику предшественников из
   `omnideskFullExport.json` переиспользуем). Итог — нормализованные переписки в `raw/`.
2. **Summarize + embed.** На каждую *новую* переписку — LLM-саммари в
   `проблема/вопрос/ответ/ключи` + эмбеддинг. Кэш на диске, ключ = `id + updated_at`:
   переписка обрабатывается один раз. Эмбеддинг-модель контролируем мы (см. §11).
3. **Cluster.** Leader-кластеризация на косинусе (перенос из спайка, `clusterer.py`) по
   **всему** `corpus/` — это локальная numpy-математика. Крупные/рыхлые группы (низкая
   связность) **под-кластеризуются** более жёстким порогом, чтобы каждая финальная группа
   была топикально чистой и влезала в контекст LLM целиком — **без сэмплинга** (снимает
   потерю хвоста, найденную в спайке).
4. **Generalize.** На группу — LLM даёт 1..K кейсов с разбиением разных проблем (перенос из
   спайка, `case_generator.py`). Кэш по отпечатку группы: не изменилась — не перегенерим.
5. **Filters (весь контроль качества, см. §5).** novelty → durability → dedup → PII-scrub.
6. **Render + publish.** Кейсы → `cases/*.md`, пересборка `cases-index.md`, обновление ветки
   маршрутизации в `CLAUDE.md`. Коммит в `HubEx.Wiki` + пер-прогонный отчёт (что
   опубликовано / обновлено / отсеяно и почему).
7. **Сова.** Расширить `build_kb` третьим источником (см. §8).

## 4. Модель данных и хранение

Линия раздела — «продукт vs генерируемый кэш».

| Что | Где | В репо вики? |
|---|---|---|
| `cases/*.md`, `cases-index.md` | HubEx.Wiki | **Да, коммитим** |
| `raw/` — сырые переписки | сторона пайплайна | Нет (gitignore) |
| `corpus/` — саммари+эмбеддинги | сторона пайплайна | Нет |
| `state/` — watermark + индекс опубликованных кейсов (id, заголовок, центроид) | сторона пайплайна | Нет |

Коммитим **только `cases/`** — маленький, обезличенный дистиллят. `raw/`/`corpus/` — firehose
с PII и жирными векторами, в вику не течёт (прецедент: `omnidesk/` уже в `.gitignore`).
Кэш и `state/` должны переживать между прогонами → устойчивое хранилище на стороне пайплайна
(persistent-том хоста или приватный стейт-репо); конкретика — §11 (Q4).

## 5. Фильтры качества

Порядок и назначение (при авто-публикации это единственный контроль — пороги консервативные):

1. **Новизна к вике.** BM25 по `pages/**` достаёт близкие страницы → LLM-судья:
   `покрыто / частично / новое` (перенос из спайка, `novelty.py`, `bm25.py`). Отсекаем «покрыто».
2. **Долговечность** (новое; спайк показал, что без него натекает ~30–40% инцидент-шума).
   Классификатор «долговечное знание vs разовый инцидент». Отсекаем инциденты
   (разовый сбой, «есть ли проблемы сейчас», запрос обратной связи). Реализация — §11.
3. **Дедуп.** Меж-кластерный (похожие группы дают перекрывающиеся кейсы) + против уже
   опубликованных кейсов из `state/`.
4. **PII-скраб.** Обезличивание: имена клиентов, телефоны, ID тенантов, номера заявок,
   адреса. Обязательно, т.к. ревью нет. Проверяется отдельным проходом, не только промптом.

## 6. Стабильность идентичности кейсов

Проблема батч-ребилда: при пересборке с нуля границы кластеров плывут → файлы кейсов
«дёргаются» (шумные диффы, у Совы едут ссылки). Лёгкое лечение (без полного stateful):
новый кейс **сопоставляется с уже опубликованными** (`state/` индекс: эмбеддинг + заголовок);
при совпадении сохраняется тот же файл/id, содержимое обновляется на месте. ~10% усилий
от stateful, но стабильность даёт.

## 7. Инкрементальность и стоимость

- **Omnidesk** — только `N_новых` запросов за прогон; историю не перекачиваем.
- **LLM-саммари** — только новые переписки, кэш на диске.
- **Кластеризация** — весь `corpus/`, но локальный numpy (секунды-минуты).
- **LLM-обобщение** — только по изменившимся группам.

Цена — на входящий поток, а не на общий объём. Эволюция к stateful — только когда объём
реально прижмёт (§11).

## 8. Интеграция с Совой

`build_kb` в `HubEx Сова 2.0` тянет из HubEx.Wiki + HubEx.API. Добавить **третий источник**:
`cases/` → `knowledge/cases/`, плюс секция «## Опыт поддержки» в `llms.txt` (рядом с
«Продукт»/«API»). Дальше `kb_search`/`kb_read` находят кейсы как обычный markdown — ручной
навигации боту не нужно. Это правка в репо Совы (отдельный PR).

## 9. Навигация

- **Агент в репо вики:** третья ветка в `CLAUDE.md` — «продукт → `index.md`; релиз →
  `releasenotes-index.md`; проблема/траблшутинг → `cases-index.md`».
- **`cases-index.md`:** аннотированный каталог по темам, как `index.md`; генерится пайплайном.
- **Сова:** секция в `llms.txt` (§8).

## 10. Формат кейса

Markdown-файл `cases/<slug>.md` (перенос из спайкового шаблона, обезличенный):

```
# <Заголовок кейса>

**Проблема.** <суть обобщённо, без частных деталей>
**Симптомы.** <как проявляется>
**Решение / типовой ответ поддержки.** <что делает поддержка>
**Ключевые слова:** <...>
```

Метаданные (число тикетов-доказательств, last-seen, id) — во frontmatter, невидимы в тексте.

## 11. Открытые решения для ревью

- **Эмбеддинг-модель** (стадии 2–3). Теперь контролируем мы. Кандидаты: та же, что у Совы
  (консистентность экосистемы), либо через OpenRouter. Требование: детерминизм и версия
  зафиксированы (эмбеддинги кэшируются; смена модели = инвалидация `corpus/`).
- **Q4 — где живёт код и кэш. РЕШЕНО (2026-07-23):** в существующем **`HubEx.Wiki.Pipeline`**
  (сабмодуль `tools/`) — пакет `cases/` рядом с `update/`, сабкоманда в `wiki_cli.py`, тесты в
  `tools/tests/`. Один пайплайн-репо, одно место запуска. Кэш (`raw/`/`corpus/`/`state/`) —
  в gitignore этого репо / persistent-том хоста. Следствие: numpy добавляется в
  `tools/requirements.txt`; LLM — через существующий `update/model_client.py`.
- **Эвристика долговечности** (фильтр 2). Рекомендация: LLM-классификатор с чёткой рубрикой
  (не сигнальная эвристика — граница «инцидент vs знание» смысловая). Оценить точность на
  размеченной выборке из спайковых кейсов.

## 12. Тестирование

- Юнит на каждую стадию на фикстурах: парс ingest, инкрементальный кэш (ключ id+updated),
  кластеризация (перенос тестов спайка), логика фильтров, сопоставление идентичности,
  рендер `cases-index.md`. LLM — на моках, без сетевых вызовов.
- **Dry-run** — полный прогон, генерящий `cases/` и отчёт, но без коммита.
- Мини-e2e на малой фикстуре переписок → ожидаемые кейсы.

## 13. Риски

- **Ложная «новизна».** Фильтр долговечности недоотсекает инцидент-шум → в базу течёт мусор.
  Митигация: консервативные пороги, пер-прогонный отчёт, git-откат.
- **Утечка PII.** Скраб пропускает частные данные. Митигация: отдельный проход + тесты на
  типовые паттерны (телефон, ID тенанта, номер заявки).
- **Дрейф эмбеддинг-модели** ломает кэш/кластеры. Митигация: версия модели зафиксирована,
  смена = явная пересборка `corpus/`.
- **Устаревание кейсов.** Продукт меняется, кейс устаревает. В батч-версии частично
  снимается ре-прогоном новизны (кейс, ставший «покрыто», отсеивается). Полный lifecycle —
  предмет будущего stateful-этапа.
