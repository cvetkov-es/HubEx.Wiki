# HubEx.Wiki — выделение пайплайна в отдельный репозиторий (сабмодуль)

> **Статус:** спека согласована 2026-07-14 (три открытых решения подтверждены мейнтейнером). Следующий шаг — план реализации (writing-plans).
> **Область:** разделение `HubEx.Wiki` на два репозитория — контент (остаётся `HubEx.Wiki`) и пайплайн (новый `HubEx.Wiki.Pipeline`), подключённый обратно git-сабмодулем в `tools/`.
> **Автор решений:** Евгений Цветков (мейнтейнер).
> **Происхождение:** пересмотр решения §2 спеки [2026-07-13-hubex-wiki-repo-design.md](2026-07-13-hubex-wiki-repo-design.md) («контент + пайплайн вместе») на основе появившегося драйвера — почти всем потребителям вики пайплайн не нужен.

## 1. Зачем

Спека 2026-07-13 §2 сознательно держала контент и пайплайн в одном репо ради автономности («скачал и сам обновляешь»). Появился встречный драйвер: **потребитель вики — ИИ-агент — пайплайн не использует**; питон-код `tools/` это контекст-шум и лишний вес в клоне для 99% читателей. Обновление запускается **локально мейнтейнером** (cron/CI не планируется — см. §14 исходной спеки), поэтому «одна папка = само-обновление» перестаёт быть весомым аргументом: читателю обновлять нечего.

Решение — вынести пайплайн в отдельный репозиторий и подключить его обратно в `HubEx.Wiki` git-сабмодулем на месте `tools/`. Тогда:
- `git clone HubEx.Wiki` → чистый контент (страницы + индексы + роутер), `tools/` пуст;
- `git clone --recursive` (или `git submodule update --init`) → полный набор для обновления;
- автономность сохраняется в ослабленной, но достаточной форме (один флаг `--recursive`).

Автономность **домена** (вики не завязана на API/БД) при этом не нарушается: выносится инструмент, а не связь с другими доменами.

## 2. Решения (принятые)

| Решение | Выбор | Почему |
|---|---|---|
| Модель разделения | **Вариант A**: пайплайн — отдельный репо, обратно сабмодулем в `tools/` | Ближе к текущему потоку запуска, меньше нового кода, чем «два независимых репо + `--content-root`»; ложится на submodule-first дизайн комбо-репозиториев |
| Где запускается `update` | **Локально мейнтейнером** (подтверждено) | Cron/CI отложены; хостинг (GitHub) только хранит репозитории |
| Имя нового репо | **`HubEx.Wiki.Pipeline`** | Подтверждено |
| Хостинг | **Host-agnostic** (`.gitmodules` без имени хоста); первый хост — GitHub | Относительный submodule-URL резолвится от origin суперпроекта на любом хосте |
| Расположение репозиториев | **Оба у одного владельца** (GitHub-аккаунт/организация) | Позволяет относительный submodule-URL и `clone --recursive` без доп. настройки |
| URL сабмодуля | **относительный** `../HubEx.Wiki.Pipeline` | Резолвится от origin суперпроекта в пределах того же владельца; переносимо между хостами (смена GitHub↔Azure не трогает `.gitmodules`) |
| `docs/superpowers/` | **уезжает в пайплайн-репо** (с историей) | Dev-артефакты (specs/plans) потребителю вики не нужны — та же логика, что и для самого пайплайна |
| Изменения Python-кода | **нет** | Резолюция корня `Path(__file__).resolve().parents[2]` идёт по файловой системе; сабмодуль физически вложен в `tools/`, граница сабмодуля для путей невидима (§4) |
| История пайплайна | **сохраняется** | Извлечение через `git filter-repo` (16 коммитов, трогавших `tools/`), фолбэк — `git subtree split` |

**Явно вне среза:** генерализация пайплайна под другие домены (API/БД) — это отдельный будущий цикл, у пайплайна пока один потребитель, швы неизвестны (YAGNI); запуск `update` в CI (cron, любой хост) и связанная submodule-авторизация в CI; content-only артефакты/ветки для потребителей; перевод комбо-репозиториев на новый сабмодуль (их ещё нет).

## 3. Конечное состояние

**HubEx.Wiki** (тот же репозиторий, имя и история сохраняются) — только контент:

```
HubEx.Wiki/
├── README.md · CLAUDE.md · AGENTS.md   ← роутер (правка: пометки про сабмодуль)
├── index.md · releasenotes-index.md    ← индексы
├── pages/                              ← admin/ · user/ · ReleaseNotes/
├── .claude/
├── .gitignore                         ← без `tools/update/drafts/`
├── .gitmodules                        ← новый: tools → HubEx.Wiki.Pipeline
└── tools/                             ← сабмодуль (пуст без --recursive)
```

`docs/superpowers/` в контент-репо **отсутствует** (уехал в пайплайн).

**HubEx.Wiki.Pipeline** (новый) — бывшее содержимое `tools/`, поднятое в корень, плюс `docs/`:

```
HubEx.Wiki.Pipeline/
├── wiki_cli.py
├── update/           ← manifest · fetch · diff · recompress · guard · model_client · report · pipeline · prompts/
├── lint/             ← check_links.py
├── tests/
├── conftest.py
├── requirements.txt
├── README.md
├── pytest.ini        ← testpaths = tests (было tools/tests)
├── .gitignore        ← update/drafts/ · __pycache__/ · *.pyc · .pytest_cache/
└── docs/superpowers/ ← specs/ · plans/ (перенос с историей, включая эту спеку)
```

## 4. Почему код не меняется

Три модуля, работающие с корнем репозитория, резолвят его одинаково — подъём по файловой системе на два уровня:

- [update/pipeline.py:14](../../../tools/update/pipeline.py) — `REPO_ROOT = Path(__file__).resolve().parents[2]`
- [update/recompress.py:11](../../../tools/update/recompress.py) — то же
- [lint/check_links.py:6](../../../tools/lint/check_links.py) — `ROOT = Path(__file__).resolve().parents[2]`

Из `tools/update/pipeline.py`: `parents[0]=tools/update`, `parents[1]=tools`, `parents[2]=` корень репо (где `pages/`, `index.md`). Из `tools/lint/check_links.py`: `parents[0]=tools/lint`, `parents[1]=tools`, `parents[2]=` корень. После разделения сабмодуль физически лежит в `<HubEx.Wiki>/tools/`, поэтому `parents[2]` по-прежнему указывает на суперпроект. Python идёт по реальной ФС — граница git-сабмодуля для путей не существует.

Следствия:
- Команда запуска **не меняется**: `python3 tools/wiki_cli.py update [--recompress]` из корня `HubEx.Wiki`.
- `tools/wiki_cli.py` кладёт в `sys.path` свою папку (`tools/` = корень пайплайн-репо) и импортирует `update` — работает.
- Существующий необязательный параметр `root` в `run_update(...)` и path-хелперах (для тестов) не задействуется — дефолт `REPO_ROOT` post-split корректен.

## 5. Хостинг (host-agnostic)

`.gitmodules` использует **относительный** URL `../HubEx.Wiki.Pipeline` — в нём **нет имени хоста**. Git резолвит его от `origin` суперпроекта при клонировании, поэтому одна и та же запись работает на любом хосте:

- GitHub: `github.com/<owner>/HubEx.Wiki` → `github.com/<owner>/HubEx.Wiki.Pipeline`
- Azure DevOps: `dev.azure.com/<org>/<proj>/_git/HubEx.Wiki` → `.../_git/HubEx.Wiki.Pipeline`
- любой другой (GitLab, self-hosted, локальный путь) — так же

Относительный URL наследует и **протокол** origin (SSH-клон → сабмодуль по SSH, HTTPS → HTTPS) — протокол тоже не зашит.

Единственный инвариант универсальности: оба репо лежат **рядом у одного владельца** (namespace) на этом хосте. Перенос семьи на другой хост = зеркалирование обоих репо туда же, `.gitmodules` не трогается.

Host-специфична только **разовая ops-операция** «создать репо + запушить»: на GitHub — `gh repo create`, на Azure — `az repos`/веб. Это внешний шаг, в контракт репозитория не входит. Первый хост — **GitHub**.

Запуск `update` локальный → `git submodule update --init` идёт под кредами мейнтейнера к текущему хосту; CI-авторизации нет (вне среза).

## 6. Миграция (пошагово)

Порядок (детализируется в плане реализации):

1. **Извлечь пайплайн с историей** в новый репо. На свежем клоне `HubEx.Wiki`:
   `git filter-repo --path tools/ --path docs/ --path-rename tools/:`
   → `tools/**` поднимается в корень, `docs/**` остаётся на месте, история коммитов, трогавших эти пути, сохраняется. Фолбэк без установки filter-repo — `git subtree split --prefix=tools` (тогда `docs/` переносится отдельным шагом).
2. **Создать репозиторий `HubEx.Wiki.Pipeline`** у того же владельца на текущем хосте (сейчас GitHub: `gh repo create`), запушить извлечённую историю — разовый host-специфичный шаг.
3. **В HubEx.Wiki:** `git rm -r tools/ docs/` → коммит; затем `git submodule add ../HubEx.Wiki.Pipeline tools`, пин на HEAD пайплайна (создаётся `.gitmodules`).
4. **Разнести конфиги** (§7).
5. **Обновить роутер** (§8).
6. **Проверки/приёмка** (§9).

## 7. Разнос конфигов

- **`pytest.ini`**: уезжает в пайплайн-репо; `testpaths = tools/tests` → `testpaths = tests`. Из контент-репо удаляется (тестов там больше нет).
- **`.gitignore` пайплайна** (новый): `update/drafts/`, `__pycache__/`, `*.pyc`, `.pytest_cache/`.
- **`.gitignore` контента**: убрать `tools/update/drafts/` (теперь внутри сабмодуля, игнорируется его собственным `.gitignore`); оставить `.superpowers/`, `__pycache__/`, `.pytest_cache/`.
- **`tools/conftest.py`** и **`requirements.txt`** едут внутри `tools/` как есть.

## 8. Обновление роутера (контент-репо)

Правится только текст, команды прежние:
- **README.md**, блок «Обновление»: пометить, что `tools/` — git-сабмодуль; перед первым запуском `git submodule update --init` (или клонировать `--recursive`); ссылку на детали вести в `tools/README.md` (доступен после init). Блок «Комбинирование с другими доменами» уже описывает submodule-модель — согласовать формулировки.
- **CLAUDE.md**, **AGENTS.md**: та же пометка про сабмодуль в разделе про пайплайн; сохранить правило «pages/** руками не правь».

## 9. Проверки / приёмка

- Свежий `git clone --recursive` → в `tools/` `python3 -m pytest -v -m "not live"` (офлайн-набор) зелёный; `python3 tools/wiki_cli.py update` (без `--recompress`) отрабатывает и печатает отчёт (нужна сеть).
- `python3 tools/lint/check_links.py` — чист.
- Голый `git clone` (без `--recursive`) → `tools/` пуст, `pages/` и индексы на месте, роутер читается.
- `git submodule status` в `HubEx.Wiki` показывает пин на нужный SHA пайплайна.

## 10. Риски и как гасим

- **Инверсия сабмодуля** (инструмент пишет в суперпроект `pages/`+индексы): приемлемо — запуск локальный, git к записи в рабочее дерево нейтрален; связь «пайплайн знает раскладку» существовала и до разделения, теперь версия пайплайна ещё и явно пиннится SHA.
- **Агенты путаются в сабмодулях** (забыть `--init`, detached HEAD): читающие вики агенты сабмодуль не трогают (не выкачан — норм); рискует только обновляющий агент/мейнтейнер — узкий blast radius. Забытый `--init` → команда падает понятной ошибкой отсутствия файла; README предупреждает.
- **`git filter-repo` не установлен**: фолбэк `git subtree split` (встроен), с отдельным переносом `docs/`.
- **Расхождение версий пайплайн↔раскладка**: гасится пином SHA в суперпроекте (`git add tools` при обновлении пайплайна).

## 11. Композиция с будущими доменами и комбо (forward-compat)

Разделение — прямой шаг к задуманной submodule-модели «домены + комбо», а не развилка в сторону:

- **Вложенность работает.** Комбо-репо (вики+API) подключает домены сабмодулями, каждый домен — свой пайплайн сабмодулем: `комбо → HubEx.Wiki → HubEx.Wiki.Pipeline` (два уровня). Git тянет рекурсивно (`clone --recursive` / `submodule update --init --recursive`).
- **Глубина init управляема — и это сохраняет главный выигрыш.** Потребителю комбо, которому нужен только контент: `git submodule update --init` (один уровень) → выкачиваются контент вики и API, а `tools/` каждого домена **остаются пустыми**. Кому нужно обновлять: `--init --recursive`. То есть «контент без пайплайна» продолжает работать и внутри комбо.
- **Ничего не форкложено.** Чтобы позже сделать *общий* пайплайн на все домены (генерализация, #3) или *свой* на каждый домен (вероятнее — источники разные: вики=HTML-краул, API=OpenAPI), пайплайн в любом случае сначала должен стать отдельным репо — что и делается здесь. Сегодняшнее решение — предпосылка для обоих путей.
- **Условие гладкой рекурсии:** держать всю семью репозиториев **рядом у одного владельца** (на любом хосте) — тогда относительные submodule-URL (`../X`) резолвятся на каждом уровне (согласуется с §2, §5).
- **Цена вложенности** (принимаем осознанно): обновление глубокого сабмодуля — бамп пина по цепочке вверх (пайплайн → домен → комбо); стандартное submodule-обслуживание.

Развилка «общий пайплайн vs пайплайн на домен» — отдельное будущее решение (#3), сегодня не принимается и не блокируется.

## 12. Вне среза (явно)

Генерализация пайплайна под другие домены; запуск `update` в CI (любой хост) и submodule-авторизация в CI; content-only ветки/артефакты; комбо-репозитории и их перевод на сабмодуль; авто-коммит/расписание. Всё это — отдельные будущие циклы.
