# HubEx.Wiki — автономный репозиторий вики HubEx для ИИ-агентов

> **Статус:** спека согласована 2026-07-13. Следующий шаг — план реализации (writing-plans).
> **Область:** новый репозиторий `HubEx.Wiki` целиком: контент (вербатим-страницы + индексы), роутер для агентов, пайплайн обновления `update`.
> **Автор решений:** Евгений Цветков (мейнтейнер).
> **Происхождение:** выделение вики из монорепы `HubEx.AI-2.0`. Наследует согласованную там спеку `update wiki` (2026-07-10) с упрощениями под отдельный репозиторий; монорепа в этом цикле **не меняется**.

## 1. Зачем

Ядро знаний `HubEx.AI-2.0` собирало все источники (API, БД, продукт, вики) в один репозиторий. Для шаринга это неудобно: кому-то нужна только вики, кому-то вики+API. Решение — дробление на доменные репозитории: каждый домен автономен и скачивается сам по себе, комбинации собираются тонкими репо-обёртками с git-сабмодулями и своим README-роутером.

`HubEx.Wiki` — первый доменный репозиторий. Вики — идеальный кандидат: источник (`wiki.hubex.ru`) публичен и не требует кред; связанность с остальным ядром минимальна (одна ссылка из `product/overview.md`); внутренние ссылки страниц ведут на URL вики, а не на локальные пути монорепы.

Потребитель — ИИ-агент (Claude Code и аналоги): репозиторий должен читаться слоями «роутер → индекс → страница», без внешних зависимостей и ссылок наружу.

## 2. Границы (принятые решения)

| Решение | Выбор | Почему |
|---|---|---|
| Состав репозитория | **контент + пайплайн обновления** | Вики публична, кред не нужно — репо полностью автономно: скачал и сам обновляешь |
| Модель комбинирования | **git submodules**; этот репо — лист, ссылок наружу нет | Один источник правды, версии зафиксированы; автономность — требование к дизайну |
| ReleaseNotes | **включаем**, индекс отдельным файлом `releasenotes-index.md` | ~113 релиз-ноутов раздули бы главный индекс; агент сможет отвечать «что нового в релизе X» |
| Засев контента | **сначала пайплайн, им же засеять всё** (admin + user + ReleaseNotes) | Единый формат с первого дня; спека монорепы и так требовала bulk-refresh копий старого краулера |
| Аннотации индекса | **admin/user переносятся из `wiki-index.md` монорепы** (правка путей), моделью генерируются только ReleaseNotes и будущие new/changed | Ручную дистилляцию 136 строк жалко терять и незачем регенерировать |
| Монорепа `HubEx.AI-2.0` | **не трогаем вообще** (ни удалений, ни пометок) | Решение мейнтейнера; переход монорепы на сабмодуль — отдельный будущий цикл |
| Снапшоты | **отдельных снапшотов нет — диффим против `pages/`** | В монорепе двойное хранение оправдывалось чувствительностью записи в `knowledge/`; здесь страницы и есть контент репозитория |
| `crawled_at` во frontmatter | **убираем** | Волатильное поле шумело бы в диффах; дату даёт git-история |
| Кросс-ссылки между статьями | **переписываются в локальные относительные** для курируемых страниц; вне курации — остаются URL | Комфорт агента; URL восстановим механически (frontmatter `url` + правило `pages/<section>/<slug>.md` ↔ `.../docs/FAQ/RU/<section>/<slug>.html`) |
| Группировка `pages/` | **как в источнике: `admin/`, `user/`, `ReleaseNotes/`** | Каноническое деление из sitemap, на нём держится соответствие «URL ↔ файл»; тематическая навигация — работа `index.md`; плоско нельзя (имена пересекаются: `Integration.md` есть в admin и user) |
| Синтезированный обзор (`overview.md`) | **в первой версии не делаем** — репозиторий выходит чистым зеркалом: страницы + индексы + пайплайн | Асимметрия рисков: без обзора агент медленнее, но верен (индекс → вербатим-страницы); ошибочный обзор даёт уверенно-неверные ответы. Ручное ведение исключено решением мейнтейнера, а контур проверки модельных правок пока слаб (guard проверяет только форму, бенчмарков нет). Дизайн модельного обзора готов и отложен в §14 |

**Явно вне среза:** любые правки `HubEx.AI-2.0`; комбо-репозитории и подключение сабмодулей; cron/расписание; бенчмарки качества; тюнинг промпта пересжатия (после первых живых прогонов); держать обе формы ссылок (локальную и URL) инлайн — YAGNI, конверсия детерминирована в обе стороны.

## 3. Структура репозитория

```
HubEx.Wiki/
├── README.md               ← роутер: что это, карта, правила ведения, правило восстановления URL
├── CLAUDE.md               ← вход для Claude Code (дублирует критичное из README)
├── AGENTS.md               ← вход для прочих агентов
├── index.md                ← аннотированный каталог admin+user, тематические секции
├── releasenotes-index.md   ← индекс релиз-ноутов (по строке на релиз)
├── pages/
│   ├── admin/              ← ~39 страниц (вербатим-копии)
│   ├── user/               ← ~99 страниц
│   └── ReleaseNotes/       ← ~113 страниц (casing как в sitemap)
├── tools/
│   ├── README.md           ← установка, команды
│   ├── requirements.txt    ← beautifulsoup4, markdownify
│   ├── wiki_cli.py         ← CLI: update [--page ...] [--recompress] [--report-file PATH]
│   ├── update/             ← модули пайплайна + prompts/
│   ├── lint/               ← check_links.py (перенос из монорепы, адаптация путей)
│   └── tests/              ← юниты на фикстурах + живой смоук (маркер live)
└── docs/superpowers/       ← specs/, plans/
```

Слои для агента: README (роутер) → `index.md` / `releasenotes-index.md` (аннотации, тематические секции) → `pages/**` (полный текст). Правила ведения в README: страницы `pages/**` руками не правятся — их перезаписывает пайплайн; правятся только индексы, README и tools.

## 4. Поток данных пайплайна

```
update
  → discover: GET wiki.hubex.ru/sitemap.xml → парсинг <loc> → фильтр курации
             → [(page_id, url)]   где page_id = <section>/<slug>
  → для каждой страницы:
       fetch HTML → извлечь #main_content_wrap → почистить хром/трекинг
       → абсолютизировать src/href → переписать кросс-ссылки на курируемые страницы
         в локальные относительные → markdownify → frontmatter → normalize
       → сравнить с pages/<section>/<slug>.md
       → статус new / unchanged / changed (+ короткий unified-diff тела для отчёта)
       → для new/changed: черновик в tools/update/drafts/<section>/<slug>.md (в .gitignore)
  → removed: файл есть в pages/, страницы нет в sitemap → флаг в отчёте (не удаляем)
  → report (markdown в stdout / --report-file): new / changed / removed / error

--recompress (единственный режим, пишущий в pages/ и индексы):
  для new/changed:
    (а) механически: перезаписать pages/<page_id>.md из черновика
    (б) моделью (claude -p, фикс-промпт): строка-аннотация в доме-стиле —
        admin/user → в тематическую секцию index.md
        ReleaseNotes → в releasenotes-index.md
    guard: аннотация ссылается только на реально существующий файл страницы
  всё остаётся unstaged — человек смотрит git diff + отчёт и коммитит сам
```

Ключевое отличие от спеки монорепы: снапшот-базы нет, роль «предыдущего состояния» играет сама `pages/**`. Без `--recompress` прогон ничего не пишет (кроме gitignored-черновиков) — режим detect-and-report чист по построению.

## 5. Компоненты

Логика — в чистых модулях, тестируемых на фикстурах; сеть и модель изолированы в тонких обёртках и мокаются.

| Файл | Ответственность | I/O |
|---|---|---|
| `tools/update/manifest.py` | `sitemap.xml` → парсинг `<loc>` → фильтр курации → `[(page_id, url)]` | сеть |
| `tools/update/fetch.py` | HTML → тело `#main_content_wrap` → чистка → абсолютизация → локализация кросс-ссылок → markdownify → frontmatter → normalize | сеть |
| `tools/update/diff.py` | **чистая**: (old_md, new_md) → статус + короткий unified-diff (`difflib`) | нет |
| `tools/update/draft.py` | **чистая**: сконвертированная страница → md-черновик (= будущая вербатим-копия) | нет |
| `tools/update/recompress.py` | оркестрация пересжатия страницы: копия + вызов модели на аннотацию + guard | файлы, модель |
| `tools/update/guard.py` | **чистая**: проверка аннотации — ссылка только на существующий `pages/<page_id>.md`, разумный лимит длины | нет |
| `tools/update/model_client.py` | обёртка `claude -p` через stdin (перенос из монорепы) | подпроцесс |
| `tools/update/report.py` | **чистая**: сводка прогона → markdown-отчёт | нет |
| `tools/update/pipeline.py` | оркестрация: `run_update(...)` | сеть/файлы |
| `tools/update/prompts/recompress.md` | фикс-промпт: страница (+текущая строка индекса, если была) → одна строка-аннотация | — |
| `tools/wiki_cli.py` | подкоманда `update [--page PAGE_ID ...] [--recompress] [--report-file PATH]` | — |

Локализация кросс-ссылок (в `fetch.py`): ссылка вида `https://wiki.hubex.ru/docs/FAQ/RU/<section>/<slug>.html` (или относительный эквивалент), где `<section>/<slug>` входит в курируемый манифест, → относительный путь до `pages/<section>/<slug>.md` от текущей страницы (например `TicketType.md` внутри секции, `../user/Filters.md` между секциями). Всё остальное (картинки `/attachments/...`, легаси-страницы, внешние сайты) — абсолютные URL.

## 6. Фильтр курации (`manifest.py`)

`sitemap.xml` даёт «вселенную» страниц (~266 `<loc>`); трекаем курированное подмножество:

- **Брать** только секции `admin`, `user`, `ReleaseNotes` (путь `/docs/FAQ/RU/<section>/<slug>.html`); корневая навигация (`/index_*.html`, `/docs/GettingStarted*.html`) отсекается автоматически — не те секции.
- Внутри секций **отсеять денилист** по slug: суффиксы `Old`, `Copy`; префиксы `index`, `main`, `GettingStarted`.
- `page_id = <section>/<slug>` (без `.html`), напр. `admin/BusinessProcess`, `ReleaseNotes/<...>`.

## 7. Конвертация HTML→md (`fetch.py`)

1. Распарсить HTML (`beautifulsoup4`), выбрать `#main_content_wrap`; не найден → ошибка страницы (§10).
2. Удалить хром и мусор: `header`/`footer`/`nav`/поиск, `<script>`/`<style>`, трекинг-пиксели (`<img>` с внешним `src` на аналитику, напр. `mc.yandex.ru`).
3. Абсолютизировать относительные `src`/`href` в `https://wiki.hubex.ru/...`; затем локализовать кросс-ссылки на курируемые страницы (§5).
4. `markdownify` → markdown; `<img>` → `![alt](https://wiki.hubex.ru/attachments/...)`.
5. Frontmatter: `title` (из `<title>`/`<h1>`), `url`, `section`, `content_hash` (`hashlib` от нормализованного тела). Поля `crawled_at` нет.
6. Нормализация: единый перевод строк, схлопывание хвостовых пробелов и лишних пустых строк — стабильный построчный git-дифф. Один и тот же нормализатор для черновика и вербатим-копии.

## 8. Дифф (`diff.py`)

- Статус страницы: `new` (нет файла в `pages/`) / `unchanged` (нормализованный текст идентичен) / `changed`.
- Для `changed` — короткий unified-diff тела (`difflib.unified_diff`, 3 строки контекста) в отчёт.
- `removed` — на уровне набора: файл в `pages/` есть, `page_id` в манифесте нет. Только флаг в отчёте; удаляет человек. Вычисляется **только при полном прогоне** (без `--page`) — на точечном наборе сравнение некорректно.
- Переименование страницы на вики отдельно не детектится — приходит как `removed` (старый slug) + `new` (новый slug) в одном отчёте; специальной логики нет.
- Сравнение — по нормализованному телу + стабильному frontmatter (`title`/`url`/`section`/`content_hash`). Появится иной шум (счётчики, даты в теле) — точечный нормализатор отдельным решением (YAGNI сейчас).

## 9. Пересжатие (`--recompress`) и guard

Для каждой `new`/`changed` страницы:

- **Механически** (без ИИ): перезаписать `pages/<page_id>.md` из черновика.
- **Моделью** (`claude -p`, фикс-промпт): вход — md страницы + текущая строка индекса (если была); выход — одна строка-аннотация в доме-стиле (md-ссылка на страницу, тире, одно предложение, `⚠` для страниц-грабель) + предлагаемая тематическая секция. admin/user → сплайс в `index.md`; ReleaseNotes → в `releasenotes-index.md`.
- **Когда модель вызывается:** для `changed` — всегда (тело менялось, аннотация могла устареть); для `new` — только если строки в индексе ещё нет; если строка уже есть (кейс засева с перенесёнными аннотациями), она сохраняется как есть.
- **Guard** (детерминированный, fail-safe): ссылка в аннотации указывает на существующий файл; длина в пределах лимита. Грязный guard → предупреждение в отчёте, файлы остаются unstaged, exit ≠ 0.
- Всё unstaged: человек смотрит `git diff` + отчёт и коммитит страницы вместе с индексами. Авто-коммита в этом срезе нет (в монорепе `--auto-commit` появился для cron-сценария — здесь YAGNI до появления расписания).

## 10. Обработка ошибок

- `sitemap.xml` не забрался / пуст после фильтра → `ManifestError`, жёсткий провал (нет источника перечня).
- Одна страница (сеть / не-200 / нет `#main_content_wrap` / пустое тело) → статус `error`, пропуск, остальные продолжают; итоговый exit-код ≠ 0.
- Модель упала при пересжатии → индекс не тронут, страница помечена в отчёте, exit ≠ 0.

## 11. Засев и миграция

Порядок внедрения (после реализации пайплайна, TDD):

1. **Каркас репозитория:** README-роутер, CLAUDE.md, AGENTS.md, скелет `index.md` (тематические секции как в `wiki-index.md` монорепы) и `releasenotes-index.md`, `.gitignore` (`drafts/`, `__pycache__/` и т.п.).
2. **Перенос аннотаций:** скрипт-однократка переносит строки `wiki-index.md` монорепы в `index.md` с правкой путей `wiki/<section>/<slug>.md` → `pages/<section>/<slug>.md` (читает монорепу, в неё не пишет; после засева скрипт удаляется).
3. **Засев страниц:** первый прогон `update --recompress` скачивает все курируемые страницы (все `new`). По правилу §9 модель вызывается только для страниц без строки в индексе: admin/user уже покрыты перенесёнными аннотациями, моделью аннотируются только ReleaseNotes.
4. **Проверки:** `check_links.py` чист; выборочное сравнение 3–5 страниц с монорепой (смысловая идентичность тел при новом формате).
5. Человек ревьюит и коммитит.

Идемпотентность: повторный `update` сразу после засева → все `unchanged`, ничего не записано.

## 12. CLI

```
python tools/wiki_cli.py update [--page PAGE_ID ...] [--recompress] [--report-file PATH]
```

- без `--page` — все курируемые страницы из sitemap;
- `--page` (повторяемый, `<section>/<slug>`) — только указанные;
- `--recompress` — перезапись затронутых страниц + аннотации (unstaged, на ревью);
- `--report-file` — дублировать отчёт в файл (по умолчанию stdout).

## 13. Тестирование (TDD)

- `manifest` — фикстура `sitemap.xml`: парс `<loc>`, фильтр секций, денилист, отсев корневой навигации.
- `fetch`/конвертер — фикстура HTML → ожидаемый md: тело извлечено, хром/трекинг срезаны, картинка абсолютизирована, кросс-ссылка на курируемую страницу стала локальной (внутри секции и между секциями), ссылка на некурируемую осталась URL, frontmatter собран (без `crawled_at`), нормализация стабильна.
- `diff`/`draft` — new / unchanged / changed, форма черновика.
- `guard` — ссылка на несуществующую страницу ловится; чистая аннотация проходит.
- `report` — сводка со статусами и ошибками.
- Сеть и модель мокаются; юнит-тесты модель не вызывают.
- **Живой смоук** (маркер `live`, пропускается офлайн): забрать `admin/BusinessProcess`, тело непустое, картинка абсолютная, guard чист.
- Прогон: `python -m pytest tools/tests -v` (офлайн `-m "not live"`).

## 14. Что дальше (вне этой спеки)

- Переход `HubEx.AI-2.0` на сабмодуль `HubEx.Wiki` (удаление копии вики из монорепы) — когда дойдёт очередь до дробления остальных доменов.
- Комбо-репозитории (вики+API и т.д.) — тонкие обёртки с сабмодулями.
- Расписание обновления (cron + PR) и `--auto-commit`.
- Бенчмарки качества индексов; тюнинг промпта пересжатия по живым прогонам.
- **Синтезированный обзор `overview.md`** (модель системы: сущности, связи, бизнес-правила). Триггер добавления: живое использование показывает, что агенты систематически буксуют на концептуальных вопросах; вводить вместе с бенчмарком качества. Отложенный дизайн (обсуждён 2026-07-13): контент пишет только модель (человек ревьюит дифф); засев — синтез из `pages/admin|user/**` (map-reduce, AI-референс `HubEx_main_info.md` как образец структуры, факты только из страниц); обновление — минимальной правкой в `--recompress` (вход: текущий обзор + диффы затронутых admin/user-страниц; выход: точечная правка или «изменений не требуется»; полная регенерация запрещена промптом — недетерминизм формулировок обесценил бы ревью); контракт: только выводимое из `pages/`, при расхождении истина — страница; guard: валидность ссылок, обязательные секции, лимит размера. Принятые риски, из-за которых слой отложен: guard не проверяет семантику, ошибочный обзор даёт уверенно-неверные ответы, автоправки без измерителя накапливают тихий дрейф.
