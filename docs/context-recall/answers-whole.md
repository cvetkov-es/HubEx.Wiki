# Ответы по варианту A

### A01
**Статус:** ЕСТЬ
**Ответ:** Доступ к полю задаётся в разделе «Поля на форме заявки» (Консоль → «Настройки заявки» → «Поля на форме заявки») — **в разрезе Ролей и Стадий заявки**, это отдельный механизм, независимый от общей настройки Ролей. Четыре варианта: **RO** — только просмотр; **RW** — просмотр и необязательное редактирование; **RWM** — просмотр и обязательное заполнение; **«Настройка не выбрана»** — поля не будет видно на форме. То есть «не видит» = «Настройка не выбрана», «только чтение» = RO, «обязан заполнить» = RWM. Настраиваются все поля формы; дополнительные поля лежат в самом низу таблицы с отметкой **А**. Вручную для каждой новой стадии настраивать не нужно: контекстное меню (три точки) у названия Роли → «Копировать в…» → отметить целевые Роли; аналогично копируются настройки Стадии. Оговорки: единственное неотключаемое поле — **«Тип заявки»** (хотя бы для одной Роли и Стадии должно быть RW); для учётной записи владельца тенанта («Системный администратор») настройка видимости полей **не работает** — все поля доступны всегда; если создать новую Стадию и не настроить для неё поля, форма заявки будет пустой (белый экран).
**Опора:** «Поля на форме заявки: тонкая настройка доступа»; «Тенант, владелец тенанта, учётные записи»

### A02
**Статус:** ЕСТЬ
**Ответ:** Импорт Заявок — **до 2000 строк за одну загрузку** ([user/Import], [user/CreatingTicket]); файл отдельно фиксирует расхождение: [user/HubExStepByStep] называет **до 1000** за раз. Загрузка только в формате специального шаблона Excel (скачивается по кнопке импорта); импорт заявок идёт **в фоновом режиме**. Своя нумерация сохраняется: в шаблоне импорта есть обязательное поле **«Номер»**, и ⚠ этот же номер присваивается Акту выполненных работ. Ограничение на номер: «Номер заявки» формируется автоматически по маске Типа заявки, **может быть изменён вручную**, ⚠ **максимум 32 символа**. Дополнительно при импорте заявок обязательны «Тип заявки» (в системе должен быть создан хотя бы один), «Описание заявки», «Заказчик», «Оборудование»/«Объект», «Часовой пояс», «Вид работ», «Критичность», «Стадия», «Срок исполнения» (формат дд.мм.гггг чч:мм), «Исполнитель», «Контактное лицо» (создаётся автоматически), «Обращение от». Повторная загрузка дополненного шаблона не приводит к дублированию ранее загруженной информации.
**Опора:** «Импорт и экспорт»; «Заявка: модель, поля, списки»; «Противоречия и расхождения между страницами вики»

### A03
**Статус:** ЕСТЬ
**Ответ:** Графики работы — Консоль → «Структура предприятия» → «Графики работы», два типа: **Недельный** и **Сменный** (повторяющийся интервал смен и выходных — 2/2, 1/3; «сутки через трое» ложится на сменный тип). «Из коробки» есть графики по умолчанию: «Выходные 9-18»; «2/2(4) c 9:00 до 18:00»; «2/2(3) с 9:00 до 18:00»; «2/2(2) c 9:00 до 18:00»; «2/2 c 9:00 до 18:00»; «Понедельник-Пятница 9:00-18:00»; «Круглосуточный 24/7». ⚠ **Изменять графики по умолчанию нельзя, но можно создавать свои персональные.** Ограничение длины: ⚠ **время одной смены не может быть более 24 часов** — при большей длительности создают подряд две смены. Для ночных смен вводят время окончания следующего дня (например, 2 часа ночи), система сама рассчитает переход через сутки; пример из вики — 3/2/3: 3 дневные смены 6:00–16:00, 2 ночные 16:00–2:00, 3 выходных. Обед: ⚠ **в HubEx нет возможности отобразить в графиках обеденное время**. Расхождение по интервалу 2/2 по умолчанию: [admin/WorkSchedule] — две смены с 10:00 до 22:00, [user/Schedule] — с 8:30 до 20:00. График назначается в карточке Сотрудника на вкладке «Трудоустройство» (иначе не работает автоназначение по графику и учёт времени по календарю); отдельные смены правятся через «Редактировать смену» (больничные, отпуска, перенос).
**Опора:** «Графики работы, смены, календарь заявок»

### A04
**Статус:** ЕСТЬ
**Ответ:** Правило описывается в Консоль → «Настройки заявки» → **«SLA: расчет крайнего срока закрытия»** → «Создать правило». Разрез: **Тип заявки, Критичность, Вид работ**, плюс индивидуально **Компания-заказчик(и)** и **Объект(ы)**. ⚠ Количество: **правило можно создать только на один Тип заявки, одну Критичность и один Вид работ** — либо по каждому пункту выбрать значение «Все». Заказчики: «Все» (на всех внесённых **и будущих**) или «По списку». Объекты (доступны после выбора Заказчика): «Все» (внесённые и будущие); «По списку»; **«Все за исключением»**. Ещё в правиле: **«График обслуживания»** (рабочее время выполнения; графики встроены в систему, уникальный добавляют через поддержку) и **«Плановое время закрытия заявки»** (максимальный срок; пример: обслуживание по будням 9:00–18:00, заявка в четверг в 17:00, плановое время 6 часов → крайний срок пятница 14:00). Правило нужно включить переключателем в списке. ⚠ **Разрешение конфликтов:** если подходят несколько правил, работает то, которое по Графику обслуживания попадает на текущее время; при совпадении графиков — **правило с наименьшим сроком закрытия**. Название сработавшего правила видно в поле «Правило расчета крайнего срока закрытия» внизу формы Заявки. Если правил нет или они выключены — срок берётся из Типа заявки и (или) Вида работ, система выбирает наименьшее значение; ⚠ вручную установленный Крайний срок правилом не изменяется.
**Опора:** «SLA и расчёт крайнего срока»; «Заявка: модель, поля, списки»

### A05
**Статус:** ЕСТЬ
**Ответ:** План загружается в поле **«План объекта»** в карточке Объекта. ⚠ **Один план на Объект.** Форматы — **.jpg, .jpeg, .png**. ⚠ **Загрузить план можно только в web-версии.** Метка в карточке Объекта — расположение по умолчанию; изменить местоположение можно в Заявке в web и в МП, но ⚠ **изменение местоположения в Заявке НЕ меняет расположение по умолчанию в карточке Объекта**. Оборудование внутри здания без своего плана: ⚠ **если у дочернего объекта нет своего плана — подтягивается план родителя**; если планы есть у обоих, при подаче Заявки можно выбрать любой. Ценность по вике: сокращает время на поиск неисправностей; заказчик через МП может сфотографировать оборудование и отметить его расположение на плане.
**Опора:** «Объекты и оборудование»

### A06
**Статус:** ЕСТЬ
**Ответ:** Вход по **одноразовому код-паролю**: код из **четырёх цифр**, повторный запрос возможен, если сообщение не пришло в течение **60 секунд**. ⚠ **Чтобы вход по код-паролю был доступен, при создании учётной записи обязательно нужно указать мобильный телефон.** ⚠ **Вход по код-паролю доступен только для мобильных номеров, зарегистрированных в РФ (формат +7хххххххххх)** — то есть подрядчикам с иностранными номерами этот способ не подойдёт. Дополнительное условие: ⚠ **без завершённой регистрации и созданного пароля пользователь не сможет авторизоваться ни по логину/паролю, ни по одноразовому код-паролю** — после создания пользователя система шлёт письмо на e-mail или sms со ссылкой на регистрацию, пользователь задаёт пароль (можно завершить регистрацию при первом входе в МП: создать пароль, затем подтвердить sms-кодом). Ссылка приглашения для Сотрудника действует **сутки**, потом — «Отправить приглашение повторно». В МП «HubEx заказчик» вход по одноразовому код-паролю доступен зарегистрированным по номеру телефона.
**Опора:** «Пользователи: Сотрудники и Заказчики»; «Каналы приёма заявок (омниканальность)»

### A07
**Статус:** ЕСТЬ
**Ответ:** Это сценарий **параллельного согласования** (два согласующих, порядок решений не задан). Настраиваются Тип заявки (например, «Закупка ТМЦ»), Стадии, Жизненный цикл и Уведомления. ⚠ **Ключевая контринтуитивная деталь: нужно создать шесть стадий, включая две пары одинаковых по смыслу стадий со звёздочкой** — «Согласована начальником подразделения» / «Согласована начальником подразделения\*» и «Согласована ответственным по закупкам» / «Согласована ответственным по закупкам\*»; обе стадии пары для одного согласующего, но лежат на разных ветках, у них разные уведомления и разные точки выхода (продолжение процедуры или её завершение). Шестая стадия — «Не согласована». Переходы: «Новая» → «Согласование заявки»; далее на две стадии согласования (ветка согласования) и «Не согласована» (основная ветка), доступ по соответствующим ролям, для «Не согласована» — **обе** роли; «Согласована начальником подразделения» → «Согласована ответственным по закупкам\*» и «Не согласована» (только «Ответственный по закупкам»); «Согласована ответственным по закупкам» → «Согласована начальником подразделения\*» и «Не согласована» (только «Начальник подразделения»); стадии со звёздочкой → «Выполнена» → «Закрыта». «Каждый узнаёт, что второй согласовал» — уведомления на пяти стадиях: «Согласование заявки» — обоим; каждая из первых стадий согласования — второму согласующему; стадии со звёздочкой — инициатору (оба согласовали); «Не согласована» — инициатору. Правила выбора получателя переиспользуются, триггеры создаются отдельные (текст разный). Доступ согласующих даётся флажком «Предоставить доступ отдельным ролям» на переходе, ⚠ выбранная Роль должна быть указана в карточке ответственного. Заявки на ветке согласования в МП отображаются на отдельной вкладке «Согласование». Если используются Участки, их необходимо указать при создании Типа заявки. Результат можно передавать в 1С через интеграцию.
**Опора:** «Согласование заявок»; «Конструктор процесса: Типы, Стадии, Статусы, Жизненный цикл»

### A08
**Статус:** ЕСТЬ
**Ответ:** Это **Плановые заявки** («Заявки» → **«Планировщик работ»** → «Создать заявку»). Разделы формы: «Название», «Тип заявки», «Вид работ», «Объект/оборудование», «Описание», «Исполнитель», «Плановое создание заявок», «Ограничить повторения». ⚠ **«Тип заявки» — только один, «Вид работ» — только один**; по Виду работ подбираются Объекты (Вид работ должен быть заполнен в карточке Объекта). ⚠ **Плановые заявки можно подавать на группу Объектов**: после выбора Вида работ активируются «К списку объектов» (ручной выбор флажками) и «Подобрать объекты» (дополнительные фильтры) — так закрывается «сотня единиц оборудования». Периодичность — «Плановое создание заявок»: «Ежедневно», «Еженедельно» и т.д. с детальной настройкой (например, каждые 3 недели по вторникам в 10:00); «Отложить начало выполнения работ» корректирует срок закрытия; «Ограничить повторения» — период создания либо количество. Исполнитель — один или несколько, либо переключатель «Автоматическое назначение исполнителя» (правило нужно привязать к стадии «Новая»). Запуск — **«Сохранить и запланировать»**. ⚠ **Чтобы изменить периодичность, Плановую заявку сначала нужно приостановить** (кнопка «Приостановить»), внести изменения и снова нажать «Сохранить и запланировать». Форма представления для ППР/ТО — «График обслуживания объектов» (тот же раздел, переключатель режима).
**Опора:** «Планировщик работ: плановые заявки и график обслуживания»

### A09
**Статус:** ЕСТЬ
**Ответ:** Разными механизмами. Разграничение по филиалам — **Участки** (Консоль → «Структура предприятия» → «Участки»): Участок классифицирует **Объекты, Типы заявок, Сотрудников и Заказчиков**, и через Роли именно им разграничивается доступ к Объектам, Типам заявок и Заявкам. Рецепт: (1) заполнить «Участок» в карточке Сотрудника, Объекта и Типа заявки; (2) в Роли блок «Объекты» → «Справочники» → «Объекты на участках пользователя»; (3) блок «Заявка» → «Справочники» → «Заявки на объектах, доступных пользователю» и ⚠ снять первые 8 пунктов (они дают больше прав на просмотр Заявок). Видимость людей ограничивается через «Пользователи и контакты — Справочники» («Все пользователи на участках» вместо «Все пользователи»). Поля Участка: «Название участка» (обязательное), «Описание», «Идентификатор из внешней системы», «Назначить участком по умолчанию»; у каждого Участка есть статистика связей с Объектами, Пользователями и Типами заявок. Группировка оборудования по производителям — **Классы оборудования** (Консоль → «Структура предприятия» → «Классы оборудования»; примеры вики: по производителю — Samsung, Apple; по стоимости). Отличия прямо из вики [admin/PlacesVSObjectsClass]: **Класс устанавливается только в карточке Объекта** и служит для группировки и фильтрации (в списке Объектов — фильтр «Класс», в Заявках — «Класс объекта»), доступ он не ограничивает; **Участок связывает Объект, Сотрудника, Заказчика и Тип заявки и автоматически ограничивает доступ**. ⚠ При удалении класса значение в карточках Объектов остаётся, фильтрация по нему не работает, правится вручную.
**Опора:** «Участки, Навыки, Виды работ»; «Объекты и оборудование»; «Роли и полномочия»

### A10
**Статус:** ЕСТЬ
**Ответ:** Настраивается **согласование с заказчиком** [admin/CustomerAgreement]. Стадии: **«Согласование с заказчиком»** — на неё Заявку переводят со стадии «Выполнена», если нужно проверить стоимость услуг и материалов (⚠ если проверка не нужна, стадию можно пропустить и настраивать переходы на «Согласована»/«Не согласована» сразу со стадии «Выполнена»); **«Согласована»** и **«Не согласована»** — на **ветке действий заказчика**, ⚠ обе доступны только заказчику. Переход «Выполнена → Согласование с заказчиком»: название перехода «Согласование заказчика» (кнопка в МП исполнителя), ветка «Основная», флажок «Изменить статус» → «На согласовании», доступ роли диспетчера или руководителя. Переходы на «Согласована»/«Не согласована»: доступ роли **«Заказчик»** плюс «+Добавить роль» для особенной настройки названий кнопок — ⚠ в МП заказчика в Заявке будет две кнопки. Оповещение: правило с «Роль, которая получит уведомление» = «Заказчик» и триггер со способом отправки Email на стадию «Согласование с заказчиком». Далее «Согласована» → «Закрыта», «Не согласована» — например, на менеджера по работе с заказчиками. «Не видеть внутреннюю кухню» обеспечивают **Статусы заявки** — визуальное отображение Стадии для мобильного приложения заказчика (в МП исполнителя видна стадия, в МП заказчика — статус; внутренние стадии согласования заказчику показывать не обязательно). Статусы для этого сценария: «На согласовании», «Согласована», «Не согласована». В МП заказчика приёмка — кнопки **«Принять работы» / «Не принимать работы»**, которые появляются **только когда исполнитель внёс выполненные работы**; «Не принимать» возвращает заявку на доработку. Дополнительно доступ заказчика урезается ролью: Заказчик видит только Объекты и Заявки компании из своей карточки и переводит Заявки только по стадиям ветки действий заказчика.
**Опора:** «Согласование заявок»; «Конструктор процесса: Типы, Стадии, Статусы, Жизненный цикл»; «Каналы приёма заявок (омниканальность)»

### A11
**Статус:** ЕСТЬ
**Ответ:** Ведётся через признак **«Мобильное оборудование»** — флажок в карточке Объекта (вкладка «Объект|Оборудование») [user/MobileObjects]. Это оборудование с динамичным адресом (прямо названы строительная и шахтовая техника, вендинговые автоматы, **оборудование в аренде**): новый адрес указывается в Заявке и **автоматически сохраняется в карточке Объекта** — именно это избавляет от правки адреса в двух местах. В web диспетчер видит количество кодов и список привязанных кодов — ⚠ только для чтения. ### B20
**Статус:** ЕСТЬ
**Ответ:** На чём: **Power BI или Apache SuperSet** — это отдельная степень свободы «Конструктор отчётов и панелей»; любой отчёт можно добавить в меню web или МП. Штатная аналитика HubEx тоже реализована на платформе Power BI. Что нужно с нашей стороны: ⚠ **для самостоятельного использования Power BI / Apache SuperSet нужен on-premise или выделенные серверы облака** — то есть в публичном облаке аналитик своими дашбордами заниматься не сможет (там же: ⚠ проектные доработки не делаются в публичном облаке). Плюс доступ ролью: полномочие **«Доступ к подключаемым плагинам и отчетам»** в блоке «Аналитика» открывает меню «Мои отчеты» и индивидуальные отчёты. Для индивидуальных отчётов и небольших автоматизаций на HubEx Automate поддержка включена в стоимость лицензии на отчёт (тогда как проектные доработки, плагины и доработки Automate силами вендора ⚠ требуют у клиента пакета расширенной технической поддержки). Насколько свежие цифры: ⚠ **данные обновляются один раз в сутки**, дата обновления отображается рядом с наименованием отчёта (то же ограничение действует и на отчёт «История перемещений»). Альтернативный путь получения данных — REST API (сервисы WORK, ES, EXPORT и др., Swagger на doc.hubex.ru) и экспорт в Excel; интерактивные BI-отчёты и панели заявлены и как возможность low-code компонента **HubEx Automate**.
**Опора:** «Степени свободы: чем и как дорабатывается система»; «Аналитика и отчёты»; «Каталог полномочий и зависимостей между ними»; «Варианты развертывания и что можно обещать по инфраструктуре»
