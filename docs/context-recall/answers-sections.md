# Ответы

### A01
**Статус:** ЕСТЬ
**Ответ:** Четыре варианта доступа к полю заявки: RO (только чтение), RW (чтение и запись, редактирование необязательное), RWM (чтение и обязательная запись), «Настройка не выбрана» — поля на форме вообще нет. Задаётся в разрезе «Роль × Стадия заявки» в `Консоль администрирования → Настройки заявки → Поля на форме заявки`; доп.поля идут внизу таблицы с отметкой «А». Не настраивать вручную каждое новое состояние помогает копирование: контекстное меню (три точки) у «Роли» или у «Стадии» → «Копировать в…». Оговорки: поле «Тип заявки» отключать нельзя, хотя бы для одной Роли и Стадии ему должна быть назначена RW; если для новой Стадии не задано ни одной настройки доступа — форма заявки открывается пустой (белый экран); есть полномочие-обход «Предоставляет доступ на чтение и запись для всех компонентов формы заявки вне зависимости от полномочий и настроек стадии» (оно же «Игнорировать эксклюзивные полномочия для доступа к полям заявки»); у учётной записи владельца тенанта («Системный администратор») видимость полей настроить невозможно — все поля доступны всегда. Полномочия роли и доступ к полям формы настраиваются раздельно (отсюда значок замка на поле «Исполнитель»).
**Опора:** Доступ к заявкам, альтернативные каналы и групповые действия; Атрибуты, согласование и приоритизация заявок; Роли, полномочия и участки

### A02
**Статус:** ЧАСТИЧНО
**Ответ:** Импорт заявок — до 2000 строк за одну загрузку (так сказано в разделах «Создание и действия с заявками», «Отчёты и экспорт», «Паттерны посадки процессов клиента» и «Ограничения-стоперы»). Номер заявки — максимум 32 символа, присваивается автоматически по «Маске номера заявки» из Типа заявки (пример маски: `[{День ДД}][{Месяц ММ}][0-9][0-9][0-9]` → 2309001), но может быть изменён вручную; в маску может входить «Код компании» из карточки компании. Сопутствующее: импорт только по скачанному из HubEx шаблону Excel, в системе должен быть хотя бы один Тип заявки, повторная загрузка дополненного шаблона не дублирует ранее загруженное, импорт идёт в фоновом режиме, при копировании данных в шаблон вставлять только значения. **Чего не хватает:** файл сам себе противоречит по числу — раздел «Первые шаги, база знаний и брендирование» утверждает «Импортом можно загрузить до 1000 заявок за раз», остальные четыре раздела дают 2000; какое значение верное, из файла не определить. Также не сказано, проверяется ли уникальность перенесённых номеров и можно ли задать свой номер прямо в шаблоне импорта.
**Опора:** Создание и действия с заявками; Отчёты и экспорт; Ограничения-стоперы; Первые шаги, база знаний и брендирование

### A03
**Статус:** ЕСТЬ
**Ответ:** Два типа графиков: Недельный (рабочее время на каждый из 7 дней) и Сменный (повторяющийся интервал строк «Смена»/«Выходной» с количеством дней — примеры 2/2, 1/3, 3/2/3; «сутки через трое» ложится на сменный тип). Путь: `консоль администратора → Структура предприятия → Графики работы → Создать график`; поля «Наименование», дни/время чч:мм, флаг «Назначить дату начала календаря» (необязателен — без него график действует со дня создания), кнопка «Показать график в календаре». Предустановленные «из коробки»: «Выходные 9-18», «2/2(4) c 9:00 до 18:00», «2/2(3) с 9:00 до 18:00», «2/2(2) c 9:00 до 18:00», «2/2 c 9:00 до 18:00», «Понедельник-Пятница 9:00-18:00», «Круглосуточный 24/7»; предустановленные изменять нельзя, свои создавать можно. Ограничение длины: одна смена не может быть больше 24 часов — при большей длительности создают подряд две смены (на 24 часа и на дополнительное время). Ночная смена задаётся временем окончания следующего дня (напр. 2:00), переход через полночь считается автоматически. **Обеденное время в графиках отобразить нельзя.** Уникальный график добавляет поддержка (чат поддержки или help@hubex.ru). График назначается сотруднику в карточке (вкладка «Трудоустройство»), смены правятся индивидуально (больничный, отпуск, перенос).
**Опора:** Приглашения, доступ и графики работы

### A04
**Статус:** ЕСТЬ
**Ответ:** Одно правило SLA (`Консоль администратора → Настройки заявки → SLA: расчет крайнего срока закрытия → Создать правило`) сопоставляет заявку по разрезам: Тип заявки, Критичность, Вид работ, Компания-заказчик, Объект. Кардинальность жёсткая: правило создаётся **на один** Тип заявки, **одну** Критичность и **один** Вид работ — либо значение «Все» по каждому пункту. Заказчики выбираются «Все»/«По списку», Объекты — «Все»/«По списку»/«Все за исключением», причём «Все» включает и будущие записи; Объекты доступны только после выбора Заказчика(ов). Правило задаёт «Плановое время закрытия заявки», отсчитываемое по «Графику обслуживания» (пример: обслуживание по будням 9:00–18:00, заявка подана чт 17:00, плановое время 6 ч → крайний срок пт 14:00). Правило нужно включить переключателем «Включено». **Конфликт нескольких подходящих правил:** работает то, которое по Графику обслуживания попадает на текущее время; при совпадении Графиков обслуживания — правило с наименьшим сроком закрытия. Применённое правило видно в заявке внизу в поле «Правило расчета крайнего срока закрытия». Оговорки: вручную установленный «Крайний срок закрытия» правилом не изменяется; если правил нет или они выключены — срок берётся из Типа заявки (а между Типом заявки и Видом работ система выбирает наименьшее).
**Опора:** SLA, автоназначение и чек-листы; Карта сущностей и связей

### A05
**Статус:** ЕСТЬ
**Ответ:** План объекта — **один на Объект** (`Карточка Объекта → Объект|Оборудование → План объекта`). Форматы: .jpg, .jpeg, .png. Загрузка **только в web-версии** (в мобильном приложении загрузить нельзя). Пин на плане в карточке Объекта — расположение по умолчанию, подставляется в Заявку; в самой Заявке есть поле «План объекта», берущееся из карточки объекта. Оборудование внутри здания без собственного плана: дочерний объект без своего плана подтягивает план родителя; если планы есть у обоих — выбирается любой. Грабли: пин, переставленный в Заявке, НЕ меняет расположение по умолчанию в карточке Объекта. В релизах от 2026-07-13 отмечено, что и в МП заказчика, и в МП исполнителя добавлена возможность указать месторасположение проблемы на плане помещения.
**Опора:** QR-коды, паспорт и планы объектов; Последние релизы

### A06
**Статус:** ЕСТЬ
**Ответ:** На экране входа есть кнопка «Вход по одноразовому коду» (sms-авторизация). Код-пароль — четыре цифры; повторный запрос доступен, если сообщение не пришло в течение 60 секунд. **Ограничение: вход по код-паролю доступен только для мобильных номеров, зарегистрированных в РФ, формат +7хххххххххх** — для подрядчиков-иностранцев с зарубежными номерами этот способ не работает. Второе условие: пользователь всё равно должен сначала пройти регистрацию и создать пароль (по ссылке из письма/sms) — до этого не работает ни вход по логину/паролю, ни по коду; незавершённую регистрацию можно закончить при первом входе в приложение (предложение создать пароль, затем подтверждение по sms-коду). При создании учётной записи обязательно указать мобильный телефон, иначе вход по коду невозможен. Также роли пользователя должна быть выдана «Мобильное приложение инженера» в разделе «Приложения».
**Опора:** Отличия ролей и вход в систему

### A07
**Статус:** ЕСТЬ
**Ответ:** Это паттерн «параллельное согласование с двумя согласующими»: собирается из Стадий заявки, Жизненного цикла (ветка «Ветка согласования», фиолетовая), Статусов заявки и уведомлений («Правила выбора получателя» + «Триггеры уведомлений»). Объём: **6 новых стадий** и уведомления на пяти стадиях (для сравнения: линейное согласование — 3 стадии, согласование с заказчиком — 3). Ключевая оговорка: требуются две разные стадии, одинаковые по смыслу («Согласована начальником подразделения» и «Согласована начальником подразделения\*») — потому что на разных ветках им нужны разные уведомления и разные точки выхода; именно это и обеспечивает независимость порядка решений. Чтобы каждый узнал о решении второго — триггер уведомления привязывается к стадии («Уведомление отправляется при переходе заявки на выбранную стадию»), получатель задаётся «Правилом выбора получателя» (категория получателей, конкретный пользователь, Роль, e-mail/телефоны через запятую), способ — Push или Email. Разделение интерфейса согласующих — флажок «Предоставить доступ отдельным ролям» на переходе и «+Добавить роль» со своим «Названием перехода» (в приложении получаются кнопки «Согласована»/«Не согласована»). Заявки ветки согласования в мобильном приложении собираются на отдельной вкладке «Согласование». Под процесс заводится свой Тип заявки (для одного Типа — только один Жизненный цикл). Оговорка: автоматический переход настраивается только на стадию согласования, переводы на стадии результата согласования пользователь делает вручную. Результат согласования можно передать в 1С через интеграцию.
**Опора:** Атрибуты, согласование и приоритизация заявок; Паттерны посадки процессов клиента; Уведомления

### A08
**Статус:** ЧАСТИЧНО
**Ответ:** Механизм — «Плановая заявка» (шаблон автосоздания заявок по расписанию), путь `Заявки → Планировщик работ → Создать заявку`; форма представления — «График обслуживания объектов» (переключатель там же). Поля плановой заявки: «Название», «Тип заявки» (только один), «Вид работ» (только один; по нему подбираются объекты), «Объект/оборудование» («К списку объектов», «Подобрать объекты» — так набирается сотня единиц), «Описание», «Исполнитель», «Плановое создание заявок» (периодичность), «Отложить начало выполнения работ» (сдвигает срок закрытия), «Ограничить повторения» (периодом или количеством), переключатель «Автоматическое назначение исполнителя»; запуск — кнопка «Сохранить и запланировать». Изменение периодичности: плановую заявку сначала нужно **«Приостановить»**, внести правки и снова нажать «Сохранить и запланировать». **Чего не хватает:** перечень вариантов периодичности в файле оборван — «Ежедневно, Еженедельно и т.д.»; можно ли задать интервал «каждые три недели» (произвольный шаг), из файла не определить. Также не указан предел количества объектов в одной плановой заявке.
**Опора:** Создание и действия с заявками; Паттерны посадки процессов клиента

### A09
**Статус:** ЕСТЬ
**Ответ:** Разными механизмами. **Участок** — ось, которая одновременно классифицирует и ограничивает доступ: связывается с Объектом (вкладка «Объект|Оборудование»), Сотрудником и Заказчиком (вкладка «Квалификация»), Типом заявки; создаётся в `Структура предприятия → Участки` (поля «Название участка», «Описание», «Идентификатор из внешней системы», «Назначить участком по умолчанию»). Разграничение филиалов делается им: заполнить Участок в карточках Сотрудника, Объекта и Типа заявки, в блоке «Объекты → Справочники» включить «Объекты на участках пользователя», в блоке «Заявка → Справочники» выбрать «Заявки на объектах, доступных пользователю» и **снять первые 8 пунктов** (они дают более широкий просмотр заявок); видимость людей — блок «Пользователи и контакты → Справочники» → «Все пользователи на участках». **Класс оборудования** (`Структура предприятия → Классы оборудования`, флажок «Назначить классом по умолчанию») — **только группировка Объектов и Заявок по объектам**, никакого доступа не ограничивает; даёт разрезы аналитики (Отчёт по объектам, Отчёт для клиента) и фильтры («Класс» в объектах, «Класс объекта» в заявках). Группировка по производителям — это Класс (либо Тип оборудования, который дополнительно несёт список Видов работ и признак обязательности адреса). Грабли: удаление класса не очищает поле «Класс» в карточках объектов — значение остаётся, но фильтрация по нему не работает; новый Участок автоматически добавляется во все ранее созданные Типы заявок, но в Объектах, Сотрудниках и Заказчиках проставляется вручную.
**Опора:** Роли, полномочия и участки; Типы и классы объектов; Карта сущностей и связей

### A10
**Статус:** ЕСТЬ
**Ответ:** Настраивается ветка действий заказчика в Жизненном цикле (голубой маркер) плюс проекция «Стадия → Статус». Схема «Согласование с заказчиком»: 3 новые стадии, причём стадия «Согласование с заказчиком» необязательна — без неё переходы на «Согласована»/«Не согласована» настраиваются сразу со стадии «Выполнена», и статус «На согласовании» создавать не нужно. Стадии «Согласована» и «Не согласована» в этой схеме доступны только заказчику; на переходе ставится флажок «Предоставить доступ отдельным ролям» и через «+Добавить роль» задаются свои «Названия перехода» — в мобильном приложении заказчика получаются две кнопки «Согласована» и «Не согласована». «Не видеть внутреннюю кухню» обеспечивает пара Стадия/Статус: сотрудники в web и «HubEx исполнитель» видят Стадию, заказчик в «HubEx заказчик» — Статус (свой цвет), несколько внутренних этапов схлопываются в один статус (пример: стадия «Согласование с руководителем» → статус «В работе»). Дополнительно периметр: роль «Заказчик» имеет доступ только к приложению заказчика, видит заявки и объекты только своей компании-заказчика, не видит сотрудников, аналитику, склады и карты; в клиентском портале ему доступны «Заявки — Все заявки», «Сообщения», «Аналитика — Отчет для клиента», в МП — «Заявки» и «Сообщения». Приёмка: принять работы и подписать акт можно только в МП «HubEx заказчик» и только после того, как исполнитель внёс выполненные работы; печать акта — из клиентского портала. Оценка выполнения доступна заказчику на стадиях «Выполнена» и «Закрыта».
**Опора:** Атрибуты, согласование и приоритизация заявок; Жизненный цикл заявки; Отличия ролей и вход в систему; Интеграции, API и клиентские приложения

### A11
**Статус:** ЕСТЬ
**Ответ:** Это «Мобильное оборудование» — оборудование с динамичным адресом: флажок «Мобильное оборудование» ставится в карточке Объекта (есть он и в «Шаблоне объектов»). При установленном флажке новый адрес указывается в Заявке и автоматически сохраняется в карточке Объекта — то есть править в двух местах не нужно; без флажка адрес заявки и карточки живут отдельно. Ограничение: мобильным может быть только объект с Типом оборудования, у которого стоит флажок «Обязательное наличие адреса (при создании объекта оборудования)» — то есть родительский объект; дочерние наследуют адрес от родителя, поэтому их адрес как мобильных не меняется. Грабли: смена адреса во второй заявке не меняет адрес в первой — там правят вручную. История перемещений единицы техники получается экспортом Заявок с отбором по этому оборудованию. Адрес объекта автоматически подставляется в Заявку.
**Опора:** Создание и редактирование объектов; Создание и действия с заявками; Типы и классы объектов

### A12
**Статус:** ЧАСТИЧНО
**Ответ:** Если речь о «Типе заявки» (единственная сущность, задающая маршрут — стадии, срок закрытия, доступные виды работ): **после создания заявки её тип изменить невозможно**. Переезд на вариант 2 даёт всё перечисленное, а серверные лицензии и обновления там на 30% дешевле, чем в on-premises.

### B17
**Статус:** ЧАСТИЧНО
**Ответ:** Списки разные и лежат на разных вкладках заявки. **«Необходимые материалы»** — отдельная вкладка заявки, это рекомендация материалов исполнителю до выезда: со склада **не списываются и в расход не идут**, на остатки не влияют (её видимость настраивается полем «Необходимые материалы на форме заявки» в `Поля на форме заявки`). **«Израсходованные материалы»** — блок внутри выполненной работы на вкладке «Выполнение»: только через него происходит списание, расход виден в отчёте `Склады → Расход` (дата загрузки, склад, количество, Сотрудник, Объект, переход в заявку по номеру), а стоимость материалов попадает в Акт выполненных работ.
