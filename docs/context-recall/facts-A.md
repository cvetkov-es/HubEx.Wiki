### A01
**Тип:** параметр
**Разделы карты:** s04
**Источники:** pages/admin/ElementsOfInterface.md
**Вопрос:** Клиент хочет, чтобы одно и то же поле в заявке одни сотрудники вообще не видели, другие видели только для чтения, а третьи были обязаны его заполнить. Какие варианты доступа к полю есть в системе, в каком разрезе они задаются и можно ли не настраивать всё вручную для каждого нового состояния заявки?
**Эталон:** Доступ настраивается в консоли администрирования в меню **Настройки заявки — Поля на форме заявки** в разрезе **Ролей** и **Стадий заявки** (таблица основных и дополнительных полей, для каждой ячейки свой уровень доступа; дополнительные поля находятся в самом низу таблицы с отметкой **А** — Additional Field). Уровней доступа четыре:
1. **RO (только для чтения)** — поле доступно только для просмотра, редактировать нельзя (пример из статьи: в закрытой заявке никто не может изменить исполнителя — для поля «Актуальный исполнитель по заявке» для всех ролей ставится RO);
2. **RW (чтение и запись)** — поле доступно для просмотра и необязательного редактирования (пример: «Вид работ» для сервисного специалиста на стадии «Новая» — RW, а на стадии «В работе» — RO);
3. **RWM (чтение и обязательная запись)** — поле доступно для просмотра и обязательно должно быть заполнено (пример: дополнительное поле «Наработка оборудования» для роли сервисного специалиста на стадии «Назначена» или «В работе»);
4. **Настройка не выбрана** — поля не будет видно на форме совсем.
Вручную для каждой новой стадии/роли настраивать не нужно: настройки можно копировать — через контекстное меню (три точки) рядом с названием **Роли** или **Стадии** пункт **«Копировать в…»** с выбором ролей/стадий-приёмников. Важная оговорка: нельзя отключать видимость поля **Тип заявки** — хотя бы для одной Роли и Стадии для него должна быть назначена настройка **RW**, так как без него создание Заявки невозможно; остальные поля не обязательны и могут быть исключены из формы.

### A02
**Тип:** параметр
**Разделы карты:** s03
**Источники:** pages/user/CreatingTicket.md
**Вопрос:** Клиент переносит из старой системы большой архив обращений и хочет сохранить свою нумерацию. Сколько записей примет одна загрузка и какие ограничения на номер?
**Эталон:** Загрузка идёт импортом по специальному шаблону в формате **Excel**, за один раз можно загрузить **до 2000 заявок** (ограничение упомянуто дважды — в разделе про список заявок и в разделе про альтернативные способы подачи). **Номер заявки** присваивается автоматически (по маске номера, настраиваемой в Типе заявки в консоли администрирования), но **может быть изменён вручную**; **максимальная длина номера — 32 символа**. Экспорт заявок выполняется по кнопке «Экспорт».

### A03
**Тип:** параметр
**Разделы карты:** s11
**Источники:** pages/user/Schedule.md
**Вопрос:** У клиента сменное производство: сутки через трое, ночные смены, обед по регламенту. Что в системе есть по графикам работы «из коробки», какие ограничения на длину смены и как отразить обеденное время?
**Эталон:** По умолчанию в бизнес-аккаунте HubEx созданы **семь** графиков работы: «Выходные 9-18»; «2/2(4) с 9:00 до 18:00»; «2/2(3) с 9:00 до 18:00»; «2/2(2) с 9:00 до 18:00»; «2/2 с 9:00 до 18:00»; «Понедельник-Пятница 9:00-18:00»; «Круглосуточный 24/7». Графики по умолчанию изменять нельзя, но можно создавать свои — в консоли администратора, раздел **Структура предприятия — Графики работы**, кнопка **Создать график**. Типов графика два: **Недельный** (рабочее время на каждый из семи дней недели — пяти-/шестидневка) и **Сменный** (повторяющийся интервал смен и выходных — 2/2, 1/3, 3/2/3 и т.д.). Ограничение: **время одной смены не может быть более 24 часов** — если сотрудники работают дольше, создают подряд две рабочие смены (на 24 часа и на дополнительное время). Ночные смены задаются вводом времени окончания следующего дня (например, с 16:00 до 2:00) — система сама рассчитает продолжительность с переходом на следующий день. Дату начала действия графика можно задать флажком **«Назначить дату начала календаря»** (необязательно; без неё график действует со дня создания). **Обеденное время в графиках работы HubEx отобразить нельзя.**

### A04
**Тип:** параметр
**Разделы карты:** s12
**Источники:** pages/admin/SLA.md
**Вопрос:** У клиента в договорах разные сроки реакции: по разным заказчикам, по разным типам обращений и по срочности. Как в системе описывается одно такое правило (что можно указать в нём и в каком количестве), и что произойдёт, если под конкретную заявку подойдут сразу несколько правил?
**Эталон:** Правила расчёта крайнего срока живут в консоли администратора в меню **Настройки заявки — SLA: расчёт крайнего срока закрытия**, создаются по кнопке **Создать правило**; название правила отображается в Заявке в поле **«Правило расчёта крайнего срока закрытия»**. Правило настраивается в разрезе **Типа заявки**, **Критичности**, **Вида работ**, а также **Компании-заказчика(ов)** и **Объекта(ов)**. Ограничение по количеству: правило можно создать **только на один Тип заявки, одну Критичность и один Вид работ** — либо по каждому из этих пунктов выбрать значение **«Все»** (правило работает для всех типов/видов работ/критичностей). Заказчики выбираются вариантами **«Все»** (включая создаваемых в будущем) или **«По списку»**; после выбора заказчика становятся доступны его **Объекты** с тремя вариантами — **«Все»**, **«По списку»**, **«Все за исключением»**. В правиле задаются **График обслуживания** (определяет рабочее время выполнения Заявок; графики встроены в систему, недостающий добавляет поддержка по обращению в чат или на help@hubex.ru) и **Плановое время закрытия заявки** (максимальный срок выполнения работ; пример: обслуживание по будням 9:00–18:00, заявка подана в четверг в 17:00, плановое время 6 часов → крайний срок закрытия пятница 14:00). Правило нужно **включить** переключателем, иначе оно не работает. Разрешение конфликта: если в одном разрезе создано несколько правил, **работать будет то, которое по Графику обслуживания попадает на текущее время; если графики обслуживания совпадают — выбирается правило с наименьшим сроком закрытия**. Дополнительно: если Крайний срок закрытия в Заявке установлен вручную, правило его не изменит; если ни одного правила не настроено/не включено — срок берётся из параметров Типа заявки или Вида работ.

### A05
**Тип:** параметр
**Разделы карты:** s07
**Источники:** pages/user/FloorPlan.md
**Вопрос:** Клиент обслуживает бизнес-центр и хочет, чтобы заявитель показывал на схеме этажа, где именно поломка. Сколько таких схем можно завести на объект, в каком виде их грузить, откуда, и что будет с оборудованием внутри здания, у которого своей схемы нет?
**Эталон:** План помещения добавляется индивидуально в карточке **Объекта** на вкладке **Объект|Оборудование** в поле **План объекта**. Для каждого **Объекта** может быть добавлен **только один план**, форматы — **.jpg, .jpeg, .png**. **Загрузить план к Объекту можно только в web-версии** (в мобильном приложении план доступен только для просмотра и простановки метки). В карточке Объекта можно отметить расположение **по умолчанию** (щелчок по плану ставит пин); это расположение подставляется на плане при подаче Заявки и может быть изменено прямо в Заявке, **при этом расположение по умолчанию в карточке Объекта НЕ изменится**. Наследование: если план загружен для **родительского** объекта, а у дочернего своего плана нет, при выборе дочернего объекта в Заявке **подтягивается план родителя**; если план есть и у родителя, и у дочернего — при подаче Заявки можно выбрать любой из них. Если план не загружен вовсе, при подаче Заявки отображается подсказка о том, что план можно добавить к Объекту. В мобильном приложении метка двигается по кнопке **Изменить** с подтверждением зелёной галочкой (крестик — не применять).

### A06
**Тип:** параметр
**Разделы карты:** s10
**Источники:** pages/user/EnterToMob.md
**Вопрос:** У клиента выездные монтажники, которые не хотят помнить пароли, и часть подрядчиков — иностранцы. Клиент спрашивает про вход в мобильное приложение по SMS: как это работает и для кого доступно?
**Эталон:** Альтернативный способ авторизации — **вход по одноразовому код-паролю (SMS-авторизация)**: в мобильном приложении нажимается кнопка **«Вход по одноразовому коду»**, вводится номер телефона, указанный в учётной записи пользователя, и кнопка **Продолжить**. На номер приходит **пароль из четырёх цифр**; если сообщение не пришло **в течение 60 секунд**, код-пароль можно запросить повторно. Код вводится вручную или автозаполнением. Ограничения: **вход по код-паролю доступен только для мобильных номеров, зарегистрированных в Российской Федерации (формат +7хххххххххх)**; чтобы пользователь мог пользоваться этим входом, при создании его учётной записи обязательно нужно указать мобильный телефон. Кроме того, пользователь **сначала должен пройти регистрацию и создать пароль** — иначе он не сможет авторизоваться ни по логину/паролю, ни по одноразовому коду (незавершённую регистрацию можно завершить при первом входе в приложение: создать пароль и подтвердить регистрацию через SMS-код). Логином является e-mail или мобильный телефон, указанные в карточке. Отдельно: для Роли пользователя в разделе **Приложения** должен быть открыт доступ к нужному приложению — **Мобильное приложение инженера** (HubEx исполнитель) или **Мобильное приложение заказчика**; там же настраиваются Веб-приложение, Веб-приложение администрирования, Доступ только к API и Электронный паспорт оборудования.

### A07
**Тип:** моделирование
**Разделы карты:** s02
**Источники:** pages/admin/TicketsAgreement.md
**Вопрос:** У клиента закупка ТМЦ согласуется двумя людьми независимо — начальником подразделения и ответственным по закупкам, порядок их решений заранее не известен, и каждый должен узнать, что второй уже согласовал. Какими сущностями и настройками HubEx это выражается?
**Эталон:** Цепочка настроек: **Тип заявки** (например, «Закупка ТМЦ»; если используются Участки, их надо указать в карточке Типа заявки) → **Стадии заявки** → **Жизненный цикл** → **Уведомления**. Для параллельного согласования с двумя согласующими создаётся **шесть новых стадий** (кроме уже существующих Новая, Выполнена, Закрыта), в том числе **две пары стадий-дублей**: «Согласована начальником подразделения» и «Согласована начальником подразделения\*», «Согласована ответственным по закупкам» и «Согласована ответственным по закупкам\*». Стадии со звёздочкой одинаковы по смыслу, но **в HubEx необходимо создать именно две разных стадии**, потому что на разных ветках процесса для них настраиваются разные уведомления и разные точки выхода. Шестая стадия — «Не согласована» (переход на неё возможен с любой из предыдущих пяти). Жизненный цикл: маршрут Новая → … → Закрыта; со стадии **Новая** переход на **Согласование заявки** (Название перехода — кнопка в приложении; **Ветка жизненного цикла — Ветка согласования**, такие заявки показываются в мобильном приложении на отдельной вкладке; можно включить **Выполнить автоматический переход**, например через 5 минут). Со стадии «Согласование заявки» — переходы на «Согласована начальником подразделения», «Согласована ответственным по закупкам» и «Не согласована»; со стадии «Согласована начальником подразделения» — на «Согласована ответственным по закупкам\*»; со стадии «Согласована ответственным по закупкам» — на «Согласована начальником подразделения\*». Разграничение прав: флажок **«Предоставить доступ отдельным ролям»** на каждом переходе (стадии начальника — роль «Начальник подразделения», стадии закупок — «Ответственный по закупкам», на «Не согласована» — обе роли); роль должна быть указана в карточке пользователя-согласующего. Уведомления: в **Настройки оповещений — Правила выбора получателя** создаются два правила (по Роли), а инициатору — правило с параметром **«Обратившийся пользователь»**; в **Триггеры уведомлений** настраиваются условия по **Стадиям заявки** и шаблон сообщения (способ отправки Email или Push). Всего уведомления настраиваются на пяти стадиях: «Согласование заявки» (обоим согласующим), «Согласована начальником подразделения» (второму согласующему), «Согласована ответственным по закупкам» (второму согласующему), стадии со звёздочкой (инициатору — согласовали оба), «Не согласована» (инициатору). ФИО инициатора видно в Заявке в блоке **Детальная информация**, поле **Инициатор заявки**.

### A08
**Тип:** моделирование
**Разделы карты:** s03
**Источники:** pages/user/PlannedTickets.md
**Вопрос:** У клиента регламентное обслуживание: одинаковые работы на сотне единиц оборудования каждые три недели, и заявки не должны заводиться руками. Как это описывается в системе и что делать, если нужно потом изменить периодичность?
**Эталон:** Используются **Плановые заявки**: меню **Заявки — Планировщик работ**, кнопка **Создать заявку**. Форма состоит из разделов: **Название** (свободная форма), **Тип заявки** (может быть выбран **только один**), **Вид работ** (**только один**; именно по Виду работ подбираются Объекты — Виды работ заполняются в карточке Объекта), **Объект/оборудование**, **Описание**, **Исполнитель**, **Плановое создание заявок** и **Ограничить повторения** (раздел появляется после выбора частоты). Заявки можно ставить не на один объект, а на группу: после выбора Вида работ становятся активны кнопки **«К списку объектов»** (выбор флажками вручную) и **«Подобрать объекты»** (дополнительные фильтры). Частота задаётся в разделе **Плановое создание заявок** — варианты **Ежедневно, Еженедельно** и т.д., с детальной настройкой времени (например, каждые 3 недели по вторникам в 10:00). Параметр **«Отложить начало выполнения работ»** сдвигает расчёт срока закрытия (пример: заявка создана в 12:00, плановый срок 4 часа → срок 16:00; при параметре 2 часа → 18:00). Раздел **«Ограничить повторения»** позволяет задать **Период создания заявки** (например, в течение года) либо ограничить по количеству (например, всего 10 заявок). Исполнителя выбирают вручную (**+Добавить исполнителя**, можно нескольких) либо включают переключатель **«Автоматическое назначение исполнителя»** — тогда исполнитель подбирается правилом автоназначения, которое нужно привязать к стадии **Новая** (оговорка из статьи: изменения стадии действуют для всех Типов заявок, в чей жизненный цикл входит эта стадия, поэтому под плановые заявки лучше сделать отдельный Тип заявки, отдельную стадию «Новая (для плановой заявки)» и свой жизненный цикл). Запуск — кнопка **«Сохранить и запланировать»**. **Чтобы изменить уже работающую Плановую заявку, её сначала надо приостановить** (кнопка **Приостановить**), внести изменения и заново нажать **«Сохранить и запланировать»**. Плановые заявки видны в календаре на месяц и на отдельной вкладке **Планировщик**; если исполнитель в настройках не указан, назначить его можно по кнопке **+** на вкладке «Планировщик».

### A09
**Тип:** моделирование
**Разделы карты:** s05
**Источники:** pages/admin/PlacesVSObjectsClass.md
**Вопрос:** У клиента филиалы в разных городах: диспетчер в одном городе не должен видеть работу другого города — ни обращения, ни оборудование, ни людей. Отдельно клиент хочет группировать оборудование по производителям для отчётности. Одним или разными механизмами это делается и чем они отличаются?
**Эталон:** Это **два разных механизма**, их нельзя путать.
1. **Участок** — используется для группировки и классификации **Объектов, Сотрудников, Заказчиков и Типов заявки** по различным критериям: географическим, функциональным и т.д. Участок может связывать в одну группу Объект, Сотрудника, Заказчика и Тип заявки; **указывая Участки, вы автоматически ограничиваете доступ к данным системы в разрезе Участков** (совместно с настройкой Ролей). Пример из статьи ровно про этот сценарий: фирма ремонтирует холодильную технику по всей России, филиалы в разных городах, диспетчеры разных городов не должны видеть Заявки, Объекты, Сотрудников и Заказчиков друг друга — участком является город или регион, и он указывается в карточках Объектов, Сотрудников и Заказчиков этого города. Аналогично Участки применяются к **Типам заявки** — так настраивается использование специфических Типов заявок для определённых пользователей (Сотрудников и Заказчиков).
2. **Класс оборудования** — используется только для **группировки Объектов и Заявок по выбранным Объектам** (например, классы по производителю: Samsung, Apple). **Класс оборудования устанавливается только в карточке Объекта** на вкладке «Объекты|Оборудование» и **никакого доступа не разграничивает**.
То есть разграничение по филиалам — это Участки (плюс настройка Ролей), а группировка по производителю для отчётности/фильтров — Классы оборудования.

### A10
**Тип:** моделирование
**Разделы карты:** s02
**Источники:** pages/admin/CustomerAgreement.md
**Вопрос:** Клиент хочет, чтобы после выполнения работ его заказчик сам подтверждал приёмку или возвращал работу, и чтобы заказчик при этом не видел внутренней кухни исполнителя. Что для этого настраивается?
**Эталон:** Настраивается связка стадий, жизненного цикла и оповещений (меню Настройки заявки и Настройки оповещений):
1. **Стадии заявки** (Настройки заявки — Стадии заявки), с разными цветами: **«Согласование с заказчиком»** — на неё исполнитель или диспетчер переводит Заявку со стадии **Выполнена** (эта стадия нужна, если после выполнения надо проверить стоимость услуг и материалов; если такая проверка не нужна, стадию можно пропустить и настраивать переходы на «Согласована»/«Не согласована» сразу со стадии «Выполнена»); **«Согласована»** и **«Не согласована»** — первая и вторая стадии **на ветке действий заказчика**, доступные **только заказчику**.
2. **Статусы заявки** (Настройки заявки — Статусы заявки) — визуальное отображение стадии для мобильного приложения заказчика: «На согласовании» (для стадии «Согласование с заказчиком»; если стадию пропускаем, статус тоже не нужен), «Согласована», «Не согласована».
3. **Жизненный цикл** (Настройки заявки — Жизненный цикл заявки): со стадии **Выполнена** добавляется переход на «Согласование с заказчиком» — **Название перехода** «Согласование заказчика» (это название кнопки в приложении HubEx исполнитель), **Ветка жизненного цикла — Основная ветка**, флажок **«Изменить статус»** со статусом «На согласовании», флажок **«Предоставить доступ отдельным ролям»** с ролью диспетчера/руководителя подразделения. Далее со стадии «Согласование заказчика» — переходы на «Согласована» и «Не согласована» с соответствующими статусами и названиями переходов, флажок **«Предоставить доступ отдельным ролям»** с ролью **Заказчик** (обе стадии доступны только заказчику), плюс кнопка **«+Добавить роль»** для особенной настройки — роль «Заказчик» и названия переходов «Согласована»/«Не согласована», чтобы в мобильном приложении заказчика было две кнопки. Дальше настраиваются переходы со «Согласована» на «Закрыта», а с «Не согласована», например, на менеджера по работе с заказчиками.
4. **Оповещение заказчика**: в **Настройка оповещений — Правила выбора получателя** создаётся правило (например, «Заказчик») с указанием Роли «Заказчик»; в **Настройки оповещений — Триггеры уведомлений** создаётся триггер (название вида «Согласование с заказчиком (email)»), выбирается шаблон описания сообщения, заголовок подставляется как «Заявка №@Model.TaskNumber», текст правится под себя, **Способ отправки сообщения — Email** (возможен Push), в блоке **Условия отправки** в поле **Стадии заявки** выбирается стадия «Согласование с заказчиком» и ставятся флажки отправки по времени, добавляется созданное правило выбора получателя.
Результат: после перехода на «Выполнена» у исполнителя появляется кнопка «Согласование заказчика», заказчик получает письмо/push, а в приложении HubEx заказчик в Заявке видит две кнопки — «Согласована» и «Не согласована»; внутренние стадии заказчику не показываются, поскольку он видит только Статус.

### A11
**Тип:** моделирование
**Разделы карты:** s06
**Источники:** pages/user/MobileObjects.md
**Вопрос:** Клиент сдаёт технику в аренду: одна и та же единица за месяц стоит на пяти площадках, и адрес в обращении каждый раз новый. Как это ведётся в системе и что нужно, чтобы адрес не приходилось править в двух местах?
**Эталон:** Это функционал **«Мобильное оборудование»** — оборудование с динамичным адресом: новый адрес указывается в **Заявке** и автоматически сохраняется в карточке **Объекта**. Типичные примеры из статьи: строительная и шахтовая техника, вендинговые автоматы, оборудование, сдаваемое в аренду. Условия и настройка:
* мобильным может быть **только объект/оборудование с Типом оборудования, у которого в настройках установлен флажок «Обязательное наличие адреса (при создании объекта оборудования)»** — то есть **только родительские объекты**. Дочерние объекты наследуют адрес от родителя, поэтому, даже если пометить их мобильными, их адрес меняться не будет;
* флажок **«Мобильное оборудование»** устанавливается в карточке **Объекта**;
* в Заявке для поля **Адрес** нажимается **Редактировать — Изменить местоположение**, указывается новый адрес, Заявка сохраняется (**Сохранить** или **Сохранить и закрыть**) — после этого адрес в карточке Объекта меняется на указанный, и так при каждой новой Заявке.
Историю перемещений такого оборудования смотрят через **экспорт Заявок** с отбором по этому оборудованию. Важная оговорка: если по мобильному оборудованию созданы две Заявки и адрес изменён только во второй, **в первой Заявке адрес не изменится** — его при необходимости правят вручную.

### A12
**Тип:** стопер
**Разделы карты:** s03
**Источники:** pages/user/CreatingTicket.md
**Вопрос:** Диспетчер клиента при заведении обращения ошибся и выбрал не ту категорию обращения, из-за которой заявка идёт не по тому маршруту. Заявка уже сохранена и по ней есть переписка. Что можно сделать?
**Эталон:** **После создания заявки её Тип изменить будет невозможно.** Чтобы заменить тип в уже созданной заявке, её необходимо **скопировать**, в копии до сохранения изменить **Тип заявки** (и при необходимости другие поля), а некорректную заявку **удалить**. При копировании поля новой заявки заполняются так же, как в исходной; пустым остаётся **Номер заявки** (заполнится после сохранения или задаётся вручную), также при сохранении заполнится правило расчёта крайнего срока закрытия. Дополнительные ограничения, важные для этого сценария: копирование доступно **только в карточном представлении списка заявок** (контекстное меню «три точки» → **Копировать**); удаление возможно **на любой стадии**, но требует полномочий Роли — во вкладке **Полномочия**, блок **Заявки**, пункты **«Удаление заявок»** и **«Удалять незакрытые заявки»** (право рекомендуется давать только начальникам служб/администраторам); удалённая заявка не исчезает из системы, а скрывается из списка, и **восстановить её нельзя**, а **просматривать удалённые заявки может только учётная запись владельца тенанта**.

### A13
**Тип:** стопер
**Разделы карты:** s02
**Источники:** pages/admin/TicketsAgreement.md
**Вопрос:** Клиент говорит: «У нас закупки идут двумя маршрутами — до 100 тысяч согласует только начальник, свыше — ещё и финдиректор. Оба маршрута — это закупка, заводить два разных вида обращений мы не хотим». Что здесь нужно сказать прямо?
**Эталон:** Прямо сказать: **для одного Типа заявки может быть настроен только один Жизненный цикл** (цитата статьи: «Для одного **Типа заявки** может быть настроен только один **Жизненный цикл**»). Значит два разных маршрута согласования обязаны быть **разными Типами заявок** — под каждый процесс создаётся свой Тип заявки; один Тип заявки достаточен только если все внутренние Заявки проходят одинаковые этапы. Смежное ограничение из того же материала: **Тип заявки после создания заявки не изменить**, а при создании Типа заявки Участки нужно указать сразу (иначе пользователи с Участками этот тип не увидят). При копировании настроек можно опереться на поле **Шаблонный тип заявки** — но оно доступно **только при создании нового Типа заявки**, потом указать его невозможно.

### A14
**Тип:** стопер
**Разделы карты:** s06
**Источники:** pages/user/DeletedObjects.md
**Вопрос:** Служба безопасности клиента спрашивает: сможем ли мы полностью стереть из системы ошибочно заведённую компанию, её оборудование, сотрудника и обращения — и вернуть их, если удалили зря?
**Эталон:** **Полного (прямого) удаления в HubEx нет**: не предусмотрено прямое удаление элементов справочников **Объекты, Сотрудники, Заказчики, Компании**, а также прямое удаление **Заявок** — они скрываются из списков и находятся через фильтры видимости. Причина — неразрывные ссылочные связи между справочниками и Заявкой (в Заявке выбираются Объект, исполнитель из Сотрудников, Компания-заказчик, автоматически заполняется Инициатор заявки, есть ссылки на дочерние/родительские заявки, а в карточке Объекта хранится «История обслуживания»); прямое удаление привело бы к потере данных без возможности восстановления. Ключевые необратимости и ограничения:
* **удалённую компанию нельзя восстановить** — можно только создать новую по образцу; **при удалении компании все привязанные к ней объекты снимаются с публикации**, а на неопубликованные объекты нельзя подавать заявки;
* **удалённый объект нельзя восстановить**; **нельзя удалять объекты, которые участвуют в активных заявках**; есть варианты «Удалить» и «Удалить с вложенными объектами»;
* **удалённую заявку нельзя восстановить**; **просматривать удалённые заявки может только «Системный администратор (владелец тенанта)»** через фильтр «Видимость заявок»;
* **удалённых сотрудников и заказчиков нельзя восстановить** (в отличие от **заблокированных** — «Бан пользователя» обратим, разблокировать можно); сотрудника можно удалить только если на него не назначены активные заявки;
* **удалённый чек-лист нельзя восстановить и нельзя просмотреть** в разделе «Чек-листы», но он **остаётся в ранее созданных заявках**, если был к ним прикреплён.
Отображение удалённых элементов можно скрыть настройкой Ролей — в блоках «Компании», «Объекты», «Пользователи и контакты» отключить полномочия «Удалённые компании», «Удалённые объекты», «Удалённые пользователи», «Удалённые роли».

### A15
**Тип:** стопер

**Вопрос:** Клиент хочет, чтобы инженер вносил в контрольный список показание счётчика. Завели поле, а потом выяснилось, что значения бывают дробные, а поле сделали текстовым. Что дальше?

### A16
**Тип:** стопер
**Разделы карты:** s04
**Источники:** pages/admin/TicketMail.md
**Вопрос:** У клиента вся переписка с заказчиками идёт с корпоративного ящика на Outlook, часть площадок сидит на mail.ru. Клиент хочет, чтобы письма превращались в обращения. Что нужно сказать до продажи?
**Эталон:** Прямые ограничения (раздел про интеграцию через imap): **интеграцию нельзя настроить для почтовых адресов outlook.com**, так как Microsoft не предоставляет доступ к своему почтовому серверу для сторонних приложений, и **нельзя настроить для адресов mail.ru** — также из-за доступа сторонних приложений к почтовому серверу mail.ru. **Рекомендуется настраивать интеграцию на ящиках yandex.ru**, другие сервисы могут работать нестабильно; обходной путь — завести ящик на yandex.ru и настроить на него пересылку со своего почтового сервиса. Всего вариантов подключения два: **через пересылку** (переадресация писем на специальный ящик, созданный для бизнес-аккаунта; заявки создаются по единому шаблону) и **через imap** (подключение своего ящика напрямую как адреса сбора заявок, индивидуальные шаблоны под разных заказчиков, двусторонняя интеграция с ответами из чата). Для Yandex по imap: **Хост = imap.yandex.ru, Порт = 993, Протокол безопасности = SSL/TLS**, логин — ящик, пароль — **пароль приложений**, сгенерированный в настройках аккаунта Яндекс (Безопасность — Пароли приложений — Почта); если сгенерированный пароль не скопировали, надо создавать новый. Ещё две ловушки: **у шаблона заявки обязательно должны быть выбраны Объект и Вид работ, иначе его нельзя будет выбрать в настройках интеграции**; и **если прочитать полученное письмо на самом адресе сбора заявок, оно не будет создано в HubEx как Заявка**. В поле **Отправитель** указывается конкретный адрес, либо «\*@yandex.ru», либо «\*@\*» для писем с любых адресов любых доменов (для общего шаблона без привязки к заказчику нужно «\*@\*»). Для интеграции также требуется активировать сервисную учётную запись **Пользователь API** (Интеграция — Служебные пользователи) с ролью с максимальными полномочиями и всеми участками; токен доступа для почты не нужен. Разбор письма на поля (Объект, Вид работ, Срок закрытия и т.д.) делается **Настройкой регулярных выражений** — это дополнительная опция, за ней надо обращаться в поддержку help@hubex.ru.

### A17
**Тип:** стык
**Разделы карты:** s01 + s07
**Источники:** pages/admin/StageType.md, pages/user/CreatingTaskTemplates.md
**Вопрос:** Клиент не верит, что бригады реально доезжают до площадок, и хочет, чтобы отчитаться о работе можно было только находясь на месте. Как это реализуется и что именно перестанет быть доступно сотруднику, пока он не подтвердит присутствие?
**Эталон:** Реализуется связкой «QR-код на объекте + Требование на Стадии заявки».
Со стороны стадий (Настройки заявки — **Стадии заявки**): при переходе на стадию можно выбрать **Требование**, без выполнения которого переход невозможен; нужное требование — **«Отсканирован QR-код объекта»** (подходит, например, для стадии **«В работе»**). Тогда исполнитель обязан отсканировать QR-код, которым промаркирован **Объект**, указанный в Заявке — так реализуется подтверждение пребывания сотрудника на объекте. Пока код не отсканирован, **сотрудник не сможет перевести Заявку на следующие стадии, заполнить выполненные работы и закрыть её**. В мобильном приложении **HubEx исполнитель** при нажатии кнопки перехода на стадию «В работе» появляется окно с запросом сканирования; **QR-код проверяется на соответствие QR-коду из карточки Объекта, выбранного в Заявке**: при несовпадении сотрудник получает уведомление, что QR-код неверный, при совпадении — переход выполняется. Другие возможные требования на стадии: «Назначен исполнитель», «Обработаны чек-листы», «Подписан акт выполненных работ»; выбор Требования не обязателен.
Со стороны QR-кодов: сам код должен быть создан и привязан к Объекту — в web-приложении либо в карточке **Объекта** на вкладке **QR-коды** по кнопке **Маркировать**, либо в меню **Заявки — Маркировка** по кнопке **Создать QR-код** (при этом создаётся **шаблон заявки** с полями Тип заявки, Объект, Заказчик, Вид работ, Критичность, Описание, Исполнитель). После сохранения QR-код генерируется, скачивается по кнопке **Скачать QR-код**, печатается и наклеивается на объект; при массовой маркировке используется **экспорт QR-кодов архивом (.zip)**. Если QR-код не привязан к Объекту, при сканировании паспорт объекта будет пустым. Заявленные преимущества функционала: гарантия качественного выполнения задачи, предотвращение мошенничества и непрофессионального поведения, повышение ответственности исполнителей.

### A18
**Тип:** стык
**Разделы карты:** s12 + s08
**Источники:** pages/admin/RulesOfChoice.md, pages/user/CreatingUser.md
**Вопрос:** Клиент хочет отказаться от ручной раздачи работ: система сама должна выбирать подходящего специалиста — с нужной специализацией, на смене и ближе всех к точке. Что для этого настраивается и почему конкретный сотрудник может в такой раздаче не участвовать?
**Эталон:** Со стороны правила (консоль администратора, **Настройки заявки — Автоназначение исполнителя**, кнопка **Создать правило**) — «робот-диспетчер» подбирает исполнителя по параметрам: **Обязательные навыки** (совпадение обязательных навыков в карточке Объекта из заявки с карточками сотрудников), **Вид работ** (совпадение Вида работ из заявки с карточками сотрудников — самый популярный параметр), **График работы** (система анализирует графики в карточках сотрудников и подбирает того, у кого на момент подачи заявки стоит рабочая смена), **Ответственный за объект**, **Часто назначается на объект**, **Участок** (сравнение участков в карточке объекта и карточках сотрудников). Можно включить **«Детальную настройку»** и задать степень важности параметров в процентах: **без детальной настройки выбранные параметры применяются с союзом «И», с включённой детальной настройкой — с союзом «ИЛИ»** в зависимости от выставленного процента. Правило привязывается к **Стадии заявки** (например, «Назначена»): в настройках стадии выбирается действие **«Автоназначение по правилу»** или **«Автоназначение с учётом удалённости от заявки»** (подбор ближайшего по карте), затем выбирается правило; появляется дополнительный параметр **«Роль»**. Переход на такую стадию может быть ручным или автоматическим — для автоматического в жизненном цикле на переходе ставится флажок **«Выполнить автоматический переход»** и задаётся время.
Со стороны карточки сотрудника (меню **Пользователи — Сотрудники**) — почему конкретный человек не участвует: **чтобы исполнитель мог участвовать в автораспределении, в карточке Сотрудника должен быть установлен флажок «Мобильный сотрудник»** (он же разрешает указывать сотрудника как исполнителя уже выполненных работ); для подбора по удалённости нужен флажок **«Отслеживать местоположение сотрудника»** (позволяет видеть пользователя на карте), а в мобильном приложении пользователь должен подтвердить использование геолокации. Кроме того, параметры, по которым идёт подбор, должны быть заполнены именно в карточке: на вкладке **Квалификация** — **Виды работ**, **Навыки**, **Участок** (плюс Ставка для клиента и Доступные склады), на вкладке **Трудоустройство** — **Компания**, **Должность** и **График работы**. Оговорка по справочникам: при создании нового Вида работ он **не привязывается автоматически** к уже существующим карточкам сотрудников — его нужно добавить вручную (создать новый Вид работ через карточку сотрудника нельзя).

### A19
**Тип:** стык
**Разделы карты:** s09 + s04
**Источники:** pages/admin/Places.md, pages/user/HiddenObjectsTicketsUsers.md
**Вопрос:** Клиент разграничил работу по филиалам. После добавления нового филиала инженеры этого филиала в мобильном приложении не могут завести обращение — система не даёт выбрать категорию обращения, а часть оборудования вообще не видна. Что произошло и что доделать?
**Эталон:** Причина — в асимметрии распространения нового **Участка** и в связке «Участок + Роль».
Со стороны настройки участков (консоль администратора, **Структура предприятия — Участки**): **при создании нового участка он автоматически добавится во все ранее созданные Типы заявок**, но **в уже созданные Объекты/оборудование, Сотрудников и Заказчиков новый участок нужно указать вручную — автоматически он не добавится** (это отдельно оговорено для каждого из трёх справочников). Флажок **«Назначить участком по умолчанию»** присваивает участок только **новым создаваемым** Объектам, Сотрудникам и Заказчикам. Участок можно указывать **в нескольких экземплярах** для Объекта, Сотрудника, Заказчика и Типа заявки. Место указания: у Объекта — вкладка «Объект|Оборудование» внизу страницы, у Сотрудника и Заказчика — вкладка **«Квалификация»**, у Типа заявки — карточка в «Настройки заявки — Типы заявок». У каждого Участка есть статистика связей с Объектами, Пользователями и Типами заявок.
Со стороны диагностики (статья «Почему пользователь не видит Заявки/Объекты/Исполнителей»): **если у Сотрудника (или Заказчика) стоит Участок, а в Типе заявки не выбрано ни одного Участка, пользователь не сможет выбрать Тип заявки при создании Заявки** — в мобильном приложении он получит ошибку об отсутствии доступных Типов заявок и Заявку создать не сможет; лечится указанием в Типе заявки того же Участка, что и у Сотрудника (участков можно указать несколько — если один и тот же Тип заявки с определённым жизненным циклом используется на всех Участках, укажите все). Невидимость оборудования лечится настройкой Роли: блок **Объекты — Справочники**, пункт **«Объекты на участках пользователя»** (варианты рядом: «Все активные объекты», «Удалённые объекты», «Объекты у компаний пользователя»), при этом одинаковый Участок должен стоять и в карточке Объекта, и в карточке Сотрудника. Смежный симптом того же корня: **диспетчер не видит нужного исполнителя при назначении** — Сотрудник, создающий Заявку, должен принадлежать тому же Участку, что и исполнители, которых он может назначить; после добавления недостающего участка в карточку диспетчера список исполнителей расширяется. Видимость Заявок отдельно управляется полномочиями блока **Заявки — Справочники** («Активные заявки на сотрудниках моих участков», «Активные заявки на объектах моей компании», «Все активные заявки», «Активные заявки по моим видам работ», «Заявки на объектах, доступных пользователю» и т.д.).

### A20
**Тип:** стык
**Разделы карты:** s02 + s01
**Источники:** pages/user/ChoiceWorkType.md, pages/admin/TicketType.md
**Вопрос:** У клиента диспетчер жалуется: при заведении обращения в выпадающем списке услуг нет той услуги, которая точно заведена в системе, а у другого диспетчера этого поля на форме вообще нет. Из-за чего так и как это чинится?
**Эталон:** Работают три независимых ограничения, и все три надо проверить.
1. **Карточка Объекта.** Чтобы в Заявке выбрать Вид работ по Объекту, он должен быть сначала указан в карточке этого **Объекта** на вкладке **Обслуживание**: «Только указанные в карточке Объекта Виды работ вы сможете выбрать затем в Заявке по этому Объекту». Создать новый Вид работ можно прямо из выпадающего списка Заявки (кнопка **Создать** открывает справочник в консоли администратора), но после создания его всё равно нужно указать в карточке Объекта, выбранного в Заявке.
2. **Карточка Типа заявки.** В Типе заявки (консоль администратора, **Настройки заявки — Типы заявок**) Виды работ выбираются параметром **«Все»** (все созданные в системе) или **«По списку»** (вручную из списка). Оговорка: **если Виды работ внесены в Тип заявки вручную («По списку»), то при создании или редактировании Заявки доступны будут только те Виды работ, которые одновременно закреплены за Объектом/оборудованием И добавлены к данному Типу заявки** — то есть работает пересечение двух списков.
3. **Доступ к полю на форме.** Поле **Вид работ** может вообще отсутствовать на форме Заявки: доступ к полям настраивается в консоли администратора в меню **Настройки заявки — Поля на форме заявки** в разрезе **Ролей** и **Стадий заявки**. Если для поля на нужной стадии никакой настройки не установлено — поле не отображается; чтобы пользователь увидел и мог выбрать Вид работ, для его Роли и стадии нужно установить **RW (чтение и запись)**.
Дополнительно (тот же Тип заявки): по нему же задаются **Время закрытия заявки** — при создании Заявки система выбирает **наименьшее** значение срока закрытия из установленных в Типе заявки и в Виде работ — и **Участки**, ограничивающие доступ к Типам заявок и Объектам.
