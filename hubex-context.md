## Что такое HubEx: класс системы, границы, с чем сравнивают

**HubEx FSM** — ERP-система класса FSM (Field Service Management) для сервисных подразделений с мобильным персоналом: ремонт, ТО, обходы, клининг [admin/AboutHubEx]. В реестре российского ПО с 15.07.2020, рег. № 6816. Может работать отдельно или как компонент группы интегрированных систем. Ключевое заявленное отличие от соседних классов — мобильное приложение исполнителя с конфигуратором: процесс «в полях» настраивается без разработки и выпуска новых версий.

Состав платформы [admin/AboutHubEx]:
- Мобильное приложение исполнителя «HubEx исполнитель» (в магазинах — HubEx Engineer) и приложение заказчика «HubEx заказчик» (HubEx Customer), iOS и Android [user/HowToSendInvitation]. Мобильное приложение можно использовать и отдельно от системы — подключать через API к HelpDesk/ServiceDesk/ТОиР клиента.
- Web-приложение для офиса (руководители, диспетчеры, логисты, менеджеры).
- Консоль администратора (конфигуратор): ролевая модель, справочники, поля, жизненный цикл, видимость. Заявлено: «не требует знаний программирования», рассчитана на IT-специалиста без опыта разработки.
- Открытый API (Swagger), БД, сервер приложений, сервер логирования.
- Электронный паспорт объекта (QR/NFC): параметры, история обслуживания, документация, гарантия, контакты; можно добавлять доп. поля. Шильды с метками на оборудовании: пользователь подаёт заявку сканированием «без писем, звонков и мессенджеров», исполнитель при сканировании получает паспорт с документацией и историей обслуживания.
- Для 1С-совместимых систем «может поставляться» 1С-конфигурация для обменов.

Работа делится на две части: пользовательские приложения (справочники, заявки, аналитика) и консоль администрирования (доступы, процесс заявки, интерфейс) [user/HubExStepByStep]. Порядок старта: Компании → Объекты/оборудование → Заказчики → Исполнители → Заявки [user/HubExStepByStep].

**Чем HubEx не является** (прямо сказано в [admin/AboutHubEx]):
- Не ITIL-система: нет классической ITIL CMDB, нет управления релизами, Change management; Problem management «настраивается вручную с рядом ограничений»; нет ITIL-управления конфигурациями. Функционально ближе к ESM, но для не-IT сервисных подразделений. Аналог объекта в ITSM — конфигурационная единица [user/HubExStepByStep].
- Не CRM: нет воронки продаж с лидами и сделками. Упрощённую воронку «можно организовать» отдельным типом заявки со своими стадиями. Разделение: CRM — от лида до заключения сделки; HubEx — от заявки до выполнения, контроля качества и отчётности. Обе системы хранят клиентов и контакты. Готовые связки с Битрикс24 — см. раздел интеграций.
- Не полноценный ТОиР: «упрощённый функционал ТОиР». Есть планировщик с плановым обслуживанием в разрезе оборудования, «в том числе собирать параметры наработок и на основании данной информации автоматизировано корректировать графики». Предиктивное ТО и стратегию по фактическому состоянию «оптимальнее» реализовывать совместно с ТОиР-системой. В компаниях с ТОиР HubEx часто получает из ТОиР готовые заявки и возвращает результаты (в ТОиР, учётную или HR-систему). Где ТОиР нет — HubEx закрывает полный цикл: учёт оборудования, графики, ППР, аварийные работы.
- Не SCADA/IoT: HubEx — оперативный слой, принимающий события 2-го уровня от SCADA/IoT как заявки.

Базовый функционал «класса Help Desk», заявленный в [admin/AboutHubEx]: заявки, база активов и объектов, база знаний, шаблоны ответов, расчёт SLA, омниканальный приём, автоматизация обработки, конструктор БП заявки, уведомления и триггеры, чек-листы, API.

**Помощники и обучение**: Telegram-бот @HubexWikiBot по возможностям системы [admin/AboutHubEx]; встроенный чат-бот **HubEx AI** — иконка в правом верхнем углу web-интерфейса, ищет статьи Wiki, отвечает диалогом, хранит историю (можно очистить); «может допускать неточности», для критичных вопросов — поддержка [user/HubExAI]. Курсы HubEx Академии «рекомендуются» [admin/AboutHubEx]. Страница-подборка видео [user/HubExVids] — содержательных фактов нет, только ссылки на видео (обзор, первые шаги, импорт Excel). Глоссарий терминов [user/Glossary].

Поддержка: web — красный знак вопроса у аватара → руководство или чат поддержки; мобильное — боковое меню → «Поддержка» → «Сообщить о проблеме» [user/HowToContactSupport], [admin/HowToEnterTheAdmin]. Почта help@hubex.ru, Telegram @hubex_bot [admin/SSOintegration].

## Развёртывание, инфраструктура, стек, нагрузка

Три варианта [admin/Deployment]:

| Вариант | Для кого | Ключевое |
|---|---|---|
| **Public Cloud** | до 500 пользователей (рекомендация; больше — можно, но лучше варианты 2–3); пилоты корпораций | минимальная стоимость; кластер >20 серверов; основной ЦОД СПб (Tier 3), реплика Москва; >100 организаций (на август 2024) |
| **Cloud на выделенных серверах** | >500 пользователей, бизнес-критично | нет влияния других клиентов; повышенная нагрузка интеграций; индивидуальные окна обслуживания и бэкапы; серверные лицензии и обновления на 30% дешевле on-prem, дороже public |
| **On-premises** | политика «всё в периметре», >1000 сотрудников, своя эксплуатация | полная независимость, закрытый контур; на 30% дороже серверной части, чем вариант 2; клиент сам администрирует сервера, БД, бэкапы |

Конфигурации для выделенных серверов и on-prem: **Бронза** — без кластера, 1 физический сервер, отказ любого сервера останавливает систему, до 1000 пользователей; **Серебро** — кластер, 2 физических сервера (3 сервера приложений, 2 БД, 2 WEB, 4 функциональных), 1000–3000; **Золото** — 4 физических (5 приложений, 4 БД, 2 WEB, 4 функциональных), более 3000 [admin/Deployment].

Ограничения public cloud [admin/Deployment]:
- интеграции свыше **10 запросов в секунду** — риск принудительного ограничения/отключения;
- окно обслуживания не переносится: обычно **22:00–24:00 по вторникам и четвергам**, система может быть частично/полностью недоступна;
- скорость может снижаться от нагрузки/DDoS на других клиентов;
- восстановление из бэкапа — только для всех клиентов облака одновременно; точечное восстановление одного клиента «крайне трудозатратно», «в ряде случаев невозможно».

Локальное размещение — «обязательное требование многих российских корпоративных клиентов»; on-prem даёт минимальную задержку обмена с внутренними системами и работу в закрытом периметре, но добавляет затраты на Change/Release management и согласования СБ на стороне заказчика; облако на выделенных серверах решает проблемы быстрее on-prem — не нужно согласовывать доступ в закрытый периметр [admin/Deployment]. Мобильные приложения при выделенном/on-prem ставятся через APK, MDM заказчика или публикуются в магазин; «в последствии появится возможность» использовать общие приложения облака [admin/Deployment]. Страница «Варианты развертывания On-Premise» — заглушка без содержания [admin/OnPremise].

Технологии [admin/AboutHubEx]: ЦОД HubEx Cloud — IaaS провайдера Tier 3 в СПб, резерв Москва в холодном резерве; кластер высокой доступности. Linux Ubuntu + Nginx (веб), Windows + Service Fabric, Node.js, .NET; сервисы в Docker; БД MS SQL Server и PostgreSQL. Backend: C#/.NET, ASP.NET Core, SignalR, RabbitMQ + Rebus, Azure Service Fabric, авторизация Keycloak, ADO.NET. Мобильные: React Native, SQLite, Firebase (уведомления, deeplinks). Web: ReactJS, Redux, Webpack, Firebase.

API: «обычно» не более **60 запросов в минуту** [admin/RESTAPI] (это лимит API-клиента; 10 запросов/сек — порог нагрузки интеграций в public cloud, разные предметы).

## Расширяемость: конфигуратор, Automate, плагины, отчёты, доработки

Уровни гибкости по возрастанию трудоёмкости [admin/AboutHubEx]:
1. **Конфигуратор** (консоль): роли, справочники, поля, ЖЦ заявки, видимость. Через настройки в мобильное приложение «можно добавлять поля данных, регулировать доступ, создавать кнопки-действия и даже добавлять свои собственные интерфейсы».
2. **HubEx Automate** — low-code с визуальным конструктором: интеграции с системами по REST API или SOAP; автоматизация сценариев внутри HubEx; свои интерфейсы/приложения (встраиваются в HubEx и сторонние системы); печатные формы по шаблонам организации; BI-отчёты и дашборды. Ограничение (на лето 2024): **не изменяет существующие интерфейсы**, только создаёт новые. Небольшая фича — 20–40 часов. Самый простой и бюджетный способ новых интерфейсов.
3. **Плагины** — встраиваются через iFrame в WEB и мобильное приложение, отдельными окнами и в меню; любой язык программирования; обмен с системой через REST API/SOAP и Automate. Ограничение: **плагин не видит данные, ещё не сохранённые пользователем на сервер**. Трудоёмкость — от 20 часов. Сам конструктор Automate встраивается через плагин.
4. **Конструктор отчётов**: Power BI или Apache Superset; отчёт можно добавить в меню WEB или в мобильные приложения. Самостоятельное использование — **только при локальном развёртывании или выделенных серверах** HubEx.
5. **Проектные доработки** — отдельная ветка кода под клиента; сотни часов; **не делаются в публичном облаке**; нужна отдельная команда (.NET+SQL, React, React Native, QA, аналитик, РП). Минус — замедление и удорожание обновлений; без обновлений возможность обновиться может быть утрачена.
6. **Продуктовые доработки** — только фичи для большинства клиентов, приоритизирует продуктовая команда; от 500 часов; «обычно в 5–10 раз» дороже проектных. В 2024 приоритет — платформенным фичам.

Условие: проектные доработки, плагины и доработки Automate силами вендора — **только при пакете расширенной техподдержки**; для индивидуальных отчётов и небольших автоматизаций Automate поддержка входит в стоимость лицензии на отчёт [admin/AboutHubEx].

**Магазин плагинов** [admin/PluginMarketplace]: каталог в консоли администратора; доступен **на тарифах выше «Минимальный»**. Категории (например «Клиенты и коммуникации», «Заявки и процессы», «Интеграции»), «Подключённые», «Скоро». Подключение мгновенно, без поддержки. После подключения плагин **по умолчанию не виден** — включается для ролей: `Путь: Консоль администратора → Администрирование → Роли → блок «Плагины»`. Для «Скоро» — ссылка «Хочу этот плагин» (голосование). Связка с ролями: вкладка «Плагины» роли работает только при включённом полномочии «Доступ к подключаемым плагинам и отчетам» (блок «Аналитика») — общий выключатель; плагин в списке полномочий имеет вид «[Название] - [Место размещения]» (пример «Акт выполненных работ - Подпункт в форме заявки»); новый плагин появляется во всех ролях выключенным, отключённый — исчезает [admin/Roles], [admin/Powers].

Примеры плагинов, описанных в вики: «База знаний» [user/KnowledgeBase], «Канбан заявок» [user/KanbanPlugin]. Печатные формы с иной логикой, чем покрывает конструктор, — «кастомная форма в рамках индивидуальных доработок» через менеджера [user/PrintingFormDesigner].

**База знаний (плагин)** [user/KnowledgeBase]: подключается через Магазин плагинов; доступ — если плагин включён для роли (пункт «База знаний» в меню); регистрация не нужна. Дерево разделов с вложенностью, drag-and-drop, поиск по заголовкам и содержимому «по мере ввода». Блочный редактор без предпросмотра; заголовки, списки, таблицы, изображения, ссылки; файлы перетаскиванием, несколько за раз. Доступ к статье — по ролям HubEx (одна/несколько/все); «отдельных ролей внутри самого плагина больше нет». Право редактирования — «режим редактирования» для сотрудников с правом. Полномочие «Доступ к подключаемым плагинам и отчетам» также даёт доступ к меню «База знаний» и «Мои отчеты» [admin/Powers].

**Канбан заявок (плагин)** [user/KanbanPlugin]: колонка = стадия ЖЦ, карточка = заявка, перенос перетаскиванием. Подключается в Маркетплейсе HubEx. Не умеет: создавать заявки, редактировать (открывает карточку HubEx в новой вкладке), показывать несколько типов заявок одновременно, массовый перенос. Один тип заявки за раз (при открытии — тип по умолчанию организации). Колонки — только стадии, связанные с маршрутом типа; удалённые и не подключённые к маршруту стадии не показываются, их заявки на доске не видны (общий счётчик может быть больше суммы колонок). Подгрузка по 30 карточек («Показать ещё»). Сортировка общая для доски (по умолчанию «Дата последнего изменения», свежие сверху). Состав полей карточки — из личной настройки карточного списка заявок. Недоступные для роли/ЖЦ колонки приглушаются при перетаскивании. Отказ переноса — 3 причины: перехода между парой стадий нет; не выполнены требования стадии; не заполнены обязательные (RWM) поля. По умолчанию скрыты закрытые заявки. Возврат на прошлую стадию — только если переход настроен.

## Модель данных: сущности и как они связаны

Сшивка по всем страницам. Центральная сущность — **Заявка**; почти все справочники существуют, чтобы классифицировать заявку, ограничивать доступ к ней и автоматизировать её маршрут.

| Сущность | Где живёт | Ключевые связи |
|---|---|---|
| **Компания** | меню «Компании» | вид: Заказчик / Подрядчик / Наша компания; к ней привязаны Объекты (Компания-владелец), Сотрудники (Компания), Заказчики (Компания), Договоры, Контактные лица [user/CreatingCompany] |
| **Объект/оборудование** | «Объекты\|Оборудование» | иерархия родитель→дочерний без ограничения вложенности [user/Glossary]; Тип, Класс, Участки, Виды работ, Навыки, Ответственный, Чек-листы, Контакты, QR-коды, Договоры [user/CreatingObjects] |
| **Сотрудник** | «Пользователи → Сотрудники» | лицензируемый пользователь; Роль, Компания, Должность, Участки, Виды работ, Навыки, Доступные склады, График работы, Ставка [user/CreatingUser] |
| **Заказчик** | «Пользователи → Заказчики» | пользователь клиента; Компания, Роль «Заказчик», Участки [user/CreatingCustomer]; нельзя назначить исполнителем [user/EngineerVSCustomer] |
| **Тип заявки** | консоль: Настройки заявки | определяет ЖЦ (ровно один на тип), срок закрытия, допустимые Виды работ, Участки, маску номера [admin/TicketType], [admin/TicketsAgreement] |
| **Стадия / Статус** | консоль: Настройки заявки | стадия — внутреннее состояние ЖЦ с действием и требованием; статус — то, что видит заказчик в своём приложении [admin/StageVSStatus] |
| **Вид работ** | консоль: Настройки заявки | классифицирует Объекты, Сотрудников, Заявки; срок закрытия, плановые трудозатраты, стоимость, чек-лист [admin/WorkType] |
| **Участок** | консоль: Структура предприятия | общий классификатор Объектов, Типов заявок, Сотрудников, Заказчиков; основа разграничения доступа [admin/Places] |
| **Роль** | консоль: Администрирование | права на меню, справочники (видимость данных), API-методы, приложения, плагины [admin/Roles] |
| **Договор** | карточка Компании / «Компании → Договоры» | Компания, Объекты по договору, срок; в заявке выбирается только договор выбранного Объекта [user/CreatingCompany] |
| **Склад / Материал** | «Склады» | склады доступны сотрудникам по списку; материалы списываются в выполненных работах [user/Materials] |

Как заявка «собирает» данные: выбран Объект → подставляется адрес (от родителя), доступны только виды работ из карточки Объекта ∩ видов работ Типа заявки (если в типе задан список) [admin/TicketType], [admin/WorkType]; подтягиваются чек-листы, привязанные к Объекту и/или Виду работ [user/Checklists]; контакты Компании и Объекта [user/Contacts]; план помещения [user/FloorPlan]; договор — только из договоров Объекта [user/CreatingCompany]. Срок закрытия: SLA-правило, иначе минимум из сроков Типа заявки и Вида работ [admin/SLA], [admin/TicketType]. Исполнитель: вручную, через календарь/карту, автоназначение на стадии [user/CreatingTicket].

Вкладки заявки после сохранения: «Заявка», «Необходимые материалы», «Сообщения», «Чек-листы», «Дочерние заявки», «Выполнение», «Акт выполненных работ», «История изменений» [user/CreatingTicket].

Разграничение доступа — несколько слоёв, влияющих одновременно [user/HiddenObjectsTicketsUsers]: (1) **Роль** — что видно в справочниках и меню [admin/Roles], [admin/Powers]; (2) **Участки/Компания** в карточках — сужают видимость при соответствующих полномочиях [admin/Places]; (3) **Поля на форме заявки** — RO/RW/RWM по ролям × стадиям [admin/ElementsOfInterface]. Плюс отдельно: права доступа к файлам по ролям [user/ViewRestriction], доступ к переходам ЖЦ по ролям [admin/TicketLifeCycle], ветки ЖЦ для заказчика [user/EngineerVSCustomer].

Тенант — рабочая область HubEx [user/SuperAndUsualUser]. «Бизнес-аккаунт» — синоним в текстах [user/CreatingCompany].

## Компании, договоры, контактные лица

**Компания** — юр. или физ. лицо: заказчик и/или подрядчик; также «Наша компания» (от чьего лица ведётся учёт) [user/CreatingCompany]. На старте в справочнике уже есть одна компания — ваша [user/HubExStepByStep]. Компании участвуют в распределении полномочий: заказчик видит только оборудование своей компании (при соответствующей настройке роли).

`Путь: Компании → «Создать компанию»`. Поля: «Вид компании» (Компания-подрядчик / Компании-заказчики / Наша компания), «Название компании», «Тип контрагента» (ИП / Физическое лицо / Юридическое лицо), «Телефон», «Веб-сайт», «Электронная почта», «Код компании» (идентификатор для заявок, используется в маске номера типа заявки), «Фактический адрес», «Файлы», «ERP ID» (для интеграций) [user/CreatingCompany]. Юр. реквизиты заполняются по ИНН кнопкой «+Заполнить по ИНН». Банковские реквизиты Нашей компании попадают в «Акт выполненных работ» и «Счет на оплату»; нет нужного банка — добавляет поддержка. При импорте вид клиента задаётся флагами «Заказчик» / «Подрядчик» / «Наша компания» (Да/Нет) [user/Import].

⚠ Чтобы реквизиты отобразились в Акте, их нужно заполнить полностью **и у Нашей компании, и у Компании-заказчика**; если у компании-заказчика объекта не заполнены все реквизиты — в Акте реквизиты не отображаются [user/Prices].

Карточка в списке: название, вид, число объектов, число пользователей; внутри — сотрудники, заказчики, заявки по объектам компании, список объектов [user/CreatingCompany].

**Договоры** [user/CreatingCompany]: отдельная страница «Компании → Договоры» (все договоры всех компаний, фильтры) или вкладка «Договоры» в карточке Компании; вкладка «Договоры» есть и в карточке Объекта (создание с предзаполненными Компанией и Объектом) [user/CreatingObjects]. Поля: «Наименование и номер договора» (обязательно), «Описание», «Условия договора», «Компания» (обязательно), «Срок действия», «Объекты по договору», «Файлы», флажок «Напомнить о завершении договора» (email). Для договоров есть дополнительные поля [user/AdditionalFields]. В заявке договор выбирается **только после выбора Объекта** и только из договоров этого Объекта; при просрочке договора в заявке — подсказка. Удалить договор можно, только если по нему нет активных заявок. Вкладка «Договоры» в карточке Компании управляется полномочием «Договоры» (блок «Компании») [admin/Powers]. Отчёт «График действия договоров» выявляет заявки вне периода действия договора [user/ContractSchedule].

**Контактные лица** [user/Contacts]: создаются в карточке Компании и на вкладке «Контакты» карточки Объекта; все контакты — в одном общем списке (можно выбрать ранее созданный). Обязательные поля — «ФИО» и «Телефон». Создавать и выбирать контакты **только в web-версии**. В заявке поле «Контакты по заказчику и объектам» показывает контакты и Заказчика, и Объекта одновременно. Полномочия: «Все контакты», «Контакты моей компании» (справочники); «Добавление контактов», «Удаление контактов» (элементы интерфейса) — блок «Пользователи и контакты». Видимость в заявке — поля «Адрес эл. почты контактного лица», «Контакты по объекту», «Телефон контактного лица», «ФИО контактного лица» в «Поля на форме заявки». Типовой кейс: скрыть контакты заказчика от сервисных специалистов, оставить диспетчерам. В мобильном паспорте объекта «Контактные лица» не редактируются [user/ObjectEditing]. При импорте заявок контакт «будет создан автоматически» [user/Import].

## Объекты и оборудование: иерархия, типы, классы, паспорт

**Объект (оборудование)** — элемент инфраструктуры, на который направлены услуги (офис, АЗС, магазин; кондиционер, кофемашина, двигатель) [user/CreatingObjects]. Привязан к Компании-владельцу. Если детальный учёт не нужен — «можно завести один обслуживаемый объект для каждого заказчика», и он автоматически подставится в заявку при выборе заказчика [user/HubExStepByStep].

Иерархия: родитель → дочерние, вложенность не ограничена [user/Glossary]. **Родительский объект обязан иметь адрес**, дочерний наследует адрес родителя (может иметь свой) [user/CreatingObjects]. Обязательность адреса задаёт **Тип оборудования** (флажок «Обязательное наличие адреса»). Ошибка «Для такого типа оборудования необходимо выбрать родительский объект» — выбран тип без обязательного адреса, а родитель не указан [user/TheDifferenceBetweenObjectTypes].

**Тип оборудования** [admin/ObjectsType]: `Путь: Консоль → Структура предприятия → Типы оборудования`. Базовые типы по умолчанию: «Объект» (с «Обязательное наличие адреса») и «Оборудование» (без). Обязательно должен быть хотя бы один тип с «Обязательное наличие адреса». Флажок «Назначить объектом по умолчанию» — тип подставляется в новые объекты и автоматически включает обязательность адреса. Настройка «Виды работ» на типе: подставляются в новые объекты этого типа; при смене типа существующего объекта система **предложит** заменить виды работ; в конкретном объекте можно вручную добавить/убрать. Тип используется в аналитике [user/ObjectsAnalytics], [user/ClientsAnalytics].
- ⚠ Тип оборудования после сохранения заблокирован; чтобы изменить — «Снять с публикации», изменить, сохранить и «Опубликовать» (иначе по объекту нельзя создавать заявки). Массовое редактирование меняет тип без снятия с публикации, но **только для дочерних объектов** [user/ChangeOfObjectType], [user/GroupActions].

**Класс оборудования** [admin/ObjectClass]: группировка объектов и заявок по объектам (по стоимости, производителю и т.п.); указывается только в карточке Объекта [admin/PlacesVSObjectsClass]. `Путь: Консоль → Структура предприятия → Классы оборудования`. Флажок «Назначить классом по умолчанию». Фильтр «Класс» в списке объектов и «Класс объекта» в фильтре заявок. Если классы не нужны — значение «По умолчанию» [user/CreatingObjects]; в мобильном приложении без класса объект создать нельзя [user/CreatingObjTemplates]. ⚠ Удаление класса не очищает поле «Класс» у объектов; фильтровать по удалённому классу нельзя, выбрать его в новом объекте нельзя.

Класс vs Участок [admin/PlacesVSObjectsClass]: класс — только группировка объектов/заявок; участок связывает Объект, Сотрудника, Заказчика и Тип заявки и **автоматически ограничивает доступ** в разрезе участков.

Карточка объекта [user/CreatingObjects]. При создании вкладки: «Объект|Оборудование», «Контакты», «Обслуживание», «Дополнительные поля»; после сохранения добавляются «QR-коды», «Дочерние объекты», «История обслуживания», «Договоры». Поля: «Название», «Родительский объект», «Серийный номер», «Тип», «Компания-владелец», «Описание», «Адрес», «Файлы», «Разрешить создавать заявки по этому объекту» (= опубликован; неопубликованный нельзя выбрать в заявке), «Участок» (несколько), «График работы» (справочно), «Класс», «План объекта», «Мобильное оборудование», «ERP ID». Вкладка «Обслуживание»: «Ответственный за объект», «Вид работ», «Навыки», «На гарантии до», «Чек-лист».

«История обслуживания» — все заявки объекта; флажок «С вложенными объектами»; показ иерархии родительских/дочерних заявок; если родительская заявка недоступна пользователю — скрывается вся её иерархия [user/CreatingObjects].

Список объектов: карточный вид (название, адрес, компания, число активных заявок); настраиваемые фильтры (в т.ч. по доп. полям, drag-and-drop, сохраняются); строка поиска с настройкой полей поиска; запуск по Enter/«Найти» (без автопоиска); множественный поиск через `;;` — **только если выбрано ровно одно поле**, не более 50 значений, вставка из Excel Ctrl+Shift+V [user/CreatingObjects]. Быстрые фильтры сохраняются над списком [user/GroupActions]. Неопубликованные объекты отмечены оранжевым маркером [user/CreatingObjTemplates].

**Массовые действия по объектам** [user/GroupActions]: родительский объект, вид работ (+/−), участок (+/−), ответственный, тип (только дочерние), класс, компания-владелец, мобильность, публикация, навык (+/−), график работы, чек-лист (+/−). Списки видов работ и участков в форме массового редактирования выводятся полностью (весь справочник).

Создание дочернего объекта: вкладка «Дочерние объекты» → «+»; контекстное меню карточки «Создать дочерний объект|оборудование»; «Создать объект» с родителем; из списка [user/CreatingObjects]. Удаление: «Удалить» или «Удалить с вложенными объектами» [admin/Powers].

**Мобильное оборудование** [user/MobileObjects]: объект с динамическим адресом (строительная техника, вендинг, аренда). Флажок «Мобильное оборудование» в карточке. Адрес, изменённый в заявке («Редактировать – Изменить местоположение»), сохраняется в карточку объекта. Работает **только для объектов с типом «Обязательное наличие адреса»** (родительских); у мобильного дочернего адрес наследуется и не меняется. ⚠ Изменение адреса во второй заявке не меняет адрес в первой. История перемещений — через экспорт заявок по объекту.

**Планы помещений** [user/FloorPlan]: поле «План объекта», один план на объект, .jpg/.jpeg/.png, загрузка **только в web**. Пин в карточке = расположение по умолчанию; в заявке можно поставить другой (карточка объекта не меняется). Дочерний без своего плана берёт план родителя; если планы есть у обоих — можно выбрать любой. В мобильном — просмотр и перенос метки.

**Редактирование объекта в мобильном** (исполнитель и заказчик) [user/ObjectEditing]: через паспорт при QR, из списка «Объекты|Оборудование», из заявки. Можно менять доп. поля («Характеристики»), «Класс оборудования», «Описание», «Файлы»; «Серийный номер» — по [user/ObjectListInMob]. Нельзя — «Тип оборудования» и «Контактные лица». Нужно полномочие «Изменение данных объекта». В мобильном исполнителя: список объектов → паспорт → «Посмотреть историю обслуживания» / «Подать заявку» (поля «Тип заявки», «Вид работ», «Исполнитель», «Описание заявки») [user/ObjectListInMob].

Создание объектов также: импорт (до 2000 за раз) [user/Import], шаблоны объектов + «Приемка и маркировка» в мобильном (объекты создаются неопубликованными) [user/CreatingObjTemplates], из формы заявки (поиск объекта → создать) [user/CreatingTicket], API `POST /fsm/ES/Assets` [admin/ExampleRequestsAPI].

⚠ Удалить объект, участвующий в активных заявках, нельзя; удалённый объект не восстанавливается; при удалении компании её объекты снимаются с публикации [user/DeletedObjects].

## Пользователи: сотрудники, заказчики, владелец тенанта, вход, SSO

Два типа пользователей [user/CreatingUser], [user/EngineerVSCustomer]:
- **Сотрудник** — может создавать и выполнять заявки; **лицензируемый пользователь**; web + «HubEx исполнитель». Диспетчеры, руководители, сервисные инженеры.
- **Заказчик** — сотрудник клиента; создаёт заявки (приложение заказчика, клиентский портал); привязан к компании-заказчику; **нельзя назначить исполнителем**; переводит заявки только по стадиям «ветки действий заказчика»; видит объекты и заявки только своей компании (при соответствующей роли). В клиентском портале — меню «Заявки - Все заявки», «Сообщения», «Аналитика - Отчет для клиента»; в мобильном — «Заявки», «Сообщения».

**Карточка сотрудника** (`Путь: Пользователи → Сотрудники → «Добавить сотрудника»`) [user/CreatingUser]:
- «Фамилия», «Имя» обязательны; «Отчество», «Пол».
- «Мобильный сотрудник» — разрешает участвовать в автораспределении и быть исполнителем выполненных работ. Без него: нет автоназначения [admin/RulesOfChoice], нет рейтинга [user/Rating]; в календаре фильтр «Мобильный сотрудник» включён по умолчанию [user/Calendar]; в KPI «Офисные сотрудники» — без этого флажка [user/EngineersAnalytics].
- «Отслеживание местоположения»: «Всегда» / «С разрешения пользователя» / «Выключить отслеживание местоположения сотрудника» (автоназначение работает, но без учёта удалённости). Сочетание «Мобильный сотрудник» + отслеживание выключено теперь допустимо.
- «Точность сбора геокоординат»: «Максимальная точность» (по умолчанию) / «Сбалансированный режим» / «Минимальная точность»; применяется после синхронизации приложения.
- «Мобильный телефон» и/или «Электронная почта» — логин; приходит приглашение. «Рабочий телефон», «Другой телефон». «SSO Login».
- «Стартовая страница» (web) — меняет только пользователь с полномочием «Настройка стартовой страницы»; по умолчанию «Все заявки».
- «Ставка для клиента» (стоимость часа) [user/CreatingUser]; в других статьях то же поле — «Ставка/час» / «Ставка в час», вкладка «Квалификация» [user/Prices], [admin/Powers]. Только рубли, копейки через запятую; массово — только при создании через импорт [user/Prices].
- «Участок», «Виды работ», «Навыки», «Доступные склады».
- «Компания» → появляются «Должность», «Табельный номер». «Роль». «График работы».
- Карточка в списке: аватар, ФИО, должность, рейтинг, активные заявки, кнопка звонка.

⚠ Удалить сотрудника можно, только если на нём нет активных заявок [user/CreatingUser]. Удалённого не восстановить; заблокированного («Бан пользователя», с причиной) — можно разблокировать [user/DeletedObjects]. Повторное приглашение — «Отправить приглашение повторно» (если не перешёл по ссылке в течение суток) [user/CreatingUser].

Типовые роли «по умолчанию»: «Сервисный специалист» — принимает/выполняет, видит только назначенные на него заявки; «Начальник Сервисной Службы» — переходы по стадиям, все заявки [user/CreatingUser]. Описание базовых ролей Заказчик / Сервисный специалист / Диспетчер — см. [admin/Roles], [user/RoleVSPosition].

**Карточка заказчика** (`Путь: Пользователи → Заказчики → «Создать заказчика»`) [user/CreatingCustomer]: вкладки «Общее» (обязательны «Фамилия», «Имя», «Телефон» и/или «Электронная почта», «Компания», «Роль» = «Заказчик»), «Квалификация» («Участок», по которому подаёт заявки), «Прочее» («Бан пользователя»). Карточка в списке — число поданных заявок.

**Перевод типа**: «Перевести к сотрудникам» / «Перевести к заказчикам»; **роль при переводе не меняется** — менять вручную [user/CreatingCustomer], [user/CreatingUser]. Полномочия «Перевод сотрудника в заказчики» / «Перевод заказчика в сотрудники» [admin/Powers]. Ошибочно созданный сотрудник вместо заказчика, отсканировав QR, «может увидеть больше данных, чем нужно» [user/CreatingUser].

**Роль vs Должность** [user/RoleVSPosition]: Роль — набор прав (у Сотрудника и Заказчика); Должность — свободный текст, только у Сотрудника, только справочно (выбор исполнителя, вкладка «Выполнение», «Расписание заявок», отчёт по должностям). Изменения ролей действуют **сразу**.

**Владелец тенанта** [user/SuperAndUsualUser] имеет две учётки: «Имя_пользователя (Системный администратор)» — ограничения ролей не действуют, видит все удалённые объекты/заявки, все поля заявки всегда доступны (скрыть нельзя), может переводить заявку на **любую стадию ЖЦ типа, даже не связанные переходом**; и «Имя_пользователя» с ролью «Системный администратор», настраиваемой как обычная.

**Вход** [user/EnterToMob]: пользователь создаётся в «Пользователи»; приходит письмо/SMS со ссылкой; без завершения регистрации и пароля нельзя войти ни по паролю, ни по одноразовому коду. Регистрацию можно завершить при первом входе в приложение (создать пароль → подтвердить SMS-кодом). **Вход по одноразовому коду** (4 цифры, повтор через 60 с) — только для российских номеров (+7…), только после завершения регистрации; чтобы он был доступен — при создании указывать мобильный. Для мобильных приложений роли нужен раздел «Приложения»: «Веб-приложение», «Веб-приложение администрирования», «Доступ только к API» («рекомендовано включать для всех»), «Мобильное приложение заказчика», «Мобильное приложение инженера», «Электронный паспорт оборудования». Приглашение — email или SMS [user/HowToSendInvitation]. Вход в портал/приложение заказчика — после регистрационного письма/SMS; зарегистрированный по телефону может входить по одноразовому коду [user/CustomerApp], [user/CustomerWeb].

**Консоль администратора**: аватар (правый верхний угол web) → «Консоль администратора»; главная — подписка, число пользователей; нет входа — не хватает прав [admin/HowToEnterTheAdmin].

**SSO** [admin/SSOintegration]: через Keycloak (Realm на тенант); стандарты SAML 2.0, OpenID Connect/OAuth 2.0, LDAP/Active Directory, Kerberos, CAS, Azure AD, Google Workspace; единый вход в WEB и МП; выбор тенанта при нескольких. Пользователь: «Вход через SSO» → корпоративный логин → редирект. Параметры SAML: Entity ID, SSO URL, X.509, NameID Format, (опц.) Metadata; OIDC: Client ID/Secret, Authorization/Token/UserInfo Endpoint, Redirect URI, (опц.) Scopes. ⚠ «Требует индивидуальной настройки для каждого клиента», время на тесты, сложные случаи — «дополнительное согласование»; подключение через поддержку. У сотрудника заполняется «SSO Login» [user/CreatingUser]. Формулировка страницы «Если HubEx поддерживает SSO…» — общая; конкретный список провайдеров дан в разделе «Ключевые возможности».

**Требования к устройствам** [user/MobileDevice]: Android — от 12.0, аккумулятор от 5000 мА·ч, процессор не ниже Helio G88 / Snapdragon 680, ОЗУ от 6 ГБ, экран от 6.5", 4G, камера от 8 МП, NFC (при NFC-метках); рекомендованы Redmi 13C, Redmi Note 11, Galaxy A15/M15/A23, Tecno Spark 20 Pro, Infinix Hot 40i. iOS — от 16.0, 6.5", 4G, 8 МП, NFC; iPhone 14, SE (3), 15, 16e. **Huawei не рекомендуются** (нет Google Play — нельзя обновлять приложения). В [admin/AboutHubEx] — совместимость со «специализированными Андроид терминалами» с Android 6.0+ (терминалы ≠ рекомендации для телефонов). «HubEx исполнитель» поддерживает системный масштаб шрифта с ограничением максимума.

## Участки, навыки, виды работ: классификаторы и их побочные эффекты

**Участок** [admin/Places] — классификация Объектов, Типов заявок, Сотрудников, Заказчиков (география, направление). `Путь: Консоль → Структура предприятия → Участки → «Создать участок»`. Поля: «Название участка» (обязательно), «Описание», «Идентификатор из внешней системы» (1С), «Назначить участком по умолчанию» (подставляется в новые Объекты, Сотрудников, Заказчиков). Статистика связей участка (объекты, пользователи, типы заявок) — для решения об удалении/переносе.

Где указывается: Объект — вкладка «Объект|Оборудование»; Сотрудник и Заказчик — «Квалификация»; Тип заявки — в карточке типа (параметр «Все» / «По списку» [admin/TicketType]). Везде можно несколько участков.

⚠ Новый участок **вручную** добавляется в существующие объекты, сотрудников, заказчиков, но **автоматически** — во все ранее созданные Типы заявок [admin/Places].

⚠ Если у пользователя указан участок, а ни в одном Типе заявки этого участка нет — пользователь не сможет выбрать тип и создать заявку («отсутствуют доступные Типы заявок») [user/HiddenObjectsTicketsUsers]. ⚠ Диспетчер видит в выборе исполнителя только сотрудников с совпадающими участками; добавить участок в карточку диспетчера [user/HiddenObjectsTicketsUsers].

Пример модели [admin/Places]: участок «Электрооборудование» на объектах + тип «Ремонт электрооборудования» с этим участком + сотрудник с этим участком → сотрудник создаёт заявки только этого типа и по объектам участка. Для заказчика — то же, объекты своей компании в пределах участка [user/CreatingCustomer].

**Навыки** [admin/Skills] — особые умения для заявки (пример: английский для настройки приборов). `Путь: Консоль → Структура предприятия → Навыки`. Поля: «Название навыка» (обязательно), «Описание», «Необязательный» (правила автоназначения могут учитывать обязательные, необязательные или обе группы). Указываются у Объекта (вкладка «Обслуживание») и Сотрудника («Квалификация»), по несколько. ⚠ Новый навык автоматически ни в объекты, ни в сотрудников не добавляется.

**Вид работ** [admin/WorkType] — вид деятельности/услуги (клининг, ремонт, диагностика, аренда, доставка). `Путь: Консоль → Настройки заявки → Виды работ`. Поля: «Название вида работ», «Описание», «Чек-лист выполняемых работ» (подтягивается в заявку), «Плановые трудозатраты» (расчёт окончания работ при выборе исполнителя), «Время закрытия заявки» (срок; итог — минимум с Типом заявки), «Основной вид работ» (подставляется в новый объект; «он может быть только один в системе» [admin/TicketMail]), «Опубликован» (только опубликованный можно указать у объекта/сотрудника/в заявке), «Стоимость вида работ» (в выполненных работах и Акте; правится вручную). Стоимость — только рубли, **без копеек**, массово не заполняется [user/Prices].

Правила видов работ:
- В заявке доступны только виды работ из карточки **выбранного Объекта** (и, если в Типе заявки задан список, — пересечение со списком типа) [admin/WorkType], [admin/TicketType], [user/ChoiceWorkType].
- ⚠ Новый вид работ **не добавляется** автоматически в существующие Объекты и Сотрудников; у сотрудника можно выбрать только ранее созданные (создать из карточки сотрудника нельзя) [admin/WorkType]. Автоподстановка — через Тип оборудования [admin/ObjectsType] или массовое действие [user/GroupActions].
- Создать вид работ можно из заявки и из вкладки «Обслуживание» объекта («+ Добавить») [admin/WorkType].
- Поле «Вид работ» может отсутствовать на форме заявки — значит для роли/стадии нет настройки в «Поля на форме заявки» (нужно RW) [user/ChoiceWorkType].
- Вид работ — «самый популярный параметр» автораспределения [admin/RulesOfChoice]; полномочие «Активные заявки по моим видам работ» открывает заявки по видам работ сотрудника [admin/Powers].

## Роли и полномочия: модель доступа

**Роль** — набор прав: видимость разделов и данных, действия, доступ к приложениям (исполнитель, заказчик, web) [admin/Roles]. Устанавливается в карточке пользователя; у одного пользователя «Роль (или Роли)» [user/HiddenObjectsTicketsUsers]. `Путь: Консоль → Администрирование → Роли` (плитки). Создание — «Добавить роль», можно на основе шаблона («Создать новую роль на основе шаблона») или «Копировать» из контекстного меню (плитка «Копия …»).

Базовые роли — примеры из [admin/Roles], [user/RoleVSPosition]: **Заказчик** — работает только в приложении заказчика, создаёт заявки только по объектам своей компании, не видит объекты других заказчиков, остальные заявки, сотрудников исполнителя, аналитику, склады и карты; **Сервисный специалист** — создаёт и (или) выполняет заявки, переводит по определённым стадиям, может создавать оборудование через маркировку, работает в приложении исполнителя, доступ может быть ограничен участками; **Диспетчер** (оператор, офисный сотрудник) — создаёт и выполняет заявки, доступ ко всем компаниям-заказчикам и объектам, переводит на любую стадию, назначает любого исполнителя на любом участке.

Три раздела роли [admin/Roles]:
1. **Полномочия** — тематические блоки; включается блок целиком или по пунктам. В блоке группы «Элементы интерфейса» (видимость меню и кнопок, в т.ч. консоли) и «Справочники» (какие данные видны). Уровни для элементов интерфейса: «Чтение и запись» (по умолчанию), «Чтение и обязательная запись», «Только для чтения». Справа — панель скрытия блоков, поиск по полномочиям (одно слово, можно без окончания: «удален»).
2. **Приложения** — web, консоль, «Доступ только к API», МП заказчика, МП инженера, «Электронный паспорт оборудования» [user/EnterToMob].
3. **Плагины** — см. раздел о расширяемости.

⚠ **API полномочия**: для действия мало включить пункт интерфейса — нужен и API-метод (пример: «Объекты - Создание объекта» + «API полномочия - Метод создания нового объекта»). Методов много — **рекомендуется включать блок целиком для всех ролей** [admin/Roles], [admin/Powers]. UI полномочия — отдельный справочник настраиваемых полномочий интерфейса: `Путь: Консоль → Администрирование → UI Полномочия → «Создать полномочие»`; содержательного описания нет [admin/UI_Permissions].

Ключевые блоки и неочевидные зависимости [admin/Powers]:
- **Заявки — элементы**: «Создание заявки» (кнопка в web), «Удаление заявок», «Кнопка создания заявки, выбрав объект из списка в Мобильном Приложении» и «Подача заявки по сканированию QR-кода» (обе требуют доступа к Объектам в «Объекты - Справочники»), «Пункт главного меню - Заявки», «Копирование заявок», «Изменение заявок» (без него все поля заблокированы), «Экспорт заявок», «Импорт заявок», «Добавление/Удаление участника в списке в сообщениях» (+ «Сообщения - Просмотр списка участников», + доступ к пользователям), «Календарь заявок сотрудника при назначении», «Настройка карточки для списка заявок» (автоматически включено для ролей с доступом к «Все заявки» [user/TicketsListView]), «Изменение закрытых заявок» (пункт «Вернуть в работу»), «Восстановление удаленной заявки» (только вместе с «Удаленные заявки»).
- **Заявки — справочники** (что видно): «Активные заявки на сотрудниках моих участков», «Активные заявки на объектах моей компании» (типично для роли Заказчика), «Все активные заявки», «Активные заявки по моим видам работ», «Дочерние активные заявки», «Заявки, на которые я когда-либо был назначен», «Предоставляет доступ на чтение и запись для всех компонентов формы заявки вне зависимости от полномочий и настроек стадии», «Заявки, где пользователь - ответственный за объект по заявке», «Заявки на объектах, доступных пользователю» (видимость заявок = видимость объектов), «Игнорировать эксклюзивные полномочия для доступа к полям заявки», «Архивные заявки» (закрытые), «Заявки, когда-либо назначенные на сотрудников моей компании» (только для трудоустроенных), «Удаленные заявки». Дополнительно в [user/HiddenObjectsTicketsUsers]: «Активные заявки на сотрудниках моей компании», «Удалять незакрытые заявки». Для удаления заявок [user/ChangingStatus] включают «Удаление заявок» и «Удалять незакрытые заявки»; рекомендуется только руководителям/админам.
- **Объекты — справочники**: «Все активные объекты», «Удаленные объекты», «Объекты на участках пользователя», «Объекты у компаний пользователя» (для Заказчика; остальные отключить [user/HiddenObjectsTicketsUsers]), «Компании и объекты, находящиеся на участке пользователя». Элементы: «Публикация объекта», «Отмена публикации объекта», «Создание объекта» (+ «Изменения данных объекта», иначе поля пустые), «Удаление объекта», «Копирование», «Экспорт», «Импорт».
- **Пользователи и контакты**: меню «Сотрудники», «Заказчики», «Приглашения», «Графики работ»; создание/копирование/удаление; «Изменение данных сотрудника или заказчика» (нужно и для создания); приглашения; экспорт/импорт; переводы типов; контакты; «Настройка стартовой страницы». Справочники: «Все пользователи», «Заблокированные пользователи», «Все пользователи внутри компании», «Все пользователи на участках». Выбор исполнителя в заявке и добавление в чат зависят от этого блока.
- **Материалы и склады**: «Пункт главного меню - Склады» (+ «- Материалы», «- Расход»), экспорт, импорт; справочник «Все склады» — видит все склады; ограничение — список складов в карточке сотрудника [user/SettingsWithMaterials].
- **Выполненные работы и стоимости**: поле «Вид Работ» на форме работ, «Израсходованные материалы на форме выполненных работ» (+ «Все склады»), «Стоимость вида работ», «Cтоимость материала», «Ставка/Час исполнителя», «Ставка/час в карточке сотрудника» (+ меню «Сотрудники» и «Все пользователи»), «Сканирование кодов для списания единиц материалов» [user/AboutDataMatrix].
- **Аналитика**: «Срез по заявкам», «История перемещений» (меню «Карты»), «Общая аналитика», «Отчет для клиента», «Отчет по объектам», «Отчет по сотрудникам», «Анализ эффективности процессов», «График действия договоров», «График обслуживания объектов» (в «Заявки - Планировщик работ»), «Сервисный акт», «Бухгалтерский акт», «Счет на оплату» (меню «Печатные формы»), «Доступ к подключаемым плагинам и отчетам».
- **Жизненный цикл заявки**: работа с ЖЦ только при «Участки - Справочники - Все участки»; кнопка «+Добавить стадию» требует: блок «Поля на форме заявки» целиком, «Роли - Все роли», меню Стадий, Статусов, Типов заявок. «Сохранение настроек полей на форме заявки» требует «Сохранение жизненного цикла заявки». «Редактирование шаблона формы заявки» — доступ к «Настройка форм».
- **Интеграция**: меню «Webhook'и» (создание/удаление/копирование/сохранение), «Переменные» (= «Интеграция - Ключи»), «Служебные пользователи». **Интеграция по эл. почте** — отдельный блок.
- Прочие блоки: QR (публикация, отмена, меню «Маркировка», создание/удаление/копирование/изменение шаблонов, меню МП «Приемка и маркировка»), Виды работ, Графики работ, Дополнительные поля, Календарь («Расписание заявок»), Карты, Классы объекта, Компании (+ «Договоры», «Все компании»), Критичности, Навыки, Плановые заявки (создание, изменение, «Активация» = кнопка «Запланировать», «Приостановка»), Поля на форме заявки, Автоматическое назначение заявок, Настройка рейтингов («Критерии оценки заявки»), Роли («Все роли», «Удаленные роли»), Сообщения («Чат с заказчиками», «Чат с сотрудниками», «Сообщения по всем доступным заявкам»), Стадии, Статусы, Типы заявки, Типы объектов, Настройка уведомлений, Участки («Все участки»), Чек-листы, Шаблоны объектов.

**Рецепт «исполнитель видит только свой участок»** [admin/Roles]: заполнить участки у Сотрудника, Объекта, Типа заявки → «Объекты - Справочники - Объекты на участках пользователя» → «Заявки - Справочники - Заявки на объектах, доступных пользователю» и **снять 8 первых пунктов** (они дают более широкий доступ).

**Рецепт «исполнитель сам берёт заявки из общего списка»** [user/AcceptanceTicket]: вкладка «Все» в МП (фильтр по стадии «Новая»); роль: «Объекты на участках пользователя» + «Заявки, где пользователь - ответственный за объект по заявке» + «Заявки на объектах, доступных пользователю»; в «Поля на форме заявки» для роли и стадии «Новая» поле «Актуальный исполнитель по заявке» = RW (иначе замок). После самоназначения — принять, чтобы стадия ушла с «Новая».

**Диагностика «не вижу»** [user/HiddenObjectsTicketsUsers]: (1) фильтры (в МП — красная точка на кнопке фильтров; в web — «Активные фильтры»); (2) справочники роли; (3) участки (объект/тип заявки/исполнители). Пустая форма заявки на стадии — для новой стадии не настроены «Поля на форме заявки» [user/HowToDealWithWhiteScreen].

**Доступ к файлам** [user/ViewRestriction]: по умолчанию файл в заявке/объекте виден всем; контекстное меню файла → «Права доступа» → роли, сохраняющие доступ (только после добавления файла). «Показать файлы в паспорте объекта» — файл доступен при сканировании QR. Скрытие удалённых сущностей: отключить «Удаленные компании», «Удаленные объекты», «Удаленные пользователи», «Удаленные роли» [user/DeletedObjects], [admin/Roles].

## Поля на форме заявки и конструктор формы

**Поля на форме заявки** — тонкая настройка видимости/редактирования полей заявки в разрезе **Ролей × Стадий** [admin/ElementsOfInterface]. `Путь: Консоль → Настройки заявки → Поля на форме заявки` → выбрать роли и стадии → таблица (основные поля + доп. поля внизу с меткой «A»). Уровни:
- **RO** — только чтение;
- **RW** — чтение и необязательная запись;
- **RWM** — чтение и обязательная запись (переход блокируется, пока не заполнено [user/KanbanPlugin]);
- **«Настройка не выбрана»** — поле не видно.

Копирование настроек: контекстное меню роли или стадии → «Копировать в…». Нельзя скрыть «Тип заявки»; для него хотя бы для одной роли и стадии нужно RW; остальные поля можно исключить [admin/ElementsOfInterface]. Полномочие «Предоставляет доступ на чтение и запись…» / «Игнорировать эксклюзивные полномочия…» обходит эти настройки [admin/Powers]; владелец тенанта (сист. админ) видит все поля всегда [user/SuperAndUsualUser]. Роль «Изменение заявок» выключена — все поля заблокированы независимо от RO/RW [admin/Powers].

Типовые применения, описанные на страницах:
- запрет менять исполнителя сервисному специалисту на «Назначена» (RO), админу — RW [admin/ElementsOfInterface];
- обязательная наработка оборудования (доп. поле RWM на «В работе») [admin/ElementsOfInterface];
- рейтинг ставит только заказчик на «Выполнена»/«Закрыта»: «Рейтинг технического специалиста» RW для Заказчика, «Настройка не выбрана» для исполнителя [user/Rating];
- «Необходимые материалы на форме заявки» RWM на «В работе» — исполнитель обязан просмотреть [user/TicketWithMaterials];
- «Выполнение» RWM на нужной стадии — контроль сканирования Data Matrix [user/AboutDataMatrix];
- «Выполненные работы» открыть на «В работе» [user/AttachingFiles];
- поле «Чек-листы» RW на «В работе» для исполнителя — нельзя перейти на «Выполнена», пока не заполнен один пункт [user/Checklists];
- контакты скрыть от исполнителей [user/Contacts]; «Инициатор заявки» — редактирование только у ролей с правом [user/UsersRequests]; «Оценочная/Фактическая стоимость» [user/Prices];
- упрощённая форма для внутренних задач — оставить только «Тип заявки» [user/CreatingTicket].

**Конструктор формы заявки** [admin/TicketFormBuilder] — только **расположение и группировка** полей, отдельно для каждого Типа заявки (кто видит/редактирует — в «Поля на форме заявки»). `Путь: Консоль → Настройка форм → Заявка`; доступ — полномочие «Редактирование шаблона формы заявки». Изначально у всех типов единый стандартный шаблон; сохранённые изменения создают кастомный шаблон типа. Блоки: создать («Новый блок»), переименовать, удалить (поля уходят в конец основного блока «Заявка»), переместить в режиме «Свернуть блоки». Основной блок «Заявка» нельзя удалить/переместить, можно переименовать. Поля перетаскиваются внутри и между блоками; **удалить поле из конструктора нельзя**. «Восстановить по умолчанию» (меню ⋮) → «Сохранить» или «Отменить».

## Заявка: создание, поля, номер, инициатор

**Заявка** — карточка задачи: содержание, исполнители, сроки; создаётся в разрезе объектов (история обращений по объекту) [user/CreatingTicket]. `Путь: Заявки → Все заявки → «Создать заявку»`. До сохранения — только вкладка «Заявка»; блоки «Заявка», «Обслуживание заказчика», «Трудозатраты», «Детальная информация».

Основные поля [user/CreatingTicket]:
- «Тип заявки» — **единственное обязательное поле в web**, отключить нельзя. ⚠ После создания **тип изменить невозможно** — только скопировать заявку с другим типом и удалить старую [user/ElectedTicket]. Для заявок из Telegram — тоже нельзя, критичность можно [admin/TelegramIntegration].
- «Номер заявки» — автоматически по маске Типа заявки, правится вручную; **до 32 символов**. Маска собирается из элементов («День ДД», «Месяц ММ», «Диапазон чисел (0-9)» …): `[{День ДД}][{Месяц ММ}][0-9][0-9][0-9]` → 2309001 для первой заявки 23 сентября; «Код компании» может входить в маску [admin/TicketType], [user/CreatingCompany].
- «Критичность» — цветной маркер в web и МП [admin/Criticality].
- «Описание заявки» — форматирование (жирный, курсив, списки, ссылки, цвет), вставка текста из сторонних систем.
- «Исполнитель» — один или несколько (вручную); через календарь и через автоназначение — **только один** сотрудник.
- «Крайний срок закрытия» — см. раздел SLA.
- «Файлы» (права по ролям), «Заказчик» (создать из заявки «+»), «Объект/оборудование» (дочерние — внутри «папок» родителей), «Вид работ» (из карточки объекта), «Адрес» (от родительского объекта, правится; у мобильного оборудования пишется в объект), «Инициатор заявки».
- Необязательные: «Договор обслуживания», «План объекта», «Компания-плательщик» (может отличаться от заказчика), «Контактные лица», «Наша компания» (если несколько собственных организаций), «Родительская заявка», «Оценочные и фактические трудозатраты» (часы), «Оценочная и фактическая стоимость» (справочные системные поля [user/Prices]), «Неисправность обнаружена» (дата), «ERPID», «Метод подачи заявки» (автоматически: «Телеграм», «Паспорт объекта» и т.д.), доп. поля внизу.

Внутренние заявки: в web можно создавать **без Заказчика, Объекта, адреса, вида работ** (бухгалтерия, IT, курьеры) [user/CreatingTicket]. ⚠ В мобильном приложении «Заказчик», «Объект», «Вид работ», «Адрес» **обязательны** при создании. Заявка без этих полей, созданная в web, в МП открывается и редактируется.

Создание в «HubEx исполнитель» [user/CreatingTicket]: кнопка подачи (правый нижний угол) → объект из списка → «Тип заявки», «Вид работ», «Исполнитель», описание; во вкладке «Дополнительные поля» — «Критичность», «Начало выполнения»; **«Срок исполнения» в МП не редактируется** (рассчитывается). Также — по QR-коду и из меню «Объекты|Оборудование» → паспорт → «Подать заявку». Создать заявку можно и свайпом пункта чек-листа влево («Создать заявку») [user/Checklists].

Создание из «Расписания заявок» — кнопка «+»; при выборе исполнителя «Дата и время выполнения»: начало — текущий день и ближайший час, окончание — начало + «Плановые трудозатраты» вида работ, иначе **+1 час**. Без даты/времени выполнения заявка не попадёт в календарь исполнителя [user/Calendar].

**Инициатор заявки** [user/UsersRequests]: заполняется автоматически при создании зарегистрированным пользователем (web/МП); можно выбрать/изменить/создать (список — все Заказчики и Сотрудники). Новый инициатор: ФИО, «Телефон» или «Электронная почта» (одно обязательно), «Компания» (из заказчика заявки; при смене заказчика компания инициатора не меняется). ⚠ Новые инициаторы по умолчанию создаются в справочнике **Заказчики**. «Посмотреть историю обращений» — все заявки инициатора. Действия доступны только ролям с правом редактировать поле «Инициатор заявки». Инициатор — получатель «Обратившийся пользователь» в уведомлениях [admin/TicketsAgreement]; из чата нельзя удалить исполнителя и инициатора [user/Messages].

Другие способы создания: импорт (до 2000 за раз, фоном) [user/Import], плановые заявки [user/PlannedTickets], QR/паспорт [user/CreatingTaskTemplates], email [admin/TicketMail], Telegram [admin/TelegramIntegration], форма на сайте [user/AlternativeWays], API [admin/ExampleRequestsAPI], Битрикс24 [admin/IntegrationBitrix24], дочерние [user/ChildTicket], копирование [user/ElectedTicket].

## Список заявок: представления, фильтры, поиск, массовые действия

Представления [user/CreatingTicket], [user/TicketsListView]: **карточное** (по умолчанию), **табличное**, **на карте** [user/TicketsOnMap]. Заявку можно открыть в боковом окне (URL не меняется; после «Сохранить» список обновляется без перезагрузки).
- Карточка: настройка шестерёнкой — включение/выключение полей и раскладка в три блока (левый 50%, центр и правый по 25%); парные поля всегда вместе («Назначено с»/«Назначено по», «Родительская заявка»/«Дочерние заявки»); «По умолчанию» — общий шаблон системы; настройка **индивидуальна для пользователя**; полномочие «Настройка карточки для списка заявок».
- Таблица: выбор колонок (вкл. доп. поля), порядок перетаскиванием, поле «Дата изменения» (последняя строка истории); настройки сохраняются в профиле и одинаковы на всех устройствах. Сортировка: «Объект», «Исполнитель», «Крайний срок закрытия», «Дата изменения» [user/CreatingTicket].
- Список у разных пользователей различается из-за ролей/участков.

**Фильтры** [user/Filters]: кнопка «Фильтры» (правый верхний угол «Все заявки»); панель «Активные фильтры» над списком (по умолчанию свёрнута). Фильтры по основным и доп. полям: числа (Равно / Диапазон / Больше / Меньше), списки (один/несколько), «Переключатель» (Да / Нет / Все варианты), даты; «Наша компания», «Назначено С/По». Мультизначения для доп. полей «Строка», «Многострочный текст», «Целое число», «Дробное число» через `;;`, не более 50 значений, Ctrl+Shift+V из Excel. Порядок полей панели — перетаскиванием, «Добавить» поля. **Быстрые фильтры** — личные; в МП только применяются (кнопки над списком и на «Карта заявок»), создаются только в web.
- ⚠ По умолчанию показываются только **открытые** заявки (фильтр «Состояние заявки»: «Только закрытые» / «Все заявки») [user/Filters]. Закрытые не видны в списках МП исполнителя и заказчика [admin/StageType].
- «Видимость заявок»: «Только удаленные» / «Все заявки»; «Избранные заявки» → «Только избранные заявки» [user/ElectedTicket].
- Фильтр «Класс объекта» [admin/ObjectClass].

**Строка поиска** [user/Filters]: запуск по «Найти»/Enter (без автопоиска); работает в карточном, табличном и картографическом режимах; несколько номеров через `;;`. Ищет одновременно по: номеру, описанию, объекту, адресу объекта, виду работ, «Компания-получатель платежа» (Наша компания), «Компания-заказчик» — совпадение в любом поле оставляет заявку.

**Массовые действия** [user/GroupActionsForTickets] (карточный и табличный вид; флажок слева от заявки → «Редактировать»):
- назначить/заменить исполнителя(ей) (в т.ч. на уже назначенные; «Нет исполнителя» снимает назначение [user/SeveralEngineers]);
- **изменить стадию — до 500 заявок за раз**: группировка по Типу заявки и текущей стадии, для каждой группы своя целевая стадия; «Изменение стадии этих заявок недоступно» — группу можно пропустить; выполняется фоном (уведомление «Массовый перевод заявок по стадиям завершён»); доступны только стадии, на которые у пользователя есть права; каждая смена — в «История изменений»;
- вернуть в работу закрытые (полномочие «Изменение закрытых заявок»);
- удалить; массовое восстановление удалённых [user/DeletedObjects].

**Копирование, удаление, избранное** [user/ElectedTicket]: копирование **только из карточного представления** (контекстное меню → «Копировать»): форма заполнена как у оригинала, пустой номер, правило SLA пересчитается при сохранении; до сохранения можно сменить тип. Удаление — 3 способа (карточка, открытая заявка, массово). Избранное — личный список, золотой флажок, фильтр «Только избранные заявки».

**Возврат закрытой заявки в работу** [user/ChangingStatus]: индикаторы «Выполнена»/«Закрыта» (иконки с датой) и бейджи в карточке; «Действия с заявкой» → «Вернуть в работу» → выбрать стадию (не текущую). Только для заявок с признаком «Закрыта» (для «выполненных, но не закрытых» — нет) и при полномочии «Изменение закрытых заявок». В истории — смена признаков «Завершена» и «Закрыта» с «Да» на «Нет».

**Удаление заявок** [user/DeletedObjects], [user/ChangingStatus]: удаление на любой стадии при наличии прав; заявки не удаляются физически — скрываются из списка. Удалённая заявка отмечается красным значком «Удалена»; **восстанавливается** («Восстановить» в меню, на детальной странице, массово — восстанавливаются только удалённые из выделенных) при полномочиях «Удаленные заявки» + «Восстановление удаленной заявки». Кто может видеть удалённые заявки — страницы расходятся (см. сводный раздел расхождений).

**Почему ничего не удаляется навсегда** [user/DeletedObjects]: ссылочные связи заявка ↔ объект ↔ сотрудник ↔ компания ↔ инициатор ↔ родитель/дочерние; история обслуживания объекта. Компании, объекты, сотрудники, заказчики, чек-листы — удалённые **не восстанавливаются** (создаются заново по образцу); исключение — заявки. Удалённый чек-лист остаётся в ранее созданных заявках. Удалённые компании/объекты/сотрудники/заказчики видны через фильтр «Видимость …». Загруженные когда-либо данные материалов удаляются только по запросу в поддержку [user/Materials].

**Дочерние заявки** [user/ChildTicket]: иерархия заявок (разбить проект, несколько исполнителей, объединить задачи). Ничем не отличаются от обычных, кроме заполненного «Родительская заявка». Web: вкладка «Дочерние заявки» → «Создать дочернюю заявку» — краткая форма (свой исполнитель, вид работ, тип, время); **объект наследуется и в краткой форме не меняется** (меняется после сохранения в боковом окне). Любую заявку можно сделать дочерней, заполнив «Родительская заявка». Мобильное: раздел «Дочерние заявки» в карточке («+», предзаполнены «Объект», «Родительская заявка», «Крайний срок закрытия» — все можно менять, включая объект) или поле «Родительская заявка» при создании (только незакрытые и неудалённые). В списке — ссылки на родительскую/дочерние; если дочерние не видны во вкладке — включить поля в «Настройки» (шестерёнка, «Выбрать все»). Видимость дочерних — полномочие «Дочерние активные заявки» [admin/Powers].

**История изменений** [user/HistoryOfChanges]: события вкладок «Заявка», «Необходимые материалы», «Чек-листы», «Дочерние заявки», «Выполнение», «Акт выполненных работ»: смены стадий (включая время офлайн-перехода), назначения, изменения полей, материалы, чек-листы и атрибуты, привязка дочерних, работы, подпись/ФИО/должность принявшего акт; дата, автор, поле. Для действий из МП исполнителя — столбец «Местоположение»: «На объекте» / «Вне объекта» / «Не определено» (первые два открывают карту с объектом, точкой исполнителя и маршрутом; нужны координаты объекта). Боковое окно записи — предпросмотр файлов, фото, ссылки на связанные заявки.

## Жизненный цикл: типы заявок, стадии, статусы, переходы

Порядок настройки: Стадии и Тип заявки → Жизненный цикл → Поля на форме заявки (для новых стадий!) → уведомления [admin/TicketLifeCycle], [user/HowToDealWithWhiteScreen].

**Тип заявки** [admin/TicketType]: `Путь: Консоль → Настройки заявки → Типы заявок`. Определяет стадии (ЖЦ), срок закрытия, допустимые виды работ. Поля: название, «Маска номера заявки», «Время закрытия заявки», «Виды работ» («Все» / «По списку»), «Участки» («Все» / «По списку»), «Шаблонный тип заявки» — копирует ЖЦ другого типа, **доступен только при создании типа**, необязателен. **Лимит маски** [ReleaseNotes/ListOfChanges03112026] — длина итогового номера, максимум **32** (прежнее ограничение в 256 введённых символов убрано): «Год ГГГГ», «Код компании» — 4; «Год ГГ», «Месяц ММ», «День ДД» — 2; «Диапазон чисел (0-9)», «Диапазон букв (А-Я)», «Символ /», «Символ _», «Символ .», свой символ в квадратных скобках (`[-]`, `[А]`) — 1. У поля счётчик «N/32»; блоки, не помещающиеся в остаток, неактивны; при 32 ввести новые символы нельзя, удалять можно. Длина больше 32 (например, вставка из буфера) — тип не сохраняется, ошибка «Максимальная длина маски номера заявки — 32 символа»; ровно 32 сохраняется. Пустая маска — «Маска обязательное поле»; текст вне квадратных скобок — «Данные введены некорректно. Воспользуйтесь преднастроенными блоками для настройки маски». Маски существующих типов автоматически не меняются; длиннее 32 — сократить при следующем сохранении типа. Для одного типа — **только один жизненный цикл** [admin/TicketsAgreement]; разные процессы = разные типы. Изменения в **стадии** действуют во всех типах, где она есть — для особого поведения создают отдельную стадию/тип (пример с «Новая» для плановых заявок) [user/PlannedTickets].

**Стадия** — состояние заявки на этапе ЖЦ [admin/StageType]. `Путь: Консоль → Настройки заявки → Стадии заявки`. Настройки: название (видно в web и МП исполнителя), описание, цвет шрифта в списке, «Действие», «Требование», флажок «Показывать сотрудника на карте и учитывать время на стадии как рабочее» (обязательно для «В пути»/«Выезд специалиста», «В работе» — для учёта времени в аналитике; местоположение на стадии видно в «История изменений»).

**Действия стадии** (необязательно) [admin/StageType]:
- «Завершить работу по заявке» — фиксирует выполнение (для «Выполнена»; срок считается по фактическому выполнению);
- «Закрыть заявку» — заявка закрыта (для «Закрыта»); закрытые по умолчанию не видны в списках МП исполнителя и заказчика;
- «Назначить сотрудника» — конкретный исполнитель;
- «Автоназначение по правилу» — с Правилом автоназначения (правило создаётся/редактируется прямо на форме стадии; флажок «Роль» — подбор с учётом роли);
- «Автоназначение с учетом удаленности от заявки» — ближайший по карте (можно вместе с правилом); нужен «Отслеживать местоположение сотрудника»;
- «Назначить на инициатора перехода»;
- «Снять назначение» (для «Отказ исполнителя»).

**Требования стадии** (без них переход невозможен; необязательно) [admin/StageType]: «Назначен исполнитель»; «Обработаны чек-листы»; «Отсканирован QR-код объекта» (подтверждение присутствия: при переходе, например, на «В работе» МП запрашивает скан, код сверяется с QR объекта заявки, неверный — ошибка; без этого нельзя внести работы и двигать заявку [user/CreatingTaskTemplates]); «Подписан акт выполненных работ».

Выполнена vs Закрыта [admin/StageType]: «Выполнена» — исполнитель по окончании работ (действие «Завершить работы по заявке»; видна в списках МП); «Закрыта» — менеджер/диспетчер (действие «Закрыть заявку»; в списках МП не видна). **Просрочена** — если выполнена позже «Крайнего срока закрытия»; не просрочена, если переведена на «Выполнена» и/или «Закрыта» до срока [admin/StageType], [user/CreatingTicket]. В печатных формах «Выполнена» = стадия с действием «Завершить работу по заявке» [user/PaymentInvoice].

**Статус** — визуальное отображение стадии **для мобильного приложения заказчика**, со своим цветом; привязывается к стадии в ЖЦ [admin/StatusType]. `Путь: Консоль → Настройки заявки → Статусы заявки`. Пример: внутренние стадии «Согласование с руководителем», закупка — заказчик видит «В работе» [admin/StageVSStatus]; «Отказ заказчика» и «Работа с отказами» — один статус «Отказ заказчика» [user/Glossary]. В web видны и стадия, и статус; в МП исполнителя — стадия; в МП заказчика — статус. Статус виден и в клиентском портале и отчётах для клиента [user/CustomerWeb], [user/ClientsAnalytics].

**Жизненный цикл** [admin/TicketLifeCycle]: `Путь: Консоль → Настройки заявки → Жизненный цикл заявки`. Сначала «Маршрут заявки» (Начальная и Конечная стадии, статус), затем «Настройка переходов между стадиями» (слева — откуда, «Добавить стадию» — куда). С одной стадии — несколько переходов. Параметры перехода:
- «Переход на стадию» (скрывается после первого сохранения);
- «Название перехода» — **название кнопки** в МП исполнителя и заказчика (панель навигации внизу заявки);
- «Описание перехода»;
- «Ветка жизненного цикла»: **основная** (красный маркер), **согласования** (фиолетовый; в МП такие заявки на отдельной вкладке «Согласование»), **действий заказчика** (голубой) — заказчик переводит только по ней [user/EngineerVSCustomer];
- «Изменить статус заявки»;
- «Выполнить автоматический переход» через заданное время (нужен для стадии с автоназначением; пример 2 минуты);
- «Автоматический переход до наступления срока исполнения» — за заданное время до дедлайна (пример: на стадию действия руководителя, если исполнитель не назначен);
- «Предоставить доступ отдельным ролям» — переход только для выбранных ролей;
- «Добавить роль для особенной настройки» — своё название кнопки для роли (пример: всем «Назначить», сервисному специалисту «Принять заявку»).

⚠ Удаление стадии: система предупреждает со списком типов и переходов, где она используется, но **не блокирует**. После удаления переход не работает (кнопки нет). Если стадию удалить и создать заново с тем же именем — переход в ЖЦ нужно удалить и создать заново [admin/TicketLifeCycle].

Особенность роли «Заказчик»: создаёт заявку, просматривает основную информацию по ней; доступа ко всем заявкам компании-исполнителя нет [user/CreatingCustomer] (может ли заказчик менять стадии — см. расхождения). Владелец тенанта двигает заявку на любую стадию [user/SuperAndUsualUser]. В МП исполнителя «ограниченный выбор» переходов, в web диспетчер «может иметь права» на любую стадию [user/ChangingStatus]; после смены стадии всем связанным — push [user/ChangingStatus].

**Базовый бизнес-процесс ремонта** (шаблон из [admin/BusinessProcess], компания по ремонту холодильного оборудования). Стадии: 1 Новая; 2 Назначена (между «Новой» и «Принятой»: нет сети, пропустил push, собирается отказаться; можно автопереход по правилу и уведомление «застряла»); 3a Отказ заказчика (автоматически «Закрытые»); 3b Отказ исполнителя (причина обязательна в МП; заявка исчезает из списка исполнителя; дальше — «Назначение на инициатора перехода», автоназначение или вручную); 4 Принята; 5a В работе (можно разбить на «Выехал на объект» / «Прибыл на объект»); 5b В пути; 6a Требует продолжения работ (можно обязательную причину); 6b Выполнена (→ проверка); 6c Выполнена без выезда (контроль руководства); 7 Согласование (например, аванс); 8 Ожидает ТМЦ (снабжение); 9a Выполнена и проверена; 9b Выполнена без выезда и проверена (фильтрация «с выездом»/«без выезда» без анализа истории).

**Критичность** [admin/Criticality]: разделение по срочности, цветной маркер в списках web и МП; параметр SLA-правил. `Путь: Консоль → Настройки заявки → Критичность заявки`; флажок «Для всех заявок по умолчанию» — ставится в новые заявки (шаблоны email берут критичность «По умолчанию» [admin/TicketMail]; Битрикс24 — критичность по умолчанию [admin/IntegrationBitrix24]). Цвет критичности окрашивает заявки в списках на карте [user/TicketsOnMap].

**Актуальность заявки** [admin/Actuality]: раздел «Настройки заявки» для отслеживания актуальности и очерёдности; создание — название и «время до выполнения заявки» **в минутах**. Как актуальность влияет на поведение заявки — на странице не описано.

**Критерии оценки** — `Путь: Консоль → Настройки заявки → Критерии оценки заявки` (см. рейтинг) [user/Rating].

## Согласования: внутренние (линейные, параллельные) и с заказчиком

Механика согласования в HubEx — это **стадии + переходы, доступные только определённым ролям + уведомления** по стадиям; отдельного движка согласований страницы не описывают [admin/TicketsAgreement].

**Линейное (один согласующий)**, пример «Закупка ТМЦ» [admin/TicketsAgreement]: отдельный Тип заявки; стадии «Согласование заявки», «Согласована», «Не согласована»; маршрут Новая → Закрыта. Переход Новая → «Согласование заявки»: название «На согласовании», «Ветка согласования», можно автопереход (пример 5 минут). Из «Согласование заявки» → «Согласована»/«Не согласована»: «Основная ветка», вручную, «Предоставить доступ отдельным ролям» = роль ответственного (пример «Ответственный по закупкам»; роль должна стоять в карточке пользователя). Далее «Согласована» → «Выполнена» → «Закрыта»; «Не согласована» → «Закрыта» или повторное «Согласование заявки». Уведомления: согласующему — правило выбора получателя по роли, триггер по стадии «Согласование заявки»; инициатору — правило «Обратившийся пользователь», два триггера (на «Согласована» и «Не согласована»). Можно передавать согласованные заявки в 1С через интеграцию (упомянуто).

**Параллельное (два согласующих, любой порядок)** [admin/TicketsAgreement]: тот же тип, другой ЖЦ (у типа один ЖЦ). Шесть стадий: «Согласование заявки», «Согласована начальником подразделения», «Согласована ответственным по закупкам», «Согласована ответственным по закупкам*», «Согласована начальником подразделения*», «Не согласована». ⚠ Стадии со звёздочкой — **отдельные стадии**, одинаковые по смыслу, но на разных ветках (разные уведомления и выходы: продолжение или завершение). Переходы: из «Согласование заявки» — каждому согласующему своя стадия (своя роль) и «Не согласована» (обе роли); из «Согласована начальником…» → «…ответственным по закупкам*» и «Не согласована» (только ответственный); симметрично для второго. Уведомления на 5 стадиях: обоим при старте; второму — что первый согласовал (отдельный триггер на каждого); инициатору — итог (один триггер на обе «*»-стадии, другой — на «Не согласована»). На страницах описан только пример с двумя согласующими; схемы для большего числа согласующих не приведены.

**Согласование с заказчиком** [admin/CustomerAgreement]: стадии «Согласование с заказчиком» (необязательна — нужна для доп. проверки стоимости после выполнения), «Согласована», «Не согласована» (две последние — **ветка действий заказчика**, доступ только роли «Заказчик»); статусы «На согласовании», «Согласована», «Не согласована». Переход «Выполнена» → «Согласование с заказчиком»: название кнопки «Согласование заказчика», основная ветка, «Изменить статус» = «На согласовании», доступ — диспетчер/руководитель. Затем → «Согласована»/«Не согласована» с ролью «Заказчик» и особой настройкой названий кнопок → в приложении заказчика две кнопки. Уведомление заказчику: правило по роли «Заказчик», триггер Email на стадию «Согласование с заказчиком». В приложении заказчика есть вкладка «Согласование» [user/CustomerApp]; кнопки «Принять работы»/«Не принимать работы» и «Отменить заявку» тоже зависят от настроек ЖЦ [user/CustomerApp].

## SLA и крайний срок закрытия

Источники «Крайнего срока закрытия» по приоритету [admin/SLA], [admin/TicketType], [admin/WorkType], [user/Glossary]:
1. Срок, установленный **вручную**, правилом не меняется.
2. **Правило SLA** («Правило расчета крайнего срока закрытия» — его имя видно внизу формы заявки).
3. Нет включённых правил — срок из **Типа заявки** и **Вида работ**: берётся **наименьший**.

Правила: `Путь: Консоль → Настройки заявки → SLA: расчет крайнего срока закрытия → «Создать правило»` [admin/SLA]. Разрезы: **один** Тип заявки или «Все», **одна** Критичность или «Все», **один** Вид работ или «Все»; Заказчики — «Все» (включая будущих) / «По списку»; Объекты выбранных заказчиков — «Все» / «По списку» / «Все за исключением». Параметры: «График обслуживания» (рабочее время выполнения) и «Плановое время закрытия заявки». Правило нужно включить (переключатель в списке).
- Пример: обслуживание по будням 9:00–18:00, заявка в четверг 17:00, плановое время 6 часов → срок пятница 14:00 [admin/SLA].
- Пример: «Понедельник-пятница 9:00-18:00», 45 часов, заявка в понедельник 9:00 → пятница 18:00 [user/Schedule].
- ⚠ Конфликт правил: если подходят несколько, работает то, чей «График обслуживания» попадает на текущее время; при одинаковых графиках — правило с **наименьшим** сроком [admin/SLA].
- В одном правиле — только одно значение (или «Все») для Типа заявки, Критичности и Вида работ; для двух типов — два правила [admin/SLA].

Плановые заявки: «Отложить начало выполнения работ» сдвигает срок (создана в 12:00, срок 4 ч → 16:00; с отсрочкой 2 ч → 18:00) [user/PlannedTickets]. В МП исполнителя срок не редактируется [user/CreatingTicket]. Через API — поле `deadline` [admin/ExampleRequestsAPI]. Импорт — «Срок исполнения» в формате дд.мм.гггг чч:мм [user/Import].

SLA в аналитике: просрочка = выполнение/закрытие позже срока; в «Отчете для клиента» заявки без срока в SLA не участвуют, их число в подсказке «i»; заявка, сданная до срока, не просрочена, даже если не закрыта [user/ClientsAnalytics]. Сервис API для SLA и критичности — `SLA` в Swagger [admin/StartIntegrationAPI].

## Назначение исполнителей: вручную, автоназначение, ближайший, несколько

Способы [user/CreatingTicket], [user/AcceptanceTicket]: (1) вручную в заявке (один или несколько); (2) в «Расписании заявок» или на карте (один); (3) автоназначение на стадии (один); (4) самоназначение исполнителем из вкладки «Все» в МП; (5) массово по списку [user/GroupActionsForTickets]; (6) в плановой заявке [user/PlannedTickets].

**Окно выбора исполнителя** [user/CreatingTicket], [user/SeveralEngineers]: «+Добавить исполнителя»; сортировка «По релевантности» (совпадения: вид работ заявки, «Ответственный за объект», участок, навыки, график работ объекта — чем больше совпадений с карточкой сотрудника, тем выше; иконки критериев справа) или «ФИО исполнителя». Кнопка «Календарь» у сотрудника — занятость (полномочие «Календарь заявок сотрудника при назначении» [admin/Powers]). «Показать исполнителей на карте» — флажок заявки и метки сотрудников [user/UserOnMap]. Должность показывается при выборе [user/RoleVSPosition]. При выборе через график: клик по свободному времени заполняет «Дата и время выполнения»; окончание = начало + «Плановые трудозатраты» вида работ [user/Schedule].

**Несколько исполнителей** [user/SeveralEngineers]: каждый получает уведомление, может добавлять выполненные работы и двигать стадии. В новой выполненной работе — все назначенные; время общее (2 часа на работу = по 2 часа каждому в Акте). Если работали в разное время — каждый вносит свою работу со своей фамилией. Альтернатива — дочерние заявки на каждого. В МП — поле «Исполнитель», флажки, «Применить»; удаление корзиной, «Изменить исполнителя», «Очистить выбор». Доступ — «Поля на форме заявки».

**Правила автоназначения (робот-диспетчер)** [admin/RulesOfChoice]: `Путь: Консоль → Настройки заявки → Автоназначение исполнителя → «Создать правило»`. Параметры:
- «Обязательные навыки» — навыки объекта заявки ↔ карточки сотрудников (с учётом признака «Необязательный» [admin/Skills]);
- «Вид работ» — самый популярный;
- «График работы» — рабочая смена на момент подачи заявки;
- «Ответственный за объект» — из вкладки «Обслуживание» объекта;
- «Часто назначается на объект» — кто чаще всего назначался;
- «Участок» — участки объекта ↔ «Квалификация» сотрудника.
Логика: без «Детальной настройки» параметры через **И**; с «Детальной настройкой» — **ИЛИ** с весами в процентах.

Применение [admin/RulesOfChoice], [admin/StageType]: правило привязывается к стадии (действие «Автоназначение по правилу» или «Автоназначение с учетом удаленности от заявки»; появляется параметр «Роль»), обычно «Назначена». Переход на эту стадию — вручную (подбор всё равно автоматический) или автоматический по времени («Выполнить автоматический переход» в ЖЦ). ⚠ В автораспределении участвуют только сотрудники с флажком **«Мобильный сотрудник»**.

**Ближайший исполнитель** [user/RulesOfChoiceGEO]: стадия «Назначена» → действие «Автоназначение с учетом удаленности от заявки» → в ЖЦ переход на неё с «Выполнить автоматический переход» (пример 1 минута). В заявке отображается расстояние исполнителя до объекта. Комбинирование с правилом (например, по виду работ) — правило создаётся «+» прямо на форме стадии. ⚠ Создание новой стадии требует правки ЖЦ. Требует «Отслеживать местоположение сотрудника» [admin/StageType]; при выключенном трекинге автоназначение работает без учёта удалённости [user/CreatingUser]. Для подстановки адреса и подбора ближайших нужен тип оборудования с «Обязательное наличие адреса» [admin/ObjectsType].

Плановые заявки: переключатель «Автоматическое назначение исполнителя» — правило нужно привязать к стадии «Новая» (с оговоркой, что изменения стадии затрагивают все типы с ней) [user/PlannedTickets].

## Графики работы, смены, календарь, карта заявок

**Графики работы** [admin/WorkSchedule], [user/Schedule]: назначение — учёт рабочего времени при назначении, переработки, автоназначение, справочное время работы объекта, SLA. Встроенные по умолчанию: «Выходные 9-18», «2/2(4) c 9:00 до 18:00», «2/2(3)…», «2/2(2)…», «2/2 c 9:00 до 18:00», «Понедельник-Пятница 9:00-18:00», «Круглосуточный 24/7»; **встроенные изменять нельзя** — создавать свои [admin/WorkSchedule]. `Путь: Консоль → Структура предприятия → Графики работы → «Создать график»` (полномочие «На смене - создание и редактирование рабочего графика»). Типы: **недельный** (флажки дней, чч:мм) и **сменный** (повторяющийся интервал строк «Смена»/«Выходной»; ночная смена — время окончания следующего дня; пример 3/2/3). Одна смена ≤ **24 часов** (больше — две смены подряд). «Назначить дату начала календаря» необязательно (иначе — с даты создания); «Показать график в календаре» нажимать заново после изменений. ⚠ **Обеденное время в графиках отобразить нельзя** [user/Schedule]. График назначается сотруднику (вкладка «Трудоустройство» [user/Schedule]) и, справочно, объекту.

**Смены, «На смене»** [user/OnDuty]: индивидуальные правки (больничный, отпуск, перенос) — «Редактировать смену» в карточке сотрудника или в «Расписании заявок» (три точки у сотрудника); в МП исполнитель правит сам (боковое меню → иконка исполнителя). Смены можно ставить **даже без выбранного графика**. «Начать смену» / «Завершить смену» в МП: другое время начала указать нельзя, «Время по» — из графика; чтобы изменить длительность — сначала правка смены. Индикатор в календаре: зелёный — на смене сейчас, серый — нет.

**Расписание заявок (календарь)** [user/Calendar]: `Путь: Заявки → Расписание заявок`; режимы день/неделя/месяц.
- Клик по заголовку блока «Назначенные»/«Неназначенные»/«Планировщик» (месяц, неделя) открывает список, отфильтрованный по выбранному дню и сотруднику.
- Справа вкладки «Неназначенные» (по «Крайнему сроку закрытия»; фильтры: срок, объекты, вид работ, тип заявки, стадия, исполнитель), «Назначенные» (не фильтруются), «Планировщик» (плановые заявки; назначить исполнителя «+»). Боковое окно заявки для назначенных/неназначенных.
- Месяц: индикатор загрузки (часы, число заявок, 8 точек от зелёного к красному); выбор сотрудника слева фильтрует; назначение «+».
- Неделя: строка на сотрудника; верхняя строка «Без исполнителя»; ячейки: белые — рабочие, серые — выходные, жёлтые — ночная смена; назначение перетаскиванием или «+»; переназначение перетаскиванием.
- День: почасовая шкала; перетаскивание из «Неназначенные заявки»; длительность — по плановым трудозатратам, иначе **4 часа**; растягивание «хвоста»; перенос на время/исполнителя; пересекающиеся заявки расширяют строку.
- Шестерёнка → «Показывать выполненные заявки».
- «Фильтровать сотрудников»: виды работ, участки, компании, роли, «Мобильный сотрудник» (включён по умолчанию).
- ⚠ Уведомления при назначении в расписании — с задержкой **5 минут по умолчанию**: переназначили в течение 5 минут — первому уведомление не придёт; после 5 минут снятие/перенос — отдельные push «С вас была снята заявка…», «Время выполнения по заявке … было изменено».
- МП исполнителя: календарь дня (красная линия — текущее время), выбор дня через месяц; заявка без «Даты и времени выполнения» не отображается.

**Заявки и сотрудники на карте** [user/TicketsOnMap]: `Путь: Заявки → Все заявки → «Заявки на карте»` (аналог `Карты → Карта` [user/GeoPosition]). Пины группируются (кластеризация); на среднем масштабе (~2500–7 км² на экране) переключатель «С кластеризацией»/«Без кластеризации» (сохраняется в сессии); заявки одного адреса — один пин с числом. Цвета: красный — просроченные, синий — назначенные, жёлтый — неназначенные, сектора — смесь. Сотрудники — метки с инициалами/аватаром. Списки «Неназначенные» и «Все» (клик по пину фильтрует; фильтры общие, «Исполнитель по заявке» на «Неназначенные» неактивен). Календарь загруженности под картой + планируемый маршрут от заявки до заявки. Назначение: перетаскивание в календарь, перетаскивание на маркер сотрудника (правой кнопкой мыши; время — ближайшие полчаса: 14:45 → 15:00, 13:10 → 13:30; длительность — плановые трудозатраты или 4 часа), кнопка «+». Плановые трудозатраты «могут быть установлены в карточках Видов работ или Типов заявки».

## Плановые работы: планировщик и график обслуживания

**Плановая заявка** — правило автоматического создания заявок для регулярного ремонта/ТО; система сама создаёт заявки и уведомляет исполнителей [user/PlannedTickets]. `Путь: Заявки → Планировщик работ → «Создать заявку»`. Поля: «Название», «Тип заявки» (**один**), «Вид работ» (**один**; по нему подбираются объекты — у которых этот вид работ в карточке), «Объект/оборудование» — один или **группа**: «К списку объектов» (флажки) или «Подобрать объекты» (фильтры), «Описание», «Исполнитель» (один или несколько, «+Добавить исполнителя»; или переключатель «Автоматическое назначение исполнителя» — правило на стадии «Новая»), «Плановое создание заявок» (Ежедневно / Еженедельно / …, детальная настройка: пример «каждые 3 недели по вторникам в 10:00»), «Отложить начало выполнения работ», «Ограничить повторения» (период, например год, или количество, например 10 заявок). Запуск — «Сохранить и запланировать». ⚠ Редактировать — только после «Приостановить», затем снова «Сохранить и запланировать». Полномочия: «Активация плановой заявки» (= «Запланировать»), «Приостановка…» [admin/Powers].

В календаре на месяц плановые заявки отмечаются «Планировщик N» на дату и на вкладке «Планировщик»; без исполнителя — назначение «+» [user/PlannedTickets], [user/Calendar].

**График обслуживания объектов** [user/PlannedTicketsSchedule] — представление плановых заявок в разрезе оборудования и периода (ППР, ТО). Переключатель в «Заявки → Планировщик работ» (полномочие «График обслуживания объектов» в блоке «Аналитика» [admin/Powers]). Параметры: «Тип заявки» (обязателен; один или несколько), «Вид работ», «Заказчик» (компании типа «Заказчик» или «Наша компания», только те, по которым есть плановые заявки), «Тип объекта», «Класс объекта», «Объект» (**только родительские**, дочерние подтягиваются), «Период С - По», «Группировка периода по» (дни/недели/месяцы — число заявок в ячейке), «Группировка объектов по» (класс/тип). Кнопка «Просмотр отчета» — нажимать после каждого изменения. Печать «Файл - Печать»; экспорт pdf, xlsx, docx, xml (для правки — xlsx).

Сбор наработок и автоматическая корректировка графиков по ним упомянуты в позиционировании [admin/AboutHubEx]; пошаговой настройки этого на страницах нет. Наработку можно фиксировать доп. полем заявки с RWM [admin/ElementsOfInterface].

## Выполнение работ, чек-листы, дополнительные поля

**Выполненные работы** (вкладка «Выполнение») — база Акта, аналитики времени и KPI [user/AttachingFiles]. Web: «Создать работу»/«Добавить работу»; поля: «Объект/Оборудование» (из заявки, не меняется), «Вид работ» (из заявки, можно изменить; полномочие «Поле "Вид Работ"…»), «Исполнитель» (из заявки, меняется; «Ставка/час» из карточки, правится), даты/время начала и окончания (часы × ставка в Акте), «Комментарий», «Израсходованные материалы», «Файлы». PDF-вложения просматриваются в браузере во всех разделах с вложениями. В списке работ показывается объект каждой работы. Несколько работ в заявке суммируются в один Акт. МП: «Выполнение» → «+» → три страницы «Основное» / «Материалы» / «Дополнительно» (файлы, комментарий). Офлайн можно добавлять работы и фото; синхронизация при появлении сети [user/AttachingFiles], [user/OfflineMode].

**Чек-листы** [user/Checklists]: `Путь: меню «Чек-листы» → «Создать чек-лист»` (пользовательское меню, не консоль). Поля: название, описание, «Объекты» (модальное окно «Поиск по объектам» с иерархией, можно отметить все дочерние группы), «Виды работ», «Пункты». Автоприкрепление к заявке: если в чек-листе указаны Объекты и/или Виды работ — при их выборе в заявке (варианты: только объект, только вид работ, оба). Без привязок — добавляется вручную. Чек-лист также задаётся в карточке Вида работ («Чек-лист выполняемых работ») и вкладке «Обслуживание» объекта [admin/WorkType], [user/CreatingObjects]; массово по объектам [user/GroupActions].
- Пункт без атрибута — флажок «выполнено». **Атрибут** — способ ответа (число, дата, строка, файл, «Значение из справочника» и др.); создаётся как доп. поле с «Используется для» = «Чек-листы» [user/Checklists], [admin/TicketAttribute]. «Тип поля» атрибута после создания не меняется [admin/TicketAttribute].
- «Вложенный файл» — фото, видео; в web также .doc, .xls, .pdf; несколько файлов на пункт.
- ⚠ Добавлять/удалять чек-лист в заявке вручную — **только в web**; в МП нет.
- МП: чек-листы в панели навигации заявки; заполненный — зелёная галочка; офлайн — заполняются (кроме фото и полей-справочников [user/OfflineMode]), значок синхронизации.
- Контроль: требование стадии «Обработаны чек-листы» (не перевести на «Выполнена», пока не заполнены все пункты) [admin/StageType]; RW для поля «Чек-листы» на «В работе» — нельзя перейти, пока не заполнен один пункт [user/Checklists].
- В печатной форме — блок «Чек-листы» [user/PrintingFormDesigner]; в экспорте медиафайлов — папка чек-листов [user/Export].

**Дополнительные поля** [user/AdditionalFields]: `Путь: Консоль → Настройки системы → Дополнительные поля → «Создать поле»`. Сущности: Компании, Объекты/оборудование, Заявки, Выполненные работы, Чек-листы (атрибуты), Договоры, Сотрудники, Заказчики. Одно поле — на несколько сущностей. Типы: Строка, Целое число, Дробное число, Дата, Дата и время, Значение из списка (один/несколько), Многострочный текст, Переключатель, Вложенный файл, **Значение из справочника** (Объекты/Оборудование, Компании, Сотрудники, Заказчики, Материалы; «Разрешить выбирать несколько значений»; применимо для Заявок, Договоров, Компаний, Выполненных работ, Объектов, Чек-листов; **недоступно офлайн**), **Рисунок** (создаётся/правится только в МП; в web — просмотр, масштаб, скачивание). «Единица измерения» — необязательно. «Показывать в паспорте объекта» — только для полей объекта. ⚠ «Тип поля» не меняется — создать новое, старое удалить.
- В объекте: вкладка «Дополнительные поля» → «+Добавить поле» (поле добавляется в карточку явно).
- В заявке: видимость и обязательность — через «Поля на форме заявки» (доп. поля внизу таблицы); участвуют в фильтрах и поиске, выводятся в таблицу списка [user/Filters], [user/TicketsListView]; видны в МП.
- В компаниях и договорах — внизу карточки, доступны для существующих и новых записей.
- Через API: `POST fsm/WORK/taskAttributes`, список — `GET fsm/COMMON/Attributes/?isRelevantForTask=true&isDeleted=false` [admin/ExampleRequestsAPI].
- Доп. поле с названием `_NFC` поддерживает сканирование NFC-карт в МП (в т.ч. офлайн) [user/OfflineMode].

## Склады, материалы, списание, Data Matrix

Раздел «Склады» на странице [user/Warehouses] — заглушка без содержания.

Вручную: «Создать склад» («Название склада», «Адрес склада», «Пользователи склада»: Никто / Все / По списку — минимум один сотрудник, «ERP ID», «Выбрать основным складом»); «Создать материал» («Наименование», «Описание», «Артикул», «Единица измерения» — по умолчанию «Штука», «Стоимость», «ERP ID», «Маркируемый материал»); копирование материала переносит и ERP ID. Список: «Номенклатура/код», «Склад/код», «Импортировано», «Кол-во на складе», «Стоимость», «Единица измерения»; поиск только по названию или коду [user/MaterialsNew].
- ⚠ Повторная загрузка с другими кодами номенклатуры создаёт **дубли**. Корректировка остатков: «Экспорт материалов» → правка → «Импорт материалов». Убрать материал — количество 0; удалить загруженные данные — только по запросу в поддержку [user/Materials].

**Доступ**: склады сотрудника — карточка «Квалификация», блок «Доступные склады» (без них расход не указать) [user/Materials]; полномочие «Все склады» — видит все [admin/Powers]. МП: меню «Склады» — доступные склады и остатки [user/Materials].

**Рекомендованные материалы** [user/TicketWithMaterials]: вкладка «Необходимые материалы» («Добавить материалы», склад или все); **не списываются** и не учитываются в расходе; видны в МП; видимость вкладки — поле «Необходимые материалы на форме заявки».

**Списание** [user/Withdrawals]: только через выполненную работу, блок «Израсходованные материалы» → «Добавить материалы» → количество и стоимость → «Выбрать» → сохранить заявку. ⚠ **Допускается уход остатков в минус**. Склад у добавленного материала меняется в выпадающем списке (только склады, где есть этот материал). Отчёт `Склады → Расход`: заявка, когда загружены, с какого склада, количество, сотрудник, объект; ссылка на заявку. Права — блоки «Материалы и склады» и «Выполненные работы и стоимости» [user/SettingsWithMaterials].

**Складские документы** [user/WarehouseOperations]: `Склады → Складские документы` (web). ⚠ На данный момент доступен **только «Оприходование»**; «Списание», «Перемещение» и «Инвентаризация» — «в разработке»/«скоро». Список: номер, тип, тип операции, статус (Черновик/Проведён), ответственный, даты, со склада/на склад, комментарий; фильтры, по умолчанию «Скрыть удалённые». Удаление проведённого документа автоматически отменяет проведение и пересчитывает остатки; критичные действия подтверждаются.
**Оприходование** [user/WarehousesGoodsReceipt]: шапка «Номер» (авто при проведении или вручную), «Дата и время» (обязательно; подставляется текущее), «Склад» (обязателен; до выбора блок материалов и сохранение недоступны), «Тип операции» (обязательно), «Ответственный» (текущий пользователь), «Заявка» (необязательно). Материалы — модальное окно с поиском по наименованию и артикулу, можно «Создать материал»; при смене склада позиции сохраняются. Проведение требует склад, номер, дату, ответственного и хотя бы одну позицию с количеством > 0.

**Два сценария складского учёта** [user/InventoryAccounting], [user/MaterialsNew]: (1) есть 1С (ERP, Торговля, УНФ) — интеграция: материалы, указанные в работах, списываются в 1С с настраиваемой периодичностью (раз в час, раз в день и т.п.), поступления обновляют остатки в HubEx; (2) нет учётной системы и поступления 1–2 раза в месяц — инвентаризация, загрузка в HubEx, расход по заявкам, сверка через выгрузку/загрузку; в период обновления остатков списывать «не рекомендуется». Вариант **«рюкзак» выездного сотрудника** — отдельный склад на каждого сотрудника.

**Data Matrix / «Честный ЗНАК»** [user/AboutDataMatrix]: сканирование кодов при списании маркированных материалов; **на тарифах выше «Минимального»**. Обязательная маркировка (по странице): с 1.09.2025 масла; с 1.10.2025 цемент, гипс, известь, сухие смеси; с 1.12.2025 герметики, монтажные пены, шпатлёвки, мастики, пасты; с 2026 — перечень запчастей. Настройка: (1) полномочие «Сканирование кодов для списания единиц материалов» (блок «Выполненные работы и стоимости»; без него элементов сканирования в МП нет); (2) признак «Маркируемый материал» в карточке материала (фильтр в списке; иконка Data Matrix в МП и web); (3) для контроля — поле «Выполнение» = RWM на нужных стадиях/ролях: переход блокируется, пока для каждого маркируемого материала число отсканированных кодов ≠ списанному количеству. Больше кодов, чем количество, добавить нельзя; дубликат кода в другой заявке/материале — понятная ошибка с деталями, остальные коды привязываются. Работает **офлайн**. В web коды видны **только для чтения**.

## Деньги и документы: стоимости, Акт, печатные формы, бренд

HubEx «фокусируется на планировании, диспетчеризации заявок, учёте оборудования и мониторинге выездных специалистов», но данные заявок могут служить основой для расчёта зарплаты, учёта материалов, фиксации обязательств заказчика, оценочной/фактической стоимости [user/Prices]. Полноценной бухгалтерии/биллинга страницы не описывают.

Составляющие стоимости работы [user/Prices], [user/ActOFAcceptance]:
- **Стоимость вида работ** — из карточки Вида работ, правится в работе; рубли без копеек;
- **Ставка исполнителя** × часы; ⚠ ставка **кратна часу, округление вверх**: 500 ₽, работа 1 ч 35 мин → 1000 ₽ (не 790) [user/ActOFAcceptance]; то же в конструкторе печатных форм: «длительность работы, округлённая вверх до целого часа»; стоимость работы — цена вида работ, **не** умножается на длительность [user/PrintingFormDesigner];
- **Материалы** — цена × количество.
Несколько исполнителей в одной работе — время одно на всех, каждому в Акте [user/SeveralEngineers]. Валюта ставки задаётся при импорте сотрудников («Ставка сотрудника», «Валюта ставки») [user/Import]; вводить ставку и стоимость вида работ можно «только в российских рублях» [user/Prices].

**Акт выполненных работ** [user/ActOFAcceptance]: вкладка заявки; формируется автоматически из выполненных работ (нужна хотя бы одна); шапка — банковские реквизиты исполнителя (из карточки Компании); работы, материалы, ставки; «Печать». В Акте предусмотрена «функция оплаты … с помощью QR-кода». В МП исполнителя — тот же Акт; «Получить подпись» → «ФИО подписанта», должность (необязательно) → подпись пальцем, телефон повернуть на 90° влево; подпись затем видна в web. «Поделиться» — Акт как PNG в мессенджеры/галерею. Требование стадии «Подписан акт выполненных работ» блокирует переход до подписи [admin/StageType]. Кто подписывает (МП исполнителя или только МП заказчика) — страницы расходятся (см. расхождения). Печать акта — и из клиентского портала [user/CustomerWeb].

**Оценочная/фактическая стоимость** — системные справочные поля заявки (оценочную, например, ставит диспетчер до выезда, фактическую — исполнитель после) [user/Prices].

**Расчёт зарплаты** [user/Prices]: фильтр заявок по исполнителю и периоду («Состояние заявки» = «Все заявки») → расширенный экспорт с флажком «Выполненные работы» → в Excel вкладка «Выполненные работы» (ставки, стоимости видов работ, часы; строки других исполнителей удалить) → формулы. Пример сдельной оплаты 40% от суммы видов работ.

**Стандартные печатные формы** (меню «Печатные формы»; полномочия в блоке «Аналитика») — построены как отчёты с панелью «Параметры» и кнопкой «Просмотр отчета» (нажимать после каждого изменения); печать «Файл - Печать», экспорт `Главная → Экспорт` (pdf, xlsx, docx, xml…; для правки — docx); выгрузка .xml/.csv/.xls для загрузки в 1С. ⚠ «При подключении» доступно ограниченное число фильтров — расширение через поддержку [user/PrintedFormAct], [user/PrintedFormActOfAccounting], [user/PaymentInvoice].
- **Сервисный акт** [user/PrintedFormAct]: подробности работ, трудозатрат, материалов; за период **по одному заказчику** (компании с типом «Заказчик» или «Наша компания»); «Объект» — только родительские (дочерние включаются); «Стадия» + «С/По» — заявки с переходом на стадии в диапазоне; ручной выбор заявок; «Компания» (наша, реквизиты в шапке); «НДС»: «Без НДС», «Без НДС (вычитание НДС)», «НДС сверху», «НДС включен». Логотип компании в левом верхнем углу (иначе логотип HubEx). Унифицированная форма — Бухгалтерский акт.
- **Бухгалтерский акт** [user/PrintedFormActOfAccounting]: унифицированная форма с реквизитами п. 2 ст. 9 402-ФЗ; стадия по умолчанию «Выполнена» (действие «Завершить работу по заявке»); «Тип акта»: «Сводный акт» / «По каждой заявке»; «№ акта» (по умолчанию из номера заявки; введённый — перед номером); НДС — те же 4 варианта.
- **Счет на оплату** [user/PaymentInvoice]: по выполненным работам отобранных заявок одного заказчика; «Тип счета»: «Сводный счет» / «По каждой заявке»; «№ счета», «Компания», НДС.

**Конструктор печатных форм** [user/PrintingFormDesigner] — раздел «Печатные формы»: шаблон документа для **любой заявки** с автоподстановкой данных.
- Список форм: поиск, вкладки «Все»/«Опубликованные»/«Черновики», переключатель «Активна» (только у опубликованных; выключенная пропадает с заявок и из МП, но не удаляется), «Дублировать» (копия-черновик со всеми настройками), «Удалить» (безвозвратно); 25/50/100 на странице.
- Настройки: название (и имя файла), описание, «Мобильная», «Доступ по ролям», ориентация (книжная/альбомная), «Пустые значения» («Прочерк» `_________` / «Не отображать»), «Редактируемая» (правка текста готовой формы перед печатью **без сохранения**). Широкая таблица (>5 колонок в книжной) — подсказка «Сделать альбомной».
- Редактор: начертания, шрифт/размер 6–120 пт, стили, выравнивание, списки, таблицы, картинки, линия, **разрыв страницы** (автоматических границ страниц нет), ссылки, «Исходный HTML».
- **Переменные** (плашки): панель с поиском, ввод `{{` или `@` с подсказками, уточнение `{{Компания-заказчик | ИНН}}`. Группы: Заявка (номер, описание, статус, стадия, тип, адрес, заявитель, исполнители, даты, стоимости, трудозатраты, оценка, договор и статус договора), Объект (серийный номер, гарантия, адрес, тип, класс, ответственный, план), Компания-заказчик/плательщик/получатель и их банки, Договор, Выполненные работы (таблица, блок «Выполнение», суммы, вложения), Материалы работ (в т.ч. склад, кто взял), Контакты заявки/заказчика/объекта, Исполнитель/Инициатор/Составитель (Составитель — кто печатает) с трудоустройством и доп. полями, Исполнители заявки, Чек-листы, Подпись (картинка, ФИО, должность), QR-код объекта, История стадий/статусов, Документ (дата формирования), доп. поля заявки/объекта/компаний/работ.
- Настройка переменной: числа/деньги — формула и «Знаков»; даты — `DD.MM.YYYY` или `D MMMM YYYY`, время `HH:mm`; трудозатраты — чч:мм:сс / минуты / часы / дни; человек — проекция (ФИО, фамилия, имя, инициалы, телефон, email); список людей — все/первый/по строкам; адрес — координаты; переключатель — 4 вида.
- Таблицы из списков (работы, контакты, материалы, история): выбор и порядок столбцов, переименование заголовков, строка итогов, «+ Ручная колонка» (Текст/Число/Деньги/Формула/Дата/Да-Нет); режим «Только первое значение». Нет данных — одна строка прочерков.
- Блоки: «Выполнение» (по каждой работе: объект, даты, таблица, опционально исполнители со ставкой и часами, материалы, комментарий; итоги «Σ стоимость работ», «Σ стоимость материалов», «Σ стоимость исполнителей», «Итого к оплате»); «Чек-листы» (все или только выполненные; столбцы; вид отметки) или таблица одного чек-листа; картинки-вложения; подпись; план объекта; QR-код объекта.
- **Формулы**: числа, + − × ÷, скобки, числовые переменные, поля текущей строки таблицы; отсутствующее значение или деление на ноль → прочерк (не 0).
- **Колонтитулы**: три зоны, простые переменные, «№ стр.», «всего стр.»; ⚠ настоящие номера страниц **только в DOCX**; в PDF и при печати на месте номера «1»; высота 12 мм; в окне печати снимать галочку «Колонтитулы» браузера.
- Автосохранение черновика **в браузере** (только этот браузер/компьютер); не заменяет «Сохранить».
- Публикация: «Опубликовать» (черновик) → далее одна кнопка «Сохранить», **меняет форму у всех сразу**; выключенная — «Сохранить» (без эффекта для пользователей) и «Включить». Роли применяются только основной кнопкой. «Мобильная» — форма в МП у тех же ролей.
- На заявке: «Скачать DOCX» («Название формы — Номер заявки.docx», A4, поля 15 мм; ⚠ не на 100% идентичен экрану — для точной раскладки PDF), «PDF / Печать» (в МП кнопки печати нет), «Редактировать». Время в датах — по часовому поясу компьютера; деньги — 2 знака, без знака валюты; оценка `4.5/5`.
- Нужна иная логика — кастомная форма через менеджера (индивидуальная доработка).

**Бренд компании** [user/Branding]: свой логотип в web и мобильном; ⚠ **обязательное условие — подписка «Корпорация»**. Форматы: МП — .png 364×64 px; web — .svg 91×32 px (шрифты преобразовать в кривые). Логотип отправляется в поддержку help@hubex.ru. Отображается: «в web-приложении, в Сервисном акте, в Отчете для клиента, в Акте выполненных работ». Готовые QR-стикеры с логотипом заказываются кнопкой «QR-стикеры на вашем оборудовании» → «Заказать QR-стикеры» [user/CreatingObjTemplates].

## Мобильное приложение исполнителя: офлайн, геолокация, маршрут, трекинг

**Офлайн-режим «HubEx исполнитель»** [user/OfflineMode]:
- ⚠ **Войти без сети нельзя** («Отсутствует подключение к сети») — логиниться до выезда в зону без связи; убедиться, что заявки загрузились в кэш: облачко зелёное — загружено, голубое — в процессе/ждёт синхронизации, красное — ошибка (обратиться в поддержку).
- Ручной переключатель «Офлайн-режим» в боковом меню; автоматическая попытка вернуться в онлайн — через **30 минут**; сбрасывается при закрытии/длительном сворачивании приложения.
- Доступно офлайн: список заявок вкладки «Мои»; редактирование «Описание» и доп. полей типов числовое, дата и время, текстовое, переключатель, «Рисунок» (в т.ч. подпись) — по правам текущей стадии, права сохраняются при офлайн-переходе; NFC для полей `_NFC`; выполненные работы с материалами и фото (и их правка в том же сеансе); чек-листы, **кроме фото и полей-справочников**; **переход на одну стадию вперёд** (пример «Новая» → «Принять заявку»). Смена стадии видна сразу с синим облаком до синхронизации. Очередь отправки синхронизируется без потери данных; время офлайн-перехода — в истории изменений.
- ⚠ Недоступно офлайн: доп. поля «Значение из справочника» (чек-листы, работы, объекты); открыть карту маршрута [user/RouteToObject].
- Data Matrix сканируется офлайн [user/AboutDataMatrix]. При отсутствии сети висит уведомление «Нет подключения к интернету», работы и чек-листы всё равно заполняются [user/AttachingFiles], [user/Checklists].

**Геолокация** [user/GEOinMob]: ⚠ работа с заявками в «HubEx исполнитель» **возможна только при включённом доступе к геопозиции** — без неё нельзя принять заявку, выехать и т.д. (iOS — «Геопозиция: Всегда»; Android — разрешение «Местоположение»). Корректность — при флажке «Отслеживать местоположение сотрудника» в карточке. На Samsung/Xiaomi — нескрываемое уведомление «Центр геолокации» (можно отключить в настройках уведомлений, оставив уведомления по заявкам). Энергосбережение/оптимизация батареи мешают GPS — инструкции для HTC, Huawei, LG, Samsung, Sony, Xiaomi [user/GEOinMob], [user/Geotracking]. Подробные пошаговые настройки iPhone, Samsung, Xiaomi, Huawei (Wi-Fi включён для точности, «Разрешать в любом режиме», точное местоположение, отключение экономии трафика, режима сна, адаптивного режима; PDF-версия инструкции) — [user/GeoSettings]; источники: GPS, ГЛОНАСС, GSM, Wi-Fi; точки перемещения передаются «с точностью до 10 метров». Для других Android — по аналогии с Xiaomi/Huawei.

**Маршрут до объекта** [user/RouteToObject]: в заявке — область карты под «Адрес» → кнопка перехода в навигатор (Яндекс Карты, 2ГИС, Google и др., установленные на устройстве); первый выбор становится по умолчанию, смена — профиль → «Приложение для навигации». Офлайн карта не открывается.

**Где видеть местоположение сотрудников** [user/UserOnMap]: (1) `Карты → Карта` — текущее положение [user/GeoPosition]; (2) «Заявки на карте» в «Все заявки» [user/TicketsOnMap]; (3) в заявке «Выбрать исполнителя из списка» → «Показать исполнителей на карте». В МП исполнителя и заказчика — карта под адресом заявки, иконка сотрудника показывает его текущую геопозицию [user/GeoPosition], [user/CustomerApp]. Нет пункта «Карты» — полномочие «Пункт главного меню - Карта» [user/GeoPosition]. Для отображения: флажок отслеживания в карточке + разрешение в телефоне.

**История перемещений (геотрекинг)** [user/Geotracking]: **только web**, `Карты → История перемещений` (полномочие «История перемещений» в блоке «Аналитика» [admin/Powers]). Сотрудник + дата (по умолчанию сегодня, глубина **до года назад**); линия маршрута (зелёная точка — начало, красная — конец; подсказка со временем точки). Слои «Показывать объекты» и «Показывать заявки» (после выбора сотрудника). **Пробег за день** считается автоматически по точкам; экран «Пробег» — сводная таблица пробега всех мобильных сотрудников за дату. Пробег — по GPS приложения, нужно «Отслеживать местоположение». Используется для анализа времени в пути, на заявке, остановок, простоев. Местоположение исполнителя при действиях в МП — в «История изменений» («На объекте»/«Вне объекта») [user/HistoryOfChanges].

## Каналы подачи заявок и клиентский контур

Сводка каналов для заказчика [user/AlternativeWays], [user/CustomerApp], [user/CustomerWeb]: приложение «HubEx заказчик», клиентский портал (web), QR/паспорт объекта без приложения, email, Telegram-бот [admin/TelegramIntegration], форма на сайте (подключается через поддержку; поля могут отличаться от примера) [user/AlternativeWays]. Плюс внутренние: web, МП исполнителя, импорт, API, Битрикс24, плановые.

**Клиентский портал** [user/CustomerWeb]: вход после регистрационного письма («Подтвердить» → пароль) или SMS; меню «Заявки», «Сообщения», «Аналитика»; видны все заявки **своей компании** со сроками и статусами. Создание: «Тип заявки», «Критичность заявки», «Описание заявки»; блок «Обслуживание заказчика»: «Заказчик» (своя организация), «Объект», «Вид работ», «Договор». Чат по заявке; меню «Сообщения» со значком непрочитанного; печать Акта; «Аналитика – Отчет для клиента». Для заказчиков есть готовая PDF-инструкция (регистрация, портал, приложение).

**Приложение «HubEx заказчик»** [user/CustomerApp]: вход «Вход по логину и паролю» (после подтверждения регистрации) или по одноразовому коду при регистрации по телефону. Вкладки: «Мои», «Согласование», «Все» (заявки своей компании и своих объектов, в т.ч. созданные коллегами), «Избранное», «Архив» (закрытые). Создание: выбрать объект из списка или сканировать QR → «Тип заявки», описание → «Создать заявку». Карта с исполнителем; чат (push о новых сообщениях); «Отменить заявку» (зависит от настроек ЖЦ); после внесения работ — «Принять работы» / «Не принимать работы» (возврат на доработку), подпись Акта на вкладке «Акт работ» (альбомная ориентация); оценка «Оцените качество исполнения заявки» (звёзды: качество и оперативность, комментарий). Лента уведомлений — только настроенные для заказчика уведомления [user/NotificationInMob]. По умолчанию в приложении заказчика **паспорт объекта при сканировании QR недоступен** [user/CreatingTaskTemplates].

**QR-коды** — три процесса [user/QRcodeMain], [user/HowToMakePassport]: (1) ввод новых объектов через МП исполнителя («Приемка и маркировка»); (2) подача заявок и просмотр паспорта в МП исполнителя и заказчика; (3) подача заявок незарегистрированными через любой сканер. Можно использовать уже наклеенный, не использованный ранее QR или распечатать свой.

**Шаблон заявки + QR** [user/CreatingTaskTemplates]: шаблон — образец заявки с полями «Тип заявки», «Объект», «Заказчик», «Вид работ», «Критичность», «Описание заявки», «Исполнитель»; привязан к объекту через QR; нужен и для email-интеграции. Создание: карточка объекта → вкладка «QR-коды» → «Маркировать», или `Заявки → Маркировка → «Создать QR-код»`. Поля: «Описание QR-кода»; «Опубликовать» (публичный паспорт — неполный — виден любому при сканировании; иначе только зарегистрированным); «Разрешить подачу заявки из Web» (кнопка «Подать заявку» в мобильном браузере); тип, заказчик, объект, вид работ (из карточки объекта), критичность, описание (правятся при подаче); «Приглашение» (из `Пользователи → Приглашения`, с ролью — например «Заказчик» — и участком) — даёт регистрацию; «Разрешить саморегистрацию» + «Разрешить регистрацию без верификации» — пользователь выбирает регистрироваться или «Не получать уведомления»; «Обязательная саморегистрация по QR-коду» — регистрация через EMAIL или СМС обязательна, «Не получать уведомления» скрыта. После сохранения — QR, «Скачать QR-код», поле «Код шаблона» (связь шаблона заявки и шаблона объекта). Массовая выгрузка QR — экспорт в .zip. ⚠ QR без привязки к объекту — паспорт пустой. Привязка существующего QR к объекту через МП автоматически создаёт шаблон — **неопубликованный**, без типа, вида работ, приглашения и разрешения подачи (дозаполнить). Паспорт по QR доступен при включённом в роли «Электронный паспорт оборудования» (и для роли из Приглашения). «История обслуживания» в паспорте — только в приложении исполнителя.

**Подача без приложения и саморегистрация** [user/SelfRegister], [user/HowToMakePassport]: камера/сканер → паспорт → описание, фото → «Продолжить» → каналы связи: «Не получать уведомления» (разово) или Email/СМС → письмо/SMS → пароль + **обязательная галочка согласия с политикой конфиденциальности** (по умолчанию не отмечена) → «HubEx заказчик». Условия: шаблон публичный; для регистрации — Приглашение в шаблоне; включён **Анонимный пользователь** (`Консоль → Интеграция → Служебные пользователи`: «Роль» — например «Заказчик», присваивается при регистрации; «Участки») [admin/ServiceUsers]. Новый пользователь — в «Пользователи → Заказчики». В заявке: «Метод подачи заявки» = «Паспорт объекта», инициатор — ФИО при регистрации [user/AlternativeWays]; если контакты не оставлены — инициатор пуст, выбирается вручную [user/UsersRequests]. Зарегистрированный, указавший свои данные, получает push для подтверждения подачи [user/HowToMakePassport]. **Индивидуальный электронный паспорт** (фирменный стиль, доп. разделы, заказ услуг/расходников, сервисные контракты) — услуга по запросу [user/HowToMakePassport].

**Шаблоны объектов и «Приемка и маркировка»** [user/CreatingObjTemplates]: `Объекты|Оборудование → Шаблон объектов и оборудования` — образец карточки (родитель, компания-владелец, тип, участок, вид работ, ответственный, гарантия, класс, мобильность, доп. поля). МП → «Приемка и маркировка»: «Продолжить без маркировки» (по шаблону или без), «Новое оборудование» по QR, «Существующее оборудование» (привязать QR). ⚠ Объекты из МП создаются **неопубликованными** — опубликовать в web (фильтр, оранжевый маркер, «Опубликовать»). Меню МП — полномочие «Пункт главного меню в мобильном приложении - Приемка и маркировка» [admin/Powers].

**Email** [admin/TicketMail]: два способа.
- **Пересылка**: адрес-ящик, созданный HubEx для тенанта (`Консоль → Интеграция → Интеграция по электронной почте`); переадресация с вашего ящика (Gmail: «Пересылка и POP/IMAP», подтверждающая ссылка приходит **как заявка** в HubEx; Яндекс: «Правила обработки писем»); фильтры отправителей/тем на стороне почты. Заявки — по единому шаблону «Шаблон для получения заявок по электронной почте через пересылку» (`Заявки → Маркировка`; по умолчанию неопубликован, тип — первый созданный, вид работ — «Основной», критичность — «По умолчанию»). Нужен «Пользователь API» (роль с максимальными правами, все участки, **токен не нужен**). Для каждого нового адреса создаётся карточка Заказчика, ему уходит ссылка на регистрацию.
- **IMAP**: подключение своего ящика как «Адрес сбора заявок», индивидуальные шаблоны под заказчиков, **двусторонняя** переписка (сообщения в чате с заказчиком уходят письмом; параметр «Возможность ответа заказчику через чат» из формы адреса отправителя удалён [ReleaseNotes/ListOfChanges03112026], [admin/TicketMail] его ещё описывает). Рекомендуется **yandex.ru** (другие «могут работать нестабильно» — ставить пересылку на Яндекс); ⚠ **нельзя** outlook.com и **mail.ru**. Яндекс: доступ почтовым программам + пароль приложения; Хост imap.yandex.ru, Порт 993, SSL/TLS. Шаблон обязан иметь Объект и Вид работ (иначе не выбрать в интеграции); общий шаблон — пустые Заказчик/Объект или «ваша компания + объект „Для почты“». «Отправитель»: конкретный адрес, `*@yandex.ru` или `*@*` (для общего шаблона). «Разрешить получение писем». «Настройка регулярных выражений» (парсинг объекта, вида работ, срока из письма) — через поддержку. Тумблер выключает без удаления. ⚠ **Прочитанное письмо в ящике сбора не превращается в заявку**. Подавший заявку с незарегистрированного адреса получает ссылку регистрации.
- Gmail при входе HubEx может требовать «Ненадежные приложения… Открыть доступ (не рекомендуется)» [user/HowToManageGmailIntegration].
- **Ящик и триггеры** [ReleaseNotes/ListOfChanges03112026]: настройка ящика определяет только адрес приёма и отправки; событие, получатели, тема, содержание, вкл/выкл уведомлений — в триггерах (стандартные — см. раздел уведомлений). Письмо о создании заявки — триггер события «Заявка создана», и для заявок по почте, и для созданных сразу в HubEx; уведомления при изменении статусов в сценарии пересылки — тоже через триггеры.
- **Ответ на письмо** [ReleaseNotes/ListOfChanges03112026]: клиент может ответить на email-уведомление, в т.ч. по заявке, созданной в HubEx, а не с почты. HubEx находит заявку по идентификатору, проверяет отправителя и его доступ, добавляет текст и вложения в чат: ответ заказчика — в чат с заказчиком, сотрудника — в чат команды. Ящик — компании или выданный формата `***@client.hubex.ru`, настроенный для приёма входящих. Ответ не попадёт в чат: нет включённого ящика для приёма ответов; письмо не связать с заявкой; отправитель неизвестен HubEx; нет доступа к заявке. Вложения добавляются, если каждый файл не больше 50 МБ.

**Telegram** [admin/TelegramIntegration]: `Консоль → Интеграция → Приложения → Telegram → «Создать связку Telegram»`; бот создаётся через @BotFather (никнейм на английском, оканчивается на «bot»), API Token вставляется в связку. Можно несколько ботов (разные Тип заявки и Критичность). Ответы бота: запрос телефона, «Спасибо, заявка принята!», сообщение о закрытии (тексты редактируемы). Пользователь делится контактом → ищется по телефону; нет — создаётся заказчик (ФИО из Telegram). Первое сообщение → заявка (заполняются только «Тип заявки», «Критичность», «Описание заявки», «Инициатор»; «Метод подачи» = «Телеграм»); дальнейшие — в чат с заказчиком до закрытия; ⚠ **нельзя две активные заявки подряд** — новая только после закрытия. Ответы диспетчера/исполнителя и файлы — приходят в бот. Тип у созданной заявки не меняется, критичность — меняется. Работает в web и мобильном Telegram.

## Уведомления, сообщения, шаблоны ответов, рейтинг

**Оповещения** [admin/Notifications]: любое событие (переход стадии, назначение, изменение времени) → **email** или **push** (МП / web). `Путь: Консоль → Настройки оповещений`. Два шага:
1. **Правило выбора получателя**: «Получатели уведомления» (одна категория, например «Выбранный исполнитель по заявке», «Обратившийся пользователь» = инициатор [admin/TicketsAgreement]), «Пользователь, который получит уведомление», «Роль, которая получит уведомление», «Email адреса», «Номера телефонов» (через запятую). ⚠ Указан пользователь **и** его роль — придёт **2 уведомления**.
2. **Триггер уведомления**: «Описание сообщения» (готовый шаблон), «Заголовок»/«Текст сообщения» с разметкой (`@Model.TaskNumber`, `@Model.AssetFullName`, `@Model.TaskNotes`, `@Model.NavigateToTaskForm()` [admin/TicketsAgreement]) — разметку не удалять; ⚠ **правка текста шаблона меняет его во всех триггерах** с этим шаблоном — копировать в новый шаблон. «Способ отправки» Push/Email; для Push — «Куда отправлять» (например «Мобильное приложение инженера»). «Условия отправки»: «Событие, из-за которого сработает триггер» («(отложенное)» — придёт спустя пару минут, на случай ошибочного назначения), критичности, стадии. ⚠ Заданы и событие, и стадии — **2 уведомления**. Можно несколько правил получателей. Триггеры выключаются переключателем.
- **Стандартные email-триггеры** — созданы автоматически для всех компаний [ReleaseNotes/ListOfChanges03112026]: «Email: триггер создания заявки» (инициатору), «Email: триггер закрытия заявки» (переход на стадию с действием «Закрыть заявку»; инициатору), «Email: триггер сообщения по заявке (чат с заказчиком)» (заказчику), «Email: триггер сообщения по заявке (чат с командой)» (всему списку наблюдателей). Включаются по умолчанию: компании с действующей подпиской, начавшейся 01.04.2026 или позже; компании, где за последние 6 месяцев создана хотя бы одна заявка со способом подачи «Электронная почта». Для остальных созданы выключенными, включаются вручную; без активной email-интеграции — созданы, но выключены. ⚠ Почтовый ящик сам по себе не включает триггеры (см. расхождения). После обновления рекомендуется проверить: ящик для приёма ответов включён, триггеры созданы и включены, получатели настроены, адрес для ответа корректен.
- Настраивать под одной учёткой в web, проверять под другой в МП.
- Быстрый рецепт email о выполнении: включить «Включить Email-уведомления» в меню аватара → скопировать триггер «Уведомление заявка выполнена» → «Способ отправки» сначала «Не выбрано», затем «Email» + кнопка «М» [user/HowToManageNotifications].
- Не приходят push — разрешить уведомления приложения в настройках телефона, выйти из приложения и войти заново; проверить правила и триггеры [user/HowToNotificationsToMobile], [user/HowNotificationsToMobile].
- Webhook'и: меню `Интеграция → Webhook'и` (по полномочиям) [admin/Powers]; сервис `MSG` в API — уведомления, Webhook, триггеры [admin/StartIntegrationAPI]. Детальной настройки webhook на страницах нет.

**Ленты уведомлений**: МП исполнителя (меню → «Уведомления»; push- и SMS-уведомления; создание, назначение, снятие назначения, стадии, сообщения; «Прочитать все», «Только непрочитанные»; есть и у заказчика — только настроенные для него) [user/NotificationInMob]; web — колокольчик, показываются только события с настроенными триггерами [user/NotificationInWeb]. Push при смене стадии — всем связанным [user/ChangingStatus].

**Сообщения по заявке** [user/Messages]: вкладка «Сообщения» (счётчик непрочитанных), меню «Сообщения» со всеми чатами («Прочитать все»); в МП — иконка в заявке и пункт меню. Участники — «Добавить»/корзина; ⚠ нельзя удалить назначенного исполнителя и инициатора. Фото **от 1 до 10 в сообщении**, видео; в МП «Сделать снимок/видео», «Открыть галерею». **Разделение на «чат с командой» и «чат с заказчиком» — «открывается по запросу»**: заказчик видит только чат с заказчиком; сотрудник — с командой, если добавлен, с заказчиком — если есть полномочие; в web чек-боксы «Также отправить сообщение команде/заказчику». Полномочия «Чат с заказчиками», «Чат с сотрудниками» (блок «Сообщения»). API: `isExternal` false — команда, true — заказчик [admin/ExampleRequestsAPI]. Telegram — через чат с заказчиком [admin/TelegramIntegration]; ответы по почте — в чат с заказчиком или чат команды, по отправителю [ReleaseNotes/ListOfChanges03112026].

**Шаблоны ответов** [user/AnswerTemplate]: `Сообщения → Шаблоны ответов → «Создать шаблон»` или кнопка «Шаблоны ответов» в чате; обязательны название и текст; для типов заявок «Для всех» / «По списку»; шаблон вставляется в поле ввода, правится перед отправкой; работает в чате с командой и с заказчиком.

**Оценка и рейтинг** [user/Rating]: оценка — на стадиях «Выполнена» и «Закрыта» в web и в МП заказчика; пятибалльная шкала + «Комментарий». Критерий по умолчанию «Качество выполненных работ»; свои — `Консоль → Настройки заявки → Критерии оценки заявки`. Итог по критериям и рейтинг сотрудника — **среднее арифметическое**. Рейтинг в списке/карточке сотрудника и в профиле МП; ⚠ только у сотрудников с «Мобильный сотрудник». В МП заказчика — «качество и оперативность» [user/CustomerApp]. Используется в «Общей аналитике», «Отчете по сотрудникам» (HubEx Рейтинг) [user/GeneralAnalytics], [user/EngineersAnalytics].

## Аналитика и отчёты

Отчёты в меню «Аналитика»; доступ — по полномочиям блока «Аналитика» [admin/Powers]. «Общая аналитика», «Отчет по объектам», «Отчет по сотрудникам», «Анализ эффективности процессов», «График действия договоров» — на **Power BI**, данные обновляются **раз в сутки** [user/GeneralAnalytics], [user/ObjectsAnalytics], [user/EngineersAnalytics], [user/ProcessEfficiency], [user/ContractSchedule]. «Отчет для клиента» — расчёт **в момент открытия** и при смене фильтров [user/ClientsAnalytics]. Свои отчёты — «Мои отчеты» (плагины/индивидуальные отчёты) [admin/Powers]; Power BI/Superset самостоятельно — только on-prem/выделенные [admin/AboutHubEx].

- **Срез по заявкам** [user/TicketsReport]: заявки по стадиям, просроченные, время выполнения по объектам, по компаниям, загрузка исполнителей.
- **Общая аналитика** [user/GeneralAnalytics]: период, фильтры («Тип заявки», «Участок»…). KPI: «Среднее время выполнения работ» (по вкладке «Выполнение»), «Среднее время закрытия заявки» (создание → закрытие), «Коэффициент полезной загрузки исполнителей» (Utilization Rate = длительность выполненных работ / часы по графикам; фильтр только по исполнителям), «Количество выполненных заявок на исполнителя» (в день, на среднедневное число исполнителей по графику), средняя оценка (прочерк, если рейтинг не используется). Динамика (поступившие, закрытые, незакрытые, пунктир прошлого периода), «Аналитические разрезы по поступившим заявкам» (цепочка разрезов, «Режим фокусировки»), круговые по типам/критичности/видам работ. Мини-диаграмма просроченных — фильтр.
- **Отчет по объектам обслуживания** [user/ObjectsAnalytics]: «Количество объектов», «Среднее количество активных объектов» и «…родительских» (активный — хотя бы одна заявка за последние **4 недели**, настраивается 1–7), **MTBF** (среднее время между заявками), **MTTR** (среднее время выполнения работ). Диаграмма «Поступившие заявки и скорость их закрытия» (разрез тип/объект/класс), таблица по объектам (плоская/иерархическая; экспорт только плоской), детальный отчёт по объекту (паспорт, карта, исполнители, список заявок), карта объектов с заявками за период.
- **Отчет по сотрудникам** [user/EngineersAnalytics]: вкладки «Заявки и SLA» (закрытые, открытые, **переназначенные** — снятие назначения/отказ, % закрытых с просрочкой, рейтинг; квадранты «Сравнение эффективности исполнителей»; средние по дням недели), «Отработанное время» («Отработано всего» — с учётом пересечений, «Выполнено работ» — без, «Переработки» — часы работ вне графика, средняя переработка и загрузка в день), «Показатели и KPI» (мобильные/офисные сотрудники, Utilization Rate — межотраслевой стандарт 80%, **HubEx Рейтинг** по 4 показателям: закрытые заявки, % нарушений SLA, часы работ, оценка; 1 — лучший; можно для премирования), отчёт-карточка сотрудника. Экспорт таблиц в Excel. Корректность — при заполненных графиках и выполненных работах.
- **Анализ эффективности процессов** [user/ProcessEfficiency]: процесс = последовательность стадий заявки; рассматриваются **только закрытые** заявки (период — по дате создания). «Количество переходов по стадиям» по умолчанию ограничено **30 000** (больше — через поддержку). Неоптимальные варианты процессов, схема прохождения (process mining: яркость линий — время перехода, ползунок числа вариантов), среднее время на стадиях, заявки с циклами, сравнение вариантов А/В (по критичности, периодам), время между двумя стадиями.
- **Отчет для клиента** [user/ClientsAnalytics]: вкладки «Открытые» (по дате создания) / «Выполненные» (по умолчанию; по дате выполнения) / «Закрытые»; период по умолчанию — последний месяц, будущие даты нельзя; >6 месяцев — предупреждение о долгой загрузке. Показываются **только заявки доступных пользователю компаний**. Фильтры: критичность, компания-заказчик, договор, объект (без вложенных), тип оборудования, участок («Без участка»), тип заявки, вид работ, статус, «Результат SLA», «Подрядчик» (одно значение). KPI: SLA (доля в срок), «Просрочено», «Выполнено», «Время реакции» (до первого перевода стадии), «Время решения» (до выполнения); сравнение с прошлым периодом. «SLA в разрезах» (зелёный ≥85%, оранжевый 60–85%, красный <60%), «Проблемные объекты» (топ-10), кросс-фильтрация, таблица (экспорт Excel), экспорт «HTML-снимок» или «.xlsx». Доступен заказчику в портале [user/CustomerWeb].
- **График действия договоров** [user/ContractSchedule]: сроки окончания договоров, заявки вне периода договора (флажок, «Открыть список заявок»).
- **График обслуживания объектов** — в планировщике [user/PlannedTicketsSchedule].

## Интеграции: REST API, служебные пользователи, Битрикс24

**Служебные пользователи** [admin/ServiceUsers]: `Консоль → Интеграция → Служебные пользователи`. **Пользователь API** — для внешних систем и почты: тумблер, «Роли» (полномочия считываются с них; обычно максимальные), «Участки» («рекомендуем выбрать все»), «Токен доступа» → «Сгенерировать», скачать .txt. ⚠ Сервисный токен **показывается один раз** [admin/StartIntegrationAPI]. Для почты токен не нужен [admin/TicketMail]. **Анонимный пользователь** — для заявок по QR без регистрации (см. каналы).

**REST API** [admin/StartIntegrationAPI], [admin/RESTAPI]:
- Авторизация: `POST /fsm/AUTHZ/AccessTokens` на хосте api.hubex.ru (облако) с `{"serviceToken": "…"}` → `access_token` (JWT), **обновляется каждые 30 минут**; далее заголовок `Authorization: Bearer …`. В примере заголовок `X-Application-ID: 5`.
- Пагинация `fetch`/`offset`; пример `GET /fsm/WORK/Tasks?fetch=50&isClosed=false&offset=0`. Лимит «обычно 60 запросов в минуту». Ошибки — по HTTP-статусу.
- Сервисы Swagger (doc.hubex.ru), каждый со своим разделом документации: AUTHN, AUTHZ, AUTH, ADM (пользователи, администрирование), ES (компании, объекты, оргструктура, локации), PA (персонал, рейтинги, навыки), WORK (заявки, чек-листы, выполнение, вложения, назначения), WSP (графики), COMMON (справочники, доп. поля), SLA, TSTG (ЖЦ), UI, EXPORT, PMP (планировщик), MSG (уведомления, Webhook, триггеры), NEWS, WH (склады, материалы).
- Сценарии, предлагаемые страницей: CRM (Bitrix24, amoCRM) — создание заявок из лидов, синхронизация статусов; 1С/SAP — импорт оборудования, ремонты, материалы (пакетно, по расписанию); Telegram/Slack — оповещения; Zabbix/PRTG — заявки по инцидентам; свои мобильные клиенты (OAuth 2.0). Рекомендация — webhook-уведомления HubEx для асинхронности.

Примеры [admin/ExampleRequestsAPI]:
- Заявка: `POST /fsm/WORK/Tasks`; **обязательные** `TaskTypeID`, `RequestMethodID` (для интеграций рекомендуется «4»); прочие `CriticalityID`, `deadline`, `companyID`, `assetID`, `LocationID`, `WorkTypeID`, `Notes` (без HTML, для списка), `NotesHtml` (с HTML, для карточки) → 201 `{id, number}`. Изменение `PATCH /fsm/WORK/Tasks/{id}` → 202. Доп. поля `POST fsm/WORK/taskAttributes`. Следующие стадии `GET /fsm/Tasks/{taskID}/stages/next`; смена стадии `POST fsm/WORK/taskstagingHistory` (`taskID`, `taskStageID`) → `isFinalStage`, `errors`. Сообщения `POST/GET fsm/WORK/Tasks/{id}/conversation/` (`isExternal`; в оба чата — два запроса). Файлы `POST fsm/WORK/taskAttachments/upload/fromForm` (multipart, `isPublic`), список `GET fsm/WORK/tasks/{id}/attachments`, оригинал `GET fsm/COMMON/attachments/{id}?noRedirect=true`.
- Справочники ID: `GET /fsm/ES/Companies`, `/fsm/ES/Assets`, `/fsm/WORK/WorkTypes`, `/fsm/WORK/TaskTypes`, `/fsm/SLA/Criticalities`, `/fsm/ES/assetTypes`, `/fsm/ES/assetClasses`, `fsm/ES/CompanyRegistrationTypes/`, `/fsm/COMMON/banks/`, `/fsm/COMMON/Contacts/`.
- Объект: `POST /fsm/ES/Assets` (обязательны `Name`, `AssetTypeID`, `AssetClassID`, `CompanyID`; `IsAutoPublish`, `IsMobileAsset`, `IsInheritParentDistricts`); публикация `PUT /fsm/ES/Assets/{id}/publish`.
- Компания: `POST /fsm/ES/Companies` (массив; `isEmployer`, `registrationTypeID`, `name`) → массив id.
- Пользователь: `POST /fsm/ADM/Users` (`isTechnician`, `mobilityID`, `geotrackingModeID`, `rate`…) + отдельно роли `POST fsm/ADM/UserRoles/` и участки `POST /fsm/ADM/UserDistricts/`; блокировка — `banReasonID`, `banTill` (9999 — навсегда).
- ⚠ Изменение объекта, компании, пользователя — **PUT, перезаписывает все поля**: передавать полный набор текущих значений + изменённое.

**Битрикс24 — приложение из маркетплейса** [admin/IntegrationBitrix24]: в Б24 приложение HubEx → «Создать робота» (CRM → Роботы, робот «[HubEx] Создание заявки HubEx» на стадии воронки; «Сразу», «Независимо от других роботов») и «Создать новый токен»; в HubEx — API-ключ Пользователя API; web-приложение HubEx → вкладка «Интеграция с Б24» → «API-ключ HubEx» + «Токен интеграции» → «Проверить подключение» → тип заявки, воронка, стадия сделки по завершении. Поток: стадия сделки → заявка; заявка на **конечной стадии ЖЦ** → сделка на заданную стадию. Поля: название и комментарий сделки → «Комментарий»; тип — из робота; критичность — по умолчанию; компания сделки → «Компания-заказчик» (нет — **создаётся новая**). Нужны права администратора в обеих системах.

**Битрикс24 через Albato** [admin/Integration]: двусторонняя связка без разработчиков: создание заявок при смене стадии сделки, передача полей сделки (контакты, комментарий, адрес, критичность…), смена стадии сделки при выполнении, передача в сделку срока, стоимости, комментария исполнителя. Шаги: регистрация в Albato, подключение Б24, Пользователь API (все участки, токен), подключение HubEx в Albato («Токен сервисного аккаунта»), связка: триггер «Изменение/создание сделки», режим «В реальном времени», «При обновлении сделки» + «Загружать каждую сделку лишь единожды» = Да, фильтр по стадии (пример «Сервисная служба»), действие HubEx «Новая задача», сопоставление полей.

Прочее: email и Telegram — встроенные интеграции (см. каналы); 1С — через API/1С-конфигурацию [admin/AboutHubEx], складской сценарий [user/InventoryAccounting]; ERP ID/внешние идентификаторы есть у компаний, объектов, участков, складов, материалов, заявок; Automate — интеграции REST/SOAP [admin/AboutHubEx]; «Ключи» (переменные интеграции) — `Интеграция → Ключи` [admin/Powers].

## Импорт и экспорт

**Импорт** [user/Import]: только по шаблону Excel (кнопка «Импорт» в справочнике → «Скачать шаблон» → «Загрузить готовый шаблон»). Повторная загрузка дополненного шаблона не дублирует ранее загруженное. Лимиты за раз: **заявки до 2000, объекты до 2000, компании до 100**; материалы до 1000 [user/Materials]. Совместимость: Excel, Excel Online — полностью; Google Spreadsheet — частично; Mac Spreadsheet — нет; сторонние сервисы — не рекомендуются. ⚠ Вставлять из других файлов **только значения** («Параметр вставки: Значения»): обычная вставка стирает справочники шаблона. Ячейки с красным флажком — подсказки.
- Объекты: обязательны название, компания (новая создаётся автоматически), тип; класс и участок из списков (новые создаются, «По умолчанию», «Все участки»); **вид работ — только один** или «Все виды работ» (дальше — массовыми действиями); родитель; адрес; ответственный; «Мобильное оборудование» Да/Нет; часовой пояс, страна; координаты не импортируются.
- Пользователи: сотрудники и заказчики раздельно, шаблоны одинаковые; фамилия, имя; телефон (79… или 89…) или email — логин; «Тип»: «Штатный сотрудник» / «Мобильный инженер» / «Заказчик»; роль, участок, должность, график (из встроенных), «Ставка сотрудника», «Валюта ставки».
- Компании: название, «Код» (для маски номера), «ERPID», контакты, «Тип контрагента», флаги вида клиента.
- Заявки: **фоновый режим**; номер, тип (нужен хотя бы один тип), описание, заказчик (должен существовать), объект (должен существовать), часовой пояс, вид работ, критичность, стадия, «Срок исполнения» (дд.мм.гггг чч:мм), исполнитель, контактное лицо (создаётся), «Обращение от».

**Экспорт** [user/Export]: Excel; учитывает фильтры. Заявки — «Обычный экспорт» (номер, тип, описание, оборудование, вид работ, срок, критичность, исполнитель…) или «Расширенный экспорт» (выбор полей, например автор перехода на стадию; выбор и вариант **запоминаются для браузера и компьютера**); «Экспорт вложений» — архив с папкой на заявку (файлы заявки, чек-листов, выполненных работ). Объекты — обычный/расширенный. Сотрудники, заказчики, компании — отдельные кнопки. Права — полномочия экспорта/импорта в блоках [admin/Powers]. Экспорт QR — .zip [user/CreatingTaskTemplates].

## Как посадить процесс клиента на сущности HubEx: типовые сборки

Сборки составлены из механизмов, описанных на страницах; каждый шаг — с источником. Это комбинации существующих настроек, а не отдельные продуктовые режимы.

**1. Сервисная компания обслуживает оборудование клиентов по договорам (B2B).**
- Клиент → Компания вида «Заказчик»; своя → «Наша компания» с банковскими реквизитами [user/CreatingCompany]. Площадки клиента → родительские Объекты типа «Объект» (с адресом), оборудование → дочерние типа «Оборудование» [admin/ObjectsType]. Виды работ задать на типе оборудования — подставятся в новые объекты [admin/ObjectsType].
- Договор на Компанию с «Объектами по договору» и сроком; контроль заявок вне срока — «График действия договоров» [user/CreatingCompany], [user/ContractSchedule].
- Пользователи клиента → Заказчики с ролью «Заказчик»: справочники «Объекты у компаний пользователя» + «Активные заявки на объектах моей компании» [admin/Powers], [user/HiddenObjectsTicketsUsers]; подача из приложения, портала, по QR [user/CustomerApp], [user/CustomerWeb].
- Сроки по договору → SLA-правила по Заказчику/Объектам/Критичности с графиком обслуживания [admin/SLA].
- Маршрут → ЖЦ типа заявки; статусы для заказчика скрывают внутренние стадии [admin/StageVSStatus]; приёмка заказчиком — ветка действий заказчика [admin/CustomerAgreement].
- Выезд: автоназначение по виду работ/участку/ближайшему [admin/RulesOfChoice], [user/RulesOfChoiceGEO]; присутствие — требование «Отсканирован QR-код объекта» [admin/StageType]; работы, материалы, подпись в Акте [user/ActOFAcceptance].
- Документы и отчётность: Сервисный акт, Бухгалтерский акт, Счёт на оплату по заказчику за период [user/PrintedFormAct], [user/PrintedFormActOfAccounting], [user/PaymentInvoice]; «Отчет для клиента» (в т.ч. в портале клиента) [user/ClientsAnalytics].

**2. Внутренняя служба эксплуатации (АХО, ФМ, производство).**
- Объекты принадлежат «Нашей компании»; заявки от сотрудников предприятия: по QR без регистрации (Анонимный пользователь, публичный шаблон) [user/SelfRegister], email [admin/TicketMail], Telegram-бот [admin/TelegramIntegration].
- Внутренние задачи без объекта/заказчика — упрощённая форма, только «Тип заявки» [user/CreatingTicket].
- Закупки и расходы — отдельный тип с линейным/параллельным согласованием [admin/TicketsAgreement].
- Планы помещений для указания места поломки [user/FloorPlan]; паспорт объекта с документацией по QR [user/HowToMakePassport].

**3. Плановое ТО, обходы, ППР.**
- Плановая заявка на группу объектов с одним видом работ, частота, ограничение повторений [user/PlannedTickets]; обзор — «График обслуживания объектов» [user/PlannedTicketsSchedule].
- Чек-лист на вид работ/объект (автоприкрепление) + требование «Обработаны чек-листы» [user/Checklists], [admin/StageType]; показания/наработка — доп. поля с RWM [admin/ElementsOfInterface]; NFC-метки — доп. поле `_NFC` [user/OfflineMode].
- Удалённые объекты без связи — офлайн-режим (вход заранее) [user/OfflineMode].

**4. Филиалы, регионы, подрядчики.**
- Участок = город/регион/направление на Объектах, Сотрудниках, Заказчиках, Типах заявок; роли «… на участках пользователя» [admin/Places], [admin/Roles]. Разные процессы для участков — типы заявок с участками.
- Подрядные организации — Компании вида «Подрядчик», их сотрудники с этой Компанией; полномочие «Заявки, когда-либо назначенные на сотрудников моей компании» (только трудоустроенные) [admin/Powers]; фильтр/разрез «Подрядчик» в Отчете для клиента [user/ClientsAnalytics]; фильтр календаря по компаниям («группа компаний, холдинг») [user/Calendar].

Мобильное и данные:

- Графики: нет обеда; смена ≤24 ч; встроенные графики не редактируются [user/Schedule], [admin/WorkSchedule].
- Email: не outlook.com и mail.ru; прочитанное письмо не станет заявкой [admin/TicketMail]. Telegram: одна активная заявка на пользователя бота [admin/TelegramIntegration].
