## Жизненный цикл заявки

Совокупность стадий, по которым проходит **Заявка**, и переходов между ними. Настраивается для **Типа заявки**; **Стадия** — состояние заявки, требующее действий системы или пользователя.

**Модель.** Тип заявки → жизненный цикл → стадии + переходы. Тип заявки определяет: этапы (стадии), срок закрытия, доступные **Виды работ**. Порядок создания: Стадии заявки и Тип заявки → затем жизненный цикл. **Статус заявки** — визуальное отображение Стадии для мобильного приложения заказчика (свой цвет), привязывается к стадии при настройке жизненного цикла; в web и в приложении «HubEx исполнитель» видна стадия, в «HubEx заказчик» — статус (пример: стадия «Согласование с руководителем» → статус «В работе»). Маршрут заявки = Начальная + Конечная стадии; переходы настраиваются только после задания маршрута. С одной стадии возможен переход на несколько стадий. Ветки перехода: основная (красный маркер), согласования (фиолетовый; такие заявки в мобильном приложении — на отдельной вкладке «Согласование»), действий заказчика (голубой). Копирование цикла: при создании Типа заявки указать «Шаблонный тип заявки» — цикл копируется. Базовый процесс ремонта: Новая → Назначена → Принята → В работе → Выполнена → Выполнена и проверена; ответвления: «Отказ заказчика» (такие заявки автоматически отмечаются как «Закрытые»), «Отказ исполнителя» (исполнитель указывает причину, заявка исчезает из его списка), «Требует продолжения работ», «Выполнена без выезда» → «Выполнена без выезда и проверена», «Согласование», «Ожидает ТМЦ» (возврат на «Назначена»), «В пути»/«Выехал на объект»/«Прибыл на объект» (разделение времени поездки и работ). «Назначена» — промежуточная стадия между «Новой» и «Принятой» (нет сети у исполнителя, пропущен пуш, готовится отказ). Смежное: SLA и автоназначение — [«SLA, автоназначение и чек-листы»], согласование — [«Атрибуты, согласование и приоритизация заявок»], печатные формы/акты — [«Работы, акты приёмки и материалы в заявке»].

**Настройка.** Путь: Консоль администратора → Настройки заявки → Жизненный цикл заявки. Также: Настройки заявки → Стадии заявки; → Статусы заявки; → Типы заявок; → Виды работ; Настройки предприятия → Участки.
Параметры перехода: «Переход на стадию» (скрывается после первого сохранения), «Название перехода» (название кнопки в мобильном приложении исполнителя и заказчика; переход выполняется на панели навигации внизу формы заявки), «Описание перехода», «Ветка жизненного цикла», флажок «Изменить статус заявки», «Выполнить автоматический переход» (с указанием времени; для стадии с «Правилом автоназначения исполнителя»), «Автоматический переход до наступления срока исполнения» (срабатывает за заданное время до дедлайна), «Предоставить доступ отдельным ролям» (переход доступен только выбранным ролям), «Добавить роль для особенной настройки» → своё «Название перехода» для роли (удаление — кнопка «Удалить»).
Настройки стадии: название (видно в web и мобильном исполнителя, в списке и внутри заявки), описание, цвет шрифта в общем списке, флажок «Показывать сотрудника на карте и учитывать время на стадии как рабочее».
«Действие» стадии (необязательно): «Завершить работу по заявке», «Закрыть заявку», «Назначить сотрудника», «Автоназначение по правилу», «Автоназначение с учетом удаленности от заявки», «Назначить на инициатора перехода», «Снять назначение».
«Требование» стадии (необязательно): «Назначен исполнитель», «Обработаны чек-листы», «Отсканирован QR-код объекта», «Подписан акт выполненных работ».
Тип заявки: «Маска номера заявки» (пример: [{День ДД}][{Месяц ММ}][0-9][0-9][0-9] → 2309001), «Время закрытия заявки», «Виды работ» (Все / По списку), «Участки» (Все / По списку), «Шаблонный тип заявки».

**Ограничения.** Поле «Шаблонный тип заявки» доступно только при создании нового Типа заявки — позже указать невозможно; указывать необязательно. При создании заявки система выбирает наименьшее значение срока закрытия из заданного в Типе заявки и в Виде работ. Если в Тип заявки виды работ внесены вручную, при создании/редактировании заявки доступны только те, что закреплены за Объектом/оборудованием И добавлены к данному Типу заявки. Для автораспределения в карточке Сотрудника нужен флажок «Мобильный сотрудник»; для автоназначения по удалённости — «Отслеживать местоположение сотрудника». QR-код проверяется на соответствие коду из карточки Объекта в заявке; при несовпадении переход не выполняется. Заявки на стадии с действием «Закрыть заявку» по умолчанию не отображаются в списках заявок мобильных приложений исполнителя и заказчика; заявки на стадии «Выполнена» — отображаются.

**⚠ Грабли.** Стадия ≠ статус: стадию видят сотрудники, статус — заказчик; внутренние этапы можно скрыть, указав заказчику общий статус. Заявка считается просроченной, если работы выполнены позже «Крайнего срока закрытия»; НЕ считается просроченной, если переведена на «Выполнена» и (или) «Закрыта» до его наступления — поэтому на «Выполнена» нужно действие «Завершить работы по заявке». Удаление стадии ломает переход на неё (кнопка исчезает в web и мобильных); при повторном создании стадии с тем же наименованием переход нужно удалить и создать заново. Время на стадии учитывается как рабочее в аналитике только при установленном флажке — на «В пути»/«В работе» его ставить обязательно; при флажке местоположение сотрудника пишется и видно во вкладке «История изменений».

## Атрибуты, согласование и приоритизация заявок

Справочники, задающие свойства заявки (критичность, актуальность, вид работ, доп.поля-атрибуты), процессы согласования на базе стадий и жизненного цикла, а также инструменты поиска заявок в списке и просмотра истории изменений.

**Модель.** «Атрибут» = дополнительное поле; способ выражения ответа для пункта «Чек-листа» — число, дата, текстовая строка, файл (чек-листы — «SLA, автоназначение и чек-листы»). Параметр «Используется для» связывает поле с областью применения («Чек-листы»); отдельный параметр «Показывать в паспорте объекта» — для доп.полей «Объектов» («QR-коды, паспорт и планы объектов»).
«Критичность заявки» разделяет заявки по важности и срочности; отображается в списке заявок web- и мобильных приложений цветным маркером; используется в правилах расчёта крайнего срока закрытия заявки (SLA — «SLA, автоназначение и чек-листы»): по очень срочным заявкам срок закрытия может быть гораздо меньше, чем по стандартным.
«Актуальность заявки» — раздел для отслеживания актуальности заявки в данный момент, позволяет оптимизировать очерёдность выполнения; содержит время до выполнения заявки.
«Вид работ» в заявке выбирается только из тех, что указаны в карточке «Объекта» на вкладке «Обслуживание». Виды работ нужны для аналитики в разрезе видов работ и для «Правил автоназначения исполнителя» («SLA, автоназначение и чек-листы»): система подбирает исполнителя, у которого вид работ в карточке совпадает с видом работ в заявке.
Согласование строится из «Стадий заявки», «Жизненного цикла заявки», «Статусов заявки» и уведомлений («Правила выбора получателя» + «Триггеры уведомлений», «Уведомления»). Для одного «Типа заявки» может быть настроен только один «Жизненный цикл». Инициатор виден в заявке в блоке «Детальная информация», поле «Инициатор заявки»; в правиле выбора получателя он адресуется параметром «Обратившийся пользователь».
Согласование бывает внутренним (контроль расходов: финансовых, трудовых, материальных) и внешним (подтверждение заказчиком выполненных работ). Информацию о согласованных заявках можно передавать в 1С через интеграцию («Интеграции, API и клиентские приложения»).
«История изменений» — вкладка заявки: события по вкладкам «Заявка» и «Выполнение» (смена стадий, назначение исполнителя, изменение значений полей, добавление выполненных работ, материалов) с датой, автором и полем, в хронологическом порядке.

**Настройка.** Атрибут: Путь: Настройки системы → Дополнительные поля → «Создать поле»; поля «Наименование поля», «Тип поля», «Единица измерения», «Используется для», «Показывать в паспорте объекта».
Критичность: Путь: Настройки заявки → Критичность заявки → «Создать критичность заявки»; название, цвет, флажок «Для всех заявок по умолчанию» (критичность устанавливается автоматически при создании новой заявки).
Актуальность: Путь: Настройки заявки → Актуальность заявок → «Создать актуальность заявки»; название и время до выполнения заявки.
Виды работ: Путь: Настройки заявки → Виды работ → «Создать вид работ»; затем указать вид работ в карточке объекта, вкладка «Обслуживание».
Видимость полей формы: Путь: Настройки заявки → Поля на форме заявки — доступ в разрезе «Ролей» и «Стадий заявки»; настройка «RW (чтение и запись)» делает поле видимым и редактируемым. Так же скрывается поле «Инициатор заявки».
Согласование: Путь: Настройки заявки → Типы заявок (свой тип под процесс, при использовании «Участков» их нужно указать в карточке типа); Настройки заявки → Стадии заявки; Настройки заявки → Статусы заявки; Настройки заявки → Жизненный цикл заявки. В переходе: «+Добавить стадию», «Название перехода» (название кнопки в мобильном приложении инженера), «Ветка жизненного цикла» («Ветка согласования» / «Основная ветка»), флажок «Выполнить автоматический переход» с временем перехода, флажок «Изменить статус», флажок «Предоставить доступ отдельным ролям», «+Добавить роль» (роли задают разные названия переходов — в мобильном приложении заказчика получаются две кнопки «Согласована» и «Не согласована»).
Уведомления: Путь: Настройка оповещений → Правила выбора получателя (поле «Роль», «Получатели уведомления» = «Обратившийся пользователь»); Настройки оповещений → Триггеры уведомлений («Название триггера», «Описание сообщения» — шаблон, «Заголовок сообщения», «Текст сообщения» в разметке с подстановками @Model.TaskNumber, @Model.AssetFullName, @Model.TaskNotes, @Model.NavigateToTaskForm(), «Способ отправки сообщения» = Email или Push, блок «Условия отправки» → «Стадии заявки» + флажки отправки по времени). Уведомление отправляется при переходе заявки на выбранную стадию.
Список заявок: карточное и табличное отображение; в табличном — выбор полей по значку шестерёнки, доп.поля, поле «Дата изменения» (последняя строка истории изменений), перетаскивание колонок. Кнопка «Фильтры» в правом верхнем углу меню «Все заявки»; панель фильтров настраивается перетаскиванием полей (порядок сохраняется автоматически) и кнопкой «Добавить» (основные поля сверху, доп.поля тенанта снизу); «Применить», сброс фильтров, сохранение быстрых фильтров с названием, «Все быстрые фильтры».

**Ограничения.** «Тип поля» в уже созданном атрибуте изменить нельзя — нужен новый атрибут. Время до выполнения в актуальности вводится в минутах. Пример автоперехода на стадию согласования — 5 минут. Линейное согласование: 3 новые стадии («Согласование заявки», «Согласована», «Не согласована») при уже созданных «Новая», «Выполнена», «Закрыта»; уведомления на трёх стадиях. Параллельное согласование с двумя согласующими: 6 новых стадий, уведомления на пяти стадиях. Согласование с заказчиком: 3 новые стадии; стадия «Согласование с заказчиком» необязательна — без неё переходы на «Согласована»/«Не согласована» настраиваются сразу со стадии «Выполнена», и статус «На согласовании» создавать не нужно. Стадии «Согласована» и «Не согласована» в схеме согласования с заказчиком доступны только заказчику. Фильтр числовых доп.полей: «Равно», «Диапазон», «Больше чем», «Меньше чем»; списочные — единичный или множественный выбор. Строка поиска ищет одновременно по «Номер заявки», «Описание заявки», «Объект», «Адрес объекта», «Вид работ»; доступна для списочного, табличного отображения и режима карты. Просмотр удалённых заявок доступен только для учётной записи владельца тенанта. Быстрые фильтры — индивидуальные настройки конкретного пользователя.

**⚠ Грабли.** По умолчанию в системе настроен фильтр «Открытые заявки», поэтому заявка в стадии «Закрыта» не видна в списке; нужен фильтр «Состояние заявки» → «Только закрытые» / «Все заявки». Удалённые заявки ищутся отдельным фильтром «Видимость заявок» → «Только удаленные» / «Все заявки». Текст из строки поиска применяется ко всем полям одновременно: цифра, входящая и в номер заявки, и в название объекта, вернёт обе группы заявок. Поле «Вид работ» может отсутствовать на форме заявки: если для роли и стадии настройка не установлена — поле не отображается. Вид работ, созданный кнопкой «Создать» из выпадающего списка в заявке, всё равно нужно затем указать в карточке объекта. В параллельном согласовании требуются две разные стадии, одинаковые по смыслу («Согласована начальником подразделения» и «Согласована начальником подразделения\*»): на разных ветках им нужны разные уведомления и разные точки выхода. Автоматический переход настраивается только на стадию согласования; переводы на стадии результата согласования пользователь делает вручную. В старую историю изменений можно перейти переключателем «Новое представление»; в старой истории доступны детали в рамках стадии и информация о местонахождении сотрудника на выбранной стадии («Геотрекинг и карта»).

## Создание и действия с заявками

Заявка — карточка задачи (содержание, исполнители, сроки), создаётся в разрезе объекта, хранит историю обращений по объекту. Учёт по заявкам даёт фиксацию обращений клиентов, формирование платёжных документов и счетов, планирование загрузки сотрудников. Жизненный цикл и стадии — [«Жизненный цикл заявки»], атрибуты и приоритизация — [«Атрибуты, согласование и приоритизация заявок»].

**Модель.** Заявка ← Тип заявки (определяет стадии и срок закрытия) — единственное обязательное поле формы, отключить нельзя. Заявка → Заказчик (компания), Объект/оборудование, Вид работ (доступны только закреплённые за выбранным объектом), Договор обслуживания, План объекта (из карточки объекта), Компания-плательщик (может отличаться от заказчика), Контактные лица, Наша компания (вручную из компаний вида «Наша компания»), Родительская заявка, Инициатор, Исполнитель (один или несколько). Иерархия: дочерние заявки подчиняются родительским; дочерняя не отличается от обычной, отличие — заполненное поле «Родительская заявка»; любую заявку можно сделать дочерней, заполнив это поле. При создании на форме одна вкладка «Заявка»; после сохранения появляются «Необходимые материалы», «Сообщения», «Чек-листы», «Дочерние заявки», «Выполнение», «Акт выполненных работ», «История изменений». Блоки вкладки «Заявка»: Заявка, Обслуживание заказчика, Трудозатраты, Детальная информация. Плановая заявка — шаблон автосоздания заявок по расписанию; График обслуживания объектов — форма представления плановых заявок. Назначение исполнителя: вручную, перетаскиванием в «Расписание заявок» (только один сотрудник), правилом автоназначения, привязанным к стадии (только один сотрудник) — [«SLA, автоназначение и чек-листы»].

**Настройка.** Путь: Заявки → Все заявки → «Создать заявку». Путь: Заявки → Планировщик работ → «Создать заявку» (переключатель между «Плановые заявки» и «Графиком обслуживания объектов»). Путь (консоль администрирования): Настройки заявки → Поля на форме заявки — видимость и заполнение всех необязательных полей в разрезе «Ролей» и «Стадий заявки»; для поля «Актуальный исполнитель по заявке» значение «RW (чтение и запись)» разрешает выбор исполнителя. Путь: Администрирование → Роли → Полномочия → блок «Заявки» → «Удаление заявок», «Удалять незакрытые заявки» (право удаления рекомендуется давать только начальникам сервисной службы либо администраторам системы). Путь: Администрирование → Роли → раздел «Объекты» → «Объекты на участках пользователя»; раздел «Заявки» → «Заявки, где пользователь — ответственный за объект по заявке», «Заявки на объектах, доступных пользователю» — без них исполнитель не видит заявки в общем списке. Выбор исполнителя: «+Добавить исполнителя», сортировка «По релевантности» (учитывает «Вид работ» заявки, «Ответственный за объект», «Участок», «Навыки», «График работ» из карточки объекта; чем больше совпадений с карточкой сотрудника, тем выше) или «ФИО исполнителя» (А→Я); кнопка «Календарь» справа от имени показывает занятость. Плановая заявка: поля «Название», «Тип заявки» (только один), «Вид работ» (только один; по нему подбираются объекты), «Объект/оборудование» («К списку объектов», «Подобрать объекты»), «Описание», «Исполнитель», «Плановое создание заявок» (Ежедневно, Еженедельно и т.д.), «Отложить начало выполнения работ» (сдвигает срок закрытия), «Ограничить повторения» (период или количество), переключатель «Автоматическое назначение исполнителя»; запуск — «Сохранить и запланировать». Список заявок: карточное отображение (по умолчанию), табличное (настройка столбцов, доп.поля в таблицу), на карте — [«Геотрекинг и карта»]; фильтры в правом боковом меню, быстрые фильтры, «Видимость заявок» → «Только удаленные», «Избранные заявки» → «Только избранные заявки». Контекстное меню (три точки) заявки: «Копировать», «Удалить», «Добавить в избранное»/«Убрать из избранного». Перевод стадии: кнопка «Перейти на стадию» → «Сохранить».

**Ограничения.** Номер заявки — максимум 32 символа, присваивается автоматически по шаблону из консоли администрирования, может быть изменён вручную. Импорт — до 2000 заявок за раз. Массовое редактирование заявок — на данный момент только исполнитель/исполнители; групповое назначение доступно для карточного и табличного представления, вариант «Нет исполнителя» снимает назначение. Копирование доступно только в карточном представлении. Оценочные и фактические трудозатраты — в часах; оценочная и фактическая стоимость — числом; «Неисправность обнаружена» — дата. «Метод подачи заявки» заполняется автоматически. Крайний срок закрытия рассчитывается правилом SLA [«SLA, автоназначение и чек-листы»]; если ни одного правила SLA не создано или не включено, срок считается по сроку закрытия «Типа заявки». Просроченной считается заявка, выполненная или закрытая позже крайнего срока; по умолчанию выполнение происходит на стадиях «Выполнена» и «Закрыта». Для роли сервисного специалиста могут быть введены ограничения на установление часовой ставки и оценки стоимости работы. Для графика обслуживания обязателен выбор «Типа заявки», «Заказчик» — одно из условий формирования; в списке заказчиков только те, по которым созданы плановые заявки; выбрать можно только родительский объект (дочерние подтягиваются автоматически); группировка периода — по дням/неделям/месяцам; экспорт в pdf, xlsx, docx, xml и другие, для редактирования рекомендуется xlsx.

**⚠ Грабли.** После создания заявки её тип изменить невозможно — заявку копируют, в копии меняют тип, некорректную удаляют; при копировании поле «Номер заявки» остаётся пустым и заполняется при сохранении. Заявки не удаляются полностью, а скрываются из списка; просмотр удалённых доступен только учётной записи владельца тенанта. В web заявку можно подать без заказчика, объекта, адреса и вида работ (внутренние задачи), но в мобильном приложении при создании поля «Заказчик», «Объект», «Вид работ», «Адрес» обязательны; заявка из web с пустыми полями в мобильном просматривается и редактируется обычно. Если в карточке объекта установлен флажок «Мобильное оборудование», изменение адреса в заявке меняет адрес и в карточке объекта. В краткой форме создания дочерней заявки нельзя выбрать объект — он наследуется от родительской; сменить можно после сохранения. Если дочерние заявки не отображаются на вкладке при ненулевом счётчике — кнопка «Настройки» (шестерёнка), выбрать поля или «Выбрать все». Изменения стадии действуют для всех типов заявок, в чей жизненный цикл включена эта стадия. Для редактирования плановой заявки её сначала нужно «Приостановить», затем снова «Сохранить и запланировать». График строится только после нажатия «Просмотр отчета», повторно при любом изменении настроек. При нескольких исполнителях время выполнения общее: 2 часа для двоих отразятся в акте как 2 часа каждому; по умолчанию в выполненную работу добавляются все назначенные исполнители. Заблокированное поле «Исполнитель» (значок замка) — вопрос доступа к полям формы, он настраивается отдельно от ролей. Создание дочерних заявок доступно только в web-приложении. Альтернативные каналы подачи (QR, импорт) — [«Доступ к заявкам, альтернативные каналы и групповые действия»], [«QR-коды, паспорт и планы объектов»].

## Доступ к заявкам, альтернативные каналы и групповые действия

Кто какие заявки видит и какие поля правит, каналы подачи заявок помимо приложений, действия над списком заявок сразу.

**Модель.** Видимость заявок задаётся двумя слоями: полномочия «Роли» (блок «Заявки» → «Справочники») и настройка полей формы в разрезе «Роль» × «Стадия заявки». Варианты полномочий: «Активные заявки на сотрудниках моих участков», «Активные заявки на объектах моей компании», «Активные заявки на сотрудниках моей компании», «Все активные заявки», «Активные заявки по моим видам работ», «Дочерние активные заявки», «Заявки, на которые я когда-либо был назначен» (даже если исполнителя заменили), «Заявки, где пользователь — ответственный за объект по заявке», «Заявки на объектах, доступных пользователю» (следует из блока «Объекты» → «Справочники»), «Удалять незакрытые заявки», «Предоставляет доступ на чтение и запись для всех компонентов формы заявки вне зависимости от полномочий и настроек стадии» (снимает ограничения полей формы). Видимость «Объектов»: «Все активные объекты», «Удаленные объекты», «Объекты на участках пользователя», «Объекты у компаний пользователя» (совпадение «Компании-владельца» объекта с компанией сотрудника из вкладки «Трудоустройство» / заказчика из вкладки «Общее»). Уровни доступа к полю: RO (только чтение), RW (чтение и запись, редактирование необязательное), RWM (чтение и обязательная запись), «Настройка не выбрана» — поля нет на форме. «Инициатор заявки» — поле с данными о пользователе, создавшем заявку (при звонке инициатором становится диспетчер); по каждому инициатору хранится история обращений — список заявок с ним, открывается из контекстного меню у ФИО. Список выбора инициатора формируется из всех «Заказчиков» и «Сотрудников» аккаунта. Каналы подачи: паспорт объекта по QR (поле «Метод подачи заявки» = «Паспорт объекта»), электронная почта (пересылка либо imap), форма на сайте компании-исполнителя. Почтовая интеграция опирается на шаблон заявки из «Заявки — Маркировка» и сервисную учётную запись. Двусторонняя интеграция: сообщения из вкладки «Сообщения» уходят ответным письмом на адрес отправителя заявки. Участки, роли, приглашения — [«Роли, полномочия и участки»], [«Приглашения, доступ и графики работы»]; шаблоны и QR — [«QR-коды, паспорт и планы объектов»]; клиентский портал и приложение заказчика — [«Интеграции, API и клиентские приложения»].

**Настройка.** Поля формы: `Консоль администрирования → Настройки заявки → Поля на форме заявки` (дополнительные поля — внизу таблицы с отметкой «А»; создаются в `Настройки системы → Дополнительные поля`). Копирование настроек — контекстное меню (три точки) у «Роли» или «Стадии» → «Копировать в…». Полномочия: `Консоль администрирования → Администрирование → Роли → вкладка «Полномочия»`. Почта: `Консоль администрирования → Интеграция → Интеграция по электронной почте` (разделы «Подключение через пересылку» и кнопка «Подключить эл. почту»); сервисный пользователь — `Интеграция → Служебные пользователи`, тумблер «Пользователя API», выбрать «Роль» с максимальными полномочиями по заявкам и объектам и «Участки» (рекомендуется все); «Токен доступа» для почты не нужен. Поля подключения imap: «Адрес сбора заявок», «Логин», «Пароль/Ключ» (пароль приложений почтового сервиса), «Хост», «Порт», «Сетевой протокол», «Протокол безопасности»; для Yandex — imap.yandex.ru, 993, SSL/TLS. «Отправитель» — конкретный адрес, `*@yandex.ru` или `*@*`; для общего шаблона без заказчика указывать `*@*`. Переключатели «Разрешить получение писем», «Возможность ответа заказчику через чат», общий тумблер включения интеграции. «Настройка регулярных выражений» — парсинг письма в поля заявки («Объект», «Вид работ», «Срок закрытия» и т.д.), подключается через help@hubex.ru; форма подачи на сайте — тоже через help@hubex.ru. Шаблон для пересылки создаётся по умолчанию с названием «Шаблон для получения заявок по электронной почте через пересылку», публиковать его для этой интеграции необязательно, флажок «Разрешить подачу заявки из Web» установлен по умолчанию, снимать не нужно. Массовые действия: `Заявки → Все заявки`, навести курсор слева от заявки, флажок → верхняя панель → «Редактировать» → «+ Изменить» (исполнители) → «Выбрать» → «Применить», либо «Удалить» с подтверждением. Удалённые заявки ищутся фильтром «Видимость заявок» = «Только удаленные».

**Ограничения.** Массовые действия доступны для карточного и табличного представления списка; заполняют/заменяют «Исполнителя» и удаляют заявки. Флажок в панели редактирования выбирает все заявки на странице. Нельзя отключать видимость поля «Тип заявки»; хотя бы для одной «Роли» и «Стадии» ему должна быть назначена RW. Остальные поля не обязательны, их можно исключить из формы. У шаблона для imap-интеграции обязательно должны быть выбраны «Объект» и «Вид работ», иначе шаблон не выбрать в настройках интеграции. imap-интеграцию нельзя настроить для outlook.com и mail.ru; рекомендуются адреса yandex.ru, другие сервисы могут работать нестабильно. Если письмо на адресе сбора заявок прочитать в почте, заявка в HubEx не создастся. Все действия над полем «Инициатор заявки» доступны только ролям, которым выдано редактирование этого поля. При создании инициатора обязательны ФИО и одно из полей «Телефон»/«Электронная почта».

**⚠ Грабли.** Пустая форма заявки (белый экран) — следствие того, что для новой «Стадии заявки» не задано ни одной настройки доступа к полям. Сотрудник должен принадлежать тому же «Участку», что и исполнители, которых он назначает, иначе их нет в списке выбора. Если у сотрудника/заказчика есть «Участок», а в «Типе заявки» участок не выбран, тип недоступен и заявку создать нельзя. Пустой список заявок часто вызван активными фильтрами (красная точка на кнопке фильтров в мобильном приложении). При изменении «Заказчика» в заявке после выбора инициатора поле «Компания» у инициатора не изменится. По умолчанию новые «Инициаторы заявки» создаются как элементы справочника «Заказчики». В шаблоне для пересылки по умолчанию «Тип заявки» — созданный в системе первым, «Вид работ» — с флажком «Основной вид работ» (он один в системе), «Критичность» — с флажком «По умолчанию»; текст письма заполняет «Описание заявки». Ссылка-подтверждение пересылки от Gmail/Yandex приходит на почтовый ящик HubEx и превращается в заявку — её нужно искать в «Описании заявки». «Приглашение» для почтовой интеграции указывать не нужно. Для каждого нового адреса клиента создаётся карточка «Заказчика», ему уходит письмо со ссылкой для регистрации.

## Типы и классы объектов

Классификаторы карточки Объекта (оборудования): «Тип оборудования» (по функциональному назначению, техническим характеристикам и др.) и «Класс оборудования» (совокупность объектов с общими характеристиками). Сам объект и его карточка — [«Создание и редактирование объектов»], иерархия и вкладки создания — там же.

**Модель.** Объект (оборудование) — элемент инфраструктуры, на который направлены услуги (виды работ); аналог конфигурационной единицы в ITSM. Объекты отображаются иерархическим списком родитель→дочерний; родительский объект обязательно должен иметь адрес, дочернему адрес необязателен — наследуется от родителя. Признак наличия адреса регулируется Типом. Адрес объекта автоматически подставляется в Заявку. Базовые типы, созданные в HubEx по умолчанию: «Объект» (флажок «Обязательное наличие адреса» установлен по умолчанию) и «Оборудование» (этого флажка нет; для него можно настроить Виды работ). Тип несёт список допустимых Видов работ; Класс — только группировка Объектов и Заявок по Объектам. Класс устанавливается только в карточке Объекта на вкладке «Объекты|Оборудование». Тип и Класс дают разрезы аналитики (Отчёт по объектам, Отчёт для клиента — [«Отчёты и экспорт»]) и фильтрации. Участок — отдельная сущность, группирует Объекты, Сотрудников, Заказчиков и Типы заявок и ограничивает доступ к данным ([«Роли, полномочия и участки»]).

**Настройка.** Путь: Консоль администратора → Структура предприятия → Типы оборудования → «Создать тип оборудования». Флажки: «Обязательное наличие адреса»; «Назначить объектом по умолчанию» (тип подставляется при создании нового Объекта и подразумевает автоматическую установку «Обязательное наличие адреса»; смена — установить флажок в карточке нужного Типа). Настройка «Виды работ» в карточке типа: выбор нескольких позиций; для новых объектов виды работ подставляются автоматически, при изменении типа у существующего объекта система предложит заменить виды работ на привязанные к новому типу; вручную по объекту можно добавить/удалить — настройки типа не изменятся. Путь: Консоль администратора → Структура предприятия → Классы оборудования → «Создать класс оборудования»; флажок «Назначить классом по умолчанию» — автозаполнение при создании объекта. Удаление класса: контекстное меню (три точки) → «Удалить». Фильтры: Объекты|Оборудование → Объекты|Оборудование → фильтр «Класс»; Заявки → Все заявки → фильтр → «Класс объекта» → «Применить». Смена типа у существующего объекта: в карточке нажать «Снять с публикации», изменить, сохранить, «Опубликовать». Массовая смена — Объекты|Оборудование → отбор → «Редактировать».

**Ограничения.** Обязательно наличие хотя бы одного Типа оборудования с признаком «Обязательное наличие адреса». Поле «Тип оборудования» в карточке Объекта после записи по умолчанию неактивно; редактирование — после снятия с публикации. Неопубликованный Объект нельзя выбрать в Заявке. При массовом редактировании сменить Тип оборудования можно только для категории дочерних объектов; снимать с публикации при этом не нужно. Ошибка «Для такого типа оборудования необходимо выбрать родительский объект» — если для выбранного Типа предусмотрен выбор родительского объекта.

**⚠ Грабли.** Удаление класса не очищает поле «Класс» в карточках Объектов: значение сохраняется, фильтрация по удалённому классу не работает (класс исчезает из выпадающего списка), выбрать его при создании нового объекта невозможно; правка — вручную. Классы можно не использовать — ставить у всех Объектов значение «По умолчанию». Класс группирует только Объекты и Заявки; Участок дополнительно ограничивает доступ ([«Роли, полномочия и участки»]).

## Создание и редактирование объектов

Ввод объектов (оборудования) в систему: шаблоны для массового создания через мобильное приложение, публикация, редактирование карточки, мобильное оборудование, удаление. Типы и классы — [«Типы и классы объектов»], QR-коды и паспорт объекта — [«QR-коды, паспорт и планы объектов»].

**Модель.** Шаблон объектов — образец карточки Объекта с заполненными полями «Родительский объект», «Компания-владелец», «Тип объекта», «Участок», «Вид работ», «Ответственный за объект»; по нему исполнитель создаёт объекты в мобильном приложении в меню «Приемка и маркировка». Варианты меню: приемка без QR-кода (по шаблону или без), приемка по QR-коду (пункт «Новое оборудование»), маркировка по QR-коду — привязка не использованного ранее в HubEx QR-кода к существующему объекту (пункт «Существующее оборудование»). При привязке QR-кода к Объекту или создании Объекта по QR-коду автоматически создаётся шаблон заявки в меню «Заявки — Маркировка» [«QR-коды, паспорт и планы объектов»]. Мобильное оборудование — оборудование с динамичным адресом: новый адрес указывается в Заявке и сохраняется в карточке Объекта. Мобильным может быть только объект с Типом оборудования, где стоит флажок «Обязательное наличие адреса (при создании объекта оборудования)»; это родительские объекты, дочерние наследуют адрес от родителя. История перемещений — экспортом Заявок с отбором по оборудованию [«Отчёты и экспорт»].

**Настройка.** Путь: Объекты|Оборудование → Шаблон объектов и оборудования. Вкладка «Объект|Оборудование»: «Название шаблона» (видно в мобильном приложении), «Описание шаблона» (необязательно), «Родительский элемент», «Тип оборудования», «Название» (если пусто — подставится название шаблона), флажок «Мобильное оборудование», «Участок», «График работы оборудования» (справочный, необязательный), «Класс оборудования» (без учёта — вариант «По умолчанию»). Вкладка «Обслуживание»: «Виды работ», «На гарантии до», «Ответственный за объект». Вкладка «Дополнительные поля» [«Чаты, сообщения и доп.поля»]. Публикация: Путь: Объекты|Оборудование → фильтр неопубликованных → контекстное меню («три точки») → «Опубликовать». Редактирование в мобильном приложении — через паспорт объекта (при подаче заявки по QR-коду, из списка «Объекты|Оборудование», из карточки Объекта в заявке); правится «Класс оборудования», «Описание», «Файлы», доп. поля на вкладке «Характеристики»; сохранение — галочка вверху справа. Полномочие: консоль администрирования → Роли → раздел «Объекты» → «Изменение данных объекта» [«Роли, полномочия и участки»]. Удаление объекта: карточка или список → «три точки» → «Удалить» / «Удалить с вложенными объектами»; групповое — галочки + «Удалить». Скрыть удалённые: Администрирование → Роли → блоки «Компании», «Объекты», «Пользователи и контакты» → поиск «удаленные» → отключить «Удаленные объекты» и др.

**Ограничения.** Объекты, созданные в мобильном приложении исполнителя, создаются неопубликованными — по ним нельзя создавать заявки. В мобильном приложении без выбора Класса объект создать нельзя. Нельзя изменить «Тип оборудования» и «Контактные лица». Нельзя удалять объекты, участвующие в активных заявках. Удалённый объект нельзя восстановить — только создать новый по примеру старого. Прямое удаление справочников Объекты, Сотрудники, Заказчики, Компании и Заявок не предусмотрено из-за ссылочных связей. При удалении компании все привязанные объекты снимаются с публикации. Удалённые объекты видны по фильтру «Видимость», компании — «Видимость компаний».

**⚠ Грабли.** Неопубликованные объекты отмечены оранжевым маркером. Дочерние объекты наследуют адрес от родителя, поэтому их адрес как мобильных не меняется. Смена адреса во второй заявке не меняет адрес в первой — там правят вручную. Готовые QR-стикеры с логотипом заказываются кнопкой «QR-стикеры на вашем оборудовании» → «Заказать QR-стикеры», запрос уходит в поддержку HubEx.

## QR-коды, паспорт и планы объектов

QR-код — штрихкод, привязанный к данным системы; сканирование с мобильного даёт доступ: ввод новых объектов ([«Склад, материалы и маркировка»]), подача заявок, паспорт объекта, подача заявок незарегистрированными.

**Модель.** QR-код связывает «Объект» и шаблон заявки. Шаблон заявки — образец «Заявки» с полями «Тип заявки», «Объект», «Заказчик», «Вид работ», «Критичность», «Описание заявки», «Исполнитель» (меняются при подаче); нужен также для интеграции с эл. почтой ([«Интеграции, API и клиентские приложения»]). Паспорт объекта — данные «Объекта|Оборудования» в приложениях «HubEx исполнитель»/«HubEx заказчик» при сканировании QR по кнопке подачи заявки. Публичный шаблон → неполный паспорт открывается в мобильном браузере любым сканером QR. «История обслуживания» доступна только в приложении исполнителя. Привязка QR, ранее не использованного в HubEx, автоматически создаёт шаблон — неопубликованный, без «Тип заявки», «Вид работ», «Приглашение» и разрешения на подачу. Пин на плане в карточке «Объекта» — расположение по умолчанию, подставляется в «Заявку». Дочерний объект без своего плана подтягивает план родителя ([«Создание и редактирование объектов»]); если планы у обоих — выбирается любой.

**Настройка.** Путь: Карточка Объекта → «QR-коды» → «Маркировать». Путь: Заявки → Маркировка → «Создать QR-код»; флажки «Опубликовать», «Разрешить подачу заявки из Web», «Разрешить саморегистрацию» (требует «Разрешить регистрацию без верификациии»), «Обязательная саморегистрация по QR-коду»; «Приглашение» задаёт Роль и Участок нового пользователя, создаётся в Пользователи → Приглашение. Экспорт QR-кодов — архив .zip. Путь: Роль → «Приложения» → «Электронный паспорт оборудования» — включить и для Роли из «Приглашения» ([«Роли, полномочия и участки»]). Подтверждение пребывания: консоль администрирования → Настройки заявки → Стадии заявки → стадия → «Требование» → «Отсканировать QR код объекта» ([«Жизненный цикл заявки»]). Путь: Карточка Объекта → «Объект|Оборудование» → «План объекта». Путь: Объекты|Оборудование → Объекты|Оборудование → «Фильтры» (сохраняемые быстрые фильтры), флажки объектов → «Редактировать».

**Ограничения.** Один план на «Объект»; .jpg, .jpeg, .png; загрузка только в web-версии. «Вид работ» шаблона — из установленных в карточке «Объекта». Без привязки QR к «Объекту» паспорт пустой. QR сверяется с QR карточки «Объекта» из «Заявки»; при несовпадении — уведомление о неверном коде, перехода нет. Массово меняются: Родительский объект, Вид работ, Участок, Навык, Чек-лист, Ответственный, Тип/Класс объекта, Компания-владелец, Мобильность, публикация, график работы.

**⚠ Грабли.** Пин, переставленный в «Заявке», НЕ меняет расположение по умолчанию в карточке «Объекта». Заказчику просмотр паспорта не доступен по умолчанию. При «Обязательной саморегистрации» пункт «Не получать уведомления» недоступен. Замена «Типа объекта» групповым редактированием возможна только для дочерних объектов. В массовом редактировании списки «Видов работ» и «Участков» — все значения справочников.

## Компании и договоры

Компания — юр- или физлицо в роли заказчика и/или подрядчика; также организация, от лица которой ведётся учёт. Компании связывают объекты, сотрудников и заказчиков и участвуют в распределении полномочий.

**Модель.** «Вид компании»: «Компания-подрядчик» (взяла обязательства выполнить работы/услуги), «Компании-заказчики» (учёт заявок в разрезе объектов заказчиков, формирование платёжных документов, создание пользователей для мобильного приложения заказчика), «Наша компания» (её банковские реквизиты отражаются в «Акте выполненных работ» и «Счёте на оплату»; создание пользователей для web и мобильного приложения исполнителя). Компания привязывается к объектам/оборудованию и пользователям: заказчик видит только оборудование, закреплённое за его компанией. Договор фиксирует взаимоотношения с клиентом, позволяет отслеживать сроки действия и классифицировать заявки; принадлежит одной компании, связан с «Объектами по договору». В заявке доступен только договор, принадлежащий выбранному объекту. Контактные лица создаются в карточке компании и в карточке объекта, хранятся в одном общем списке; в заявке оба показываются в поле «Контакты по заказчику и объектам». Пользователи — «Сотрудники» (лицензируемые, web + «HubEx исполнитель») и «Заказчики» (мобильное приложение «HubEx заказчик», привязан к компании-заказчику); подробности ролей — [«Роли, полномочия и участки»], [«Отличия ролей и вход в систему»], карточка сотрудника — [«Приглашения, доступ и графики работы»].

**Настройка.** Путь: Компании → Создать компанию. Поля: «Название компании», «Тип контрагента» (Индивидуальный предприниматель / Физическое лицо / Юридическое лицо), «Телефон», «Веб-сайт», «Электронная почта», «Код компании» (идентификатор заявок этой компании, используется в маске номера заявки для определённого типа заявки), «Фактический адрес», «Файлы», «ERP ID» (идентификатор во внешней системе для интеграции). Вкладка «Компания»: юридические реквизиты (ИНН, КПП) — автозаполнение кнопкой «+Заполнить по ИНН»; банковские реквизиты; «+Добавить контактное лицо» (обязательны «ФИО» и «Телефон»). Путь: карточка компании → вкладка «Договоры». Обязательны «Наименование и номер договора» и «Компания»; «Описание», «Условия договора» — свободная форма; «Срок действия» заполнять, если контролируется срок окончания и есть особые денежные условия; «Объекты по договору»; «Файлы»; флажок «Напомнить о завершении договора» + контактные данные — уведомление на e-mail. Доп. поля для договора — [«Чаты, сообщения и доп.поля»]. Роли контактов: Администрирование → Роли → «Пользователи и контакты — Справочники»: «Все контакты», «Контакты моей компании»; «Пользователи и контакты — Элементы интерфейса»: «Добавление контактов», «Удаление контактов». Видимость контактов в заявке: Настройки заявки → Поля на форме заявки (поля «Адрес эл. почты контактного лица», «Контакты по объекту», «Телефон контактного лица», «ФИО контактного лица»; значения не выбрано / RO / RW / RWM) — [«Атрибуты, согласование и приоритизация заявок»]. Аналитика → График действия договоров: сроки окончания и заявки вне периода действия договора (значок флажка, «Открыть список заявок») — Power BI, [«Аналитика Power BI»]. Компании импортируются и экспортируются — [«Отчёты и экспорт»].

**Ограничения.** Создавать и выбирать контактные лица можно только в web-версии HubEx. В карточку компании и в карточку объекта можно добавить несколько контактных лиц. В заявке выбрать договор можно только после выбора объекта; при просрочке договора в заявке показывается информационная подсказка. Данные в отчёте «График действия договоров» обновляются раз в сутки, дата обновления — вверху слева. Если нужного банка нет в списке — чат с поддержкой в web-приложении или help@hubex.ru.

**⚠ Грабли.** Карточка компании в списке показывает название, вид, количество объектов/оборудования и пользователей; внутри — число сотрудников, заказчиков и заявок по её объектам. Контактное лицо из карточки объекта отображается в заявке, в которой данная компания указана в поле «Заказчик» — как и контакт из карточки компании; если контакты заполнены и у заказчика, и у объекта, отобразятся оба.

Источники: [user/CreatingCompany] [user/CreatingCustomer] [user/CreatingUser] [user/Contacts] [user/ContractSchedule]

## Роли, полномочия и участки

Ролевая модель доступа: **Роль** — набор прав и полномочий, определяющий уровень доступа пользователя; управляет видимостью разделов и данных, возможностями взаимодействия с ними и доступом к приложениям исполнителя, заказчика и web-версии. Роль устанавливается в карточке пользователя.

**Модель.** Роль → два раздела: «Полномочия» (доступ к элементам интерфейса и справочникам) и «Приложения» (доступ к приложениям и электронному паспорту объекта). Полномочия разбиты на тематические блоки (Заявки, Объекты, Компании, Материалы и склады, Пользователи и контакты, QR, Аналитика, Стадии, Статусы, Типы заявки, Участки, Чек-листы, Шаблоны объектов, Интеграция, Сообщения, Уведомления, Роли, API полномочия и др.); блок включается целиком переключателем или детально по пунктам. Каждый блок содержит одну-две группы: «Элементы интерфейса» (видимость пунктов основного меню и консоли администрирования) и «Справочники» (какие данные видны). Отдельно блок «API полномочия» — права на методы работы с данными; рекомендация источника — включать его полностью для всех ролей.
Примеры базовых ролей из источника: «Заказчик» (только приложение заказчика, заявки только по объектам компании-заказчика; не видит объекты других заказчиков, прочие заявки нашей компании, сотрудников, аналитику, склады, карты); «Сервисный специалист» (сотрудник-исполнитель, создаёт и/или выполняет заявки, перевод по определённым стадиям, создание оборудования через маркировку, приложение исполнителя, возможен доступ в разрезе участков); «Диспетчер» (оператор/офисный сотрудник, доступ ко всем компаниям-заказчикам и их объектам, перевод заявки на любую стадию, назначение любого исполнителя на любом участке).
**Участок** — классификация Объектов, Типов заявок, Сотрудников, Заказчиков по критериям (географическим, функциональным). Участок связывается с Объектом, Сотрудником, Заказчиком, Типом заявки; у каждого Участка ведётся статистика связей с Объектами, Пользователями (Сотрудники+Заказчики) и Типами заявок — для решений об удалении/переносе.
**Навык** — дополнительное особое умение для выполнения заявки; классифицирует Объекты и Сотрудников, используется в правилах автоназначения исполнителя [«SLA, автоназначение и чек-листы»]. Флаг «Необязательный» — правила выбора могут учитывать обязательные навыки, необязательные или обе группы.
**UI полномочия** — настраиваемые полномочия, отвечающие за пользовательский интерфейс; есть преднастроенный список.
**Служебные пользователи** — сервисные учётные записи для интеграции с внешними системами, эл. почтой и подачи заявок незарегистрированными [«Интеграции, API и клиентские приложения»]. «Пользователь API»: выбираются Роли (полномочия считываются с них; обычно полные права у Администраторов, Системных администраторов, Руководителей служб), Участки, «Токен доступа» (кнопка «Сгенерировать», скачивается файлом). «Анонимный пользователь»: Роль, присваиваемая при регистрации незарегистрированного пользователя, и Участки для создания заявок.

**Настройка.** Роли: `Путь: Администрирование → Роли`, кнопка «Добавить роль»; поле «Создать новую роль на основе шаблона» копирует настройки существующей (шаг можно пропустить). Копия также через контекстное меню (три точки) → «Копировать» (название с «Копия»). В интерфейсе редактирования справа панель показа/скрытия блоков и поиск по полномочиям (рекомендация: одно ключевое слово, без знаков препинания, можно без окончания).
Уровни доступа для активных элементов интерфейса: «Чтение и запись» (устанавливается по умолчанию), «Чтение и обязательная запись» (обязательное редактирование, напр. поля «Ставка исполнителя», «Стоимость вида работ в выполненных работах»), «Только для чтения».
Доступ к полям формы заявки в разрезе Стадий и Ролей — `Путь: Настройки заявки → Поля на форме заявки` [«Атрибуты, согласование и приоритизация заявок»]; переходить туда следует, когда уже созданы Роли и Стадии.
Участки: `Путь: Структура предприятия → Участки`, кнопка «Создать участок». Поля: «Название участка» (обязательное), «Описание участка», «Идентификатор из внешней системы» (для связи с внешней системой, напр. 1С), «Назначить участком по умолчанию» (участок по умолчанию присваивается новым Объектам, Сотрудникам, Заказчикам). Указание участка: Объект — вкладка «Объект|Оборудование» внизу страницы; Сотрудник — вкладка «Квалификация»; Заказчик — вкладка «Квалификация»; Тип заявки — карточка типа (`Путь: Настройки заявки → Типы заявок`).
Навыки: `Путь: Структура предприятия → Навыки`, кнопка «Создать навык»; поля «Название навыка» (обязательное), «Описание», «Необязательный». Навыки: Сотрудник — вкладка «Квалификация», Объект — вкладка «Обслуживание».
UI полномочия: `Путь: Администрирование → UI Полномочия`, кнопка «Создать полномочие», заполнить обязательную информацию и сохранить.
Служебные пользователи: `Путь: Интеграция → Служебные пользователи`, включение тумблером.
Ограничение видимости по участкам (пример источника для сервисного специалиста): заполнить «Участок» в карточках Сотрудника, Объекта, Типа заявки; в блоке «Объекты → Справочники» включить «Объекты на участках пользователя»; в блоке «Заявка → Справочники» выбрать «Заявки на объектах, доступных пользователю» и снять первые 8 пунктов (они дают больше прав на просмотр Заявок).
Ключевые пункты «Справочники» блока Заявки: «Активные заявки на сотрудниках моих участков», «Активные заявки на объектах моей компании», «Все активные заявки», «Активные заявки по моим видам работ», «Дочерние активные заявки», «Заявки, на которые я когда-либо был назначен», «Заявки, где пользователь — ответственный за объект по заявке», «Заявки на объектах, доступных пользователю», «Архивные заявки» (доступ к закрытым), «Игнорировать эксклюзивные полномочия для доступа к полям заявки» / «Предоставляет доступ на чтение и запись для всех компонентов формы заявки вне зависимости от полномочий и настроек стадии».
Блок Объекты → Справочники: «Все активные объекты», «Удаленные объекты», «Объекты на участках пользователя», «Объекты у компаний пользователя», «Компании и объекты, находящиеся на участке пользователя». Блок Пользователи и контакты → Справочники: «Все пользователи», «Заблокированные пользователи», «Все пользователи внутри компании», «Все пользователи на участках». Блок Участки → Справочники: «Все участки». Блок Компании → Справочники: «Все компании». Блок Материалы и склады → Справочники: «Все склады». Блок Роли → Справочники: «Все роли», «Удаленные роли».

**Ограничения.** Снять 8 первых пунктов в «Заявка → Справочники» при настройке доступа по участкам. Зависимости полномочий, названные прямо: создание объекта требует «Объекты → Создание объекта» + «API полномочия → Метод создания нового объекта»; поля в карточке Объекта — «Объекты → Изменения данных объекта»; работа с жизненным циклом возможна только при включённом «Участки → Справочники → Все участки»; кнопка «+Добавить стадию» требует полностью блока «Поля на форме заявки», «Роли → Справочники → Все роли», «Стадии → Пункт административной панели — Стадии заявок», «Статусы заявки → Пункт административной панели — Статусы заявок», «Типы заявки → Пункт административной панели — Тип заявок»; сохранение настроек полей на форме заявки требует «Жизненный цикл заявки → Сохранение жизненного цикла заявки»; создание Роли и её сохранение — «Роли → Изменение ролей»; заполнение полей карточек Сотрудника/Заказчика — «Изменение данных сотрудника или заказчика»; заполнение полей Приглашения — «Изменение приглашений»; «Израсходованные материалы на форме выполненных работ» требует «Материалы и склады → Справочники → Все склады»; поле «Ставка/час» в карточке Сотрудника требует «Пользователи и контакты → Пункт главного меню-Сотрудники» и «Все пользователи»; подача заявки в мобильном приложении (по списку и по QR) требует доступа к Объектам через блок «Объекты → Справочники»; добавление участника в чат требует «Сообщения → Чат с сотрудниками», «Пользователи и контакты → Все пользователи» (или «Все пользователи на участках») и «Сообщения → Просмотр списка участников в сообщениях». Ограничение по складам задаётся в карточке Сотрудника (вкладка «Квалификация») — с этих же складов можно указывать материалы в Заявке [«Склад, материалы и маркировка»].

**⚠ Грабли.** Новый Участок автоматически добавляется во все ранее созданные Типы заявок; в уже созданных Объектах, Сотрудниках и Заказчиках его нужно указать вручную. Новый Навык в уже созданных Сотрудниках и Объектах также указывается вручную. Для Объекта, Сотрудника, Заказчика и Типа заявки можно указать несколько участков и несколько навыков (для Сотрудника и Объекта). Участок Сотрудника/Заказчика в статье о участках — вкладка «Квалификация», а в описании полномочия «Все пользователи на участках» — вкладка «Трудоустройство»; Компания в карточке Сотрудника — вкладка «Трудоустройство», у Заказчика и Объекта — «Общее». «Публикация объекта»: флажок «Разрешить подавать заявки» есть и без этого полномочия и установить его можно (при включении полномочия на создание объекта); по объекту, снятому с публикации, нельзя подавать Заявки. Отключение «Изменение QR кодов и планировщика» показывает пустую карточку шаблона заявки. Полномочие «История перемещений» отвечает за отчёт в меню «Карты», а не «Аналитика» [«Геотрекинг и карта»]. «Доступ к подключаемым плагинам и отчетам» даёт и меню «Мои отчеты», и меню «База знаний» [«Первые шаги, база знаний и брендирование»]. Печатные формы «Сервисный акт», «Бухгалтерский акт», «Счет на оплату» включаются полномочиями блока «Аналитика» [«Печатные формы»].

## Отличия ролей и вход в систему

Пользователи HubEx делятся на **Сотрудников** и **Заказчиков**; уровень доступа задаёт **Роль**. Здесь же — регистрация и способы авторизации, включая вход владельца тенанта и подачу заявок без регистрации.

**Модель.** Тенант — рабочая область в HubEx. **Роль** — набор прав и полномочий, определяющих уровень доступа: видимость разделов и данных, возможности взаимодействия с ними, доступ к приложениям исполнителя, заказчика и web-версии. Роль заполняется в карточке Сотрудника и Заказчика; **Должность** — только в карточке Сотрудника. Роль и Должность могут называться одинаково, но всегда имеют разное влияние в системе. Должность — единица штатного расписания, заполняется в свободной форме, нужна только для справочного отображения на формах выбора исполнителей; отображается при выборе исполнителя на вкладке «Заявка», на вкладке «Выполнение» у исполнителя и в календаре «Заявки — Расписание заявок».
Сотрудник vs Заказчик: Сотрудника можно назначить исполнителем по Заявке, Заказчика назначить исполнителем нельзя. Заказчики переводят Заявки только по стадиям ветки действий заказчика в настройке жизненного цикла, Сотрудники — по основной ветке действий (жизненный цикл — [«Жизненный цикл заявки»]). Заказчики имеют доступ к Объектам и видят Заявки только той компании, которая указана в карточке Заказчика. Сотрудники — диспетчера, специалисты, менеджеры, начальники подразделений; Заказчики — ответственные лица со стороны компании-заказчика.
Владелец тенанта имеет две учётные записи: первая обозначается при входе как «Имя_пользователя (Системный администратор)» — ограничения по ролям на неё не распространяются, доступны всевозможные данные и объекты, видны все удалённые Объекты, Заявки и т.д.; видимость полей на форме Заявки для неё настроить невозможно — все поля доступны по умолчанию, скрыть их нельзя; может переводить Заявку на любую стадию жизненного цикла выбранного Типа заявки, в том числе на стадии, не связанные между собой. Вторая запись обозначается как «Имя_пользователя» и имеет роль «Системный администратор», настраиваемую аналогично другим Ролям. Учётную запись владельца тенанта можно использовать для настройки системы и установления ограничений через Роли.
Примеры базовых ролей: Заказчик — работает только в приложении для заказчика, создаёт заявки только по объектам компании-заказчика, не видит объекты других заказчиков, остальные заявки компании, сотрудников, аналитику, склады и карты. Сервисный специалист — сотрудник-исполнитель, может создавать и (или) выполнять заявки, доступен перевод заявки по определённым стадиям, может создавать новое оборудование через функционал маркировки, работает в приложении исполнителя, для него может быть настроен доступ в разрезе участков. Диспетчер (оператор, офисный сотрудник) — создаёт и выполняет заявки, имеет доступ ко всем компаниям-заказчикам и их объектам, может переводить заявку на любую стадию и назначить любого исполнителя на любом участке.
Пользователь, прошедший самостоятельную регистрацию, вносится в справочник «Пользователи — Заказчики».

**Настройка.** Роли создаются и настраиваются в консоли администрирования (см. [«Роли, полномочия и участки»]). Изменения в существующих ролях начинают действовать для пользователей сразу же. Видимость полей документа Заявка для ролей — Путь: Настройки заявки → Поля на форме заявки. Доступ к приложениям — Путь: Роли → Приложения: «Веб-приложение» (доступ через браузер — Chrome, Opera, Mozilla Firefox и т.д.), «Веб-приложение администрирования» (консоль администрирования), «Доступ только к API» (системное взаимодействие с HubEx, рекомендовано включать для всех), «Мобильное приложение заказчика» (вход в «HubEx заказчик»), «Мобильное приложение инженера» (вход в «HubEx исполнитель»), «Электронный паспорт оборудования» (просмотр паспорта Объекта при сканировании QR-кода). Логин — мобильный телефон или e-mail, указанные при создании пользователя; на них приходит ссылка для подтверждения регистрации и создания пароля. Альтернативный вход — кнопка «Вход по одноразовому коду» (sms-авторизация). Анонимная подача — Путь: консоль администратора → Интеграция → Служебные пользователи → «Анонимный пользователь»: указать Роль (например, Заказчик) и Участки, по которым возможно создание Заявок. Шаблон заявки для подачи по QR-коду — [«QR-коды, паспорт и планы объектов»], [«Создание и действия с заявками»].

**Ограничения.** Заказчикам в клиентском портале доступны пункты меню «Заявки — Все заявки», «Сообщения», «Аналитика — Отчет для клиента»; в мобильном приложении «HubEx заказчик» — «Заявки» и «Сообщения». Код-пароль из sms — четыре цифры; повторный запрос — если сообщение не пришло в течение 60 секунд. Вход по код-паролю доступен только для мобильных номеров, зарегистрированных в РФ (формат +7хххххххххх). Мобильные приложения: «HubEx исполнитель» и «HubEx заказчик» для Android и iOS.

**⚠ Грабли.** Пользователь должен пройти регистрацию и создать пароль для HubEx — иначе он не сможет авторизоваться в мобильном приложении ни по логину и паролю, ни по одноразовому код-паролю; авторизация по sms становится доступна только после завершения регистрации и создания пароля. Чтобы был возможен вход по код-паролю, при создании учётной записи обязательно указывать мобильный телефон. Незавершённую регистрацию можно закончить при первом входе в приложение: приглашение создать пароль, затем подтверждение регистрации через sms-код. Для подачи заявки по QR-коду без приложения шаблон заявки должен быть публичным, а для самостоятельной регистрации в качестве заказчика в шаблоне заявки должно быть указано «Приглашение». Если в приглашении включена обязательная регистрация при подаче заявки через сканирование QR-кода, кнопка «Не получать уведомления» пользователю не отображается (регистрация по «Email» или «СМС»). Незарегистрированные пользователи могут создавать Заявки только при включённой сервисной учётной записи «Анонимный пользователь». Для доступа к мобильным приложениям важно предоставить Роли пользователя соответствующий доступ в разделе «Приложения».

## Приглашения, доступ и графики работы

Регистрация новых пользователей по приглашению, ограничение видимости файлов и графики работы (недельные/сменные), используемые при назначении, автоназначении и SLA.

**Модель.** После создания «Сотрудника» или «Заказчика» в web-приложении система шлёт письмо со ссылкой на регистрацию — на указанный e-mail либо sms на телефон; пользователь переходит по ссылке, задаёт пароль, после чего входит в web или мобильное приложение (HubEx Engineer для исполнителя, HubEx Customer для заказчика). Файлы, прикреплённые к «Заявке» или карточке «Объекта», имеют настройку доступа по «Ролям» (роли ведутся в консоли администратора, см. [«Роли, полномочия и участки»]); настройка в заявке и в объекте не отличается. График работы: два типа — Недельный (рабочее время на каждый из 7 дней) и Сменный (повторяющийся интервал строк типа «Смена»/«Выходной» с количеством дней, напр. 2/2, 1/3, 3/2/3). График назначается сотруднику индивидуально, справочно закрепляется за объектом/оборудованием, и используется как «График обслуживания заявки» в SLA [«SLA, автоназначение и чек-листы»] — пример: график «Понедельник-пятница с 9:00 до 18:00» + плановое время 45 ч, заявка создана в понедельник 9:00 → крайний срок пятница 18:00. Графики применяются в автоназначении по графику, виду работ, навыкам [«SLA, автоназначение и чек-листы»] и в отчёте по отработанному времени и переработкам [«Отчёты и экспорт»]. Смены сотрудника редактируются индивидуально (больничный, отпуск, перенос смены).

**Настройка.** Права на файл: контекстное меню (три точки) у файла → «Права доступа» → флажки Ролей; функция доступна только после добавления файла. Флаг «Показать файлы в паспорте объекта» открывает файл при сканировании QR-кода и просмотре паспорта [«QR-коды, паспорт и планы объектов»]. Графики: консоль администратора → «Структура предприятия» → «Графики работы» → «Создать график»; поля «Наименование», дни/время чч:мм, флаг «Назначить дату начала календаря», кнопка «Показать график в календаре». График сотрудника: «Пользователи» → «Сотрудники» → карточка → вкладка «Трудоустройство». Правка смены: там же кнопка «Редактировать смену», либо «Заявки» → «Расписание заявок» (режимы день/неделя/месяц) → три точки → «Редактировать смену»; варианты «На смене» / «Не на смене», далее «Сохранить». Исполнитель правит свой график сам в мобильном приложении (боковое меню → иконка исполнителя). Смена в мобильном: «Начать смену» / «Завершить смену». График объекта: «Объекты/оборудование» → карточка → поле «График работы».

**Ограничения.** По умолчанию файлы доступны всем пользователям. Время одной смены не может быть более 24 часов; при большей длительности создают подряд две смены — на 24 часа и на дополнительное время. Предустановленные графики изменять нельзя, свои создавать можно. Графики по умолчанию: «Выходные 9-18», «2/2(4) c 9:00 до 18:00», «2/2(3) с 9:00 до 18:00», «2/2(2) c 9:00 до 18:00», «2/2 c 9:00 до 18:00», «Понедельник-Пятница 9:00-18:00», «Круглосуточный 24/7». Обеденное время в графиках отобразить нельзя. Дата начала не обязательна: без неё график действует со дня создания.

**⚠ Грабли.** Смены можно устанавливать, даже если в карточке сотрудника НЕ выбран график работ. При «Начать смену» другое время начала указать нельзя, «Время по» заполняется автоматически по настройкам графика; чтобы изменить часы, сначала меняют смену, потом жмут «Начать смену». Ночная смена задаётся временем окончания следующего дня (напр. 2:00), длительность с переходом через полночь считается автоматически. После изменений «Показать график в календаре» нужно нажимать повторно. График у объекта — исключительно справочное поле. При постановке заявки на время в форме выбора исполнителя «Начало» = выбранное время, «Окончание» считается по «Плановым трудозатратам» вида работ.

## SLA, автоназначение и чек-листы

Три механизма автоматизации заявки: расчёт «Крайнего срока закрытия» (SLA), подбор исполнителя роботом-диспетчером и чек-листы работ. Связующий справочник всех трёх — «Вид работ».

**Модель.** Вид работ — специфический вид деятельности (услуг), который может выполняться Сотрудником и направлен на Объект; классифицирует Объекты, Сотрудников и Заявки. Поля: «Название вида работ», «Описание», «Чек-лист выполняемых работ» (автоматически подтягивается в Заявку при выборе вида работ), «Плановые трудозатраты» (для автоматического расчёта срока окончания работ на форме выбора исполнителя), «Время закрытия заявки», «Основной вид работ» (подставляется по умолчанию при создании нового Объекта), «Опубликован» (тогда доступен для указания у Объекта, Сотрудника и выбора в Заявке), «Стоимость вида работ» (формирует итоговую сумму по Заявке в Акте выполненных работ [«Работы, акты приёмки и материалы в заявке»]; автозаполняется при создании выполненных работ на вкладке «Выполнение», можно изменить вручную).
Источники крайнего срока: Тип заявки, Вид работ, правило SLA. Из значений Типа заявки и Вида работ система выбирает наименьшее [«Атрибуты, согласование и приоритизация заявок»].
Правило SLA сопоставляет параметры Заявки и при совпадении заполняет «Крайний срок закрытия»; применённое правило показывается на форме Заявки внизу в поле «Правило расчета крайнего срока закрытия». Срок = «Плановое время закрытия заявки» (максимальный срок выполнения работ), отсчитанное по «Графику обслуживания» (рабочее время выполнения Заявок). Пример: обслуживание по будням 9:00–18:00, заявка подана в чт 17:00, плановое время 6 ч → крайний срок пт 14:00.
Правило автоназначения — набор критериев: «Обязательные навыки» (совпадение обязательных навыков карточки объекта из заявки с карточками сотрудников), «Вид работ» (самый популярный параметр), «График работы» (у кого рабочая смена на момент подачи заявки [«Приглашения, доступ и графики работы»]), «Ответственный за объект» (указывается в карточке объекта на вкладке «Обслуживание»), «Часто назначается на объект», «Участок» (участки карточки объекта против вкладки сотрудника «Квалификация» [«Роли, полномочия и участки»]). Правило действует только как действие Стадии заявки [«Жизненный цикл заявки»].
Чек-лист = Пункты; Пункт может содержать Атрибут — способ измерения/выражения (число, дата, текстовая строка, вложенный файл). Без атрибутов пункт отмечается флажком. Привязка чек-листа к Объектам/оборудованию и (или) Видам работ даёт автоприкрепление к Заявке при выборе их в Заявке; без привязок — добавление вручную. Чек-листы заявки видны на вкладке «Чек-листы».

**Настройка.** Путь: Консоль администратора → Настройки заявки → «SLA: расчет крайнего срока закрытия» → «Создать правило» (разрезы: Тип заявки, Критичность, Вид работ, Компания-заказчик, Объект; Заказчики «Все»/«По списку», Объекты «Все»/«По списку»/«Все за исключением»; «Все» включает и будущие записи). Правило нужно включить переключателем («Включено») — при создании или позже в общем списке.
Путь: Консоль администратора → Настройки заявки → «Виды работ» → «Создать вид работ». Также создаётся из формы Заявки (кнопка «+»/«Создать +») и из Объекта, вкладка «Обслуживание» → «Добавить» → «+ Добавить».
Путь: Консоль администратора → Настройки заявки → «Автоназначение исполнителя» → «Создать правило»; либо на форме создания/редактирования Стадии заявки кнопкой «+» после выбора действия. Переключатель «Детальная настройка» задаёт степень важности параметров в процентах.
Путь: Консоль администратора → Настройки заявки → «Стадии заявки» → стадия → поле «Действие» = «Автоназначение по правилу» или «Автоназначение с учетом удаленности от заявки» → выбрать правило. Появляется параметр «Роль». Автопереход на стадию: Жизненный цикл заявки → переход → «Выполнить автоматический переход» + время [«Жизненный цикл заявки»].
Путь: Чек-листы (левое боковое меню HubEx) → «Создать чек-лист»: «Название чек-листа», «Описание», «Объекты», «Виды работ». Атрибут: Консоль администратора → Настройки системы → «Дополнительные поля» → «Создать новое поле» → «Наименование поля», «Тип поля» (напр. «Вложенный файл»), «Используется для» = «Чек-листы» [«Чаты, сообщения и доп.поля»]. Блокировки: Стадии заявки → требование «Обработаны чек-листы»; Поля на форме заявки → «RW» для поля «Чек-листы».

**Ограничения.** Правило SLA создаётся только на один Тип заявки, одну Критичность и один Вид работ, либо значение «Все» по каждому пункту. Выбор Объектов доступен только после выбора Заказчика(ов). Графики обслуживания и графики работ встроены в систему; уникальный график добавляет поддержка (Чат с поддержкой в web-приложении или help@hubex.ru). Конфликт правил SLA: работает то, которое по Графику обслуживания попадает на текущее время; при совпадении Графиков обслуживания — правило с наименьшим сроком закрытия. Для участия в автораспределении в карточке Сотрудника должен быть установлен флажок «Мобильный сотрудник». Чтобы выбрать Вид работ в Заявке по Объекту, Виды работ должны быть указаны в карточке этого Объекта и добавлены к Типу заявки. Вложенным файлом может быть фото или видео; в WEB-версии в чек-лист можно приложить .doc, .xls, .pdf; допускается несколько файлов к одному пункту.

**⚠ Грабли.** Установленный вручную «Крайний срок закрытия» правилом не изменяется. Новый Вид работ НЕ добавляется автоматически в уже созданные Объекты и НЕ привязывается к карточкам существующих сотрудников — привязка вручную; через карточку сотрудника создать новый вид работ нельзя, только добавить ранее созданный. Автоназначение: с выключенной «Детальной настройкой» выбранные параметры применяются с союзом «И», с включённой — с союзом «ИЛИ», в зависимости от выставленного процента. Переход на стадию с правилом может быть ручным или автоматическим — при ручном переходе подбор Сотрудника тоже выполняется автоматически. При создании новой Стадии заявки нужно изменить настройку Жизненного цикла заявки, если он уже создан и настроен. Вручную добавлять и удалять чек-листы в заявке можно только через WEB-версию, в мобильном приложении такой возможности нет; офлайн чек-лист заполняется и сохраняется, получает значок синхронизации и загружается автоматически при появлении сети. Карта расстояния до Объекта открывается в Заявке: «Исполнитель» → «Показать исполнителей на карте» [«Геотрекинг и карта»].

## Работы, акты приёмки и материалы в заявке

Учёт выполнения внутри заявки: выполненные работы, рекомендованные материалы, акт выполненных работ, оценка заявки. Материалы и склады как справочник — [«Склад, материалы и маркировка»], печатные формы — [«Печатные формы»].

**Модель.** Заявка → вкладка «Выполнение» → одна или несколько «Выполненных работ»; несколько работ, если заявка выполнялась в несколько этапов/дней или разделена на нескольких исполнителей. Поля работы: «Объект/Оборудование» (из заявки, не изменяется), «Вид работ» (из заявки, изменяем), «Исполнитель» (из заявки, изменяем), даты и время начала/окончания, «Комментарий», «Израсходованные материалы», «Файлы». Стоимость работы = стоимость «Вида работ» + «Ставка/час» исполнителя × часы + стоимость материалов. Акт выполненных работ — вкладка заявки, формируется автоматически из добавленных выполненных работ; все работы суммируются в один акт по заявке. Фиксирует выполнение услуг и финансовые обязательства заказчика; заказчик подписывает и оплачивает; есть оплата акта по QR-коду. В шапке акта — банковские реквизиты организации-исполнителя из карточки «Компании» ([«Компании и договоры»]); в составе — работы, материалы, ставка исполнителя. Вкладка «Необходимые материалы» — рекомендация материалов исполнителю до выезда; со склада не списываются и в расход не идут. Списание — только через материалы в выполненной работе; расход виден в «Склады → Расход». «Оценочная стоимость» и «Фактическая стоимость» — системные поля формы заявки, справочные. Оценка заявки — оценка работы сотрудника, выполнявшего её; по умолчанию критерий «Качество выполненных работ»; итог по нескольким критериям — среднее арифметическое; рейтинг сотрудника — среднее по оценённым заявкам, виден в справочнике «Сотрудники» и в карточке.

**Настройка.** Ставка: Путь: Пользователи → Сотрудники → карточка → вкладка «Квалификация» → «Ставка в час». Стоимость вида работ: Путь: Консоль администратора → Настройки заявки → Виды работ → «Стоимость». Критерии оценки: Путь: Консоль администратора → Настройки заявки → Критерии оценки заявки. Доступ к полям «Выполненные работы», «Необходимые материалы на форме заявки», «Рейтинг технического специалиста» — Путь: Консоль администратора → Настройки заявки → Поля на форме заявки, в разрезе ролей и стадий: RO / RW / RWM ([«Роли, полномочия и участки»], [«SLA, автоназначение и чек-листы»]). Реквизиты: Путь: Компании → Все компании → карточка. Доп. поля выполненных работ — см. [«Чаты, сообщения и доп.поля»]. Стоимость материалов задаётся при импорте складов и материалов, меняется через шаблон «Экспорта материалов» и загрузку обратно.

**Ограничения.** Ставка исполнителя кратна одному часу: при ставке 500 ₽ и работе 1 ч 35 мин итог 1000 ₽, не 790 ₽. «Ставка в час» — только в рублях, копейки через запятую можно; «Стоимость» вида работ — только в рублях, копейки добавить НЕЛЬЗЯ. Массовое заполнение ставки — только при создании сотрудников через импорт; массовое заполнение стоимости видов работ невозможно. Реквизиты должны быть заполнены и у вашей компании, и у компании-заказчика — иначе в акте они не отображаются и функционал не работает. Оценка доступна на стадиях «Выполнена» и «Закрыта» в web и мобильном приложении заказчика. Рейтинг сотрудника доступен только при включённой настройке «Мобильный сотрудник». Для заполнения акта нужна хотя бы одна выполненная работа.

**⚠ Грабли.** Подпись заказчика появляется в web-версии акта только после подписания через мобильное приложение исполнителя («Получить подпись» → ФИО подписанта, должность необязательна, подпись пальцем; телефон повернуть на 90° влево). Мобильный акт идентичен web-акту; «Поделиться» отправляет его картинкой .png. Необходимые материалы ≠ израсходованные: первые не списываются. Офлайн в «HubEx исполнитель»: выполненные работы, включая материалы и фото, добавляются без сети и синхронизируются позже (значок синхронизации); чек-листы офлайн заполняются без прикрепления фотографий; переход возможен только на одну стадию вперёд; нужно войти в приложение и дождаться кэширования заявок заранее (облачко: зелёное — загружено, голубое — идёт, красное — не удалось). Расчёт зарплаты — не встроенная функция: фильтр по исполнителю и периоду + расширенный экспорт с флажком «Выполненные работы», далее расчёт в .xlsx; при нескольких исполнителях по заявке в выгрузку попадают и чужие строки.

Источники: [user/ActOFAcceptance] [user/AttachingFiles] [user/Prices] [user/Rating] [user/OfflineMode] [user/TicketWithMaterials]

## Склад, материалы и маркировка

Учёт ТМЦ: склады и материалы, складские документы, расход по заявкам, сканирование Data Matrix. Меню web-версии «Склады»: «Материалы», «Расход», «Складские документы».

**Модель.** Материал ↔ склад ↔ количество. Склады создаются импортом материалов (поле «Название склада») или вручную; созданные при импорте доступны для выбора в карточках Сотрудников. Без доступных складов в карточке сотрудник не может указать расход. Расход фиксируется в заявке в выполненной работе (блок «Израсходованные материалы»), стоимость материалов идёт в Акт выполненных работ («Работы, акты приёмки и материалы в заявке»). Отчёт «Склады → Расход»: по заявке — дата загрузки, склад, количество, Сотрудник, Объект; переход в заявку по номеру. Складские документы — типы «Оприходование», «Списание», «Перемещение», «Инвентаризация», статусы «Черновик»/«Проведён»; черновик на остатки не влияет и в отчётах не отображается, проведённое оприходование обновляет остатки склада. Склады в документе: оприходование — «Со склада» = «—»; списание — «На склад» = «—»; перемещение — оба; инвентаризация — оба «—». Материал с признаком «Маркируемый материал» требует привязки кодов Data Matrix («Честный ЗНАК») к позиции списания. Сценарии: интеграция с 1С (ERP/Торговля/УНФ) — списания из выполненных работ автоматически уходят в 1С с настраиваемой периодичностью (час, день, иной интервал), поступления обновляют остатки в HubEx; «рюкзак» — отдельный склад на каждого выездного сотрудника.

**Настройка.** Путь: Склады → Материалы; кнопки «Импорт материалов» («Скачать форму шаблона»/«Загрузить готовый шаблон»), «Экспорт материалов». Поля шаблона: «Номенклатура материала», «Код номенклатуры» (синхронизация с другими системами), стоимость номенклатуры, «Название склада», «Количество на складе», «Единица измерения» (новые единицы добавляет поддержка). «Создать склад»: «Название склада» (обязательное), «Адрес склада», «Пользователи склада» (радио: «Никто» — доступен только пользователям с полномочием доступа ко всем складам / «Все» — всем сотрудникам тенанта / «По списку»), «ERP ID» (числовое), чекбокс «Выбрать основным складом». Вкладка «Материалы» → «Создать материал»: «Наименование» (обяз.), «Описание», «Артикул», «Единица измерения» (обяз., по умолчанию «Штука»), «Стоимость», «ERP ID», чекбокс «Маркируемый материал»; контекстное меню — «Копировать» (префикс «Копия»), «Удалить». Видимость складов — Путь: Пользователи → Сотрудники → карточка → «Квалификация» → блок «Доступные склады». Полномочия — Путь: Администрирование → Роли → Полномочия: блок «Материалы и склады» (пункты меню «Склады», «Склады - Материалы», «Склады - Расход», разрешение экспорта/импорта), блок «Выполненные работы и стоимость» → «Израсходованные материалы на форме выполненных работ», блок «Выполненные работы и стоимости» → «Элементы интерфейса» → «Сканирование кодов для списания единиц материалов». Обязательность сканирования — Путь: Настройки заявки → Поля на форме заявки: поле «Выполнение», уровень RWM для нужных ролей и стадий. Оприходование — «Складские документы» → «Создать документ»: «Номер» (авто при проведении или вручную), «Дата и время», «Склад» (до его выбора материалы и сохранение недоступны), «Тип операции», «Ответственный» (текущий пользователь), «Заявка» (необязательно); «Добавить материалы» — поиск по наименованию и артикулу.

**Ограничения.** За один раз загружается до 1000 материалов. Импорт совместим с Excel, ExcelOnline, частично с Google Spreadsheet, не совместим с Mac Spreadsheet. Поиск складов и материалов — только по названию или коду. Режим «По списку» требует ≥1 сотрудника. Проведение оприходования требует: склад, номер, дата и время, ответственный, ≥1 позиция с количеством больше 0. Data Matrix доступен на тарифах выше «Минимального»; кодов нельзя добавить больше, чем количество материала к списанию. «Списание», «Перемещение», «Инвентаризация» — в разработке, доступно только «Оприходование». Удаление загруженных данных — только по запросу на help@hubex.ru.

**⚠ Грабли.** Повторная загрузка остатков с другими кодами номенклатуры создаёт дубликаты позиций; для корректировки рекомендуется экспортировать перечень, править, загружать заново. Удаление материала со склада — количество 0. Уход остатков в «минус» при фактическом расходе допускается. В период обновления остатков списывать материалы в Заявках не рекомендуется. При копировании материала переносится и ERP ID. Удаление проведённого документа отменяет проведение и пересчитывает остатки; «Отмена проведения» возвращает его в «Черновик». При смене склада в документе добавленные позиции сохраняются. При выключенном переключателе сканирования его элементы в мобильном приложении не отображаются. Сканирование работает и офлайн, синхронизация автоматическая; в веб-версии привязанные коды только для чтения. Страница [user/Warehouses] — заглушка без содержания.

## Печатные формы

Документы по заявкам: три готовых формы в меню «Печатные формы» (Сервисный акт, Бухгалтерский акт, Счёт на оплату) и «Конструктор печатных форм» для собственных шаблонов, встраиваемых вкладками в заявку.

**Модель.** Готовые формы строятся за период индивидуально по одному Заказчику, могут включать сведения по нескольким Заявкам сразу. Заказчик выбирается из Компаний с типом «Заказчик» или «Наша компания» [«Компании и договоры»]. Отбор Заявок: Объект → Стадия → период «С»–«По» (переход на выбранную стадию) → ручной выбор в поле «Заявка». Сервисный акт: работы, трудозатраты исполнителей, израсходованные материалы [«Работы, акты приёмки и материалы в заявке»]. Бухгалтерский акт: унифицированная форма факта продажи услуги, реквизиты по п. 2 ст. 9 ФЗ №402-ФЗ от 06.12.2011 (название и дата документа, реквизиты сторон, перечень услуг/материалов, стоимость, должности и подписи). Счёт на оплату: платёжные реквизиты продавца; формируется исходя из выполненных работ по отфильтрованным Заявкам. Конструктор: шаблон = текст + стандартные таблицы + переменные `{{...}}`; каждый шаблон даёт свою вкладку в заявке с динамической подстановкой.

**Настройка.** Путь: Печатные формы → Сервисный акт / Бухгалтерский акт / Счёт на оплату. Поле «Компания» — наша компания, реквизиты в шапке. «НДС»: «Без НДС», «Без НДС (вычитание НДС)», «НДС сверху», «НДС включен». У Бухгалтерского акта и Счёта: «Тип акта»/«Тип счета» = «Сводный акт»/«Сводный счет» либо «По каждой заявке»; «№ акта»/«№ счета» свободной формы. Кнопка «Просмотр отчета»; печать — «Файл → Печать»; экспорт — «Главная → Экспорт» (pdf, xlsx, docx, xml и др.; для правки рекомендуется docx). Конструктор: Конструктор отчётов → «+» → «Название» (= название вкладки), «Описание» (необязательно) → «Сохранить». Меню трёх точек: «Удалить», «Деактивировать»/«Активировать».

**Ограничения.** При подключении каждой из трёх форм в панели «Параметры» доступно ограниченное количество фильтров; расширение — через help@hubex.ru. В поле «Объект» выбирается только родительский объект (дочерние выбираются автоматически). Конструктор не поддерживает: кастомизируемые таблицы, вычисления в форме, условное отображение блоков — такие формы делает команда HubEx в рамках индивидуальных доработок. Стандартные таблицы конструктора: чек-листы, список выполненных работ.

**⚠ Грабли.** У Бухгалтерского акта и Счёта поле «Стадия» по умолчанию — «Выполнена» (стадия с действием «Завершить работу по заявке»); у Сервисного акта умолчание не указано. «№ акта»/«№ счета» по умолчанию берётся из номера Заявки; заполненное поле выводится перед номером Заявки. При изменении любых настроек «Просмотр отчета» нужно нажимать повторно. Логотип компании отображается в левом верхнем углу Сервисного акта; без загруженного логотипа — стандартный логотип HubEx [«Первые шаги, база знаний и брендирование»]. В конструкторе переменная вставляется в конец формы — переместить вручную; дата-время подставляется по часовому поясу тенанта (по умолчанию); отсутствующее значение даёт пустую строку; «Распечатать» вызывает окно печати браузера, PDF — средствами браузера. Деактивированная форма скрыта в заявках, но сохранена.

## Чаты, сообщения и доп.поля

Переписка внутри «Заявки» (web и мобильные приложения), шаблоны ответов и механизм дополнительных полей для сущностей системы. Смежное: [«Интеграции, API и клиентские приложения»] — интеграции и клиентские приложения, [«Атрибуты, согласование и приоритизация заявок»] — атрибуты заявок, [«Роли, полномочия и участки»] — роли и полномочия.

**Модель.** Для каждой «Заявки» есть обмен сообщениями; все сообщения по «Заявкам», включая новые и непрочитанные, собираются в пункте меню «Сообщения» — и в web, и в мобильных приложениях. Участники чата добавляются/удаляются вручную. По запросу открывается разделение на «Чат с командой» и «Чат с заказчиком»: заказчику в мобильном приложении доступны переписка и просмотр только в чате с заказчиком; «Сотруднику» в мобильном и web доступен чат с командой, если его добавили в чат по кнопке «+», и чат с заказчиком, если для его «Роли» настроен доступ. Шаблоны ответов — библиотека готовых текстов для чатов с заказчиками и с исполнителями, привязывается к «Типам заявок». Telegram-бот: сообщения пользователя после подтверждения о приёме заявки попадают в чат с заказчиком по созданной «Заявке» (подробнее в [«Интеграции, API и клиентские приложения»]). Дополнительные поля — единый механизм для 6 сущностей: Компании, Объекты/оборудование, Заявки, Выполненные работы, Чек-листы, Договоры; доп.поле чек-листа — это «Атрибут» ([«SLA, автоназначение и чек-листы»]).

**Настройка.** Доступ к чатам: Консоль администратора → «Администрирование» → «Роли» → «Полномочия» → блок «Сообщения» → подключить нужные чаты. Шаблоны: «Сообщения» → «Шаблоны ответов» → «Создать шаблон», либо кнопка «Шаблоны ответов» в чате внутри «Заявки». В шаблоне обязательны название и текст; область — «Для всех» либо «По списку» «Типов заявок». Доп.поля: Консоль администратора → «Настройки системы» → «Дополнительные поля» → «Создать поле»; поля формы — «Название поля» (обяз.), «Тип поля» (обяз.: Строка, Целое число, Дробное число, Дата, Дата и время, Значение из списка (единственный/множественный выбор), Многострочный текст, Переключатель, Вложенный файл, Значение из справочника (единственный/множественный выбор)), «Единица измерения» (необяз.), «Используется для» (обяз., можно несколько сущностей), «Показывать в паспорте объекта» (необяз.). Видимость доп.полей заявки: Консоль администратора → «Настройки заявки» → «Поля на форме заявки» — выбрать «Роли пользователей» и «Стадии заявки», задать RO/RW/RWM ([«Атрибуты, согласование и приоритизация заявок»]). В объекте доп.поле добавляется на вкладке «Дополнительные поля» кнопкой «+Добавить поле».

**Ограничения.** В чат можно отправить от 1 до 10 фотографий в одном сообщении. Из чата нельзя удалить назначенного исполнителя и инициатора заявки. В уже созданном доп.поле нельзя изменить «Тип поля» — нужно создать новое, а старое удалить. Обращение в поддержку HubEx: web — знак вопроса в правом верхнем углу (руководство пользователя или чат поддержки); мобильное — боковое меню → «Поддержка» → «Сообщить о проблеме».

**⚠ Грабли.** Шаблон ответа вставляется в текстовое поле, его можно отредактировать и только затем отправить. В web-приложении сообщение уходит в оба чата через чек-бокс «Также отправить сообщение команде» / «Также отправить сообщение заказчику»; в мобильном приложении исполнителя чаты переключаются. «Показывать в паспорте объекта» действует только для доп.поля объекта/оборудования (паспорт — данные, отражаемые в мобильных приложениях исполнителя и заказчика при сканировании QR-кода, см. [«QR-коды, паспорт и планы объектов»]). Доп.поля компаний и договоров становятся доступны и в уже существующих карточках, и в новых; в карточке компании они внизу под «Контактными лицами», в карточке договора — внизу. Доп.поля заявок располагаются внизу таблицы «Поля на форме заявки» и могут использоваться в фильтрации и поиске заявок.

## Уведомления

Подсистема оповещений: событие в системе преобразуется в сообщение и доставляется на email или push-уведомлением на мобильное устройство/в web-приложении. Настраивается в консоли администратора; лента прочтения — в мобильных и web-приложениях.

**Модель.** Два объекта: «Правило выбора получателя» (кто получит) и «Триггер уведомления» (условие запуска + шаблон сообщения + способ отправки + ссылки на правила; правил в триггере может быть несколько). Правило задаёт: категорию получателей (одну, напр. «Выбранный исполнитель по заявке»), конкретного пользователя, одну «Роль», а также «Email адреса» и «Номера телефонов» через запятую. Триггер: «Шаблон сообщения» → «Описание сообщения» (готовый шаблон для «Заголовка сообщения» и «Текста сообщения»), «Способы отправки сообщения» (Push / Email), при Push — «Куда отправлять сообщения» (какое мобильное или веб-приложение, напр. «Мобильное приложение инженера»), «Условия отправки»: «Событие, из-за которого сработает триггер», «Критичности заявки…» (из «Настройки заявки → Критичности заявки», можно несколько), «Стадии заявки…» (можно несколько). Лента уведомлений показывает события: создание заявки, назначение на заявку, снятие назначения, переход на стадии, сообщения по заявке; в мобильной ленте отображаются отправленные пользователю push- и sms-уведомления. Заказчику приходят только уведомления, настроенные для него в консоли; в web отображаются только события с настроенными триггерами.

**Настройка.** Путь: Консоль администратора → Настройки оповещений → Правила выбора получателя (кнопка «Создать правило выбора получателя»). Путь: Консоль администратора → Настройки оповещений → Триггеры уведомления (кнопка «Создать триггер уведомления»); в общем списке триггер включается/выключается переключателем, контекстное меню (три точки) → «Копировать» создаёт копию внизу списка («Копия <название>»). Email-уведомления себе: иконка аватара → «Включить Email-уведомления». Лента: web — иконка колокольчика в правом верхнем углу; мобильное «HubEx исполнитель» — основное меню → «Уведомления»; кнопка «Прочитать все», переключатель «Только непрочитанные».

**Ограничения.** В правиле «Получатели уведомления» — одна категория, «Роль» — одна. Способ отправки: Push или Email. Текст шаблона общий: правка меняет его во всех триггерах с этим шаблоном — рекомендуется скопировать текст и создать новый шаблон. Разметку в заголовке и тексте (`@Model.TaskNumber` и т.д.) удалять нельзя. Кнопка «Прочитать все» становится неактивной, когда всё прочитано.

**⚠ Грабли.** Выбор и конкретного пользователя, и его «Роли» в одном правиле → 2 уведомления. Заполнение и «События…», и «Стадий заявки…» в триггере → 2 уведомления. События со словом «отложенное» (напр. «Изменено назначение по заявке (отложенное)») приходят не моментально, а спустя пару минут — защита от смены ошибочно назначенного исполнителя. Настраивать оповещения рекомендуется под одной учётной записью в web, проверять получение — в «HubEx исполнитель» под другой. При смене способа отправки на Email сначала установить «Не выбрано» (сброс), затем Email и нажать кнопку «М» со стрелкой вниз (параметр разметки). Если push не приходят — разрешить показ всех и всплывающих уведомлений в настройках приложений ОС; рекомендуется после подключения выйти из приложения («Выйти»), полностью закрыть и войти заново. Пустая лента: в мобильном — «Все уведомления прочитаны», в web — «Уведомлений нет». Тексты уведомлений и чаты по заявке — см. [«Чаты, сообщения и доп.поля»].

## Аналитика Power BI

Семейство аналитических панелей HubEx на платформе Power BI. Меню **Аналитика**: «Общая аналитика», «Отчет по сотрудникам», «Отчет по объектам обслуживания», «Отчет для клиента», «Анализ эффективности процессов». Данные во всех отчётах обновляются один раз в сутки, дата обновления показана на панели. Плоские выгрузки — «Отчёты и экспорт».

**Модель.** Все панели строятся на данных «Заявок»: «Общая аналитика» — по заявкам, «Отчет по сотрудникам» — заявки в разрезе сотрудников, «Отчет по объектам обслуживания» — в разрезе объектов, «Отчет для клиента» — в разрезе заказчиков, «Анализ эффективности процессов» — по маршрутам стадий. Расчёты зависят от заполнения вкладки «Выполнение» в заявке (время работ), графиков работы в карточке «Сотрудника», рейтинга заявки, «Крайнего срока закрытия». Просроченная заявка — закрытая позже крайнего срока.
Процесс = последовательность прохождения заявки по конкретному набору стадий; разные наборы («Новая — Назначена — В работе — Выполнена — Закрыта» против маршрута с «Не принята исполнителем») — разные процессы. Цикл — прохождение через одну/несколько одинаковых стадий более одного раза.
«Коэффициент полезной загрузки исполнителей» (Utilization Rate) = длительность всех выполненных работ за период / часы по графикам работ. «Количество выполненных заявок на исполнителя» = выполненные заявки за период / среднедневное количество исполнителей по графику. «HubEx Рейтинг» считается по четырём показателям: количество закрытых заявок за период, % закрытых с нарушением SLA, количество выполненных работ (часов), рейтинг от заказчиков; значение 1 — самый эффективный за период. MTBF — среднее число часов между возникновением заявок; MTTR — среднее время выполнения работ на объекте. «Отработано всего» учитывает пересечение времени (три работы 12:00–13:00 = 1 час), «Выполнено работ» — без учёта пересечения (те же = 3 часа). «Переработки» — часы из «Выполнения», не входящие в График работы. Активный объект — объект, по которому за последние 4 недели создана хотя бы одна заявка; аналогично активный родительский объект. «SLA подрядных организаций» = закрытые с просрочкой / все закрытые за предыдущий месяц.
Разбиение исполнителей на 4 квадранта в «Сравнение эффективности исполнителей» по осям «Среднее кол-во выполненных заявок в день» и «Закрыто в срок, %» относительно средних по организации: 1-я (верх-право) — оба выше среднего; 2-я (верх-лево) — мало заявок, без нарушений SLA; 3-я (низ-лево) — мало заявок и нарушения SLA; 4-я (низ-право) — много заявок с просрочкой, перегружены. Заявки с 4-й категории можно переназначать на 2-ю.

**Настройка.** Путь: Аналитика → Общая аналитика / Отчет по сотрудникам / Отчет по объектам обслуживания / Отчет для клиента / Анализ эффективности процессов. Период — слева вверху. Кнопка «Фильтров» / «Открыть панель фильтров» (справа): «Тип заявки», «Участок», «Должность», «Вид работ» и т.д.; фильтр применяется ко всем визуализациям панели (в «Отчете по сотрудникам» — на всех вкладках). В «Анализе эффективности процессов» для «Варианта А» и «Варианта В» доступны свои наборы фильтров.
Вкладки «Отчета по сотрудникам»: «Заявки и SLA», «Отработанное время», «Показатели и KPI»; плюс отчёт-карточка сотрудника — щелчок по ФИО в любой визуализации и кнопка-стрелка на панели настроек. Вкладки «Анализа эффективности»: «Выявление проблем в бизнес-процессах», «Сравнение эффективности бизнес-процессов», «Время прохождения заявок по стадиям» (поля «Со стадии 1» и «На стадию 2»).
Детализация: кнопки «Открыть аналитические разрезы» / «Включить аналитические разрезы», добавление разреза по «+», сброс — крестик у характеристики. Детализация по дням/неделям/месяцам — кнопки ↑ / ↓↓ при наведении на визуализацию. «Режим фокусировки» — разворот визуализации. Выбор показателя визуализации — «Открыть меню визуализации» / «Открыть параметры визуализации» (синяя шестерёнка). Экспорт в Excel: контекстное меню (три точки) → «Экспортировать данные». В «Отчете по объектам обслуживания»: переключение таблицы показателей с плоской структуры на иерархическую, переход по кнопке «В отчет по объекту», возврат кнопкой «Назад» (синяя стрелка). Флажки «Мобильный сотрудник» и «Отслеживать местоположение сотрудника», «Должность» — в карточке «Сотрудника» («Роли, полномочия и участки», «Приглашения, доступ и графики работы»); геотрекинг — «Геотрекинг и карта».

**Ограничения.** «Количество переходов по стадиям» — по умолчанию ограничение отображения до 30 000 переходов; расширение — через чат с поддержкой в web-приложении или help@hubex.ru. Период активности объекта задан значением 4 недели, изменяется по кнопке «Фильтров» в диапазоне от 1 до 7 недель. Межотраслевой стандарт Utilization Rate — 80%, отмечен на графике чёрной линией. Экспортировать в Excel можно только таблицу с плоской структурой. На вкладках «Выявление проблем» и «Сравнение эффективности процессов» рассматриваются только закрытые заявки; выбранный период — период создания заявок. Если рейтинг не используется, в отчёте будет прочерк. «Коэффициент полезной загрузки исполнителей» в «Общей аналитике» фильтруется только в разрезе исполнителей.

**⚠ Грабли.** «Отработано всего» и «Выполнено работ» расходятся при пересечении времени работ — это разные показатели, а не ошибка. Переработкой считается любой час из «Выполнения» вне графика работы, даже если других работ в этот день не вносилось. Без актуальных графиков работы в карточках сотрудников и заполненной вкладки «Выполнение» Utilization Rate, «Количество выполненных заявок на исполнителя», MTTR и переработки считаются некорректно. Чем больше число «HubEx Рейтинга», тем хуже: 1 — лучший. «Просрочено» в «Отчете для клиента» включает и активные, и выполненные заявки с истёкшим крайним сроком. Мини-диаграмма просроченных заявок в «Общей аналитике» — сама фильтр: щелчок по красному сектору фильтрует все диаграммы.

## Отчёты и экспорт

Аналитическая панель «Срез по заявкам», выгрузка справочников в Excel и загрузка данных по шаблонам Excel. Календарь-планировщик «Расписание заявок» — рабочий инструмент диспетчера по назначению заявок; внешняя BI-аналитика — [«Аналитика Power BI»].

**Модель.** «Срез по заявкам» — панель диаграмм: статистика по «Заявкам» на стадиях, просроченные, время выполнения работ в разрезе «Объектов»; количество «Заявок» в разрезе «Компаний»; загруженность исполнителей по количеству назначенных «Заявок». Экспорт/импорт охватывают «Заявки», «Объекты|Оборудование», «Пользователей» (раздельно «Сотрудники» и «Заказчики»), «Компании» — формат Excel. Импорт — только по скачанному из HubEx шаблону Excel; поля шаблона соответствуют полям карточки сущности (для объектов — за исключением географических координат адреса). Повторная загрузка дополненного шаблона не дублирует ранее загруженное. При импорте объектов новая «Компания», «Класс», «Участок» создаются автоматически, если вписаны отсутствующие; «Тип объекта» и «Вид работ» берутся из существующих списков (создаются в консоли администратора — [«Типы и классы объектов»], [«SLA, автоназначение и чек-листы»]). Для импорта «Заявок» в системе должен быть создан хотя бы один «Тип заявки». Календарь «Расписание заявок» — три режима (день, неделя, месяц), вкладки «Неназначенные», «Назначенные», «Планировщик»; неназначенные раскладываются по «Крайнему сроку закрытия», в недельном — в строке «Без исполнителя». Индикатор загрузки: часы, число «Заявок», цветная шкала из 8 точек. Индикатор смены: зелёный — на смене, серый — нет ([«Приглашения, доступ и графики работы»]).

**Настройка.** Путь: Аналитика → Срез по заявкам. Путь: Заявки → Все заявки (кнопки «Экспорт заявок», «Импорт»). Путь: Объекты|Оборудование → Объекты|Оборудование (кнопка «Экспорт объектов и оборудования»). Путь: Пользователи → Сотрудники / Пользователи → Заказчики («Экспорт сотрудников», «Экспорт заказчиков»). Путь: Компании («Экспорт компаний»). Варианты экспорта заявок и объектов: «Обычный экспорт» (минимальный набор основных полей) и «Расширенный экспорт» (пользователь сам выбирает поля). Для заявок доступен вариант «Экспорт вложений». Путь: Заявки → Расписание заявок; шестерёнка справа вверху → флажок «Показывать выполненные заявки»; кнопка «Фильтровать сотрудников» → отбор по «Видам работ», «Участкам», «Компаниям», «Ролям», признаку «Мобильный сотрудник» → «Применить». Редактирование смены — контекстное меню (три точки) → «Редактировать смену».

**Ограничения.** Единоразовая загрузка при импорте: «Заявки» до 2000 строк, «Объекты» до 2000, «Компании» до 100. Экспорт и импорт полностью совместимы с Excel, ExcelOnline, частично с Google Spreadsheet, не совместимы с Mac Spreadsheet; сторонние сервисы для работы с шаблонами не рекомендуются. Экспорт медиафайлов — архив с папкой на каждую «Заявку» (номер и наименование оборудования), внутри — файлы вкладок «Заявка», «Чек-листы», «Выполнение». Уведомления при назначении в «Расписании заявок» приходят с задержкой в 5 минут по умолчанию.

**⚠ Грабли.** Настройки экспорта (вариант и выбор полей расширенного) сохраняются локально за пользователем для текущего браузера и компьютера, не в системе. Фильтры справочника действуют на экспорт, в том числе на экспорт медиафайлов — выгружается только отобранное. При копировании данных в шаблон импорта вставлять нужно только значения: обычная вставка Ctrl+V переносит формат и стирает данные справочников в шаблоне. Импорт заявок идёт в фоновом режиме, заявки загружаются постепенно. Заявки в списке «Назначенные» не фильтруются. Признак «Мобильный сотрудник» в фильтре сотрудников по умолчанию включён — остальные сотрудники не видны, пока флажок не снят. Заявка без заполненных «Даты и времени выполнения» не отображается в календаре у исполнителя. При назначении через календарь срок берётся из плановых трудозатрат, либо по умолчанию 4 часа; при создании заявки с выбором исполнителя «Окончание» = плановые трудозатраты «Вида работ», а если они не заполнены — по умолчанию +1 час. Переназначение или перенос в течение 5 минут отменяет push первому исполнителю.

## Геотрекинг и карта

Карты в web-приложении и мобильных приложениях: текущее положение сотрудников и заявок, ретроспектива перемещений, построение маршрута до объекта. Назначение заявок с карты — здесь; стадии и атрибуты заявок — [«Жизненный цикл заявки»], [«Атрибуты, согласование и приоритизация заявок»]; геонастройки устройств — [«Геонастройки устройств»].

**Модель.** Три инструмента для геопозиции **Сотрудника**: меню «Карты → Карта»; «Заявки → Все заявки» → кнопка «Заявки на карте»; в **Заявке** при выборе исполнителя («Выбрать исполнителя из списка» → «Показать исполнителей на карте»; адрес заявки отмечен флажком, исполнители — кружком с инициалами или аватаром). Функционал «Карты → Карта» аналогичен режиму «Заявки на карте». **Заявки** на карте — булавки (пины); при уменьшении масштаба группируются в один пин, разные **Объекты** по одному адресу тоже объединяются; в центре пина — количество заявок по адресу. Цвета пина: красный — просроченные (дата закрытия меньше текущей), синий — назначенные, жёлтый — неназначенные; сектора — комбинации. Два списка справа: «Неназначенные» и «Все»; цвет заявки в списке зависит от «Критичность». Календарь загруженности показывает загрузку сотрудников на день и путь исполнителя по карте (планируемый маршрут от заявки до заявки). **История перемещений** — ретроспектива: время в пути, на заявке, остановки, простои.

**Настройка.** Путь: Карты → Карта. Путь: Карты → История перемещений. Путь: Заявки → Все заявки → «Заявки на карте». Пункт меню включается: Администрирование → Роли → «Полномочия» → блок «Карты» → «Пункт главного меню - Карта». Отображение перемещений исполнителя: в карточке **Сотрудника** флажок «Отслеживание местоположения сотрудника» (он же «Отслеживать местоположение сотрудника») + разрешение приложению **HubEx исполнитель** читать геопозицию в настройках телефона iOS/Android. В «Истории перемещений» флажок «Отображение объектов» показывает все родительские объекты, доступные пользователю, чёрными метками. Навигатор для маршрута: настройки аккаунта мобильного приложения → поле «Приложение для навигации».

**Ограничения.** История перемещений доступна только в web-версии; отчёт обновляется один раз в день — при дате позднее даты обновления данные не отобразятся. Координаты считываются не чаще одного раза в три минуты, а также при перемещении на 10 и более метров; погрешность координат — 10 метров. Остановка — нахождение в точке радиусом 200 метров более 5 минут. Назначение с карты: заявка ставится на ближайшее время (14:45 → 15:00, 13:10 → 13:30), продолжительность — из плановых трудозатрат, либо по умолчанию 4 часа (трудозатраты задаются в карточках «Видов работ» или «Типов заявки»). Карту в мобильном приложении в офлайн-режиме открыть нельзя.

**⚠ Грабли.** Геотрекинг — не онлайн-слежение: обновление раз в день, в отличие от «Карты → Карта» с текущей геопозицией. Перетаскивание заявки на маркер исполнителя — правой кнопкой мыши. При назначении из «Неназначенные» заявка пропадает из списка, из «Все» — получает маркер с инициалами. Энергосбережение Android (HTC, Huawei, LG, Samsung, Sony, Xiaomi) ломает GPS — приложение HubEx исключить из оптимизации батареи.

## Платформа и деплой

HubEx FSM — отечественная ERP-система класса FSM (Field Service Management) для сервисных подразделений с мобильным персоналом: ремонты, техобслуживание, обходы, клининг. Раздел покрывает состав платформы, способы расширения, техстек и три варианта развёртывания.

**Модель.** Реестр российского ПО с 15.07.2020, рег. номер №6816. Компоненты: мобильное приложение (iOS/Android, исполнитель работ, обходчик, ИТР, техник, мастер смены + отдельное приложение заказчика работ); WEB-приложение для офисного персонала (руководители, диспетчеры, логисты, менеджеры); панель администрирования (конфигуратор); открытый API + документация в Swagger; БД; сервер приложений; сервер логирования; 1С-конфигурация (опционально, для упрощения интеграции с 1С-совместимыми системами). Мобильное приложение может использоваться отдельно от платформы — подключается по API к HelpDesk/ServiceDesk/ТОиР системе компании. Электронный паспорт объекта — репозиторий данных об оборудовании (параметры, история обслуживания, документация, гарантия, контакты), может дополняться QR/NFC-меткой; подробнее [«QR-коды, паспорт и планы объектов»].

Уровни расширения по возрастанию трудоёмкости: конфигуратор (без кода) → HubEx Automate (low-code, визуальный конструктор: интеграции REST API/SOAP, автоматизации сценариев, новые интерфейсы, печатные формы по шаблонам, BI-отчёты) → плагины (любой язык, встройка через iFrame, в WEB и мобильное) → проектные доработки (отдельная ветка разработки под клиента) → продуктовые доработки (в основной продукт, приоритезирует продуктовая команда HubEx). Конструктор отчётов — Power BI или Apache SuperSet, любой отчёт можно добавить в меню навигации WEB или мобильных приложений; см. [«Аналитика Power BI»], [«Отчёты и экспорт»].

Позиционирование против смежных классов систем — [«Позиционирование против смежных классов»].

**Настройка.** Вход в консоль администратора: web-приложение → значок аватара в правом верхнем углу → «Консоль администратора». Открывается в новом окне; на основной странице — информация об аккаунте (подписка, количество пользователей), слева меню («Роли», «Участки», «Жизненные циклы» и др.). Если войти не удалось — не хватает прав доступа; обращение в «Чат с поддержкой» (кнопка рядом с аватаром, красный вопросительный знак) или help@hubex.ru. Telegram-бот по возможностям системы: @HubexWikiBot.

Установка мобильного приложения: APK-файл, MDM-система заказчика или публичные магазины приложений.

**Ограничения.** Требование мобильного приложения: Android 6.0 и выше (в т.ч. специализированные Android-терминалы) либо Apple-смартфоны.

Варианты развёртывания:
1. **Public cloud** — общее облако, кластер высокой доступности, более 20 серверов; основной ЦОД Санкт-Петербург (Tier 3), резервный — Москва (холодный резерв, переключение при выходе из строя основной площадки). На август 2024 — более 100 организаций. Рекомендуется до 500 пользователей; свыше 500 работать могут, но подходят варианты 2/3. Интеграции: свыше 10 запросов/сек не поддерживаются, при превышении доступ может быть принудительно ограничен, интеграция отключена. Окно обслуживания обычно 22.00–24.00 вторник и четверг, перенести нельзя. Восстановление данных — только для всех клиентов облака одновременно; восстановление данных отдельного клиента крайне трудозатратно, а в ряде случаев невозможно. Минимальная стоимость.
2. **Cloud на выделенных серверах** — отдельные серверы, нагрузка других клиентов не влияет. Серверные лицензии и обновления на 30% дешевле варианта 3. Возможны индивидуальные бэкапы/восстановления, индивидуальные окна обслуживания, повышенная нагрузка от интеграций (свыше 10/сек без рисков отключения), георезервирование (реплика в Москве).
3. **On-premises** — на серверах заказчика, работа в закрытом периметре. Серверные лицензии и обновления на 30% дороже варианта 2. Индивидуальное окно обновления — опция. Рекомендуется при более 1000 пользователей. Минусы: доп. работы по поддержке в закрытом контуре, затраты на Change management/Release management/согласования СБ.

Конфигурации серверов для вариантов 2 и 3: **Бронза** — без кластера, один физический сервер, по одному виртуальному каждого вида; отказ любого сервера останавливает систему; до 1000 пользователей. **Серебро** — кластер высокой доступности, 2 физических сервера: 3 сервера приложений, 2 БД, 2 WEB, 4 функциональных; 1000–3000 сотрудников. **Золото** — 4 физических сервера: 5 серверов приложений, 4 БД, 2 WEB, 4 функциональных; более 3000 сотрудников.

Техстек: Linux Ubuntu + Nginx (веб-серверы), Windows + Service Fabric, Node.js, .NET; сервисные приложения в Docker на Ubuntu; БД — MS SQL Server и PostgreSQL; сборка — vsts-agent-win-x64/linux-x64. Разработка: .NET/C#, ASP.NET Core, SignalR, RabbitMQ + Rebus, кластеризация Azure Service Fabric, авторизация Keycloak, работа с БД ADO.Net. Мобильное: React Native, JavaScript, SQLite, Firebase (уведомления, deeplinks). Web: ReactJS, JavaScript, Webpack, Redux, Firebase.

Трудоёмкость: фича на HubEx Automate — 20–40 часов; плагин — от 20 часов; проектная разработка — сотни часов; минимальная продуктовая фича — от 500 часов. Стоимость продуктовых доработок обычно в 5–10 раз выше проектных.

**⚠ Грабли.** Проектные доработки НЕ делаются в публичном облаке HubEx Cloud — требуют локального развёртывания или выделенных серверов. То же для самостоятельного использования Power BI / Apache SuperSet. Обязательное условие проектных доработок, плагинов и доработок HubEx Automate силами вендора — пакет расширенной технической поддержки у клиента; для индивидуальных отчётов и небольших автоматизаций HubEx Automate поддержка включена в стоимость лицензии на отчёт. Отдельная ветка разработки расходится по коду с продуктом: замедляется обновление до новых версий, растёт стоимость поддержки; при отказе от обновлений возможность обновляться может быть утрачена вовсе. Под отдельную ветку планируется отдельная команда: .NET+SQL back-end, React front-end, React Native мобильный, тестировщик, аналитик, РП. На лето 2024 HubEx Automate не позволяет изменять уже существующие в системе интерфейсы, только создавать новые. Плагин не умеет взаимодействовать с данными системы, ещё не сохранёнными пользователем на сервер. В варианте 2 время решения проблем меньше, чем при локальном размещении, — не нужны согласования доступов в закрытый периметр заказчика. При on-premises уровень надёжности может быть максимальным, если надёжность локальной инфраструктуры выше Tier 3.

Требования к мобильному устройству исполнителя и настройка геолокации ОС для корректной передачи геопозиции из приложения «HubEx исполнитель». Использование геоданных на карте и история перемещений — «Геотрекинг и карта».

**Модель.** Приложения: «HubEx исполнитель», «HubEx заказчик» (Android — Google Play, iOS — App Store). Определение местоположения: GPS и ГЛОНАСС + сигналы GSM и Wi-Fi; Wi-Fi-модуль включают для позиционирования при отсутствии GPS-сигнала (подключаться к сети не нужно). Фиксирование передвижений исполнителя обеспечивает служба GPS устройства. Корректное считывание геопозиции требует также флажка «Отслеживать местоположение сотрудника» в карточке «Сотрудника».

Samsung: «Настройки → Подключения» (Wi-Fi); «Настройки → Локация» → «Разрешения приложений» → «Разрешить в любом режиме». Xiaomi: «Настройки → Местоположение» → «Доступ к местоположению»; «Настройки → Приложения → Все приложения → Разрешение приложений → Местоположение» → «Разрешать в любом режиме» + «Использовать точное местоположение». Huawei: «Настройки → Данные о местоположении»; «Настройки → Приложения → Права → Геоданные» → «Разрешать всегда». Дополнительно на Android снимают ограничения энергосбережения/оптимизации батареи, фонового режима, экономии трафика, автозапуска (пути даны для Samsung, Xiaomi, Huawei, а также HTC, LG, Sony).

## Первые шаги, база знаний и брендирование

Стартовый порядок настройки HubEx, глоссарий терминов, встроенный ИИ-помощник, подключаемая база знаний, брендирование логотипом.

**Модель.** Работа складывается из двух частей: пользовательские приложения (web и мобильные — заполнение справочников, заявки, аналитика) и консоль администрирования (доступ, работа с заявками, интерфейс). Перед созданием заявок заполняются справочники в порядке: обслуживаемые Компании → Объекты/оборудование → Заказчики → Исполнители. Компании — юр- или физлица, выступающие заказчиками и (или) подрядчиками; туда же вносится своя организация, от лица которой ведётся учёт. Два типа пользователей: «Сотрудники» (лицензируемые, web + приложение «HubEx исполнитель», создают и выполняют заявки; диспетчер, руководитель, сервисный специалист) и «Заказчики» (создают заявки в мобильном приложении заказчика, привязаны к компании-заказчику) — подробнее [«Отличия ролей и вход в систему»], [«Приглашения, доступ и графики работы»]. Объект (оборудование) — элемент инфраструктуры, аналог конфигурационной единицы в ITSM, привязан к компании-заказчику; [«Типы и классы объектов»], [«Создание и редактирование объектов»]. Способы подачи заявки: вручную (web/мобильные), полуавтоматически сканированием QR-кода [«QR-коды, паспорт и планы объектов»], импортом Excel. Глоссарий сводит термины, раскрытые у соседей: жизненный цикл, стадия, статус, тип заявки, срок закрытия — [«Жизненный цикл заявки»], [«Атрибуты, согласование и приоритизация заявок»]; вид работ, навыки, автораспределение, чек-листы — [«SLA, автоназначение и чек-листы»]; участок — [«Роли, полномочия и участки»]. База знаний — дополнительно подключаемый виджет компании-партнёра HiHub с собственной авторизацией; иерархия: пространства → разделы → статьи; свои роли (Администратор / Редактор / Пользователь), не роли HubEx. HubEx AI — встроенный чат-бот в web-интерфейсе, отвечает по материалам HubEx Wiki, хранит историю переписки (её можно очистить).

**Настройка.** Путь: Боковое меню → Компании → «Создать компанию» (перед началом работы там уже есть одна — ваша). Путь: Боковое меню → Объекты|Оборудование → «Создать объект». Путь: Боковое меню → Заявки → «Создать заявку» (обязательны объект, адрес, описание и др.). Мобильные приложения: «HubEx исполнитель», «HubEx заказчик» (Android, iOS). Подключение базы знаний — запрос в help@hubex.ru; после подключения появляется пункт меню «База знаний», виден пользователям с полномочием роли «Доступ к подключаемым плагинам и отчетам». В БЗ: Пространства → «Создать новое рабочее пространство»; раздел — «+Добавить статью (\/) → Добавить раздел»; учётки — Инструменты → Приглашения; роль — Инструменты → Пользователи пространства → Действия → «Установить роль» / «Удалить из пространства». HubEx AI — иконка 🤖 в правом верхнем углу web-интерфейса. Логотип для брендирования отправляется в help@hubex.ru письмом с файлом.

**Ограничения.** Импортом можно загрузить до 1000 заявок за раз. В базе знаний можно зарегистрировать 5 учётных записей, включая созданную администратором при первом входе. Статусы статьи: «Опубликовано» — всем пользователям; «Черновик» — только учётной записи-автору и администраторам; «Архив» — только редакторам и администраторам. Брендирование доступно для web- и мобильного приложения; обязательное условие — подписка «Корпорация». Логотип: для мобильных .png 364×64 px, для web .svg 91×32 px; шрифты в .svg преобразовать в кривые. Логотип компании отображается в web-приложении, в Сервисном акте, в Отчёте для клиента, в Акте выполненных работ.

**⚠ Грабли.** Если детальный учёт по объектам заказчика не нужен, заводится один обслуживаемый объект — он автоматически подставляется в заявку при выборе заказчика. Регистрироваться в БЗ рекомендуется администратору бизнес-аккаунта HubEx: первый зарегистрировавшийся становится создателем и по умолчанию администратором БЗ. При нескольких пространствах учётку сначала привязывают к выбранному пространству; для доступа ко всем — выбрать пространство «Общая база знаний». При первом входе в БЗ доступен демонстрационный раздел, его можно очистить. Несколько сотрудников могут работать в БЗ под одной учётной записью. HubEx AI может допускать неточности в сложных или нестандартных случаях; для критичных вопросов — поддержка. Вертикальный логотип рекомендуется трансформировать в «Название компании + логотип». Страница HubExVids — каталог обучающих видеороликов, фактического содержания по функционалу не несёт.

## Интеграции, API и клиентские приложения

Внешние точки входа в HubEx: REST API, готовые интеграции с Битрикс24, SSO, почтовый канал, а также клиентские интерфейсы заказчика (портал и мобильное приложение).

**Модель.** REST API HubEx: клиент-сервер, HTTP, ответ обычно JSON; базовый хост `https://api.hubex.ru`. Сервисы (микросервисы, каждый со своим SWAGGER на doc.hubex.ru): AUTHN (аутентификация учётных записей), AUTHZ (авторизация), AUTH (учётная запись и авторизационные данные), ADM (пользователи и администрирование), ES (компании, объекты, оргструктура, локации), PA (персонал: трудоустройство, назначение на оборудование, рейтинги, навыки), WORK (заявки, чек-листы, выполнение, вложения, назначения), WSP (графики рабочего времени), COMMON (справочники: валюты, часовые зоны, единицы измерения, доп.поля), SLA (критичность и SLA), TSTG (жизненный цикл заявки), UI, EXPORT, PMP (планировщик работ), MSG (уведомления, Webhook, триггеры), NEWS, WH (склады и материалы).
Методы: GET (безопасный, идемпотентный), POST (не идемпотентен — повтор создаст новый объект), PUT (полная замена записи), PATCH (частичное обновление), DELETE. Авторизация двухступенчатая: служебный пользователь → Service Token → `POST /fsm/AUTHZ/AccessTokens` с телом `{"serviceToken": …}` → JWT `access_token`, далее заголовок `Authorization: Bearer …`.
Ключевые эндпойнты: заявки `POST/PATCH /fsm/WORK/Tasks[/{id}]`, доп.поля заявки `POST /fsm/WORK/taskAttributes` (список ID — `GET /fsm/COMMON/Attributes/?isRelevantForTask=true&isDeleted=false`), стадии `GET /fsm/Tasks/{taskID}/stages/next` и `POST /fsm/WORK/taskstagingHistory`, чат `POST/GET /fsm/WORK/Tasks/{taskID}/conversation/`, файлы `POST /fsm/WORK/taskAttachments/upload/fromForm` (multipart) и `GET /fsm/WORK/tasks/{taskID}/attachments`, исходный файл `GET /fsm/COMMON/attachments/{id}?noRedirect=true`; объекты `POST /fsm/ES/Assets`, `PUT /fsm/ES/Assets/{id}`, публикация `PUT /fsm/ES/Assets/{id}/publish`; компании `POST/PUT /fsm/ES/Companies`; пользователи `POST /fsm/ADM/Users`, `PUT /fsm/ADM/Users/{id}`, роли `POST /fsm/ADM/UserRoles/`, участки `POST /fsm/ADM/UserDistricts/`.
Обязательные поля заявки: `TaskTypeID`, `RequestMethodID`. Обязательные поля объекта: `Name`, `AssetTypeID`, `AssetClassID`, `CompanyID`. Блокировка пользователя — поля `banReasonID` и `banTill` в PUT по пользователю.
Битрикс24: два пути — приложение HubEx из Маркетплейса Битрикс24 (робот «[HubEx] Создание заявки HubEx» на стадии сделки + токен интеграции) либо коннектор через сторонний сервис Albato (триггер по сделке → действие «Новая задача» в HubEx). SSO — через Keycloak, Realm настраивается под тенант.
Клиентские интерфейсы заказчика: клиентский портал (меню «Заявки», «Сообщения», «Аналитика») и мобильное приложение «HubEx заказчик» (Android/iOS). Вкладки в МП: «Мои», «Согласование», «Все» (по вашей компании и вашим объектам), «Избранное», «Архив».

**Настройка.** Служебный пользователь: Путь: Консоль администратора → Интеграция → Служебные пользователи → «Пользователь API» → выбрать «Роли» и «Участки» → «Токен доступа» → «Сгенерировать» (скачивается .txt). Для интеграции считываются полномочия выбранных ролей. Связка с Битрикс24: веб-приложение HubEx → вкладка «Интеграция с Б24» → поля «API-ключ HubEx» и «Токен интеграции» → «Проверить подключение» → задать тип заявки в HubEx, воронку Битрикс24 и стадию перевода сделки. Заголовки запроса: `Authorization: Bearer …`, `Content-Type: application/json`, `X-Application-ID`. Параметры листинга: `fetch`, `offset`, `isClosed`. Gmail как источник заявок: настройки аккаунта Google → «Безопасность» → «Ненадёжные приложения, у которых есть доступ к аккаунту» → «Открыть доступ (не рекомендуется)» → тумблер «Включить»; сама интеграция по почте описана отдельно. Параметры SSO: для SAML 2.0 — Entity ID, SSO URL, X.509-сертификат, NameID Format, опционально Metadata URL/XML; для OpenID Connect — Client ID, Client Secret, Authorization/Token/UserInfo Endpoint URL, Redirect URI, опционально Scopes. Подключение SSO — через службу поддержки HubEx.

**Ограничения.** Service Token показывается только один раз. Access Token обновляется каждые 30 минут. Лимит частоты запросов — «обычно 60 запросов в минуту». Коды: 200–299 успех, 400–499 ошибка клиента, 500–599 ошибка сервера; создание — 201 Created, изменение — 202 Accepted. SSO поддерживает SAML 2.0, OpenID Connect/OAuth 2.0, LDAP/Active Directory, Kerberos, CAS, Azure AD, Google Workspace; требует индивидуальной настройки для каждого клиента, времени на тестирование, для сложных случаев — дополнительного согласования. Вход в МП «HubEx заказчик» и в портал возможен только после регистрационного письма на e-mail или sms. Принять работы и подписать акт можно только в МП «HubEx заказчик» — и только после того, как исполнитель внёс выполненные работы; печать акта — из клиентского портала.

**⚠ Грабли.** PUT обновляет все поля — для изменения объекта, компании или пользователя нужно передавать все поля с текущими значениями плюс изменяемое. Для интеграции `RequestMethodID` рекомендуется значение «4» (в примере запроса стоит 1). `Notes` — описание без html (список заявок), `NotesHtml` — с html (карточка заявки). В чат `isExternal=false` — команда, `true` — заказчик; чтобы отправить в оба, нужны два запроса. Из Битрикс24 при создании заявки: название сделки → «Комментарий», комментарий сделки → «Комментарий», тип заявки задаётся при создании робота, критичность берётся по умолчанию, компании-заказчика нет в HubEx — будет создана новая. Токены хранить не в открытом виде.

## Карта сущностей и связей

Сквозной граф справочников HubEx: чем связана каждая сущность и каким путём настройка одного объекта доходит до заявки. Нужен, чтобы выбрать, каким элементом модели выразить элемент процесса клиента.

**Модель.** Узлы и рёбра:
- **Заявка** — центр графа. Обязательное поле формы — Тип заявки; далее Заказчик, Объект, Вид работ, Договор обслуживания, План объекта, Компания-плательщик, Наша компания, Родительская заявка, Инициатор, Исполнитель(и) [«Создание и действия с заявками»].
- **Тип заявки** — единственный вход в процесс: определяет стадии (через Жизненный цикл), срок закрытия, доступные Виды работ, Участки, маску номера. Для одного Типа заявки может быть настроен только один Жизненный цикл.
- **Стадия** — точка подвеса автоматики. К ней крепятся Действие (назначение / автоназначение / завершение / закрытие), Требование (назначен исполнитель, обработаны чек-листы, отсканирован QR-код объекта, подписан акт), Правило автоназначения, Триггер уведомления (отправка при переходе на стадию), доступ к полям формы (Роль × Стадия). Статус — проекция Стадии для заказчика [«Жизненный цикл заявки»].
- **Вид работ — главный связующий узел.** Классифицирует Объекты, Сотрудников и Заявки; через него сцеплены: допустимость в заявке (виды из карточки Объекта, вкладка «Обслуживание», и — если внесены вручную — добавленные к Типу заявки), подбор исполнителя правилом автоназначения, чек-лист (подтягивается в Заявку при выборе вида работ), «Время закрытия заявки», «Стоимость вида работ» в Акте выполненных работ, разрез аналитики.
- **Крайний срок закрытия** — три источника: Тип заявки и Вид работ (система выбирает наименьшее) и правило SLA, сопоставляющее Тип заявки / Критичность / Вид работ / Компанию-заказчика / Объект и отсчитывающее «Плановое время закрытия» по Графику обслуживания.
- **Объект** = Тип оборудования (несёт список Видов работ и признак обязательности адреса) + Класс + Участок(и) + Навыки + Ответственный за объект + Виды работ. Иерархия родитель→дочерний, адрес наследуется; адрес объекта автоматически подставляется в Заявку.
- **Участок** — ось, которая одновременно классифицирует и ограничивает доступ: связывается с Объектом, Сотрудником, Заказчиком и Типом заявки; видимость включается полномочиями роли («Объекты на участках пользователя», «Заявки на объектах, доступных пользователю»).
- **Навык** — классифицирует Объекты и Сотрудников, читается правилами автоназначения; флаг «Необязательный» делит навыки на две группы.
- **Атрибут** (доп. поле) — одна сущность на три применения: пункт чек-листа (число, дата, текстовая строка, файл), паспорт объекта (флажок «Показывать в паспорте объекта»), поля и фильтры заявки [«Чаты, сообщения и доп.поля»].
- **Роль** = Полномочия (блоки, внутри «Элементы интерфейса» и «Справочники») + Приложения. Со Стадией пересекается дважды: поля формы заявки и «Предоставить доступ отдельным ролям» на переходе, вплоть до отдельного названия кнопки для роли.

**Настройка.** Порядок сборки, следующий из зависимостей: справочники (Типы и Классы оборудования, Участки, Навыки, Виды работ, Критичность, Актуальность, Дополнительные поля) → Роли и Стадии заявки → Типы заявок → Жизненный цикл заявки → Поля на форме заявки (Роль × Стадия) → SLA, правила автоназначения, чек-листы → Триггеры уведомлений. Стадии и Тип заявки создаются до Жизненного цикла; в «Поля на форме заявки» переходят, когда Роли и Стадии уже созданы.

**Ограничения.** Точки необратимости и жёсткие кардинальности: Тип заявки в созданной заявке изменить невозможно (лечится копированием); «Шаблонный тип заявки» указывается только при создании нового Типа; «Тип поля» созданного атрибута изменить нельзя; «Тип оборудования» в карточке Объекта правится только после снятия с публикации, а неопубликованный Объект нельзя выбрать в Заявке. Правило SLA создаётся на один Тип заявки, одну Критичность и один Вид работ либо «Все» по каждому пункту; Объекты выбираются только после выбора Заказчика. Правило автоназначения действует только как действие Стадии. Класс оборудования группирует только Объекты и Заявки. Прямое удаление справочников Объекты, Сотрудники, Заказчики, Компании и Заявок не предусмотрено из-за ссылочных связей. Графики обслуживания и графики работ встроены в систему; уникальный график добавляет поддержка. Стоперы моделирования целиком — «Ограничения-стоперы».

**⚠ Грабли.** Новые записи справочников не проставляются задним числом: новый Участок автоматически добавляется во все ранее созданные Типы заявок, но в Объектах, Сотрудниках и Заказчиках указывается вручную; новый Навык и новый Вид работ — вручную во всех карточках. Вид работ, созданный из выпадающего списка в заявке, всё равно нужно указать в карточке объекта. Пропавшее поле формы — это пересечение Роль × Стадия, а не только роль: если для роли и стадии настройка не установлена, поле не отображается. Удаление Класса не очищает поле «Класс» в карточках Объектов; удаление Стадии ломает переход на неё. Не путать оси: Класс — группировка, Участок — группировка плюс доступ; Стадия — для сотрудников, Статус — для заказчика [«Жизненный цикл заявки»].

## Паттерны посадки процессов клиента

Сборка поверх «Жизненный цикл заявки»–«Создание и действия с заявками», «Компании и договоры», «Роли, полномочия и участки», «SLA, автоназначение и чек-листы», «Склад, материалы и маркировка»: чем выражается процесс заказчика, где степени свободы, обо что упирается. Детали соседних разделов не повторяются — только связи.

**Модель.** Ядро посадки: процесс клиента → Тип заявки → Жизненный цикл (Стадии + Переходы) → Действия и Требования стадии. Для одного Типа заявки настраивается только один Жизненный цикл, поэтому каждый различимый процесс — отдельный Тип заявки; у типа свои маска номера, время закрытия, список Видов работ, Участки.

Паттерны:
1. **Несколько процессов у одного заказчика** — отдельные Типы заявок; цикл копируется через «Шаблонный тип заявки».
2. **Две картины одного процесса** — Стадии (web и «HubEx исполнитель») против Статусов («HubEx заказчик»): внутренние этапы схлопываются в один статус для заказчика.
3. **Согласование** — ветка согласования в цикле + уведомления на стадиях; внутреннее (контроль финансовых, трудовых, материальных расходов) и внешнее (подтверждение заказчиком). Объём: линейное — 3 новые стадии, параллельное с двумя согласующими — 6, с заказчиком — 3 (стадия «Согласование с заказчиком» необязательна). Результат согласования можно отдать в 1С [«Интеграции, API и клиентские приложения»].
4. **Роле-зависимый интерфейс перехода** — «Предоставить доступ отдельным ролям» + своё «Название перехода» на роль (в приложении заказчика — две кнопки «Согласована»/«Не согласована»).
5. **Выезд** — стадии «В пути»/«Выехал на объект»/«Прибыл на объект» разделяют время поездки и работ; флажок «Показывать сотрудника на карте и учитывать время на стадии как рабочее» [«Геотрекинг и карта»].
6. **Дисциплина на месте** — «Требования» стадии: назначен исполнитель, обработаны чек-листы, отсканирован QR-код объекта [«QR-коды, паспорт и планы объектов»], подписан акт выполненных работ [«Работы, акты приёмки и материалы в заявке»].
7. **Регламент работ** — Чек-лист, привязанный к Объектам и/или Видам работ (автоприкрепление к заявке); измеряемые параметры пунктов — Атрибуты (число, дата, текстовая строка, вложенный файл).
8. **Робот-диспетчер** — правило SLA (крайний срок по Графику обслуживания) + действие стадии «Автоназначение по правилу» / «с учетом удаленности от заявки»; критерии — навыки, вид работ, график работы, ответственный за объект, частота назначений, участок [«SLA, автоназначение и чек-листы»].
9. **Плановое обслуживание (ППР)** — Плановая заявка как шаблон автосоздания по расписанию + График обслуживания объектов как форма представления.
10. **Составные работы** — родительская заявка и дочерние; дочерняя отличается только заполненным полем «Родительская заявка», любую заявку можно сделать дочерней.
11. **Отказы и паузы** — ответвления цикла: «Отказ заказчика» (заявки автоматически отмечаются как «Закрытые»), «Отказ исполнителя» (с причиной, заявка исчезает из его списка), «Требует продолжения работ», «Ожидает ТМЦ» (возврат на «Назначена»), «Выполнена без выезда».
12. **Периметр видимости** — Участок (географический или функциональный критерий) в карточках Объекта, Сотрудника, Заказчика и Типа заявки + пункты «Справочники» роли; заказчик видит только оборудование, закреплённое за его компанией.
13. **Подряд и несколько юрлиц** — виды компаний «Наша компания», «Компании-заказчики», «Компания-подрядчик»; компания-плательщик может отличаться от заказчика; «Код компании» участвует в маске номера заявки.
14. **Договорной контур** — Договор принадлежит одной компании, связан с «Объектами по договору», классифицирует заявки; в заявке доступен только договор выбранного объекта; контроль окончания — флажок «Напомнить о завершении договора» и график действия договоров [«Аналитика Power BI»].
15. **Материалы у выездных** — сценарий «рюкзак»: отдельный склад на каждого выездного сотрудника; расход фиксируется в выполненной работе, стоимость идёт в Акт выполненных работ; маркируемые позиции — коды Data Matrix; обмен с 1С (ERP/Торговля/УНФ) с настраиваемой периодичностью.
16. **Внешние каналы подачи** — служебные пользователи: «Пользователь API» (роли + участки + токен) и «Анонимный пользователь» (роль при регистрации незарегистрированного + участки) [«Интеграции, API и клиентские приложения»].

**Настройка.** Порядок первичной посадки: Стадии заявки → Статусы заявки → Типы заявок → Жизненный цикл (сначала маршрут Начальная + Конечная стадии, переходы настраиваются только после этого) → Роли → Настройки заявки → Поля на форме заявки (доступ в разрезе Ролей и Стадий) → Участки и Навыки → Виды работ (плюс указание их в карточке объекта, вкладка «Обслуживание») → SLA, автоназначение, чек-листы. Точные пути — в «Жизненный цикл заявки», «Атрибуты, согласование и приоритизация заявок», «Роли, полномочия и участки», «SLA, автоназначение и чек-листы».

**Ограничения.** Для одного Типа заявки — только один Жизненный цикл. «Шаблонный тип заявки» доступен только при создании нового Типа заявки. После создания заявки её тип изменить невозможно (обходной путь — копия). «Тип поля» созданного атрибута изменить нельзя. Правило SLA создаётся на один Тип заявки, одну Критичность и один Вид работ либо значение «Все» по каждому пункту; графики обслуживания встроены в систему, уникальный добавляет поддержка. В схемах согласования автоматический переход настраивается только на стадию согласования, переходы на стадии результата пользователь делает вручную. Вид работ в заявке выбирается только из указанных в карточке Объекта; если у Типа заявки виды работ внесены вручную — из пересечения с ними. Массовое редактирование заявок на данный момент — только исполнитель/исполнители. Создание дочерних заявок, создание и выбор контактных лиц, ручное добавление и удаление чек-листов — только в web. В мобильном приложении при создании заявки поля «Заказчик», «Объект», «Вид работ», «Адрес» обязательны, в web заявка без них возможна. Для участия в автораспределении нужен флажок «Мобильный сотрудник», для автоназначения по удалённости — «Отслеживать местоположение сотрудника». Из складских документов доступно только «Оприходование», остальные типы в разработке; Data Matrix — на тарифах выше «Минимального». Импорт: до 2000 заявок и до 1000 материалов за раз. Просмотр удалённых заявок — только у учётной записи владельца тенанта.

**⚠ Грабли.** Стадии общие: изменение стадии действует для всех типов заявок, в чей жизненный цикл она включена, а удаление стадии ломает переход на неё — «свой» этап процесса делается новой стадией, а не правкой чужой. На стадии «Выполнена» нужно действие «Завершить работу по заявке», иначе просрочка считается неверно. Новый Участок автоматически добавляется во все ранее созданные Типы заявок, но в Объектах, Сотрудниках и Заказчиках указывается вручную; новый Навык и новый Вид работ в существующие карточки — тоже вручную. Автоназначение: с выключенной «Детальной настройкой» параметры применяются с союзом «И», с включённой — «ИЛИ» в зависимости от процента. При нескольких исполнителях время общее: 2 часа для двоих отразятся в акте как 2 часа каждому. Полномочия роли и доступ к полям формы заявки настраиваются раздельно (замок на поле «Исполнитель»); без пунктов «Справочники» блока Заявки исполнитель не видит заявки в общем списке. Заявки на стадии с действием «Закрыть заявку» по умолчанию не отображаются в мобильных списках; в web по умолчанию включён фильтр «Открытые заявки». Параллельное согласование требует двух разных стадий, одинаковых по смыслу — им нужны разные уведомления и разные точки выхода.

## Ограничения-стоперы

Сквозной список жёстких границ из разделов файла: что нельзя изменить после создания, что не поддерживается, где предел объёма. Для квалификации лида и проверки концепции на реализуемость.

**Модель.** Неизменяемое после создания: Тип заявки в созданной Заявке (обходится копированием заявки с заменой типа и удалением исходной); «Тип поля» у созданного доп.поля (нужен новый атрибут); «Шаблонный тип заявки» (доступен только при создании нового Типа заявки).
Единственность/кардинальность: для одного Типа заявки — только один Жизненный цикл; правило SLA — на один Тип заявки, одну Критичность, один Вид работ либо «Все» по каждому; плановая заявка — один Тип заявки, один Вид работ; назначение перетаскиванием в «Расписание заявок» и правилом автоназначения — только один сотрудник.
Пределы объёма: импорт за раз — Заявки до 2000, Объекты до 2000, Компании до 100; номер заявки — максимум 32 символа. API: лимит частоты запросов «обычно 60 запросов в минуту»; Access Token обновляется каждые 30 минут; Service Token показывается один раз. Public cloud: интеграции свыше 10 запросов/сек не поддерживаются, при превышении доступ может быть принудительно ограничен, интеграция отключена; рекомендуется до 500 пользователей (свыше 500 работать могут, но подходят варианты выделенных серверов/on-premises); окно обслуживания обычно 22.00–24.00 вт и чт, перенести нельзя; восстановление данных — только для всех клиентов облака одновременно, восстановление данных отдельного клиента крайне трудозатратно, а в ряде случаев невозможно.
Функциональные стоперы каналов: массовое редактирование заявок — на данный момент только исполнитель/исполнители; копирование заявки — только в карточном представлении; создание дочерних заявок — только в web; добавление и удаление чек-листов в заявке вручную — только через WEB, в мобильном такой возможности нет; принять работы и подписать акт — только в МП «HubEx заказчик» и только после внесения выполненных работ исполнителем; печать акта — из клиентского портала; просмотр удалённых заявок — только учётной записи владельца тенанта; вход по код-паролю — только для номеров РФ (+7хххххххххх).
Платформенные: проектные доработки НЕ делаются в публичном облаке (нужно локальное развёртывание или выделенные серверы), то же для самостоятельного использования Power BI / Apache SuperSet; обязательное условие проектных доработок, плагинов и доработок HubEx Automate силами вендора — пакет расширенной техподдержки у клиента. На лето 2024 HubEx Automate не позволяет изменять уже существующие интерфейсы, только создавать новые. Плагин не умеет взаимодействовать с данными системы, ещё не сохранёнными пользователем на сервер. Уникальный график обслуживания/работ добавляет поддержка. SSO требует индивидуальной настройки для каждого клиента и подключается через поддержку. Экспорт/импорт не совместимы с Mac Spreadsheet.

## Позиционирование против смежных классов

Чем отвечать на «у нас уже есть HelpDesk / ТОиР / 1С» и как HubEx встаёт в существующий ландшафт заказчика. Опора — заявленный класс продукта и способы встраивания.

**Модель.** Заявленный класс: отечественная ERP-система класса FSM (Field Service Management) для сервисных подразделений с мобильным персоналом; профиль работ — ремонты, техобслуживание, обходы, клининг. Три сценария посадки:
1. Платформа целиком — WEB для офисного персонала (руководители, диспетчеры, логисты, менеджеры) + мобильные приложения исполнителей + отдельное приложение заказчика работ.
2. Только мобильное приложение — прямо заявлено: может использоваться отдельно от платформы, подключается по API к HelpDesk/ServiceDesk/ТОиР системе компании. Ход для лида, который учётную систему менять не собирается: HubEx закрывает полевой слой.
3. Сосуществование с 1С-контуром — 1С-конфигурация в составе платформы (опционально), для упрощения интеграции с 1С-совместимыми системами.

Смежные функции, закрываемые самим HubEx: электронный паспорт объекта как репозиторий данных об оборудовании — параметры, история обслуживания, документация, гарантия, контакты ([«QR-коды, паспорт и планы объектов»]). BI-слой не собственный: конструктор отчётов — Power BI или Apache SuperSet ([«Аналитика Power BI»], [«Отчёты и экспорт»]).

Импортозамещение: реестр российского ПО с 15.07.2020, рег. №6816.

**Настройка.** Глубина встраивания задаётся не настройкой, а вариантом развёртывания и уровнем расширения (конфигуратор → HubEx Automate → плагины → проектные → продуктовые доработки) — [«Платформа и деплой»]. Интеграционный контур: открытый API + Swagger, REST API/SOAP в HubEx Automate; см. [«Интеграции, API и клиентские приложения»].

**Ограничения.** Плотный обмен с внешней учётной системой упирается в вариант развёртывания: в public cloud интеграции свыше 10 запросов/сек не поддерживаются, при превышении доступ может быть принудительно ограничен, интеграция отключена; выделенные серверы такую нагрузку держат без рисков отключения. Проектные доработки и самостоятельное использование Power BI / Apache SuperSet требуют локального развёртывания или выделенных серверов — в публичном облаке не делаются. На лето 2024 HubEx Automate не позволяет изменять уже существующие в системе интерфейсы, только создавать новые: «повторить привычный экран их системы» — это уже проектная ветка. Плагин не умеет взаимодействовать с данными системы, ещё не сохранёнными пользователем на сервер. Детали вариантов и трудоёмкости — [«Платформа и деплой»].

**⚠ Грабли.** Сценарий «мобильное приложение отдельно» описан именно как подключение мобильного клиента HubEx к HelpDesk/ServiceDesk/ТОиР заказчика; обратной конфигурации (HubEx как бэкенд для чужого мобильного клиента) в источниках нет — не обещать. Отдельная ветка разработки под клиента расходится по коду с продуктом: замедляется обновление, растёт стоимость поддержки, при отказе от обновлений возможность обновляться может быть утрачена вовсе — цена «подгонки под их процесс» кодом, а не конфигуратором.
